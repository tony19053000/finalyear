# V1.0 lab run — 72 h soak + chaos on 4 laptops (roadmap 1.0.2, D409–D411)

The procedure the team runs **without an agent present**, as day **L3** of the V1.0 campaign
(`docs/briefs/V1.0-release.md` §4). It produces the evidence for V1.0 success criterion 2
("72 h soak: no crashes, leaks, or lost jobs") and folds in the 0.6.13 100-job mixed run and the
V0.3 24 h liveness soak.

| D410 rule | What it checks | Tool that records it |
|---|---|---|
| 1 lost jobs = 0 | every submitted job terminal, right outcome, one commit, output checked | `soak_load.py run` + `collect` |
| 2 crashes = 0 | every process restart is one chaos caused | `soak.py run` (every laptop) |
| 3 memory | RSS quiet-1 → quiet-2 < +10 %, slope < 5 MB/h | `soak.py run` |
| 4 FDs / handles / threads | quiet-2 ≤ quiet-1 + 5 % | `soak.py run` |
| 5 DB growth | bytes/job stable, nothing grows while idle, WAL bounded | `soak.py run` on L1 (`--db-url`) |
| 6 disk | agent cache under its cap, logs rotate | `soak.py run --dir-watch` |
| 7 heartbeat | every OFFLINE explained | `fabric_check.py soak` |
| D411 chaos | ≥ 1 applied action / 45 min | `chaos.py run` + `chaos_win.ps1` |

Plan **3 days + 2 h** of setup. **L1** = the controller laptop (Linux, controller `.deb`, its own
agent); **L2** = the second Linux laptop; **L3, L4** = Windows laptops (installer). All four run
the **same `v1.0.0-rc.N` packages** (D406); write the version and SHA down.

The run is judged by `soak.py report` (the D410 analyzer). **Whatever it prints is the result** — a
FAIL caused by our bug restarts the soak after the fix (`rc.N+1`); an outside event (power cut,
Windows update) goes into `notes.json` and the run continues if < 1 h was lost.

> **Before the lab:** the agents' dry run proves the tools end to end on one machine:
> `MESHFORGE_SOAK_DRYRUN_HOURS=1 uv run --extra agent --extra controller pytest tests/cluster/soak --run-soak`
> (`docs/briefs/progress/V1.0-G1.md` has the last result). Do not start the 72 h run on a commit
> whose dry run failed.

## A. Before the day

- [ ] **A1 — Release build everywhere.** L1/L2: `dpkg -l meshforge-agent meshforge-controller`;
      L3/L4: *Apps → MeshForge* shows the version. All the same `rc.N`. Write it down.
- [ ] **A2 — Power and sleep.** Every laptop on mains power. Linux:
      `sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target`.
      Windows: *Settings → System → Power* → screen and sleep **Never**; *Windows Update → Pause
      updates* for 1 week. Undo all of it after the run (G4).
- [ ] **A3 — Clocks.** Every laptop's clock synced (Linux `timedatectl` → `System clock
      synchronized: yes`; Windows *Settings → Time → Sync now*). The analyzer allows 30 s skew.
- [ ] **A4 — SSH from L1 to L2 (and to L1 itself).** On L1: `ssh-keygen -t ed25519` (no
      passphrase) and `ssh-copy-id <user>@<L2-IP>`; check `ssh -o BatchMode=yes <user>@<L2-IP> true`
      prints nothing and exits 0.
- [ ] **A5 — The chaos wrapper + sudo rule (L1 and L2, lab laptops only).** The chaos commands
      all go through one root-owned script that checks its arguments (`lab/mf-chaos`):
      ```bash
      sudo install -o root -g root -m 0755 lab/mf-chaos /usr/local/sbin/mf-chaos
      echo "$USER ALL=(root) NOPASSWD: /usr/local/sbin/mf-chaos" | sudo tee /etc/sudoers.d/mf-chaos
      sudo chmod 0440 /etc/sudoers.d/mf-chaos && sudo visudo -cf /etc/sudoers.d/mf-chaos
      ```
      (on L2 copy `lab/mf-chaos` over first, e.g. `scp lab/mf-chaos <user>@<L2-IP>:`). The rule
      allows **only** that script — no shell, no `systemctl`: the script's argument rules are
      the security boundary, so never edit the installed copy. Check:
      `sudo -n /usr/local/sbin/mf-chaos cleanup - -` prints `cleanup done: ...` without a password
      prompt, and `sudo -n /usr/local/sbin/mf-chaos net-down 'x;y' 1` is refused (`bad value`).
      **Delete the rule and the script after the run** (G1). For `upgrade_reinstall` the
      controller `.deb` must be in `/var/lib/mf-lab/`, and it and every folder above it
      root-owned, not group/world-writable, no symlinks:
      `sudo install -o root -g root -m 0644 -D <deb> /var/lib/mf-lab/<deb>` (and
      `sudo chmod 0755 /var/lib/mf-lab`); use that path in A8. `restart_postgres` needs
      `/opt/meshforge` root-owned (the `.deb` installs it so).
- [ ] **A5b — disk_fill target volume.** `disk_fill` fills the **agent CAS volume** until only
      512 MiB are free (half the agent's fixed 1 GiB free-disk floor), so the agent must refuse
      work `disk_full`. The fill file (`fill_file`, default
      `/var/lib/meshforge/mf-chaos-fill.bin`; Windows `C:\ProgramData\MeshForge\mf-chaos-fill.bin`)
      must be on the **same filesystem as the agent's CAS**: Linux `df --output=target
      /var/lib/meshforge/cas /var/lib/meshforge` prints the same mount twice; Windows: same
      drive letter as `C:\ProgramData\MeshForge\cache`. **On L1 the PostgreSQL data dir
      (`/var/lib/meshforge/db/data`) is usually on the same volume**: with 512 MiB free it keeps
      working (the fill lasts 10 min), but write down `df -h /var/lib/meshforge` before the run
      and do not run anything else that writes to that disk during the soak. `chaos.py` runs
      `df` first and logs the action `skipped` when that disk already has < 1 GiB free.
      The wrapper only accepts `/var/lib/meshforge/mf-chaos-fill.bin` or
      `/var/lib/meshforge/<one folder>/mf-chaos-fill.bin`; that folder (and
      `/var/lib/meshforge`) must be a real directory (no symlink) owned by `root` or
      `meshforge` and not world-writable, and the file must not exist beforehand (a leftover:
      run C3's cleanup). Check: `stat -c '%U %a %F' /var/lib/meshforge`.
- [ ] **A6 — The network interface names.** Linux: `ip -br link` (e.g. `wlp2s0`); Windows:
      `Get-NetAdapter | Format-Table Name,Status` (e.g. `Wi-Fi`). Needed for net_down/netem.
- [ ] **A7 — The node ids.** On L1: `compute nodes` — note each laptop's `node_id` and hostname.
- [ ] **A8 — `targets.json`** in a new run folder on L1, e.g. `~/mf-soak/` (the run folder itself
      is created by `soak.py plan`):
      ```json
      {"targets": [
        {"label": "L1", "os": "linux", "roles": ["controller", "agent"], "executor": "local",
         "hostname": "<L1 hostname>", "node_ids": ["<L1 node_id>"], "iface": "wlp2s0",
         "vars": {"controller_deb": "/var/lib/mf-lab/meshforge-controller_<rc>_amd64.deb"}},
        {"label": "L2", "os": "linux", "roles": ["agent"], "executor": "ssh",
         "ssh": "<user>@<L2-IP>", "hostname": "<L2 hostname>", "node_ids": ["<L2 node_id>"],
         "iface": "wlp3s0"},
        {"label": "L3", "os": "windows", "roles": ["agent"], "executor": "windows",
         "hostname": "<L3 hostname>", "node_ids": ["<L3 node_id>"], "iface": "Wi-Fi"},
        {"label": "L4", "os": "windows", "roles": ["agent"], "executor": "windows",
         "hostname": "<L4 hostname>", "node_ids": ["<L4 node_id>"], "iface": "Wi-Fi"}
      ]}
      ```
      `executor: local` on L1 runs its actions without SSH (a reboot of L1 then also stops the
      chaos driver — it resumes, B6). Paths that differ from the `.deb` defaults go in `vars`
      (`pg_bin`, `pg_data`, `fill_file`, `agent_cgroup`). Every value may contain only
      letters, digits and `_ @ % + = : , . / -` (anything else is refused before it reaches
      `sudo`); the wrapper also pins `fill_file` (A5b), `pg_bin` under `/opt/meshforge/`,
      `pg_data` under `/var/lib/meshforge/`, `agent_cgroup` to
      `/sys/fs/cgroup/system.slice/meshforge-agent.service` (or a folder below it) and
      `controller_deb` to `/var/lib/mf-lab/` (A5).
- [ ] **A9 — Log in** on L1 as the admin: `compute login --controller https://<L1-IP>:47110
      --fingerprint <FP>` (the soak tools use this login).

## B. Start (L1 unless stated otherwise)

- [ ] **B1 — Plan.** From the repository root:
      ```bash
      uv run python lab/soak.py plan --out ~/mf-soak/RUN --targets ~/mf-soak/targets.json \
          --seed <any int> --start-in-min 30 --hours 72 --link wifi     # or ethernet
      ```
      It prints t0, the job mix and every chaos action. `RUN` = e.g. `2026-11-02-V1.0-soak`.
      The first 30 min after t0 are warm-up; hours 0–6 and 66–72 are quiet (no chaos).
- [ ] **B2 — Copy the run folder to L3 and L4** (USB stick or a share): at least `plan.json` and
      `chaos-schedule.json`, e.g. to `C:\mf-soak\RUN`.
- [ ] **B3 — Samplers, one per laptop**, before t0 (they record the warm-up). L1:
      ```bash
      echo '<meshforge_admin DB password>' > ~/mf-soak/db.pw && chmod 600 ~/mf-soak/db.pw
      uv run --extra agent python lab/soak.py run --dir ~/mf-soak/RUN --label L1 --interval 60 \
          --db-url postgresql://meshforge_admin@127.0.0.1:47150/meshforge \
          --db-password-file ~/mf-soak/db.pw \
          --dir-watch cas=/var/lib/meshforge/cas@<[agent.gc] cas_bytes in MB, default 20480>
      ```
      L2: the same without `--db-*`, `--label L2`. (Linux services log to the journal, which
      rotates itself: check `journalctl --disk-usage` at C1 and D1 instead of a folder.)
      L3/L4 (PowerShell, repository root):
      `uv run --extra agent python lab\soak.py run --dir C:\mf-soak\RUN --label L3 --dir-watch
      logs=C:\ProgramData\MeshForge\logs --dir-watch cache=C:\ProgramData\MeshForge\cache@<cas_bytes + envs_bytes in MB, default 51200>`
      (a folder named `log*` is judged by rule 6's "logs rotate").
      Each prints `sampling [...] every 60 s until ...`. Run them in `tmux` / a window that stays
      open. **If one dies or the laptop reboots: run the same command again — it resumes.**
- [ ] **B4 — Transition recorder** (L1, rule 7):
      `uv run python lab/fabric_check.py soak --hours 73 --link wifi --checkpoint
      ~/mf-soak/RUN/fabric-soak.checkpoint.json` (resumes the same way).
- [ ] **B5 — Load generator** (L1): `uv run --extra controller python lab/soak_load.py run --dir
      ~/mf-soak/RUN`. It waits for t0, then prints one line per job. Killed → same command again
      (idempotency keys: a job is never submitted twice).
- [ ] **B6 — Chaos driver** (L1): `uv run --extra controller python lab/chaos.py run --dir
      ~/mf-soak/RUN`. It first prints `cleanup L1: ok ...` / `cleanup L2: ok ...` (every start
      and resume undoes leftovers), then waits for each action; Windows actions are logged
      `delegated`. Ctrl+C (or closing the terminal) undoes lasting faults before it exits.
- [ ] **B7 — Windows chaos** (L3 and L4, **Administrator** PowerShell, repository root):
      `powershell -ExecutionPolicy Bypass -File lab\chaos_win.ps1 -RunDir C:\mf-soak\RUN -Label L3`.
      It prints `cleanup L3: adapter ... enabled, fill file absent` first (every start undoes
      leftovers). After a `reboot` action the laptop restarts: log in and run the same command
      again (and the sampler, B3).

## C. During the 72 h

- [ ] **C1 — Look twice a day** (morning/evening): every terminal still running; `uv run python
      lab/chaos.py show --dir ~/mf-soak/RUN` shows outcomes; the dashboard shows the nodes.
- [ ] **C2 — Write down what our tools cannot see**: a laptop that slept anyway, a Windows update
      restart, the router rebooting, someone closing a lid. Into `~/mf-soak/RUN/notes.json`:
      `{"events": [{"from": "2026-11-03T02:10:00+05:30", "to": "2026-11-03T02:40:00+05:30",
      "host": "L3", "reason": "Windows update restart"}]}` (`"host": "*"` = everything).
      Never add a note for something chaos did or to explain away our bug.
- [ ] **C3 — Abort / stuck fault.** To stop the run early, or when a laptop is left without
      network / with a full disk: Ctrl+C the chaos driver (it cleans up), then
      `uv run python lab/chaos.py cleanup --dir ~/mf-soak/RUN` on L1 (idempotent, safe to repeat;
      `--only L2` for one laptop) and, on each Windows laptop, `powershell -ExecutionPolicy Bypass
      -File lab\chaos_win.ps1 -RunDir C:\mf-soak\RUN -Label L3 -Cleanup`. A laptop whose network
      is down cannot be reached over SSH: its fault undoes itself when its time is up (the
      wrapper's `trap`), or run `sudo /usr/local/sbin/mf-chaos cleanup <iface> -` on it directly.

### Manual chaos actions

`revoke_rejoin` (once, on an agent laptop, unless `targets.json` gives a command for it) — the
driver (or `chaos_win.ps1`) prints `>>> MANUAL revoke_rejoin on Lx`. Then:
1. L1: `compute node revoke <Lx node_id>` (the laptop's jobs move elsewhere).
2. L1: `compute fabric invite` → a new join code.
3. On Lx: open **MeshForge**, *Leave* if it still shows the old fabric, then *Join* with the code
   (`docs/user/join-a-laptop.md`). Note the new `node_id` (`compute nodes`) and add it to Lx's
   `node_ids` in `RUN/plan.json` **and** `targets.json` (attribution of the new node).
4. Press Enter in the driver's terminal. `skip` + Enter if it cannot be done now.

## D. After the 72 h (L1)

- [ ] **D1 — Wait for the end.** `soak_load.py run` prints `load done`; the samplers stop by
      themselves at the plan's end (72 h + 30 min tail) with `done: N ticks`.
- [ ] **D2 — Collect:** `uv run --extra controller python lab/soak_load.py collect --dir
      ~/mf-soak/RUN` → `wrote .../jobs-final.json: N jobs, 0 not terminal, ... (0 bad)`.
- [ ] **D3 — Gather the files into L1's run folder:** `samples.L2.jsonl` (scp from L2),
      `samples.L3.jsonl`, `samples.L4.jsonl`, `chaos-log.l3.jsonl`, `chaos-log.l4.jsonl` (from
      the Windows laptops' run folders).
- [ ] **D4 — Judge:** `uv run python lab/soak.py report ~/mf-soak/RUN` prints one line per rule
      and `VERDICT: PASS | FAIL | INCONCLUSIVE`; writes `RUN/verdict.json` and
      `lab/reports/<day>-V1.0-soak.md`. INCONCLUSIVE = data missing (a file not copied, a sampler
      that did not run): fix the input, run `report` again — never a pass. The `chaos` rule
      counts a `disk_fill` only when some job attempt on that laptop failed `disk_full` inside
      its window (`proof` in `verdict.json`); one without (`unproven`) makes the rule
      INCONCLUSIVE: check A5b (the fill file on the CAS volume?) and the action's `detail`.

## E. What to paste back

Copy the whole `RUN` folder to `lab/reports/raw/<day>-V1.0-soak/` (without `db.pw`, which is not
in it) and commit it with `lab/reports/<day>-V1.0-soak.md`. In the chat paste: the printed rule
table + VERDICT line, the rc version + SHA (A1), and every `notes.json` event.
