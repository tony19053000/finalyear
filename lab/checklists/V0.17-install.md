# V0.17 lab — install, upgrade, rollback, uninstall on fresh machines (roadmap 0.17.8, D397, criteria 1–3)

This checklist judges V0.17's three success criteria on **real, fresh machines**. CI already runs every step
below on clean runners and containers (`package-linux`, `package-windows`, `upgrade-from-release-linux`,
`upgrade-windows`); only this lab can prove a fresh Windows PC, boot/sign-out, a real GPU and Docker Desktop, and a
person doing it **without a terminal** within 10 minutes. It also closes the open lab items of G1, G2, G3, G4 and
spikes SP1/SP3, so each OS needs **one** lab session, not six.

| Criterion (roadmap V0.17) | Part | Pass when |
|---|---|---|
| **C1** a fresh Windows laptop: download → joined, **< 10 min, no terminal** | W1 | stopwatch total < 10:00, no terminal opened, node CONN `yes` |
| **C2** uninstall leaves no services or firewall rules | W5, L5 | every `verify_uninstall` paste ends `CLEAN: nothing left behind` |
| **C3** install / upgrade / uninstall on fresh machines, both OSes | W1–W5, L1–L5 | every step's expected line present |

Machines (Q8, Q34):

| Name | What | Used in |
|---|---|---|
| **VC** | fresh **Ubuntu 24.04** VM (or spare laptop): the controller | L1–L5, all W parts |
| **VA** | fresh **Ubuntu 24.04** (or 22.04) VM: a Linux agent | L2–L5 |
| **VW** | fresh **Windows 11** VM (Hyper-V / VirtualBox; no GPU): Windows agent, the timed run | W1, W3–W5 |
| **LW** | the team's **real Windows 11 laptop** with NVIDIA + Docker Desktop that ran the dev agent (Q34) | W2 |

"Fresh" means: no Python, no uv, no Docker, no MeshForge checkout installed on VC/VA/VW. VMs and LW on the same
network (bridged networking for the VMs, not NAT).

Every step ends with **PASTE BACK:** — copy it into `lab/reports/<date>-V0.17-install.md` (from
`lab/reports/TEMPLATE.md`). Write **PASS / FAIL** next to each criterion with the line that decides it. A step that
could not be run is written down as such — never as a pass. Screenshots go to `lab/reports/raw/` (the ones marked
📷 also replace the `TODO-SCREENSHOT` placeholders in `docs/user/`; list in
`tests/unit/test_v017_g5_troubleshooting_codes.py::LAB_SCREENSHOTS`).

## 0. Before you start

- [ ] **0.1 — the two builds.** From the GitHub Releases page download the **previous release** (v0.17.0: agent
  `.deb`, controller `.deb`, `MeshForge-Agent-Setup-0.17.0-1.exe`, `SHA256SUMS`) and **this build** (the newest
  release, or the `package-linux` / `package-windows` artefacts of the commit under test). Check:
  `sha256sum -c SHA256SUMS --ignore-missing` (Windows: `Get-FileHash <file>` and compare).
  If no release exists yet (Q36): use the CI artefacts of `main` as "previous" and of the commit under test as
  "this build", and write that down.
  **PASTE BACK:** both version numbers and the `sha256sum -c` output.
- [ ] **0.2 — the verifier.** Copy `lab/verify_uninstall.py` (and `lab/verify_uninstall_windows.ps1`) from the
  release's source to VC, VA and VW/LW. It needs only the machine's own `python3` (Windows: any Python 3.10+, or
  run it from the repository on LW).
- [ ] **0.3 — a stopwatch** (phone) and screen recording on VW (Win+Alt+R / OBS) for part W1.

## Linux

### L1. Controller from scratch (VC) — closes G2's lab item

- [ ] **L1.1** `sudo apt install ./meshforge-controller_<previous>_amd64.deb`. Expect the last lines
  `... is running version <previous>` and `Create your fabric: run this to get the one-time setup link`.
  **PASTE BACK:** the last 15 lines.
- [ ] **L1.2** `sudo meshforge-controller setup url`; open the link in Firefox **on VC**. 📷 `controller-setup.png`
  (the page before "Create the fabric"). Create the admin (`labadmin`, a 12+ character password). The page shows a
  join code, its QR and the dashboard address. **PASTE BACK:** the "Laptops join at" address and the CA fingerprint.
- [ ] **L1.3** On VC: `compute login` is `/opt/meshforge/controller/current/bin/compute login --controller
  https://<VC-IP>:47110 --fingerprint <fp> -u labadmin`; `sudo meshforge-controller doctor`.
  **PASTE BACK:** both outputs (`all checks passed`).

### L2. Linux agent, previous version (VA) — closes G1/G3 lab items

- [ ] **L2.1** `sudo apt install ./meshforge-agent_<previous>_amd64.deb` → `... is running version <previous>` and
  `this laptop has not joined a fabric yet`. App menu → **MeshForge** opens the console. Join with a new invite
  code from the dashboard (Settings > Invites). Policy: turn **Run jobs** and **Allow jobs without a container**
  on. **PASTE BACK:** the install's last 6 lines; `meshforge-agent identity show` (node_id);
  `compute nodes` on VC (VA `yes`).
- [ ] **L2.2** A job from VC: the `hello` project of `docs/user/run-a-workload.md`, `compute run ./hello --node
  <VA> -f`. **PASTE BACK:** the output.

### L3. Upgrade previous → this build (VC then VA)

- [ ] **L3.1 controller** `sudo apt install ./meshforge-controller_<this>_amd64.deb` → `pre-<this>.dump` backup,
  `... is running version <this>`. `compute jobs` still lists L2.2's job. **PASTE BACK:** the last 10 lines,
  `ls /var/lib/meshforge/db/backups`, `compute jobs`.
- [ ] **L3.2 agent** `sudo apt install ./meshforge-agent_<this>_amd64.deb` → `is running version <this>`;
  `meshforge-agent identity show` = the **same node_id**; `meshforge-agent policy show` = the L2.1 choices;
  `ls -a /opt/meshforge` shows **no** `.previous`. The dashboard's Nodes page shows VA's version (no "update
  available"). Run L2.2's job again. **PASTE BACK:** all of it.

### L4. Forced rollback (Q38) — the rollback really works

- [ ] **L4.1 agent** On VA, make the upgrade fail on purpose, then install this build again:
  ```bash
  sudo install -d /opt/meshforge/.upgrade
  echo <this version> | sudo tee /opt/meshforge/.upgrade/fail-upgrade-to
  sudo apt install --reinstall ./meshforge-agent_<this>_amd64.deb
  ```
  Expect `UPGRADE FAILED ... forced failure` and `ROLLED BACK: the previous version <this> runs again
  (/opt/meshforge/current -> .previous/<this>)`; the service stays active; `meshforge-agent doctor` exits 1 with
  `FAIL upgrade running the previous version`; the trigger file is gone. Then the same `apt install --reinstall`
  again → `is running version <this>`, `doctor` exit 0. **PASTE BACK:** both install outputs, both `doctor`
  outputs, `readlink /opt/meshforge/current` after each.
- [ ] **L4.2 controller** On VC the same with `/opt/meshforge/controller/.upgrade/fail-upgrade-to`, after making
  the start count as an upgrade (only a version change backs up):
  `sudo sed -i 's/"version": "[^"]*"/"version": "0.0.9"/' /var/lib/meshforge/db/schema-version.json`.
  Expect `the database was restored from the backup` and `UPGRADE FAILED - ROLLED BACK`; `compute jobs` still lists
  the jobs; VA reconnects (`compute nodes`). Install again → healthy. **PASTE BACK:** both outputs, `compute nodes`.
- [ ] **L4.3 power cut (optional, VM only)** On VA: `sudo dpkg --unpack ./meshforge-agent_<this>_amd64.deb`, then
  **hard power-off the VM** (not a shutdown). Boot: `systemctl status meshforge-agent` active; `meshforge-agent
  doctor` says `an upgrade to ... was interrupted` and names the fix; `sudo dpkg -i
  ./meshforge-agent_<this>_amd64.deb` → `is running version`. (Also paste `dpkg -s meshforge-agent | grep Status`
  before the reinstall.)
  **PASTE BACK:** doctor before, configure output after.

### L5. Uninstall → verify → reinstall same node → purge → verify

- [ ] **L5.1** VA: `sudo apt remove meshforge-agent`; `sudo python3 verify_uninstall.py --os linux` → `CLEAN`
  with `kept` data lines. `sudo apt install ./meshforge-agent_<this>_amd64.deb` → same node_id, connects.
  `sudo apt purge meshforge-agent`; `sudo python3 verify_uninstall.py --os linux --data-removed` → `CLEAN`.
- [ ] **L5.2** VC (controller + agent on one machine): install this build's agent package on VC too and join;
  `sudo apt purge meshforge-agent` → `sudo python3 verify_uninstall.py --os linux --package agent --data-removed`
  → `CLEAN`, controller still running; `sudo apt purge meshforge-controller` → `--data-removed` (all) → `CLEAN`.
  **PASTE BACK:** every verifier output.

## Windows

### W1. Timed fresh install → joined (VW) — **criterion 1**

Keep VC running with a new invite code on its dashboard (Settings > Invites > New invite: code + QR).
A person who has not done this before, if possible; no terminal at any point.

- [ ] **W1.1** Start the stopwatch when `MeshForge-Agent-Setup-<this>-1.exe` has **finished downloading**.
  Double-click → SmartScreen: **More info → Run anyway** (📷 `windows-smartscreen.png`) → UAC **Yes** → licence →
  folder → "What this computer will share" (📷 `windows-installer-share.png`) → install → the last page
  "MeshForge is installed and running." (📷 `windows-installer-finished.png`) → Finish with **Open MeshForge**.
- [ ] **W1.2** In the console: Start → paste the code (or scan the QR with the webcam) → Join → the policy step
  (leave the safe defaults) → Save and continue → checks → Done. **Stop the stopwatch** when VC's
  `compute nodes` (or the dashboard's Nodes page) shows VW connected (CONN `yes`).
  **PASTE BACK:** the time per step (download done → installer finished → joined), the total, "terminal opened:
  no", the screen recording file name. **C1 PASS** = total < 10:00 and no terminal.

### W2. Real laptop with the dev agent (LW) — closes G4's Q34 lab steps and SP1 §4

Do G4's laptop steps exactly as written in `docs/briefs/progress/V0.17-G4.md` "🧑 Lab steps" 1–9 (same node_id
before/after, dev task disabled, reboot + delayed start, sign-out/in same PID, console checks, give Docker access,
a CUDA job from the service, non-admin console access, uninstall keep-data + verifier), installing **the previous
release** first. Then:

- [ ] **W2.10 upgrade previous → this build**: run `MeshForge-Agent-Setup-<this>-1.exe`. Expect "installed and
  running", the same node_id (`meshforge-agent identity show` in an administrator PowerShell),
  `type "C:\Program Files\MeshForge\current.txt"` = `<this>-1` and `sc.exe qc MeshForgeAgent` binPath naming the
  same folder. Repeat the CUDA job of step 7. **PASTE BACK:** all.

### W3. Forced rollback (VW)

- [ ] **W3.1** Administrator PowerShell:
  ```powershell
  New-Item -ItemType Directory -Force "$env:ProgramFiles\MeshForge\upgrade"
  Set-Content "$env:ProgramFiles\MeshForge\upgrade\fail-upgrade-to" "<this>-2"
  ```
  Run `MeshForge-Agent-Setup-<this>-2.exe` (the revision-2 installer from the CI artefact). Expect the last page
  "The new version did not start; the previous version runs again." with the line `forced upgrade failure`.
  Then: `type "C:\Program Files\MeshForge\current.txt"` = `<this>-1`, `sc.exe qc MeshForgeAgent` binPath
  `...\<this>-1\python\python.exe`, `sc.exe query MeshForgeAgent` RUNNING, the trigger file gone,
  `C:\Program Files\MeshForge\upgrade\rolled-back.json` present. Run the revision-2 installer again → "installed
  and running", current.txt `<this>-2`. **PASTE BACK:** the finish page text (or
  `C:\ProgramData\MeshForge\logs\setup-result.json`) of both runs and the commands' output.

### W4. Upgrade previous release → this build (VW)

- [ ] **W4.1** Uninstall (data kept), install the **previous** release, join again if asked (it is the same node),
  then run this build's installer. Expect "installed and running", same node_id, current.txt and binPath on this
  build. **PASTE BACK:** node_id before/after, current.txt, binPath.

### W5. Uninstall → verify → reinstall same node → remove all → verify — **criterion 2**

- [ ] **W5.1** Settings → Apps → MeshForge Agent → Uninstall → "also remove all data?" **No**
  (📷 `windows-uninstall-data.png`). Administrator PowerShell: `python verify_uninstall.py --os windows` → `CLEAN`

  `python verify_uninstall.py --os windows --data-removed` → `CLEAN`; `Get-NetFirewallRule | Where-Object
  DisplayName -like '*MeshForge*'` prints nothing. **PASTE BACK:** both verifier outputs and the firewall command.
