# V0.6 lab run — automatic placement and failures on 4 laptops (roadmap 0.6.13)

The procedure the team runs **without an agent present**. It produces the real-machine evidence for
the V0.6 success criteria that loopback and the chaos suite cannot prove:

| # | Criterion | How | Part |
|---|---|---|---|
| 1 | 100 mixed jobs across 4 laptops with agent kills and a Wi-Fi drop: **0 lost, 0 duplicated** | `lab/sched_check.py` submit → scripted disruptions → `check` | E |
| 2 | Controller `kill -9` with **20 running** jobs → every job right, no duplicate runs | part F | F |
| 4 | A tiny job whose transfer dominates stays **Local**; a heavy one goes to the faster laptop | `compute run` from L2 + `compute explain` | D |
| 0.6.6 | The network matrix fills from peer probes, bounded, plausible vs iperf3 | `compute network` | C |
| G3 | Partition and kill behaviour **on Wi-Fi** (retry elsewhere, old result never committed, overlap logged; no orphan process) | part G | G |

Criteria 3 (`compute explain`) and 5 (policies) are proven by component tests; part D shows 3 on
real machines as a side effect.

Plan about **2.5 hours**. **L1** = the controller laptop (Linux; PostgreSQL, the controller, its
own agent, every command unless stated otherwise); **L2–L4** = the other laptops (Windows);
`<L1-IP>` … = each laptop's address on the network of the part you are in (**Wi-Fi** in this
whole run unless a part says otherwise — the point of V0.6 is behaviour on the real network).

**Whatever you measure is the result — write it down, do not repeat a step until it passes.**

## C. The network matrix (0.6.6)

Wait **5 minutes** after B (12 ordered pairs; one probe starts every ~15 s, at most 48 MiB of probe
traffic per minute across the fabric). Then:
```bash
uv run compute network
uv run compute network --json > ~/mf-lab/v06/C-network.json
```
**Expected:** a 4 × 4 matrix with a value in every off-diagonal cell (`<bandwidth> <rtt> <age>`), no
`(stale)`, no `fail:`. A `fail:http_403` or `fail:unreachable` cell means the target's firewall or
`[agent.peer] bind` is wrong (A2). The status line shows `failed 0` and the budget used. If you
measured iperf3 on Wi-Fi in the V0.5 run (part D2), compare: probes download 4–8 MiB over one
connection, so they read **lower** than a 30 s `-P 4` iperf3 — same order of magnitude is the pass.
Write down L1→L2 and L2→L1 from both tools.

## D. Criterion 4 on real machines — Local when the transfer dominates

On **L2** (a laptop with an enrolled agent; install the CLI there: `uv sync`, then set the two
variables of B3 in its PowerShell with `$env:MESHFORGE_CLI__CONTROLLER_URL=...` and
`$env:MESHFORGE_CLI__TOKEN=...`):
```powershell
mkdir $HOME\mf-lab\c4-tiny; cd $HOME\mf-lab\c4-tiny
python -c "import os; open('blob.bin','wb').write(os.urandom(300*1024*1024))"   # 300 MB
"print('tiny job done')" | Out-File -Encoding ascii main.py
"name: c4-tiny`nentrypoint: python main.py" | Out-File -Encoding ascii compute.yaml
```
1. **History first, on L2 only** (the planner predicts from recorded runs):
   `uv run compute run . --node <L2-ID>`; wait for it to succeed (`uv run compute jobs`).
   **Do not run `c4-tiny` on any other laptop before step 2.** A laptop that ran it keeps the
   300 MB project in its cache, and the planner then — correctly — sees nothing to transfer
   there, so a faster laptop wins and the step cannot show what it is meant to. (If that
   happened: write new random bytes into `blob.bin` — a new project nobody holds — and start
   step 1 again.)
2. **The test:** `uv run compute run .` (automatic placement) then
   `uv run compute explain <JOB_ID>`.
   **Expected:** chosen = `<L2-ID>`, mode `local`; L2's `transfer` is `0.00s (measured)`
   (seeded) and its `compute` is `history`; every other laptop's `transfer` is ~300 MB / its
   link — `measured, from <last 8 of L2-ID>` (the probed link from L2, part C) or
   `history, from controller (last transfer … ago)` — and its `compute` is `scaled` (from L2's
   run, by the CPU score ratio; plain `history` for a laptop without a benchmark score); the
   job succeeds.
3. **Inverse — heavy compute, small project.** Make `c4-heavy` the same way with **no** `blob.bin`
   and `main.py` = `import time; t=time.time()` + a 60 s CPU loop
   (`while time.time()-t<60: sum(range(10000))`). Run it pinned on L2 and on `<STRONG-ID>` — the
   laptop with the highest CPU score in `uv run compute nodes` — (history; the project is a few
   bytes, so who holds it does not matter here), then `uv run compute run .` + `explain`.
   **Expected:** chosen = the laptop whose predicted `compute` is smallest (`scaled` or
   `history`) — not L2 unless L2 is the strongest.
4. Paste both `explain` outputs.

## E. Criterion 1 — 100 mixed jobs with kills and a Wi-Fi drop

The kit submits 100 ledger jobs (sleep 5–60 s, some with 2–5 s of CPU work, ~10 % exit 3 on
purpose, `retry: max_attempts 5`, policies cost_model / least_loaded / random / cache_affinity,
priorities −2…2). Keep a clock visible; T = the moment the submit finishes.
```bash
uv run python lab/sched_check.py submit --n 100 --seed 6 --out ~/mf-lab/v06/E-run.json
```
Scripted disruptions (**hard kills** — the agent gets no chance to say goodbye):

| When | Where | Do | Restart |
|---|---|---|---|
| T+1 min | L3 | `taskkill /F /T /IM meshforge-agent.exe` | after 30 s (B2 command) |
| T+3 min | L4 | `taskkill /F /T /IM meshforge-agent.exe` | after **2 min** (past the lease: its attempts end `LOST` and retry elsewhere) |
| T+5 min | L2 | **Wi-Fi off** (tray icon) — a partition: its agent keeps running | Wi-Fi on after **90 s** |
| T+8 min | L1 | `pkill -9 -f "meshforge-agent run"` | after 10 s (B2 command, with `DOCKER_HOST`) |
| T+10 min | L3 | `taskkill /F /T /IM meshforge-agent.exe` | at once |

Write down the real times you did each step. Then:
```bash
uv run python lab/sched_check.py wait ~/mf-lab/v06/E-run.json --timeout 3600
```
**Collect the ledgers** into `~/mf-lab/v06/E-ledger/` on L1: L1's `/tmp/mf-lab/v06-ledger/*.txt`
and each Windows laptop's `C:\mf-lab\v06-ledger\*.txt` (USB stick or `scp`; one file per laptop,
named by host). Then:
```bash
uv run python lab/sched_check.py check ~/mf-lab/v06/E-run.json \
  --ledger ~/mf-lab/v06/E-ledger --partitioned <L2-ID> --out ~/mf-lab/v06/E-report.json
echo $?
grep -c controller.jobs.execution_overlap ~/mf-lab/v06-controller.log
```
**Expected:** exit `0`, `"criterion_1": "PASS"`: `lost` empty, `duplicate_commits` empty,
`duplicate_executions_under_kills` empty. `overlaps_under_partition` may list L2's attempts (D117:
a partitioned laptop keeps running; its result is never committed) and the overlap `grep` count
should match it. `retried_after_failure` is fine.

The check is strict (it never passes on missing evidence):

| Exit | `criterion_1` | Meaning |
|---|---|---|
| `0` | `PASS` | nothing lost, nothing duplicated, and a ledger `end` line for every committed job |
| `4` | `INCONCLUSIVE` | `committed_without_ledger_evidence` is non-empty: a laptop's ledger file is missing or incomplete. **Not a pass.** Collect every ledger and run `check` again. Also exit `4` when `RUN.json` lists no jobs (nothing was checked). Identical ledger lines (one file copied under two names) count once (`identical_ledger_lines`) |
| `3` | `FAIL` | a job was lost (not finished, or meant to succeed and did not) or ran twice (two `done` attempts, a completed run the controller counted as lost on a laptop that was not partitioned, or **the same attempt executed twice**) |

Before trusting a "ran twice" FAIL, look at `ledger_files` in the report: if two files are copies of one ledger and one copy is torn or partial (differs by even a byte), the lines no longer count as identical and read as a second execution. Delete the bad copy and run `check` again.

If anything lands in a FAIL list, paste the job's `uv run compute jobs <JOB_ID>` and
`uv run compute explain <JOB_ID>`.

## F. Criterion 2 — controller `kill -9` with 20 running jobs

Clear the ledgers (A5). Then:
```bash
uv run python lab/sched_check.py submit --n 20 --sleep 120-150 --no-fail --seed 7 \
  --out ~/mf-lab/v06/F-run.json
watch -n 2 'uv run compute jobs --state running | tail -n +2 | wc -l'
```
When it shows **20** (every slot busy): in Terminal A press nothing — in Terminal C run
```bash
pkill -9 -f meshforge-controller; date
```
Wait **20 s**, start the controller again (B1, same command). Agents reconnect within ~10 s and
their jobs keep running. Then `wait`, collect the ledgers to `~/mf-lab/v06/F-ledger/`, and
```bash
uv run python lab/sched_check.py check ~/mf-lab/v06/F-run.json \
  --ledger ~/mf-lab/v06/F-ledger --out ~/mf-lab/v06/F-report.json
```
**Expected:** exit `0`; `states` = `{"succeeded": 20}`; `attempts_per_job` = `{"1": 20}` (every
running attempt was adopted after the restart, none re-run); no duplicates.

## G. V0.6 G3 behaviour on Wi-Fi (partition and kill)

**G1 — partition.** A 2-minute ledger job, placed automatically:
```bash
mkdir -p ~/mf-lab/v06-long && cp lab/workloads/v06-ledger/main.py ~/mf-lab/v06-long/
printf 'name: v06-long\nentrypoint: python main.py 120 0 0\noutputs: [out/*]\n' \
  > ~/mf-lab/v06-long/compute.yaml
J=$(uv run compute run ~/mf-lab/v06-long)
uv run compute jobs $J                                # note its node, call it <X>
```
Turn **Wi-Fi off on <X> for 60 s** (past the lease), then on. **Expected:** `compute jobs $J`
shows attempt 1 `lost` on `<X>` and attempt 2 on another laptop, the job `succeeded` once;
`grep execution_overlap ~/mf-lab/v06-controller.log` has a line for attempt 1 after `<X>`
reconnects; `<X>`'s agent log shows the attempt cancelled/released (`fenced`), and the job's
result (`uv run compute get $J`) names attempt 2.

**G2 — kill, no orphan.** `J=$(uv run compute run ~/mf-lab/v06-long)` again, then hard-kill the agent of the laptop it runs on
(E's commands). On that laptop **before restarting the agent**: Windows Task Manager → Details,
Linux `pgrep -af "main.py 120"`. **Expected:** no `python … main.py` left from the job. Restart
the agent; the job retries elsewhere and succeeds.
