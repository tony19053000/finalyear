# V0.4 lab run — remote execution on 4 laptops (roadmap 0.4.15)

The procedure the team runs **without an agent present**. It produces the real-machine
evidence for the V0.4 success criteria that loopback tests cannot prove:

| # | Criterion | How | Part |
|---|---|---|---|
| 1 | CPU and GPU examples run on **every** node type; outputs **byte-identical** to a local run on the same hardware class (CPU example everywhere; PyTorch on CPU; GPU on the same GPU model + driver) and **within `compare.py`'s stated tolerance** (rtol `1e-3`, atol `1e-5`) across different CPU/GPU models (D76) | `compute run --node` / `--local`; digests compared (C), `compare.py` verdicts (D) | C, D |
| 2 | Log lines reach the client **≤ 1 s** after being printed remotely | `lab/exec_check.py latency` | E |
| 3 | Cancel stops the workload **≤ 5 s**; timeout enforced within 2 s of the limit | `lab/exec_check.py cancel` + a timeout job | F |
| 5 | Sandbox on Windows (Docker Desktop): outside-the-workdir files invisible; case-insensitive unpack refused | test run on each Windows laptop | G |
| 0.4.8 | A real PyTorch CUDA workload in the pinned `cuda-pytorch` image | part D on the GPU laptops | D |

Plan about **2 hours**. Words used below: **L1** = the controller laptop (Linux; runs PostgreSQL,
the controller, its own agent, and every command unless stated otherwise); **L2–L4** = the other
laptops (Windows); **`<L1-IP>`** = L1's Ethernet address (V0.3 checklist A3).

Every measured number is written by the tools into `lab/reports/raw/<date>-V0.4-exec-check.jsonl`
or printed by `compute`; paste what part H asks for. **Whatever you measure is the result — write
it down, do not repeat a step until it passes.**

## C. Criterion 1 — the deterministic CPU example on every laptop (20 minutes)

The local baseline first (L1's own agent), then each other laptop:
```bash
uv run compute run workloads/examples/cpu-deterministic --local -f
uv run compute run workloads/examples/cpu-deterministic --node <L2-ID> -f
uv run compute run workloads/examples/cpu-deterministic --node <L3-ID> -f

```
Each prints its `JOB_ID` first, then `done: 148933 primes, …` and exits 0 (`echo $?`).

Compare the outputs:
```bash
uv run compute jobs --json | python3 -c "import json,sys; [print(j['job_id'], j['placement']['node_id'][:12], j['state']) for j in json.load(sys.stdin)['jobs'][:4]]"
for J in <JOB_L1> <JOB_L2> <JOB_L3> <JOB_L4>; do

```
**Expected:** four identical `sha256sum` lines, equal to
`d85fca4c255d086a52b98aa22bc5aaa1ec00eb62f27b40cd1c0986e29b01c598` (the golden digest pinned by
`tests/unit/workloads/test_cpu_example.py`). The attempts' `output_digest`
(`curl -s -H "Authorization: Bearer $MESHFORGE_CLI__TOKEN" $MESHFORGE_CLI__CONTROLLER_URL/v1/jobs/<J> | python3 -m json.tool`)
must be identical too. A difference is a real criterion-1 failure: paste both `result.json` files.

## D. Criterion 1 (PyTorch) and 0.4.8 — the training example (30–40 minutes)

**D1 — PyTorch on the CPU, every laptop (byte-identity expected on the same CPU model).** Make a
CPU-only copy of the example once:
```bash
rm -rf /tmp/pytorch-cpu && cp -r workloads/examples/pytorch-train /tmp/pytorch-cpu
printf 'name: pytorch-train-cpu\nentrypoint: python main.py --steps 400 --device cpu\nenv: {base: cuda-pytorch}\nresources: {gpu: none}\noutputs: [results/]\nlimits: {timeout: 20m}\n' > /tmp/pytorch-cpu/compute.yaml
uv run compute run /tmp/pytorch-cpu --local -f
uv run compute run /tmp/pytorch-cpu --node <L2-ID> -f      # then L3, L4
```
Fetch each (`uv run compute get <J>`) and compare every laptop with L1:
```bash
python3 workloads/examples/pytorch-train/compare.py outputs/<JOB_L1>/results outputs/<JOB_L2>/results
```
It prints `IDENTICAL`, `WITHIN TOLERANCE` or `DIFFERENT`. **Expected:** `IDENTICAL` between laptops
with the same CPU model; between different CPU models `IDENTICAL` or `WITHIN TOLERANCE` (float32
vector kernels differ — README of the example). `DIFFERENT` is a failure: paste both `run.json`.

**D2 — PyTorch on the GPU (0.4.8), every GPU laptop:**
```bash
uv run compute run workloads/examples/pytorch-train --node <GPU-LAPTOP-ID> -f
```
Expected: the log ends `done on cuda: …`; `outputs/<J>/results/run.json` names the GPU. Run it
**twice** on the same laptop: `compare.py` must say `IDENTICAL` (same GPU + driver). Across
different GPU models expect `WITHIN TOLERANCE`. L1's GPU run is the local baseline
(`compute run workloads/examples/pytorch-train --local -f`). If a job ends `failed (env_error)`,
paste the agent window around the failure (image pull or GPU pass-through).

## E. Criterion 2 — live log latency, per laptop (15 minutes)

For each of L2, L3, L4 (the ticker waits 3 s before printing so the follower is connected first):
```bash
J=$(uv run compute run lab/workloads/log-ticker --node <Lx-ID>)
uv run python lab/exec_check.py latency $J --name Lx --clock-offset-ms <Lx offset vs L1 from A4>
```
It prints `p50_ms`, `p95_ms`, `max_ms` and `within`. **Expected:** `max_ms` ≤ 1000. The live path
batches for up to 100 ms on the agent, so a p50 around 100–150 ms on Ethernet is normal. Negative
numbers mean the clocks are not in sync (A4) — fix and re-run that laptop only, and say so.

Also look at it: `uv run compute logs <J> -f` prints the ticks as they arrive.

## F. Criterion 3 — cancel and timeout on a real laptop (15 minutes)

**F1 — cancel**, for L2 (and one more laptop if time allows):
```bash
mkdir -p /tmp/sleeper && printf 'import time\nprint("sleeping", flush=True)\ntime.sleep(300)\n' > /tmp/sleeper/main.py
J=$(uv run compute run /tmp/sleeper --node <L2-ID>)
sleep 10      # let it reach running (the first run on Docker may pull an image: wait until
              # `uv run compute jobs` shows it running)
uv run python lab/exec_check.py cancel $J --name L2
```
**Expected:** `"state": "cancelled"`, `seconds` ≤ 5. On L2, Task Manager (or `docker ps`) shows no
leftover `python` process / container for it.

**F2 — timeout:**
```bash
printf 'name: sleeper-timeout\nentrypoint: python main.py\nlimits: {timeout: 20s}\n' > /tmp/sleeper/compute.yaml
uv run compute run /tmp/sleeper --node <L2-ID> -f; echo "exit $?"
```
**Expected:** it ends after about 20 s (plus start-up) with `failed (deadline_exceeded)` and exit
code **126**. The overshoot = the time between `running` and `failed` in
`curl -s -H "Authorization: Bearer $MESHFORGE_CLI__TOKEN" $MESHFORGE_CLI__CONTROLLER_URL/v1/jobs/$J`
(`transitions`) minus 20 s; must be ≤ 2 s.

## Exit codes

| Code | `compute run -f` | `lab/exec_check.py` |
|---|---|---|
| 0 | the job succeeded | done, within the bound |
| 1–125 | the workload's own exit code (`user_error`) | – |
| 126 | the fabric failed the job (stderr names the failure type) | – |
| 128 | the job was cancelled | – |
| 130 | Ctrl-C: `compute` detached, the job keeps running | – |
| 2 | wrong arguments | wrong arguments |
| 3 | – | done, but over the bound or too few lines |
| 4 | configuration error (e.g. `--local` on a laptop without an agent) | – |
| 6 | controller unreachable | controller unreachable |

## Troubleshooting

| Symptom | What to do |
|---|---|
| `409 no_feasible_plan` at submit | that node does not advertise `exec` (B2 not applied) or has no GPU runtime for a `gpu: required` job |
| job stays `queued` | the node is SUSPECT/OFFLINE (`compute nodes`), or busy with another job (one per node in V0.4) |
| `failed (env_error)` on Docker | the image could not be pulled / started: pull it by hand (A3) and re-run |
| `failed (output_error)` | outputs could not be uploaded: is L1:47110 reachable from that laptop? (`curl http://<L1-IP>:47110/healthz` there) |
| `compute: … 401` | `MESHFORGE_CLI__TOKEN` not set in this terminal (B3) |
