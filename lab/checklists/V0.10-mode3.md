# V0.10 lab — Mode 3 Task Splitting on real laptops (roadmap 0.10.10)

This checklist runs V0.10's success criteria on **3–4 heterogeneous laptops**: the same things
`tests/cluster/test_v010_mode3.py` checks on one machine (G9), now over a real network with real, different
hardware. Words used: **L1** = the controller laptop (Linux, also runs an agent), **L2–L4** = the Windows laptops
(agents native or in WSL2, as set up in V0.4–V0.9). `<L1>`…`<L4>` = each laptop's node id from `compute nodes`.

| Criterion (roadmap V0.10, calibrated by D274) | Part | Pass when |
|---|---|---|
| **C1** 3,000-image classification split over 3 laptops == single-laptop output | A | every run of the campaign has the **same output digest** and `verify` says `OK` |
| **C2** makespan ≤ 1.25 × ideal Σ-throughput bound | B | `report` prints `c2: PASS` (judged only when the best single laptop needs ≥ 300 s; shorter = `REPORTED`) |
| **C3** speedup vs best single laptop (≥ 0.8 × Σr/r_best; ≥ 2.0 × on 3 laptops if Σr/r_best ≥ 2.5) | B | `report` prints `c3: PASS` |
| **C4** `kill -9` of one laptop at ~50 % → correct, complete output, every chunk committed once | C | job `succeeded`, digest == part A's, ledger line says `max won per chunk 1` |
| **C5** planner picks "don't split" when splitting is predicted slower | D | rank 1 is `local`/`offload`, explain says `not split: …` |

Every step ends with **PASTE BACK:** — copy it into `lab/reports/<date>-V0.10-mode3.md` (from
`lab/reports/TEMPLATE.md`). Write **PASS / FAIL** next to each criterion in the report, with the line that decides
it. A step that could not be run is written down as such — never as a pass.

## A. C1 — identical output: `split.image_classify`, 3,000 images (forced split vs every single laptop)

The split is **forced** through a campaign (`strategies: [mode3]`, D287) so the run does not depend on the
planner's choice; `local` / `mode1` runs are the same job "don't split" on one laptop (one lane, one chunk —
the same code path, D269). `split.image_classify` is integer arithmetic (D287): its output must be identical on
every CPU.

- [ ] **A1 — campaign.** On L1 write `c1.yaml` (use 3 laptops: L1 + the two most different others; with 4
  laptops list all four under `nodes` and the mode3 set stays "every node"):

  ```yaml
  name: lab-v010-c1
  seed: 31
  families:
    - family: split.image_classify
      params: {images: 3000}
  strategies: [local, mode1, mode3]
  nodes: [<L1>, <L2>, <L3>]
  origin: <L1>
  repetitions: 3
  session_label: wifi
  budget: {max_runs: 20, max_hours: 2}
  ```

  ```bash
  compute bench plan c1.yaml           # 12 runs: local L1, mode1 L2, mode1 L3, mode3 {L1,L2,L3} x 3
  compute bench create c1.yaml         # prints camp_...
  compute bench start <camp_id> --per-node 1 --cooldown 2
  compute bench status <camp_id>       # repeat until done
  ```

- [ ] **A2 — every output identical and correct.** When `status` says `done`:

  ```bash
  compute bench runs <camp_id> --json > c1-runs.json
  uv run python -c "import json; [print(r['seq'], r['strategy'], r['node_id'], r.get('node_set'), r['seed'], r['job_id'], r['state']) for r in json.load(open('c1-runs.json'))['runs']]"
  for j in $(uv run python -c "import json; print(' '.join(r['job_id'] for r in json.load(open('c1-runs.json'))['runs']))"); do
    echo "$j $(compute jobs $j --json | uv run python -c "import json,sys; print(json.load(sys.stdin).get('output_digest'))")"
  done
  ```

  Pick one `mode3` job `<M3>` and one `mode1` job `<S1>` from the list, then (the seed is the run's `seed` column):

  ```bash
  compute get <M3> --dest out-m3 && uv run python lab/mode3_check.py verify split.image_classify out-m3 --param images=3000 --seed <SEED>
  compute get <S1> --dest out-s1 && uv run python lab/mode3_check.py verify split.image_classify out-s1 --param images=3000 --seed <SEED>
  compute explain <M3>
  compute watch <M3> --json
  ```

  Expected: 12 runs `done`; **one** output digest across all 12 jobs; both `verify` print `OK` and the same
  `output digest`; `explain` shows the chosen `split` row over every laptop of the set (forced by the campaign);
  `watch --json` shows `chunks.done == chunks.total` and one entry per laptop in `lanes`.
  **C1 PASS** = all of these. **PASTE BACK:** the runs list, the digest list, both `verify` outputs, the
  `explain` output and the `watch --json` line of `<M3>`.

## B. C2 + C3 — makespan and speedup on a long CPU job (`mc`, ≥ 5 min on one laptop)

D274: rates are measured **in the same session** by single-laptop runs of the **same job**; C2 is judged only
when the best single laptop needs ≥ 300 s. The split run is the planner's own choice (it should split a job this
long; if it does not, that is a finding — paste `compute explain`).

- [ ] **B1 — single-laptop runs** (one at a time; each takes minutes): for each laptop `<Lk>` of the set

  ```bash
  compute run mc --node <Lk> -f --no-progress      # prints the job id first; note it: S_<Lk>
  ```

- [ ] **B2 — the split run** (nothing else running):

  ```bash
  compute run mc -f                                 # job id: M; the progress bar shows lanes per laptop
  compute explain M
  compute watch M --json
  ```

- [ ] **B3 — numbers.**

  ```bash
  compute telemetry export --since <SESSION_START> -o b-runs.parquet
  compute telemetry export --since <SESSION_START> --table chunks -o b-chunks.parquet
  uv run python lab/mode3_check.py report b-runs.parquet b-chunks.parquet --split M --single S_<L1> --single S_<L2> --single S_<L3> --out b-report.json
  compute get M --dest out-mc && uv run python lab/mode3_check.py verify split.montecarlo_range out-mc --param items=5000 --param samples=5000000 --seed 10
  ```

  `report` prints the per-laptop items/s (`rates`), `rate_ratio` (Σr/r_best), the ideal bound (items / Σr +
  slowest lane start + combine), `makespan_ratio`, `speedup`, and `c2` / `c3` (`PASS`, `FAIL`, `REPORTED`,
  `INCONCLUSIVE` + `problems`). `recorded_bound_s` is the job's own bound from its chunks (G8) — report it too.
  **C2 / C3 verdicts** = the `report` lines. `verify` must say `OK`.
  **PASTE BACK:** the job ids, `explain M`, `watch M --json`, the whole `report` output and `b-report.json`, the
  `verify` output. If `explain` shows M was **not** split, paste it and write C2/C3 as "not run: planner kept it
  whole" with the margin line.

## C. C4 — `kill -9` of one laptop at ~50 %

A forced split of a longer `image_classify` (20,000 images: the largest; ~1 min on L1, longer on slower
laptops). The victim is **not L1** (it runs the controller). Three repetitions: if a job ends before you could
kill, use the next one.

- [ ] **K1 — campaign.** `c4.yaml` = `c1.yaml` with `name: lab-v010-c4`, `seed: 41`, `params: {images: 20000}`,
  `strategies: [mode3]` and `max_runs: 5`. `compute bench create c4.yaml`, `compute bench start <camp_id> --per-node 1 --cooldown 10`.
- [ ] **K2 — the kill.** As soon as `compute bench runs <camp_id>` shows a `submitted` run, take its job id `K`
  and run `compute watch K`. When the bar is between **30 % and 70 %** items done and the victim's line shows a
  chunk running, on the **victim** laptop:

  ```powershell
  taskkill /F /T /IM meshforge-agent.exe            # native Windows agent
  ```
  ```bash
  pkill -9 -f "meshforge-agent run"                  # WSL / Linux agent
  ```

  Note the time. Do **not** restart the victim until `K` has ended. Expected: within the node lease (about
  15–30 s) the victim's lane turns `lost`, its chunk goes back to the queue, the other lanes finish it, `K`
  ends `succeeded`. Then restart the victim's agent the normal way.
- [ ] **K3 — evidence.**

  ```bash
  compute jobs K
  compute explain K
  compute watch K --json
  compute telemetry export --campaign <camp_id> --table chunks -o c4-chunks.parquet
  uv run python -c "import pyarrow.parquet as pq,collections,sys; t=[r for r in pq.read_table('c4-chunks.parquet').to_pylist() if r['job_id']==sys.argv[1]]; won=collections.Counter(r['chunk_index'] for r in t if r['won']); print('chunks', len(won), 'max won per chunk', max(won.values()), 'items', sum(r['items'] for r in t if r['won'])); print(collections.Counter((r['node_id'][-6:], r['won'], r['failure_type']) for r in t))" K
  compute get K --dest out-k && uv run python lab/mode3_check.py verify split.image_classify out-k --param images=20000 --seed <SEED of K's run>
  compute bench runs <camp_id> --json > c4-runs.json      # then cancel the rest: compute bench cancel <camp_id>
  ```

  Then, for the "same digest" half: run the same job **unsplit** once — `compute bench` cannot pin one
  campaign run, so build it: `uv run python lab/mode3_check.py build split.image_classify ic20k --param images=20000 --seed <SEED of K's run>`
  and `compute run ic20k --node <L1> -f --no-progress` → job `U`; `compute jobs U` and `compute jobs K` must
  show the **same output digest** (the campaign's job folder and this one are byte-identical: same family,
  params, seed).
  Expected: `K` `succeeded`; `compute jobs K` lists the victim's lane `lost` / `node_lost`; the python line
  prints `max won per chunk 1` and `items 20000`; `verify` `OK`; digests of `K` and `U` equal.
  **C4 PASS** = all of these. **PASTE BACK:** the kill time and command, `compute jobs K`, `explain K`, `watch K
  --json`, the python lines, `verify`, `compute jobs U`.

## D. C5 — "don't split" on a real link

`hf` (0.3) is 60 files × 1 MiB with one hashing round: little work per byte, so shipping items to other laptops
costs more than it saves. Submitted from **L1** (its own agent is the Local candidate and `compute run` seeds its
cache — the items are already there).

- [ ] **D1.**

  ```bash
  compute network                                   # the measured links (if any)
  compute run hf -f --no-progress                   # job id: H
  compute explain H
  ```

  Expected: rank 1 is `local` on `<L1>` (or `offload` on one laptop); the split table's title says
  `not split: the best set … is above … = (1 - 0.1) x … (best single node …)` and the set rows say `fail:`; the
  `ITEMS_FETCH` column shows the cost of moving the files to the other laptops.
  **C5 PASS** = the job ran unsplit and `explain` says why. If it **was** split, that is a finding: paste it
  (it means the measured links were fast enough that splitting was predicted faster — then also run it once
  more over Wi-Fi with Ethernet unplugged). **PASTE BACK:** `compute network`, `explain H`.
