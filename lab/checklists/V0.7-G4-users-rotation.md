# V0.7 G4 lab check - users, logins and certificate rotation on real laptops (tester)

Needs: controller laptop **L1** (Linux), >= 2 agent laptops (**at least one Windows**, L2/L3), all
enrolled (G3 checklist section A), G4 code pulled everywhere. Roughly 40 minutes. Paste back the
lines marked **PASTE**. `<L1-IP>` is L1's LAN address.

## 0. Database password and users (L1)
1. Start the controller with the dev database password: `meshforge-controller` with
   `MESHFORGE_DATABASE__PASSWORD=meshforge-dev`. **PASTE** the last stderr line and the exit code
   (`echo $?`). Expected: `config_error`, "the database password is the published development
   default", exit **4**. Then set a strong password (OPERATIONS 0a1 "Database password") and start it.
2. `meshforge-controller user create admin --admin` and `meshforge-controller user create alice`.
   `meshforge-controller fabric show` - note the **full** CA fingerprint.
3. `curl -k https://<L1-IP>:47110/v1/nodes` and `curl -k https://<L1-IP>:47110/healthz`.
   **PASTE** both status lines. Expected: `401` and `200` (D148: only /healthz is open).

## A. Login from another laptop (L2, and once on Windows L3)
1. `compute login --controller https://<L1-IP>:47110 --fingerprint "<a WRONG fingerprint>" --user alice`.
   **PASTE** the error. Expected: "does not hold the fabric CA with that fingerprint ... Nothing was sent".
2. The same with the right fingerprint; then `compute whoami`. **PASTE** both outputs. Expected:
   `logged in to https://<L1-IP>:47110 as alice (user)` and `alice (user)`; no token printed.
3. Linux: `ls -l ~/.config/meshforge/compute/`; Windows: `icacls %APPDATA%\MeshForge\compute\login.json`.
   **PASTE**. Expected: `-rw-------` / only your user.
4. Five wrong passwords then the right one: `compute login ... --user alice` x6. **PASTE** the 6th
   answer. Expected `429` "too many failed logins", then success after waiting the `Retry-After`.

## B. Owner rule
1. As alice on L2: `compute run lab/workloads/<any> --node <L3 id> -f`; note the job id.
2. On L1 log in as admin (`compute login --user admin`), run a job, note its id.
3. As alice: `compute jobs <admin job id>` and `compute logs <admin job id>`. **PASTE**. Expected:
   "no such job" for both. As admin: `compute jobs <alice job id>` works.
4. As alice: `compute fabric invite`. **PASTE**. Expected `(403): this call needs an admin account`.
5. As alice: `compute logout`, then `compute jobs`. **PASTE**. Expected: refused, "run `compute login`".

## C. No plaintext (extends G3 section B)
Repeat G3 B with a capture running during A.2 and B.1: `strings g4.pcap | grep -c -e <alice's password> -e mfat_`
**PASTE** the number. Expected `0`.

## D. Rotation on a running fabric (D140)
1. On L2: `meshforge-agent identity show`. **PASTE** `cert_serial` and `cert_renewal_due`.
2. On L2 while a long job runs on it: `meshforge-agent rotate-key`. Within `[agent.cert]
   renew_check_interval_s` (or at once after an agent restart) **PASTE** `identity show` again and the
   job's final state. Expected: new `cert_serial`, same `node_id`, the job `succeeded` (no `lost`).
3. On L1: `compute nodes` - L2 still `online`. **PASTE**.
