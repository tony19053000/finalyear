# V0.3 lab run — fabric core on 4 laptops (roadmap 0.3.15)

This is the step-by-step procedure the team runs **without an agent present**. It produces the
evidence for the five V0.3 success criteria (roadmap, V0.3):

| # | Criterion | Tool | Part |
|---|---|---|---|
| 1 | All 4 laptops appear with hardware matching `docs/LAB.md` | `fabric_check.py inventory` + **your eyes** | C |
| 2 | Cable pulled → OFFLINE **≤ 8 s**; restored → ONLINE **≤ 10 s**, **no agent restart** | `fabric_check.py watch` | D |
| 3 | Controller killed + restarted → all agents back **≤ 15 s**, no manual action | `fabric_check.py restart-check` | F |
| 4 | Agent restart keeps the same `node_id` | `fabric_check.py watch --action agent` (+ F) | E |
| 5 | 24 h soak on Ethernet: **zero false OFFLINE**; agent RSS growth **< 10 %** | `fabric_check.py soak` + `agent_rss.py` | G |

Plan about **2 hours** for parts A–F, then the 24 h soak (G) — it can start right after F.

Every tool writes its results itself: a JSON file under `lab/reports/raw/<date>-V0.3-…/` and a
report `lab/reports/<date>-V0.3-….md`. Re-running a tool **adds** to the same day's report and
keeps anything you typed into it (Goal, Expected vs actual, Conclusion …).

Words used below:

- **L1** = the controller laptop (Linux; runs PostgreSQL, the controller, an agent, and all
  `fabric_check.py` commands). **L2, L3, L4** = the other laptops (Windows; run an agent).
- **`<L1-IP>`** = L1's **Ethernet** IPv4 address, e.g. `192.168.1.20` (how to find it: A3).
- **Terminal A/B/C** on L1 = three separate terminal windows, all in the repository folder.

## A. Before the day (prerequisites)

Tick every box. If one is missing, stop and fix it first — a run on a half-prepared lab is
wasted time and, worse, misleading evidence.

- [ ] **A1 — Inventory done on all 4 laptops** (`docs/SESSION_HANDOFF.md` §3 item 0):
      `lab/reports/inventory/<hostname>.json` exists for each and `docs/LAB.md` §1 is filled in.
      Criterion 1 compares against that table; without it criterion 1 cannot be judged.
- [ ] **A2 — Same code everywhere.** The repository is pushed to GitHub and every laptop has
      pulled it (`docs/SESSION_HANDOFF.md` §3 item 1). On **each** laptop, from the repo folder:
      ```
      git pull
      git rev-parse --short HEAD
      ```
      All four must print the **same** hash. Write it down — it goes into every report.
- [ ] **A3 — Gigabit switch, 4 Ethernet cables, all laptops wired** (`docs/SESSION_HANDOFF.md`
      §3 item 4). Find L1's Ethernet address:
      ```bash
      ip -4 -brief addr      # the line for the Ethernet interface (enp…/eth…), e.g. 192.168.1.20/24
      ```
      A DHCP reservation for each laptop is strongly recommended (the address must not change
      during the 24 h soak).
- [ ] **A4 — Wi-Fi OFF on all four laptops** for parts D and G. If Wi-Fi stays on, pulling the
      cable just moves the traffic to Wi-Fi and the node never goes OFFLINE — the test would
      measure nothing. (Turn it off in the system tray / top bar; airplane mode is fine if
      Ethernet stays up.)
- [ ] **A5 — Windows network profile = Private** on L2–L4 (Settings → Network → Ethernet →
      Network profile type).
- [ ] **A6 — Firewall: only on L1, only two ports.** Inbound TCP **47100** (gRPC, agents dial
      in) and **47110** (REST). The Windows laptops need **no** inbound rule (agents only dial
      out — that is part of what this run proves). On L1, only if `sudo ufw status` says
      `active`:
      ```bash
      sudo ufw allow from 192.168.1.0/24 to any port 47100,47110 proto tcp   # use your subnet
      ```
- [ ] **A7 — Power:** every laptop plugged in, "sleep when plugged in" = never, lid stays open.
      - Windows (PowerShell): `powercfg /change standby-timeout-ac 0` and
        `powercfg /change hibernate-timeout-ac 0`. Pause Windows Update for a week
        (Settings → Windows Update) so it does not reboot during the soak.
      - Ubuntu: Settings → Power → *Automatic Suspend* = Off.
- [ ] **A8 — Two people for part D** (one at L1's keyboard, one at the laptop whose cable is
      pulled), unless the laptops sit next to each other.

## B. Start the fabric

**L1 — Terminal A (controller):**
```bash
uv sync --extra controller --extra agent
docker compose -f deploy/docker-compose.dev.yml up -d --wait          # PostgreSQL
MESHFORGE_CONTROLLER__GRPC_BIND=<L1-IP>:47100 \
MESHFORGE_CONTROLLER__HTTP_BIND=<L1-IP>:47110 \
uv run meshforge-controller
```
Leave it running. (You will kill and restart it in part F — keep this window.)

**L1 — Terminal B (L1's own agent):**
```bash
uv run meshforge-agent run --controller <L1-IP>:47100
```

**L2, L3, L4 — one PowerShell window each** (native Windows, not WSL), in the repo folder:
```powershell
uv sync --extra agent
uv run meshforge-agent run --controller <L1-IP>:47100
```
Leave these windows open and **do not log off** (a logged-off Windows session may end the
agent — `docs/OPERATIONS.md` §3).

**L1 — Terminal C (all the checks run here):**
```bash
export MESHFORGE_CLI__CONTROLLER_URL=http://<L1-IP>:47110
uv run compute nodes
```
Expected: **4 rows**, every one `STATE online`, `CONN yes`. Note each laptop's **HOSTNAME** —
the commands below use it. If a laptop is missing, see *Troubleshooting* at the end.

All `fabric_check.py` commands below run in **Terminal C** and use the URL from
`MESHFORGE_CLI__CONTROLLER_URL` (or pass `--controller http://<L1-IP>:47110`). `--name L1`
labels this laptop in the reports.

## C. Criterion 1 — hardware inventory (5 minutes)

```bash
uv run python lab/fabric_check.py --name L1 inventory
```
It prints one row per node: hostname, node_id, OS, state, agent version, CPU (cores/threads),
RAM, GPUs (model, VRAM, driver, compute capability) and capability tags.

**What to do:** compare every row with that laptop's column in `docs/LAB.md` §1 and its
`lab/reports/inventory/<hostname>.json`. **The tool does not decide whether they match — you
do.** Open `lab/reports/<date>-V0.3-fabric-inventory.md` and write, under *Expected vs actual*,
one line per laptop: "matches" or exactly what differs (e.g. "L3 GPU: LAB.md says RTX 2050,
controller shows none — NVML not available?").

A note like `hostname 'X' has 2 node ids` means that laptop enrolled twice at some point (its
identity was reset). Only the connected one matters today; mention it in the report.

---

## D. Criterion 2 — pull the network cable (about 30 minutes)

Do this for **L2, L3 and L4**, one laptop at a time. **Not L1** — its cable carries the
controller itself.

```bash
uv run python lab/fabric_check.py --name L1 watch --node <L2-HOSTNAME> --link ethernet
```
The tool runs **5 repetitions**. Each repetition:

1. It waits until the laptop is online and connected.
2. It shows `>>> PULL the network cable of <host> …`. The person at L1 counts "3, 2, 1, now";
   on **now** the other person **pulls the Ethernet cable out of the laptop** (laptop end)
   and the person at L1 **presses Enter at the same moment**.
3. It prints `offline detected X.XX s after Enter (bound 8 s: within)`.
4. It shows `>>> PLUG the network cable of <host> back in …`. Plug it back in and press Enter
   at the same moment.
5. It prints `online detected X.XX s after Enter (bound 10 s: …)`.

Do **not** plug the cable back in before the tool asks. Do not touch the agent's window.

**Expected:** OFFLINE within **8 s** (the loopback prediction is ~6.0 s: the 6 s lease plus up
to one poll), ONLINE within **10 s**, and in the report the column *Agent process restarted* =
**no** for every row. The loopback prediction for ONLINE is ~0.3 s; a real re-plug adds link
negotiation (1–3 s) and possibly the agent's reconnect backoff, so expect more — **whatever you
measure is the result; write it down, do not repeat until it passes.**

The *Session end reason* column records how the controller learned about the loss:
`lease_expired` (nothing arrived, the lease ran out — a silent pull) or `stream_lost` (the OS
reset the TCP connection). Both are valid; which one happens on your hardware is itself
evidence, so do not "fix" it.

Messages you may see:

| Message | Meaning / what to do |
|---|---|
| `… was reached … BEFORE Enter was pressed` | Enter came late; that repetition does not count. The tool continues. |
| `offline not seen within 60 s of Enter` | The laptop did not lose its connection — is Wi-Fi really off (A4)? |
| `… came back as a different node …` | Its identity changed: a real criterion-4 failure. Report it. |
| `waiting for … to be online and connected …` | Plug the cable in / check the agent window. |

The exit code is `0` when all 5 repetitions were within the bounds with no agent restart, `3`
otherwise (the report says which).

## E. Criterion 4 — restart an agent, keep the node_id (about 15 minutes)

For **each of the four laptops** (L1 included, its agent is in Terminal B):

```bash
uv run python lab/fabric_check.py --name L1 watch --node <HOSTNAME> --action agent --link ethernet
```
Each of the 5 repetitions asks you to:

1. `>>> STOP the agent on <host> …` — press **Ctrl-C in that laptop's agent window** and Enter
   in Terminal C at the same moment.
2. `>>> START the agent on <host> again …` — in the agent window press **Up-arrow, then Enter**
   (re-runs `uv run meshforge-agent run --controller …`) and Enter in Terminal C.

**Expected:** OFFLINE almost at once (end reason `agent_closed` — a clean goodbye), back ONLINE
**under the same node_id** (the tool follows that one id; a new id ends the repetition with
`node_id_changed`), and *Agent process restarted* = **yes** (proves the restart really happened).
There is no time bound for this criterion; the *Within bounds* column says `n/a`.

Optional cross-check on one laptop: `uv run meshforge-agent identity show` before and after —
the same `node_id`.

## F. Criterion 3 — kill and restart the controller (about 10 minutes)

```bash
uv run python lab/fabric_check.py --name L1 restart-check --link ethernet
```
It records which nodes are connected, then shows `>>> KILL the controller now and START it
again straight away`. For each of the 5 repetitions:

1. In **another** L1 terminal, kill the controller hard (this is a crash, not a clean stop —
   **do not use Ctrl-C**):
   ```bash
   pkill -KILL -f meshforge-controller
   ```
2. At once, in **Terminal A**, press **Up-arrow, Enter** to start the controller again (the same
   command as in part B). Try to be quick (a few seconds): the agents' retry backoff grows while
   the controller is down (capped at 5 s).
3. Do nothing else. The tool sees the controller go down and come back by itself and prints
   `all 4 node(s) connected X.XX s after the controller came back (bound 15 s: …)`.

(If the controller ever runs on Windows instead, kill it in PowerShell with
`Get-CimInstance Win32_Process -Filter "CommandLine LIKE '%meshforge-controller%'" | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }`.)

**Expected:** every node back within **15 s** of the new controller answering (loopback
prediction ~2.4 s), *node_id kept* = **yes**, *Agent process restarted* = **none**. The time it
took you to restart the controller is shown separately as *Controller outage* and is not part of
the bound.

## G. Criterion 5 — the 24-hour soak on Ethernet

Start it right after part F, with every agent running and **Wi-Fi still off** everywhere.

1. **On every laptop** (L1 in a new terminal, L2–L4 in a second PowerShell window), start the
   memory sampler for that laptop's agent:
   ```bash
   # L1 (bash)
   uv run --extra agent python lab/agent_rss.py run --hours 24 --name L1
   ```
   ```powershell
   # L2 / L3 / L4 (PowerShell) — use the laptop's own label
   uv run --extra agent python lab\agent_rss.py run --hours 24 --name L2
   ```
   It finds the running `meshforge-agent` process by itself (on Windows it skips the `uv.exe`
   and launcher processes and takes the Python process below them) and prints one line a
   minute. If it says several agents are running, pass `--pid <PID>` (Task Manager → Details,
   the `python.exe` whose command line contains `meshforge-agent`).
2. **On L1, Terminal C:**
   ```bash
   uv run python lab/fabric_check.py --name L1 soak --hours 24 --link ethernet
   ```
   It prints a line only when something changes (a state change, a session end, the controller
   not answering).
3. **Leave everything alone for 24 hours.** Do not touch cables, lids, Wi-Fi or the agent
   windows. If someone *has* to touch a laptop, write down the time and what was done — those
   events are then not "false" OFFLINEs.
4. **If a tool window closes or a laptop reboots by accident:** start the same command again.
   Both tools resume from their checkpoint (saved at every change and at least every 5 minutes
   / every sample); the time the tool was not running is recorded as a *gap* and does not
   count towards the 24 h, so the tool keeps going until 24 h have really been observed.
5. **After 24 h** both tools stop by themselves and print a summary.
   - Copy each Windows laptop's file `lab\reports\raw\<date>-V0.3-agent-rss\<name>.json` into the
     same folder on L1 (USB stick, or commit + pull). `<date>` is the day the sampler **started**.
   - On L1: `uv run python lab/agent_rss.py report --day <date>` — rebuilds
     `lab/reports/<date>-V0.3-agent-rss.md` with one row per laptop.

**Expected:** soak report — *OFFLINE events* **0**, *Controller outages* **0**, *Observed h*
≥ **24**. SUSPECT events and `stream_lost` session ends may appear (a brief blip the agent
survived); they are recorded, but they are not OFFLINEs. RSS report — *Growth %* **< 10** on
every laptop and *Agent restarts seen* **0**. (Growth is measured from the first sample taken
10 minutes after the sampler started, so start-up allocations do not count as a leak.)

## Exit codes (all tools)

| Code | `fabric_check.py` | `agent_rss.py` |
|---|---|---|
| 0 | done; every measured value within its bound | done; growth < 10 %, no agent restart |
| 1 | cannot write the result / checkpoint unreadable | same |
| 2 | wrong command-line arguments | same |
| 3 | done, but something failed or a bound was exceeded — see the report | done, but growth ≥ 10 %, a restart, or no agent seen |
| 4 | — | psutil missing: use `uv run --extra agent …` |
| 5 | — | no agent process found (or several: pass `--pid`) |
| 6 | the controller could not be reached | — |
| 130 | Ctrl-C: what was measured so far is written; `soak` resumes when re-run | same |

## Troubleshooting

| Symptom | What to do |
|---|---|
| `cannot reach the controller at http://127.0.0.1:47110` | The controller listens on `<L1-IP>`, not 127.0.0.1: set `MESHFORGE_CLI__CONTROLLER_URL` (part B) or pass `--controller`. |
| A laptop missing from `compute nodes` | Look at its agent window. "connect/backoff" repeating → L1's firewall (A6) or a wrong `<L1-IP>`. |
| `hostname 'X' matches 2 node(s)` | That laptop enrolled twice; pass `--node node_…` (the connected one from `compute nodes`). |
| The agent exits with code 5 at start | Another agent already runs on that laptop (a second window, or the Task Scheduler task). Stop the other one. |
| `agent_rss` exit 4 | You ran it without `--extra agent`. |
| More detail about the three liveness fields (STATE / CONN / AGE) | `docs/OPERATIONS.md` §5 and ARCHITECTURE §12.3. |
