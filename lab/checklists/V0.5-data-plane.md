# V0.5 lab run — data plane with multi-GB data on Wi-Fi and Ethernet (roadmap 0.5.11)

The procedure the team runs **without an agent present**. It produces the real-machine evidence for
the V0.5 success criteria that loopback tests cannot prove:

| # | Criterion | How | Part |
|---|---|---|---|
| 1 | Resubmitting an unchanged project transfers **0 bytes**; one changed file transfers only that file | `compute data push` / `compute run` twice, the `uploaded … skipped …` line and the job's transfer rows | E |
| 2 | A 5 GB transfer on **Ethernet** reaches **≥ 80 %** of the iperf3-measured bandwidth *(calibrate)* | iperf3 baseline (D) vs the job's staging throughput (F) | D, F |
| 3 | An interrupted transfer resumes without re-sending completed chunks | kill the fetching agent mid-transfer, restart (H) | H |
| 6 | Data comes from a **peer** when the peer is closer/faster than the controller | per-source bytes of a job whose input a peer holds (G) | G |
| 0.5.8 | `compute node prepare` pulls the pinned images / builds an env ahead of a run | part J | J |
| 0.5.9 | GC keeps a laptop under its quota without touching what runs or is pinned | part I | I |

Criteria 4 (corruption) and 5 (warm env ≤ 3 s) are proven by component tests and the G2 lab numbers;
nothing to do here unless part K shows otherwise.

Plan about **2.5 hours** (most of it waiting for 5 GB to move). Words used below: **L1** = the
controller laptop (Linux; runs PostgreSQL, the controller, its own agent, and every command unless
stated otherwise); **L2–L4** = the other laptops; **`<L1-IP>`**, **`<L2-IP>`** … = each laptop's
address on the network of the part you are in (Ethernet in most parts, Wi-Fi where it says so).

Every number below is printed by `compute`, `iperf3` or the agent logs; paste what part L asks for.
**Whatever you measure is the result — write it down, do not repeat a step until it passes.**

## A. Before the day

- [ ] **A1 — Same code everywhere.** On each laptop: `git pull` then `git rev-parse --short HEAD`.
      All four must print the **same** hash. Write it down.
- [ ] **A2 — Free disk ≥ 20 GB** on every laptop (`df -h ~` / Explorer). The dataset is 5 GB and

- [ ] **A3 — iperf3** on L1 and L2: `sudo apt install iperf3` (Linux),

- [ ] **A4 — Ethernet switch** connecting L1–L4 (criterion 2 is an **Ethernet** criterion). Note
      the switch model and each NIC's link speed (Linux: `ethtool <iface> | grep Speed`; Windows:
      `Get-NetAdapter | ft Name, LinkSpeed`).
- [ ] **A5 — Firewall.** L1: TCP 47100 + 47110 (as in V0.3/V0.4) **and** 47120. Every agent
      laptop: inbound **TCP 47120 on the LAN / Private profile only** (the peer blob port,
      `docs/OPERATIONS.md` §0d):
      ```bash
      sudo ufw allow from <LAN-CIDR> to any port 47120 proto tcp          # Linux
      ```
      ```powershell
      New-NetFirewallRule -DisplayName "MeshForge peer blobs" -Direction Inbound `
        -Protocol TCP -LocalPort 47120 -Profile Private -Action Allow    # Windows (admin)
      ```
      And for part D only: TCP 5201 (iperf3) on L1 the same way.

## B. Start the fabric with peers on (Ethernet)

**B1 — L1, Terminal A (controller):**
```bash
uv sync --extra controller --extra agent
docker compose -f deploy/docker-compose.dev.yml up -d --wait
MESHFORGE_CONTROLLER__GRPC_BIND=<L1-IP>:47100 \
MESHFORGE_CONTROLLER__HTTP_BIND=<L1-IP>:47110 \
uv run meshforge-controller
```

**B2 — every laptop: an agent that runs jobs and serves its cache to peers.** In the agent's
`config.toml` (`uv run meshforge-agent run --help` prints where it is), add:
```toml
[agent.execution]
enabled = true

[agent.peer]
bind = "<this laptop's LAN IP>"     # never 0.0.0.0

[agent.gc]
cas_bytes = 30_000_000_000          # 30 GB: no eviction during parts C-H
```
Then L1 Terminal B / L2–L4 PowerShell: `uv run meshforge-agent run --controller <L1-IP>:47100`.
Each window must show `agent.peer.listening` with its address and port 47120 (else the firewall or
`bind` is wrong — fix before going on).

**B3 — L1, Terminal C (everything below runs here):**
```bash
export MESHFORGE_CLI__CONTROLLER_URL=http://<L1-IP>:47110
export MESHFORGE_CLI__TOKEN=$(uv run meshforge-controller token show)
uv run compute nodes
```
Expected: 4 rows `online`. `uv run compute nodes <NODE_ID>` shows each laptop's `peer_endpoint`
(`<its IP>:47120`). Write down the NODE_IDs as `<L1-ID> … <L4-ID>`.

## C. The dataset (5 GB of incompressible data) and a reader job

On L1 (≈ 1 minute):
```bash
mkdir -p ~/mf-lab/ds5g ~/mf-lab/reader
python3 - <<'EOF'
import os, pathlib
d = pathlib.Path.home() / "mf-lab/ds5g"
for i in range(5):                       # 5 files x 1 GiB, random bytes
    with open(d / f"part{i}.bin", "wb") as f:
        for _ in range(1024):
            f.write(os.urandom(1024 * 1024))
(d / "labels.csv").write_text("a,b\n1,2\n")
EOF
cat > ~/mf-lab/reader/main.py <<'EOF'
import hashlib, pathlib
h = hashlib.sha256()
for p in sorted(pathlib.Path("data/ds").glob("*.bin")):
    with open(p, "rb") as f:
        while b := f.read(1 << 20):
            h.update(b)
print("dataset sha256", h.hexdigest())
EOF
printf 'name: reader\nentrypoint: python main.py\ninputs:\n  - ref: ds5g@1\n    mount: data/ds\nlimits: {timeout: 2h}\n' > ~/mf-lab/reader/compute.yaml
```

## E. Criterion 1 — upload once, never again

```bash
time uv run compute data push ds5g ~/mf-lab/ds5g        # 1st time: uploads ~5 GB
time uv run compute data push ds5g ~/mf-lab/ds5g        # 2nd time
```
**Expected:** the first prints `uploaded 6 files / ~5368709128 bytes, skipped 0` and
`registered ds5g@1`; the **second** prints `uploaded 0 files / 0 bytes, skipped 6` and
`already registered as ds5g@1`. Then change one file and push again:
```bash
echo "c,d" >> ~/mf-lab/ds5g/labels.csv
uv run compute data push ds5g ~/mf-lab/ds5g
```
**Expected:** `uploaded 1 files / <a few> bytes, skipped 5` and `registered ds5g@2`.

## F. Criterion 2 — a 5 GB fetch on Ethernet

```bash
J=$(uv run compute run ~/mf-lab/reader --node <L2-ID>)     # prints the job id
uv run compute logs $J -f
uv run compute jobs $J
uv run compute jobs $J --json > ~/mf-lab/F-$J.json
```
The `transfer` lines show, for tree `ds5g@1`: one `cache` line (`staged in X s`, the whole
staging: fetch + verify + copy into the job folder) and one line per source (`from controller:
N MiB …`, `from <peer>: …`). **Throughput** = (sum of the sources' MiB) / (the cache line's
seconds). Compare with D1: `throughput (MB/s) × 8 / iperf3 Mbit/s`. The criterion asks
≥ 80 % — this number includes copying into the workdir, so it is conservative.
Also from L2's agent log: the `agent.cas.staged`/`agent.cas.input_staged` lines.

Repeat once on **Wi-Fi** (L2 on Wi-Fi only) — a *new* laptop must fetch (L3), because L2 has it
cached now: `--node <L3-ID>`. Wi-Fi has no pass mark; record the number next to D2.

## G. Criterion 6 — a peer serves when it is the better source

L2 holds `ds5g@1` now (part F). Run the reader on L4:
```bash
J=$(uv run compute run ~/mf-lab/reader --node <L4-ID>)     # prints the job id
uv run compute logs $J -f
uv run compute jobs $J
```
**Expected:** `transfer` lines from the controller **and** from `<L2-ID>`. Then make the controller
the worse source — put **L1 on Wi-Fi** while L2, L4 stay on Ethernet (restart the controller with
its Wi-Fi address in B1, agents reconnect within ~10 s), clear L4's copy so it must fetch again:
```bash
# on L4: stop its agent (Ctrl-C), print its data dir, delete the cache and the GC
# index there, start the agent again (B2):
#   uv run python -c "from meshforge.common.config import default_data_dir as d; print(d())"
#   Linux:   rm -rf <data dir>/cas <data dir>/gc
#   Windows: Remove-Item -Recurse "<data dir>\cas", "<data dir>\gc"
J=$(uv run compute run ~/mf-lab/reader --node <L4-ID>)     # prints the job id
uv run compute logs $J -f
uv run compute jobs $J
```
**Expected:** most bytes `from <L2-ID>`, few `from controller`, job succeeded with the same
`dataset sha256` line as part F.

## H. Criterion 3 — kill the fetching agent and resume

Clear L3's cache as in G (stop agent, delete `cas` and `gc`, start it). Then:
```bash
J=$(uv run compute run ~/mf-lab/reader --node <L3-ID>)
```
Watch L3's agent window; ~20 s after `agent.execution.status ... staging` appears, **Ctrl-C the
agent**, wait 5 s, start it again (B2). The job fails `node_lost` (job-level retries arrive in
V0.6) — submit it once more to the same node:
```bash
J2=$(uv run compute run ~/mf-lab/reader --node <L3-ID>)
uv run compute logs $J2 -f
uv run compute jobs $J2
```
**Expected:** the `cache` line shows `resumed_chunks=` **> 0** (the 8 MiB chunks verified before the
kill) and the sources' MiB together are **less than 5 GB** by about resumed_chunks × 8 MiB.

## I. GC under quota pressure (0.5.9)

On L3 set a small quota in its `config.toml` and restart its agent:
```toml
[agent.gc]
cas_bytes = 2_000_000_000     # 2 GB, below the 5 GB dataset
min_age_s = 0
interval_s = 60
```
1. Pin version 2: `uv run compute data pin ds5g@2`.
2. Within a minute L3's log shows `agent.gc.pass` with `evicted` > 0 and `over_quota` naming
   `blob` only if what is left is pinned or in use. `uv run compute nodes <L3-ID>` cache counts
   drop accordingly.
3. Run the reader on L3 again (`-f`): it must **succeed** (it fetches what GC evicted) and, while
   it runs, `agent.gc.pass` lines must not evict anything of `ds5g@1` (in use).
4. Unpin: `uv run compute data pin ds5g@2 --off`; restore `cas_bytes` and restart the agent.

built by the venv/subprocess runtime. Exit code (`echo $?`): 0 when nothing failed, 1 otherwise.

## K. If something looks wrong

- No `from <peer>` line in G: `uv run compute nodes <L2-ID>` must show `peer_endpoint` and a
  `cache` `tree` count ≥ 1; the controller lists a peer only once its cache index is live (after
  its post-Hello snapshot) - wait 10 s after an agent restart.
- A peer dropped: the agent log `agent.cas.source_dropped` says why (`unauthorized`, `timeout`,
  `integrity_error`, too slow).
