# V0.14 lab — the planner on real laptops (roadmap 0.14.8, criteria 1–4)

This checklist runs V0.14's success criteria on the **4 lab laptops**: the chain
`tests/cluster/test_v014_planner_e2e.py` runs on one machine (G6: benchmark campaigns → calibration → evaluator
report → `compute explain`), now on real, different hardware and a real network. On one machine the timings are
noise, so the harness only proves the code path; **only this lab can PASS the criteria.**
Words used: **L1** = the controller laptop (Linux, also runs an agent), **L2–L4** = the Windows laptops (agents
native or in WSL2, as set up in V0.4–V0.10). `<L1>`…`<L4>` = each laptop's node id from `compute nodes`.

**Shell.** Every command runs on **L1** in a **Linux bash shell** (L1's own terminal, or WSL2 Ubuntu if L1 is
ever a Windows laptop) with the usual CLI setup (`MESHFORGE_CLI__CONTROLLER_URL`, `compute login` as the
**admin** — calibration and evaluation are admin commands). Not PowerShell / cmd. The dashboard steps use a
browser on any laptop, signed in as the admin.

| Criterion (roadmap V0.14, brief §5) | Part | Pass when |
|---|---|---|
| **C1** calibrated `cost_model` within **15 %** of the oracle's measured median in **≥ 80 %** of labelled groups, on held-out families | B | the report's `criterion 1: PASS` (not `too_few_groups`, not `leaked`) |
| **C2** calibrated `cost_model` mean regret lower than every rule policy, paired CIs do not overlap 0 | B | `criterion 2: PASS` (`not_separable` / `FAIL` / `too_few_groups` = not met) |
| **C3** decision latency p99 **< 100 ms** with 4 laptops | C | `criterion 3: PASS` from the report's stored decision times |
| **C4** every decision explainable in the UI and `compute explain` with identical fields | D | the three jobs' `explain --json` == the API, and the Plan tab shows the same values |
| **0.14.8** the planner on 2 workloads it has never seen | E | part E's table filled; C1/C2 verdicts of the held-out unseen families |

Every step ends with **PASTE BACK:** — copy it into `lab/reports/<date>-V0.14-planner.md` (from
`lab/reports/TEMPLATE.md`). Write **PASS / FAIL / NOT MET** next to each criterion with the line that decides
it. A step that could not be run is written down as such — never as a pass. The Markdown reports (`--md`) are
files: attach them to the report folder (`lab/reports/raw/`).

## A. Data and calibration

- [ ] **A0 — the criterion-size campaign.** Criteria 1 and 2 need **≥ 10 counted groups** per evaluation (fewer =
  `too_few_groups`, never PASS), and the earlier campaigns have 5 groups (0.9.10) and 1 group (0.10.10). This
  campaign gives 10 groups for each of three families, with replays and decision times. On L1 write `v014.yaml`:

  ```yaml
  name: lab-v014-planner
  seed: 1408
  families:
    - family: cpu.primes
      params: {limit: [100000000, 105000000, 110000000, 115000000, 120000000, 125000000, 130000000, 135000000, 140000000, 145000000], repeats: 4}
    - family: cpu.zlib
      params: {size_mb: [64, 72, 80, 88, 96, 104, 112, 120, 128, 136], level: 6, repeats: 2}
    - family: split.image_classify
      params: {images: [2000, 2500, 3000, 3500, 4000, 4500, 5000, 5500, 6000, 6500]}
  strategies: [local, mode1, mode3]
  nodes: all
  origin: <L1>
  repetitions: 3
  session_label: wifi
  budget: {max_runs: 500, max_hours: 10}
  ```

  ```bash
  compute bench plan v014.yaml        # 390 runs: 30 groups; local + 3 x mode1 (+ mode3 for split.image_classify)
  compute bench create v014.yaml      # prints camp_... = <CAMP_A>

  compute bench status <CAMP_A>       # repeat until done (complete)
  compute bench report <CAMP_A>
  compute bench labels <CAMP_A>
  ```

  Expected: `plan` says 390 runs (`cpu.primes` / `cpu.zlib`: 10 groups × 4 configurations; `split.image_classify`:
  10 × 5) and an estimate of a few hours; at the end `done (complete)`; `labels` shows mostly `best` / `tie`.
  Keep all 4 laptops online for the whole run (criterion 3 reads these decisions).
  **PASTE BACK:** the `plan` summary, the campaign id, the final `status`, the `report` summary block and the
  `labels` output.

## B. Criteria 1 and 2 — evaluation on held-out families

The evaluator re-plans each run's stored decision under every policy and compares the pick with the best
measured configuration. Its calibrated rows use a **leave-one-family-out refit** (never the live version), so a
family's verdict is never measured on its own training data. Never use `--allow-leak` here (it stamps every
verdict `leaked`).

- [ ] **B1 — all families at once** (each with its own held-out calibration):

  ```bash
  compute planner eval --campaign <CAMP_A> --md lab-eval-all.md
  ```

  Add `--campaign <CAMP_0910> --campaign <CAMP_01010>` if 0.3 showed they have replays.
- [ ] **B2 — one family at a time:**

  ```bash
  for f in cpu.primes cpu.zlib split.image_classify; do
    compute planner eval --campaign <CAMP_A> --holdout "$f" --md "lab-eval-$f.md"
  done
  compute planner reports
  ```

  Expected: every report `leaked: no`; verdict lines `criterion 1: …`, `criterion 2: …` (with one `vs <policy>`
  line per rule policy), `criterion 3: …`; `decision latency: …` lines. **C1 PASS** = B1's `criterion 1: PASS`
  (and no family in B2 below 80 % without an explanation in the report). **C2 PASS** = B1's `criterion 2: PASS`.
  A `too_few_groups` verdict is **NOT MET**, never a pass.
  **PASTE BACK:** the printed verdict lines of B1 and of each B2 run, the `planner reports` table; attach the four
  `.md` files.
