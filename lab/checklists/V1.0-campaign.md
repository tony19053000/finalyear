# V1.0 lab campaign — one combined checklist (days L0–L5, brief §4)

This is the **one** 🧑 lab campaign of V1.0 (`docs/briefs/V1.0-release.md` §4, D406–D421). It folds every open
lab step of V0.2–V0.17 into six lab days run on the **release-candidate packages** (`v1.0.0-rc.N`), and it is
the only way the `lab` rows of `release/acceptance.yaml` can turn PASS. The older checklists are **reused, not
copied**: each day says which of their sections to run and what changes. Read a section in its own file when
the step says so.

| Day | What | Time | Main output |
|---|---|---|---|
| **L0** | hardware + network inventory, spikes S1/S2/S3/S6/S7; quiet-machine perf checks on laptop L1 | ½ day + 1 evening | inventory JSON × 4, S1 matrices, perf results |
| **L1** | fresh install of `rc.N`, upgrade `rc.N-1 → rc.N`, rollback, uninstall/verify, timed Windows install | 1 day | install timings, verifier outputs, screenshots |
| **L2** | functional acceptance on the installed build (fabric, Mode 1, data, security, dashboard, Mode 3) | ½ day (long) | analyzer JSONs + reports |
| **L3** | 72 h soak + chaos | 3 days + 2 h setup | soak verdict |
| **L4** | evaluation: data night, analysis day, policy-matrix night, ablation morning | 2 nights + 1 day + 1 morning | raw campaign data, evaluator + ML reports |
| **L5** | demo rehearsal × 2, fallback recordings | ½ day | recordings, timings |

**Names used here.** *Days* are always written **Day L0 … Day L5**. *Laptops* are **L1 … L4** exactly as in
every older checklist: **L1** = the controller laptop (native Linux, controller `.deb` + its own agent);
**L2** = the second Linux laptop (agent `.deb`; if the team has only one Linux laptop, L2 is a Windows laptop
and uses the Windows lines below and `"os": "windows"` in the soak's `targets.json`); **L3, L4** = the Windows
laptops (installer). `<L1>` … `<L4>` = each laptop's node id from `compute nodes`.

**Shells.** Commands shown in `bash` run in a Linux terminal (L1, L2). Commands shown in `powershell` run in a
native Windows PowerShell (never WSL) — "Administrator PowerShell" when the step says so.

## 0. Rules for the whole campaign (read once)

### 0.1 Which build — the release candidate (D406)

- The campaign runs on **`v1.0.0-rc.N`** from the release CI (agent `.deb`, controller `.deb`,
  `MeshForge-Agent-Setup-1.0.0-rc.N-1.exe`, `SHA256SUMS`). A developer checkout is **not** evidence (D406).
- Write down, before Day L0, and paste into every day's report:
  ```bash
  RC=1.0.0-rc.N                       # the package version, exactly as the packages print it
  RC_SHA=<the 40-character commit SHA the rc was built from (release page, or `meshforge-agent --version`)>
  ```
- Every laptop also has a **repository checkout at `$RC_SHA`** for the lab tools (`lab/*.py`, `scripts/*`):
  `git fetch && git checkout $RC_SHA && uv sync` (L1: `uv sync --all-extras --group evaluation`). The lab
  tools come from the checkout; **the product under test is always the installed package** (`compute`,
  `meshforge-agent`, `meshforge-controller` from `/usr/bin` or the Windows install).
- Check the installed version on every laptop at the start of each day:
  - Linux: `meshforge-agent --version` (and on L1 `meshforge-controller --version`) → `$RC` and `$RC_SHA`;
  - Windows (Administrator PowerShell): `meshforge-agent --version` and
    `type "C:\Program Files\MeshForge\current.txt"` → `$RC-1`.

### 0.2 Where pastes go

- Raw output of a day goes to **`lab/reports/raw/<date>-V1.0-<day>-<topic>/`** (for example
  `lab/reports/raw/2026-11-02-V1.0-L0-inventory/`), one folder per topic; the hand-written report of a day goes
  to `lab/reports/<date>-V1.0-<day>.md` (copy `lab/reports/TEMPLATE.md`). The soak keeps its own names
  (`lab/reports/raw/<date>-V1.0-soak/`, `V1.0-soak.md` part E).
- Never paste passwords, tokens, private keys or Wi-Fi keys (docs/LAB.md §6). Private IPs and MACs are fine.
- A step that could not be run is written down as **NOT RUN** with the reason — never as a pass. Whatever a
  tool prints is the result: do not repeat a step until it passes.

### 0.3 How a step becomes a manifest PASS — `record-lab`

Lab evidence reaches `scripts/release_check.py` only through an **evidence file** (schema
`meshforge.acceptance-evidence/1`). After each step that decides a `lab` row, on L1 in the checkout:

```bash
uv run python scripts/release_check.py record-lab <ROW-ID> --verdict PASS \
    --package-version "$RC" --sha "$RC_SHA" \
    --evidence <the files of the step> --detail "<the deciding numbers, one line>"
```

It writes `lab/reports/raw/acceptance/<time>-V1.0-<ROW-ID>-PASS.json`; commit it with the step's raw files.
`--verdict PASS` only when the deciding line of the step says PASS. Anything else — FAIL, NOT MET,
`not_separable`, `too_few_groups`, INCONCLUSIVE — is recorded as `--verdict FAIL` with that line in `--detail`;
the Lead decides at G6 what it means for the release (a `not_separable` ML result is an honest, accepted
outcome per the brief §0, but `release_check.py` counts it as FAIL until the Lead records a decision).
`--evidence` files must exist and be committed. The `--sha` must be known to the checkout's git.

At any time, `uv run python scripts/release_check.py --only lab --sha "$RC_SHA" --package-version "$RC"` prints
which lab rows are PASS / MISSING / FAIL.

### 0.4 A fix during the campaign → `rc.N+1`, and what to redo (D406 / `affected_by`)

1. A code fix is never hot-patched on a laptop. The agents fix it on `main`, the release CI builds
   **`rc.N+1`**, and the team installs it **by the upgrade path** (L1/L2 `sudo apt install ./<new>.deb`;
   Windows: run the new installer). Paste the upgrade output: it is extra evidence for `V0.17-c3`.
2. Set `RC`/`RC_SHA` to the new build, check out the new SHA everywhere, then run
   ```bash
   uv run python scripts/release_check.py --only lab --sha "$RC_SHA" --package-version "$RC"
   ```
   Every lab row whose evidence was recorded at the old SHA **and** whose `affected_by` globs match a changed
   file shows `MISSING ... stale (...): changed since: <files>`. **Redo exactly those rows' steps** (the table
   in §9 says which step makes each row). Rows not listed stay valid. A change to `pyproject.toml` or
   `uv.lock` stales every row backed by `src/` (`GLOBAL_AFFECTED`).
3. Evidence that is not a manifest row follows its own rule:
   - **Soak (Day L3):** a D410 FAIL caused by our bug restarts the 72 h soak on the fixed build; an outside
     event (power cut, Windows update) is attributed in `notes.json` and the run continues if < 1 h was lost,
     else restarts (brief §4).
   - **Evaluation (Day L4):** each evaluation campaign must come from **one build** (the report marks mixed
     builds "not evidence"). If the rc changes while an L4 campaign is open, and
     `git diff --name-only <old> <new>` touches `src/meshforge/controller/planner/`, `controller/ml/`,
     `controller/planner_eval/`, `controller/calibration_store.py`, `controller/jobs/`, `controller/split/`,
     `bench/`, `agent/execution/` or `scripts/eval/`, start that campaign again under a **new name and a new
     raw folder**. Otherwise finish it and write the rc change into the day's report.
   - **Quiet-machine perf (Day L0 part Q):** redo when the change touches the measured paths (benchmark
     kernels, agent session/heartbeat, controller event stream, planner; docs/LAB.md D422).
