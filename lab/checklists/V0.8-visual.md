# V0.8 lab run — dashboard visual review + real 4-laptop fabric in the browser (roadmap 0.8.10)

This is the procedure the team runs **without an agent present**. It produces the evidence for V0.8
success criterion 4 (team visual review, brief §24) and the parts of criteria 1–3 that only real
machines can show: other browsers, Windows, a real LAN, a projector.

| Part | What it proves | Who / where |
|---|---|---|
| A | Everyone runs the same build | all 4 laptops |
| B | Brief §24 visual rules and the "avoid" list — page by page | the whole team, one shared screen |
| C | Every Mode 1 operation works in **Firefox** (D179: Chromium is automated, Firefox is this review) | L1 |
| D | The dashboard works from a **Windows** browser (Edge or Chrome) | L2 |
| E | A real 4-laptop fabric in the browser: live nodes, submit → run → logs → outputs; performance on real hardware | L1 + L2–L4 |
| F | Light and dark theme on a **projector** | evaluation room |
| G | `compute --install-completion` in **Windows PowerShell** (D187) | L2 |
| H | Controller restarted **on a different port** (D191) | L1 + any browser |

Plan about **2½ hours**. Words used below: **L1** = the controller laptop (Linux), **L2–L4** = the
Windows laptops; **`<L1-IP>`** = L1's LAN address (e.g. `192.168.1.20`); the dashboard address is
**`https://<L1-IP>:47110/`**.

Every step ends with **PASTE BACK:** — exactly what to copy into the report
`lab/reports/<date>-V0.8-visual.md` (create it from the template at the end of this file).
Screenshots go into `lab/reports/raw/<date>-V0.8-visual/` with the file name given.

## C. Firefox (L1, ~20 min)

The automated e2e suite runs Chromium only (its certificate pinning is a Chromium switch). Here a
person runs the core flows in Firefox (CA imported as in A4: Settings → Privacy & Security →
Certificates → View Certificates → Authorities → Import `ca.crt`, tick "trust this CA to identify
websites").

- [ ] **C1** Open `https://<L1-IP>:47110/` — no certificate warning; the sign-in page shows.
- [ ] **C2** Keyboard only (Tab / Shift+Tab / Enter / Space, no mouse): sign in as `alice`; you can
      see where the focus is at every step.
- [ ] **C3** Jobs → Submit a job: pick a small project folder (any folder with a `main.py` that
      prints a few lines and writes a file under `results/`, plus a `compute.yaml` with
      `entrypoint: python main.py` and `outputs: [results/]`), **Upload and submit** → the job page opens, the log
      streams live, the job ends `succeeded`.
- [ ] **C4** Outputs tab → **Download outputs**; Plan tab shows the decision table; Attempts tab
      shows one attempt with its node.
- [ ] **C5** Submit a long job (`for i in range(600): print(i); time.sleep(0.1)`), keyboard only:
      Tab to **Cancel job**, Enter, Tab to the dialog's **Cancel job**, Enter → state `cancelled`.
- [ ] **C6** Open the browser console (F12 → Console) and repeat C3 once: **no red errors**.
- [ ] **C7** Sign out (keyboard only) → "You are signed out."

**PASTE BACK:** Firefox version (Help → About), each of C1–C7 pass/fail, the job ids of C3 and C5,

## E. Real 4-laptop fabric (L1 + L2–L4, ~30 min)

- [ ] **E1** Nodes page: each laptop's row matches `docs/LAB.md` (OS, CPU, RAM, GPU). Unplug L3's
      cable (or stop its agent): within **~10 s** the row shows offline, without reloading the page;
      plug it back → online again.
- [ ] **E2** Node detail of L2: the CPU sparkline moves while you start a heavy program on L2
      (e.g. a video or a build); the "latest sample" time keeps updating, a new time every ~2 s.
      That time is **L2's own clock** (when L2 measured), so do not compare it with L1's clock —
      laptops on Wi-Fi are often seconds apart. The real lag is measured skew-safe in E3.
- [ ] **E3** Performance on real hardware (criterion 2). On L1, in the repository folder, with the fabric idle, run (it seeds
      **400 real jobs** — 100 per laptop — then **10 000** cancelled jobs into this fabric's database;
      run it on a lab database, not on one you want to keep clean):
      ```bash
      uv run playwright install chromium
      export MF_PASSWORD='<admin password>'   # the browser signs in with it
      export MF_TOKEN='<admin API token>'      # seeding goes through the API with it
      uv run python scripts/ui_perf --controller https://<L1-IP>:47110 \
          --ca ~/.meshforge/identity/ca.crt --user admin --history 100 --bulk 10000 \
          --out lab/reports/raw/<date>-V0.8-visual/ui-perf.json
      ```
      Get the admin API token from the dashboard: Settings → Tokens → **Create API token**, copy the
      value shown once (revoke it there after the run). `--ca` is the fabric `ca.crt` (A4). The script prints a Markdown table and
      `THRESHOLD BROKEN: ...` for any limit it misses, then `VERDICT: pass|fail|skew_uncertain`.
      **Skew-safe (V0.9 G0):** live updates are timed from when an event *reached the controller*
      (L1's clock), never from a laptop's own sample time, so L2–L4's clocks do not matter. The
      browser's offset to L1 is measured by pings at the start and printed as
      `clock (<phase>): {"clock_offset_ms": ..., "clock_offset_bound_ms": ..., ...}` (also in
      `ui-perf.json` under `phases.<phase>.events.clock`). Exit code **0** = all limits met,
      **1** = a limit broken, **3** = `skew_uncertain`: the offset could not be pinned within
      ±50 ms, so the live numbers are neither pass nor fail — re-run on L1 itself (the command
      above already runs the browser on L1; a bound over 50 ms there means L1 is overloaded) or
      with L1 on Ethernet.
- [ ] **E4** Invite → join: Settings → Invites → Create invite; on a **fifth** machine (or after
      `meshforge-agent identity` reset on L4, see `meshforge-agent identity --help`) join with the code
      shown (`meshforge-agent join`, the command the Invites page prints), or by
      scanning the QR with a phone and typing the decoded text. The node appears in Nodes.

**PASTE BACK:** E1 seconds to offline / online, E2 pass/fail, the **full E3 output** (table +
machine JSON + the `clock (...)` lines + `VERDICT` + exit code) and `ui-perf.json`, E4 pass/fail +
the new node id.

## G. Windows PowerShell completion (L2, D187, ~5 min)

In **Windows PowerShell** (not WSL, not Git Bash):

```powershell
compute --install-completion
# close and reopen PowerShell
compute jo<Tab>           # completes to: compute jobs
compute node <Tab>        # cycles: gc, prepare, revoke
compute --install-completion   # a second time
Select-String -Path $PROFILE -Pattern "Register-ArgumentCompleter" | Measure-Object
Get-ExecutionPolicy -List
```

Expected: the completions work; the profile holds the block **once** (count = 1) after the second
install; the execution policy is **unchanged** from before (compute never changes it — if scripts are
disabled, `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` is your own choice, docs/CLI.md §6).

**PASTE BACK:** the output of the last two commands, and "completion worked: yes/no".

## H. Controller restart on a different port (L1, D191, ~10 min)

1. Open the dashboard in a browser on L2, signed in, on the Jobs page. Keep the tab open.
2. On L1 stop the controller (Ctrl+C) and start it again on port **47120**:
   ```bash
   MESHFORGE_CONTROLLER__HTTP_BIND=<L1-IP>:47120 meshforge-controller   # plus your usual options
   ```
3. The **old tab** (port 47110) must show that the controller is unreachable (connection status in
   the header) — not a blank page, not a crash; it cannot follow to the new port (a different
   address is a different site to the browser).
4. Open `https://<L1-IP>:47120/` in a new tab: the sign-in page shows (the session cookie belongs to
   the old address); sign in; Jobs shows the same jobs as before.
5. Restart the controller on **47110** again: the old tab reconnects by itself within ~10 s (header
   status back to live) with no reload.

**PASTE BACK:** for steps 3, 4, 5: what the page showed (one line each) + screenshots `H3.png`,
`H5.png`. Note: agents dial the gRPC port (47100), which does not change here.
