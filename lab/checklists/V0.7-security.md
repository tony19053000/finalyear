# V0.7 security lab check (🧑 0.7.12) - items carried by the agents (tester)

This file collects the real-machine checks that the V0.7 agent groups could not run (no Windows, no
Docker Desktop, no GPU in CI). G7 extends it with the full pairing / revocation / Wireshark run;
the G3 and G4 checklists (`V0.7-G3-mtls-revocation.md`, `V0.7-G4-users-rotation.md`) stay valid.

Needs: controller laptop **L1** (Linux), a Linux agent **L2**, a Windows agent **L3** with Docker
Desktop, all enrolled, V0.7 G6 code pulled everywhere. Paste back the lines marked **PASTE**.

## W. Windows owner caps (G5, D161 - job object)
1. On L3 set `[agent.policy] allow_unsandboxed = true`, `max_ram_bytes = 536870912`,
   `max_cpu_percent = 25`; restart the agent.
2. `compute run lab/workloads/<a job that allocates 1 GiB> --node <L3 id>`. **PASTE** the final
   state line. Expected: `failed oom` (or `MemoryError` in its log), never `succeeded`.
3. A busy-loop job on L3 for 60 s: watch Task Manager. **PASTE** the CPU % you saw. Expected: about
   25 % of the machine (the hard CPU-rate cap).
4. `compute nodes` on L1. **PASTE** L3's row. Expected `NOT ENFORCED` shows `vram` (and `ram` only on
   a GPU laptop), never `cpu`.

## D. Docker Desktop on Windows (G5 allow-list, `cgroupns=private`)
1. Stop the subprocess runtime on L3 (`allow_unsandboxed = false`), restart; run a normal job with
   `--node <L3 id>`. **PASTE** its final state. Expected `succeeded`. If it fails
   `config_error sandbox_violation: ...`, **PASTE** the agent log line
   `agent.execution.sandbox_violation` (field `what`) - that is a Docker Desktop difference to fix.
2. `docker info` on L3: **PASTE** the `Security Options` and `Cgroup Version` lines.

## L. Linux CPU share via the systemd unit (G6, D161)
1. On L2 copy the updated `deploy/systemd/meshforge-agent.service` (it now has `Delegate=yes` +
   `DelegateSubgroup=agent`), `systemctl --user daemon-reload && systemctl --user restart
   meshforge-agent`, `systemctl --version | head -1`.
2. `journalctl --user -u meshforge-agent | grep cpu_cgroup`. **PASTE**. Expected
   `agent.execution.cpu_cgroup_ready` (systemd >= 254) or `cpu_cgroup_unavailable` with a reason.
3. With `max_cpu_percent = 25` and `allow_unsandboxed = true`, a busy-loop job on L2 (no Docker or
   `runtime: subprocess`): `top` shows about 25 % of all threads for its python. **PASTE** the `top` line.
4. `compute nodes`: L2's `NOT ENFORCED` must not contain `cpu` when step 2 said ready.

## E. Environment builds are wheels-only (G6, WS-I4)
1. A job whose `requirements.txt` names an sdist-only package (e.g. an old pure-sdist project).
   **PASTE** the failure. Expected `env_error` with "installs are wheels-only ... only_binary = false".
2. Set `[agent.envs] only_binary = false` on that laptop, restart, re-run. Expected `succeeded`.

## S. Job secrets (G6, D144) - G7 folds this into its full capture run
1. On L2 as alice: `printf 'MF-LAB-SECRET-%s' "$RANDOM$RANDOM" | tee /tmp/val | compute secret set LAB_KEY`;
   `compute secret list`. **PASTE** the list (names only, no value).
2. Start `tcpdump -i any -w g6.pcap 'tcp port 47100 or tcp port 47110 or tcp port 47120'` on L1.
3. A job on **L3 (Windows)** with `secrets: [LAB_KEY, {name: LAB_KEY2, as_env: true}]` (set LAB_KEY2
   too) that prints the SHA-256 of its secret file and then prints the value itself. **PASTE**
   `compute logs <job>`: expected the SHA-256 of `/tmp/val` and `[secret:LAB_KEY]` where the value was.
4. Stop tcpdump; `strings g6.pcap | grep -c MF-LAB-SECRET`. **PASTE**. Expected `0`.
5. On L3 while a `sleep 60` job with the secret runs: look in `%LOCALAPPDATA%\MeshForge\...\secrets`
   (data dir) - a folder exists; after the job ends it is gone. **PASTE** `dir` before/after.
