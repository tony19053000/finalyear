# Spike S6 — execution environments per laptop (task 0.2.10)

**Question:** on this laptop, is **Docker** usable for running workloads, does a container
actually get the **GPU**, and what does an execution environment **cost** — starting a
container, pulling an image, bringing a PyTorch-CUDA container up to its first CUDA
operation, and building a `uv` venv with a cold and with a warm cache?

That is ARCHITECTURE §27 **Q4** ("Docker Desktop GPU reliability on team Windows laptops")
and the premise of **ADR-0004** ("Docker first, uv venv fallback"). The numbers are the
calibration input for **V0.4.7** (runtime interface + Docker runtime with CPU/RAM/pids
limits, non-root, workdir-only mount), **V0.4.8** (GPU pass-through via the NVIDIA
Container Toolkit / Docker Desktop) and **V0.5 success criterion 5** ("warm env cache: job
start overhead ≤ 3 s *(calibrate)*; cold build time recorded").

Script: `lab/spikes/s6_environments.py` · code: `lab/spikes/_s6/` · results:
`lab/reports/raw/<date>-S6-environments/<host>.json` · report:
`lab/reports/<date>-S6-environments.md`.

Standard library plus the `docker` and `uv` **command lines** only — no docker SDK, no
psutil, and **no torch on the host**: torch runs *inside* the container, which is the whole
point of the `docker-gpu-torch` case.

## 1. What is measured

### 1.0 `docker-facts` — collected before any case, stored in `extra.docker`

Not a timed case (it has no repetitions and no row in the results table); it is the
`docker version --format '{{json .}}'` + `docker info --format '{{json .}}'` block that
makes every other Docker verdict explainable, and it is rendered as the **Docker facts**
table of the report: client/server version, daemon OS (and, for Docker Desktop, whether
the **WSL2 backend** is in use), kernel, registered runtimes (and whether an `nvidia`
runtime key is present), cgroup version, storage driver, whether the *tool itself* ran
inside WSL, and the host GPUs from `nvidia-smi -L`.

When Docker cannot be reached at all, this block carries the typed reason
(`docker_cli_missing`, `docker_daemon_unreachable`, `docker_permission_denied`) with a fix
hint, and the run continues with the venv cases instead of dying.

### 1.1 The seven timed cases

| Case id | What it does | Metrics (unit) | The question it answers |
|---|---|---|---|
| `docker-start` | `docker run --rm` of `python:3.12-slim` in the full ADR-0004 sandbox shape, running `python -c print('ok')` | `start_to_exit_ms` (ms), `exit_code` | Is Docker usable **with the limits V0.4.7 wants**, and what does a warm container start cost per job? |
| `docker-pull-cold` | `docker rmi python:3.12-slim`, then `docker pull`, once per repetition | `pull_s` (s), `bytes_on_disk` (B), `digest` | What does a **cold** image cost (the planner's "env not cached on that node" penalty)? |
| `docker-gpu-smi` | `docker run --gpus all nvidia/cuda:12.6.3-base-ubuntu24.04 nvidia-smi --query-gpu=name,driver_version,memory.total` | `start_to_exit_ms` (ms) | **Q4, part 1:** does a container see the GPU at all on this machine? The GPU name/driver/VRAM it printed are kept in `attrs.gpu`. |
| `docker-gpu-torch` | `pytorch/pytorch:2.8.0-cuda12.6-cudnn9-runtime` with `--gpus all`: import torch, `torch.cuda.is_available()`, a 1024×1024 fp32 matmul, `torch.cuda.synchronize()` | `start_to_ready_ms`, `total_ms` (ms), `import_s`, `first_cuda_op_s` (s) | **Q4, part 2 and the V0.4.8/V0.5 number:** how long from `docker run` to a *usable* CUDA context? |
| `venv-cold` | `uv venv --python 3.12` + `uv pip install -r` (numpy, grpcio, pydantic — pinned) with a **fresh empty cache per repetition** | `create_s`, `install_s`, `total_s` (s), `site_packages_bytes`, `cache_bytes` (B) | ADR-0004 fallback: what does building an environment from nothing cost? |
| `venv-warm` | the same, `--offline`, from a cache warmed **once** in setup | same as `venv-cold` | V0.5 criterion 5: what does a **warm** env cache really save? |
| `venv-start` | the warm venv's interpreter running `import numpy; import grpc; print('ok')` | `start_to_exit_ms` (ms) | The venv equivalent of `docker-start`: per-job process start overhead. |

**The sandbox shape** used by `docker-start` is exactly the ADR-0004 / V0.4.7 wish list, so
a daemon that refuses any of it is caught here and not in V0.4:
`--network none --cpus 1 --memory 512m --pids-limit 64 --user 65534:65534 --read-only
--tmpfs /tmp`. A refusal is classified as `sandbox_flag_refused` and names the flag.
The GPU cases deliberately do **not** use the sandbox flags (a GPU container needs devices
and a writable filesystem); they use `--rm --gpus all` and a generated `s6-…` container
name so cleanup can find them.

**`start_to_ready_ms` is defined**, not guessed: the script inside the container prints
`ready_wall_s = time.time()` *after* `import torch` and the first CUDA op; the host
subtracts the wall-clock time at which it launched `docker run`. If the two clocks
disagree (result outside `0 … total_ms`), the sample is `null` and `clock_suspect: true` —
never a made-up number. `total_ms` (pure host-side wall clock around `docker run`) is
always recorded, so there is a trustworthy upper bound even then.

**Repetitions:** `--warmup 1` + `--reps 5` per case by default (`MIN_VALID_REPS = 5`), with
`--pause 0.2` between repetitions. Warmup samples are stored in the JSON but never enter a
summary. Fewer than 5 measured repetitions makes every row of that case `INVALID (n<5)`,
and the tool says so on stderr before it starts.

**Typed failures, never silence.** Everything that can go wrong has a `failure_type` and a
`fix`: `docker_cli_missing`, `docker_daemon_unreachable`, `docker_permission_denied`,
`no_nvidia_runtime`, `nvidia_driver_error`, `sandbox_flag_refused`, `image_pull_failed`,
`image_remove_failed`, `insufficient_disk`, `container_failed`, `timeout`,
`cuda_unavailable_in_container`, `no_gpu_on_host`, `uv_cli_missing`, `python_not_found`,
`network_error`, `uv_failed`, `venv_unavailable`, `process_failed`, `budget_exhausted`,
`container_leak`, and `skipped_by_flag` for an operator skip. A case skipped by a flag is
listed in `extra.skipped` and does **not** make the run incomplete; anything else does
(exit code 3).

**Honesty fields in every result** (`extra`): `facts` (OS, WSL status, CPU count, RAM, `uv`
version, host GPUs, free disk at the temp dir and at the Docker root), `docker` (the facts
block above), `images` (digest + size of every image used), `pinned_requirements`,
`skipped`, `warnings`, `budget_remaining_s`, `metric_units`, `quick`, and
`gpu_torch_cold_pull_note` — the one-off PyTorch image pull is stored as
`cases["docker-gpu-torch"].attrs.cold_pull` with `note: "single informational measurement
(n=1), not a sample of any case"` and is **never** a row of the results table.

**Cleanup is in `finally`,** including on Ctrl-C: the run's temp directory is removed (with
a Windows read-only retry), every container whose name starts with `s6-` is force-removed,
and anything still there afterwards is reported as `container_leak`. `docker-pull-cold`
re-pulls the small image at the end so the machine is left as it was found.

## 2. How to run (🧑 one run per laptop)

**Preconditions on every laptop**

- `git pull`, then `uv sync` (no extras needed — S6 does not import torch on the host).
- Docker running: Linux → Docker Engine, and the current user in the `docker` group;
  Windows → **Docker Desktop started**, and (for the GPU cases) its **WSL2 backend**
  enabled. Docker's and NVIDIA's documentation require the WSL2 backend for `--gpus`;
  whether `--gpus all` then works on *these* laptops is exactly what this spike measures.
- `uv` on `PATH`, and a **Python 3.12** it can find without downloading
  (`UV_PYTHON_DOWNLOADS=never` is forced, so `uv python find 3.12` must succeed;
  otherwise the venv cases fail with `python_not_found` and the fix `uv python install 3.12`).
- Network (the pull and `venv-cold` cases download: a few hundred MB of small-image pulls —
  `python:3.12-slim` is removed and re-pulled once per repetition — plus ~100 MB of wheels
  per cold venv repetition, plus the PyTorch image below).
- **Disk:** the `docker-gpu-torch` image is ~3.7 GB compressed. The tool refuses to pull it
  unless **≈ 3 × compressed size (~11 GB) is free** at the Docker root — layers are
  downloaded and then extracted, and Docker holds both for a while. With less free space
  the case is recorded as `insufficient_disk` with the fix `docker system prune` /
  `docker builder prune`, or `--skip-gpu-torch`. Also keep a few hundred MB free in the
  system temp directory for the venv cases.
- Plugged in, nothing heavy running (a browser or an editor open will show up in the
  millisecond numbers — record it in the report's *Machines & conditions* row).

**Smoke run first, then the real run.** `--quick` is 2 repetitions and no PyTorch case: it
takes about a minute and proves the tool works here. **Its rows are `INVALID (n<5)` by
design and are not a measurement of the machine.**

```bash
# Linux (bash), native — Laptop 1
uv run python lab/spikes/s6_environments.py run --quick --name L1     # smoke test
uv run python lab/spikes/s6_environments.py run --name L1             # the real run
```

```powershell
# Windows (PowerShell), native — NOT inside WSL. Docker Desktop must be running.
uv run python lab\spikes\s6_environments.py run --quick --name L2     # smoke test
uv run python lab\spikes\s6_environments.py run --name L2             # the real run
```

Use `--name L2` / `L3` / `L4` per laptop (the real hostname is stored in the JSON either
way). Run S6 **alone** — not at the same time as S1/S3 traffic or S7 benchmarks.

**Before it downloads the PyTorch image** the real run prints, on stderr:

```
!! downloading pytorch/pytorch:2.8.0-cuda12.6-cudnn9-runtime (~3.7 GB compressed) once; Ctrl-C now to skip, or pass --skip-gpu-torch
```

Ctrl-C there is safe: the child is killed, the temp dir and any `s6-` container are cleaned
up, and the tool exits `130` **without** writing a result — so re-run with
`--skip-gpu-torch` if the download is not wanted. The image is pulled **once** (the five
repetitions then reuse it) and is **left on the machine** afterwards; remove it later with
`docker rmi pytorch/pytorch:2.8.0-cuda12.6-cudnn9-runtime` if the space is needed.

**Flags**

| Flag | Effect |
|---|---|
| `--name NAME` | label used in the report (default: hostname) |
| `--reps N` | measured repetitions per case (default 5, quick 2); below 5 ⇒ every row INVALID, and the tool warns |
| `--warmup N` | warmup repetitions, stored but not summarised (default 1) |
| `--quick` | smoke run: 2 repetitions, no `docker-gpu-torch`, 900 s budget; marked as a smoke test in the JSON and the report |
| `--skip-docker` | only the venv cases |
| `--skip-gpu` | skip both GPU container cases (laptop without an NVIDIA GPU, or a known-broken driver) |
| `--skip-gpu-torch` | skip only the PyTorch-CUDA case (no ~3.7 GB download) |
| `--no-network` | skip every case that downloads (`docker-pull-cold`, `venv-cold`, `venv-warm`, `venv-start`) |
| `--gpu-torch-image IMAGE` | a different PyTorch-CUDA image (e.g. a smaller or a newer tag) |
| `--timeout SECONDS` | wall-clock budget for the **whole** run (default 3600, quick 900); a case that no longer fits is recorded as `budget_exhausted`, never as a fake failure |
| `--pause SECONDS` | pause between repetitions (default 0.2) |
| `--out-dir DIR` | result folder (default `lab/reports/raw/<UTC date>-S6-environments`) |

**Exit codes:** `0` every non-skipped case complete · `1` cannot write the result (or the
folder already holds another host's file with the same name) · `2` usage error · `3`
result written but incomplete (a typed failure — see `errors` in the JSON; operator skips
do not count) · `130` Ctrl-C.

**What the human pastes back — both of these:**

1. the result JSON, `lab/reports/raw/<date>-S6-environments/<host>-<id>.json` (unedited;
   `git add` that folder and commit, or paste the file), **and**
2. the **full stderr** of the real run (it contains the progress lines, the pull warning,
   the verdict summary and any `!!` warning that the JSON alone does not spell out).

If the run exited `3`, paste it anyway — an honest failure with a `failure_type` is a
result. Do not hand-edit the JSON.

**Then build the comparison** (any machine, once the JSONs are in one folder):

```bash
uv run python lab/spikes/s6_environments.py report \
  --results lab/reports/raw/2026-09-20-S6-environments \
  --out lab/reports/2026-09-20-S6-environments.md \
  --labels L1=<host1>,L2=<host2>,L3=<host3>,L4=<host4>
```

`--results` is repeatable (several folders), `--date YYYY-MM-DD` overrides the date taken
from the folder name. A laptop named in `--labels` with no result file becomes a `TBD`
row — a missing laptop is visible instead of absent. Re-running `report` is safe and
idempotent; it never touches the raw JSONs.

### 3.2 The generated blocks

After the harness **Results** table (the raw evidence) the report adds:

1. **Environment verdicts per laptop** — columns `docker` · `gpu-in-container` ·
   `torch-cuda-in-container` · `runtime recommendation (ADR-0004)`.
2. **Environment costs per laptop** — one row per cost, one column per laptop, cells
   `mean ± stdev (n=k)`.
3. **Calibration for V0.5 criterion 5** — one line per laptop: warm venv start and warm
   container start in seconds, each marked `(within)` or `(EXCEEDS)` against the ≤ 3 s
   target, plus the PyTorch-CUDA start when it was measured.
4. **Docker facts** — the `docker-facts` table of §1.0.
5. **Diagnoses and fixes** — every non-`yes` verdict with its typed reason and fix.

### 3.3 What each verdict value means

| Value | Meaning |
|---|---|
| `usable` (docker) | `docker-start` ran **every** requested repetition cleanly, `n ≥ 5`, and `docker info` was ok |
| `yes` (GPU columns) | the case ran every requested repetition cleanly with `n ≥ 5` |
| `unusable` / `no — <failure_type>: <message> [fix: …]` | measured and failed; the typed reason and fix are shown |
| `flaky k/n` | `k` of `n` repetitions worked — never rounded up to `yes` |
| `INVALID (n<5)` | it worked, but with fewer than 5 measured repetitions (e.g. a `--quick` run): not a lab result |
| `INVALID (malformed)` | the result file's case entry is not a usable object (hand-edited or corrupt): reported, never `yes` |
| `skipped` | an operator flag skipped the case |
| `n/a` | the host has no NVIDIA GPU, so GPU-in-container is not applicable |
| `TBD` | nobody ran it — **or** it could not be measured for a reason that says nothing about the runtime (`insufficient_disk`, `image_pull_failed`, `timeout`, `budget_exhausted`): "not measured" is never rendered as "no" |
| `docker` / `venv-fallback` (recommendation) | `docker` only from `usable` **and** (`gpu-in-container: yes` **or** no NVIDIA GPU on the host); `venv-fallback` when Docker is unusable/flaky, or GPU-in-container is `no` on a GPU host; otherwise `TBD` with the reason. Never `docker` from an INVALID row. |

Only **measured** repetitions decide a cell; a failed *warmup* never demotes a clean case
(it is listed as a note instead). When one laptop has several result files, the newest by
`timestamp_utc` wins and every file is listed in the verdict's `sources`. All free text
(OS strings, error messages) is escaped before it enters a table cell.

### 3.4 Sanity ranges — orientation, not pass/fail

These are the magnitudes to expect; a number well outside them means "look again", not
"failed". Only the Linux numbers in §5 are measured so far.

- `docker-start` (warm, small image, sandboxed): tens to a few hundred **ms** on a Linux
  Engine. **Docker Desktop on Windows goes through a WSL2 VM and is expected to be
  slower — by how much is exactly one of the things this spike is for (TBD).**
- `venv-start` (interpreter + `import numpy, grpc`): ~0.1 s on Linux; Windows process start
  and imports from NTFS are typically slower (TBD).
- `venv-warm` total: well under 1 s when the cache really is warm. If it is close to
  `venv-cold`, the cache is not being hit — check `offline: true` in the case `attrs`.
- `venv-cold` total: a few seconds for these three wheels (~100 MB) on a decent link; it is
  dominated by the download, so it measures the network as much as the machine.
- `docker-pull-cold` (`python:3.12-slim`, ~43 MB on disk): seconds, network-dominated.
- `docker-gpu-smi`: a little slower than `docker-start` (bigger image, device setup).
- `docker-gpu-torch` `start_to_ready_ms`: **seconds** — importing torch and creating a CUDA
  context is far more expensive than starting an empty container. This is the number V0.5
  criterion 5 has to live with for GPU jobs, which is why it is measured separately from
  `docker-start`.
- `import_s` + `first_cuda_op_s` should be a large part of `start_to_ready_ms`; if
  `start_to_ready_ms` is `null` with `clock_suspect: true`, use `total_ms` and say so.

## 4. Known limits

- **One machine per run.** S6 measures *this* laptop. Nothing here crosses the network to
  another node; a `yes` on one laptop says nothing about another. Four laptops = four runs.
- **Background load is in the numbers.** These are millisecond-scale measurements of
  process and container start. A browser, an indexer, a VPN client or Windows Defender will
  move them. The report's *Machines & conditions* row must record what was running; the
  Laptop 1 numbers in §5 were taken with a developer desktop open and are therefore an
  upper bound, not a best case.
- **`--quick` rows are INVALID by design** (2 repetitions < 5) and the PyTorch case is
  skipped. A quick run proves the tool works here; it is never evidence about the machine,
  and both the JSON (`extra.quick`) and the report say so.
- **Disk pressure silently removes the most interesting case.** If less than ~3× the
  compressed image size is free, `docker-gpu-torch` becomes a typed `insufficient_disk`
  skip and `torch-cuda-in-container` stays `TBD` — which is exactly what happened on
  Laptop 1. Free the space and re-run to get that number.
- `docker-pull-cold` **removes and re-pulls** `python:3.12-slim` once per repetition
  (5 × ~43 MB by default) and re-pulls it at the end. On a metered or slow connection use
  `--no-network` (which skips it) and accept a `skipped` cell.
- The pull and cold-venv numbers are **network-bound**: they describe this laptop *on this
  link at this moment*, not a property of the machine. Re-running on a different Wi-Fi will
  give different numbers, and that is expected.
- `venv-cold` / `venv-warm` install a **fixed three-wheel set** (numpy, grpcio, pydantic —
  pinned to the project's lock where they overlap). A real job's environment will be
  bigger; treat these as a floor and scale by download size, not by a constant.
- The venv cases use a **private cache** in the run's temp directory and
  `UV_NO_CONFIG=1`, so the developer's own `~/.cache/uv` is neither read nor polluted.
  That means `venv-warm` measures a *freshly warmed* cache, not a long-lived one.
- The GPU cases do **not** use the sandbox flags, so a `yes` there is not evidence that a
  *sandboxed* GPU container works. V0.4.8 must re-check the combination.
- `docker-gpu-torch` uses one published PyTorch-CUDA image and one CUDA version. Another
  image, another CUDA/driver pair, or a different GPU can behave differently; the image
  digest is recorded in `extra.images` so a later re-run is comparable.
- `sandbox_flag_refused` is detected from the daemon's **error text**. A daemon that
  silently ignores a flag instead of refusing it would not be caught here.
- No TLS, no registry authentication, no proxy configuration is exercised. A corporate
  proxy in front of Docker Hub will show up as `image_pull_failed`, correctly typed but not
  diagnosed further.
- **Laptop 1's numbers are one machine, not the fleet** (see §5). Nothing in §5 is evidence
  about Windows, Docker Desktop, or the WSL2 backend.

## 6. What the result decides

- **ARCHITECTURE §27 Q4** is answered only when the Windows laptops have run: `docker` +
  `gpu-in-container: yes` there means Docker Desktop is a usable GPU runtime for the fabric;
  a `no` or a `flaky` means V0.4.8's GPU pass-through cannot rely on Docker on Windows, and
  the venv/GPU-service path (ADR-0004 fallback, ADR-0005) becomes the Windows GPU story.
- **ADR-0004 (Docker first, uv venv fallback)** gets its per-laptop evidence: the
  `runtime recommendation` column is literally the ADR's decision applied to each machine.
  Any laptop with `venv-fallback` must be recorded in the ADR's consequences and in
  `docs/LAB.md`, with its typed reason.
- **V0.4.7 (runtime interface + Docker runtime)**: `docker-start` proves (or disproves) that
  `--cpus/--memory/--pids-limit/--user/--read-only/--tmpfs/--network none` are all accepted
