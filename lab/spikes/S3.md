# Spike S3 — transport throughput (task 0.2.7)

**Question (ARCHITECTURE §27 Q2):** when a laptop hands bytes to another laptop, how
much of a plain TCP connection do we keep if those bytes travel over **gRPC byte
streams** (ADR-0005, tensors / GPU remoting) or over **HTTP with `Range`** (ADR-0003,
the content-addressed data plane), from **1 MiB to 2 GiB**? And what message (chunk)
size should the fabric use? The answer is a number per pair of laptops and per link,
not an opinion: raw TCP is the baseline, everything else is expressed as a percentage
of it, and the verdict sentences in the report are generated from the measured data.

Script: `lab/spikes/s3_transport.py` · code: `lab/spikes/_s3/` · results:
`lab/reports/raw/<date>-S3-transport/<client>__to-<server>_<link>.json` · report:
`lab/reports/<date>-S3-transport.md`.

Standard library plus `grpcio` (a core dependency), so the spike runs after a plain
`uv sync` on Linux, WSL and **native Windows**. If `grpcio` cannot be imported the run
does not crash: the server serves raw TCP + HTTP only, says why in its `hello`, and every
gRPC case becomes a typed, non-fatal `grpc_unavailable` failure.

## 1. What is measured

One `serve` process hosts **all three transports** on three consecutive ports
(`--port` raw TCP + control, `+1` gRPC, `+2` HTTP). That is deliberate: every transport
then sees the same CPU, the same NIC and the same interpreter, and the client can ask
for the server's view of *any* transfer over one control channel.

| Case id (per size) | What | Transport |
|---|---|---|
| `tcp-down-<size>` | server streams `size` bytes in `chunk`-sized writes; **baseline** | raw TCP |
| `tcp-up-<size>` | client streams to the server, which counts and verifies | raw TCP |
| `grpc-down-<size>` | server-streaming RPC, one `bytes` message per chunk | gRPC |
| `grpc-up-<size>` | client-streaming RPC (first message = JSON request, then chunks) | gRPC |
| `http-get-<size>` | `GET /blob?...`, HTTP/1.1 keep-alive | stdlib HTTP |
| `http-range<N>-<size>` | `N` **parallel** `Range` requests on `N` connections, joined | stdlib HTTP |
| `grpc-down-<sweepsize>-chunk<c>` | the same gRPC download at chunk `c` (sweep) | gRPC |

Default sizes `1MiB, 8MiB, 64MiB, 256MiB, 1GiB, 2GiB`; default chunk `1MiB`; default
sweep `64KiB, 256KiB, 1MiB, 4MiB` at `64MiB`; default `--range-parts 4`.

**Metrics per repetition** (same keys for every transport, so one table can hold them):

| Metric | Meaning |
|---|---|
| `recv_mbps`, `recv_mib_s` | throughput **at the receiver**: `bytes · 8 / wall_s / 1e6` and `bytes / wall_s / 2²⁰` |
| `wall_s`, `ttfb_s`, `stream_s` | the measured window, time to first byte, first-byte→last-byte |
| `client_cpu_s`, `server_cpu_s` | `time.process_time()` delta on each side during the window (all threads, so gRPC's C-core threads count) |
| `cpu_ms_per_mib` | `(client_cpu_s + server_cpu_s) · 1000 / MiB moved` — how much of the result is Python and framing rather than the link |
| `client_rss_peak_mib`, `server_rss_peak_mib` | process-wide **peak** RSS: evidence that nothing buffered the whole payload |
| `bytes`, `server_bytes` | receiver count and the sender's/receiver's own count, compared per sample |

**The measured window** is *request sent → last byte* for downloads and the server's own
*request seen → last byte* for uploads. Connection establishment is excluded for every
transport alike (socket, HTTP connections and gRPC channel are connected before the clock
starts); request latency is included, because otherwise a 1 MiB payload delivered in one
message would show an empty window and infinite speed. `stream_s` keeps the steady-state
rate as raw evidence but is never the headline number.

**Payload and correctness.** All three transports move the *same* deterministic payload:
one fixed 4 MiB pseudo-random block (`random.Random(20260919)`, reproducible across
CPython versions and operating systems) repeated, so the byte at absolute offset `i` is
`BLOCK[i % 4MiB]`. Both sides can generate and verify *any* byte range without holding
the payload in RAM (2 GiB is never materialised) and without sending a checksum over the
wire: the receiver rolls a CRC-32 and compares it with the CRC of the same range computed
locally. A transport that drops, duplicates or reorders bytes raises
`checksum_mismatch` instead of producing a fast number.

**Typed failures** (`_s3/protocol.py`, recorded per repetition and per case):
`server_unreachable`, `connection_lost`, `timeout` (these three are *fatal*: the case
aborts at once and `hello` is retried), `protocol_error`, `server_error`,
`transport_error`, `short_transfer`, `checksum_mismatch`, `no_stats`,
`grpc_unavailable` (non-fatal). If the server has really gone, the remaining cases are
**skipped and listed** in `errors`, so a dead peer costs a bounded time instead of
`reps × cases` timeouts.

**Loopback ceiling.** Before measuring a peer, the client starts a second `serve`
**process** on `127.0.0.1` (a real process, so sender and receiver do not share one GIL,
exactly like the two-laptop run), measures `tcp-down`, `grpc-down` and `http-get` once at
`--ceiling-size`, and stops it. It also records the raw CRC-32 rate of this laptop
(`crc_rate_mib_s`). Python moves these bytes in user space, so above roughly 1 Gbit/s the
*tool*, not the link, can be the limit — the report says so instead of pretending the link
is slow.

**gRPC default message-limit probe.** One shot each (not a measurement): a 4 MiB message
with gRPC's *default* `max_receive_message_length` (4 MB = 4194304 bytes, inclusive — so
it is expected to **pass**), and the same message with the client's limit lowered by one
byte, to record the exact error the fabric would hit when a tensor chunk is larger than
the receiver's limit (expected: refused, `transport_error` /
`StatusCode.RESOURCE_EXHAUSTED`).

**Why no `.proto` file.** A spike must not change the shipped contracts, so the gRPC
service is registered through gRPC's **generic handler** API with identity (`bytes`)
serializers: the messages on the wire are exactly the payload chunks. A real protobuf
`bytes` field would add a tag plus a varint length — a handful of bytes per message, far
below the resolution of this measurement. What we measure is gRPC's HTTP/2 framing, flow
control and copies, not protobuf.

**Safety (docs/LAB.md §6).** `--bind` must be a private/loopback address unless
`--allow-any`; every transport admits **LAN peers only**; request sizes and chunk sizes
are range-checked before anything is allocated; connections are capped per transport
(16 by default) with a header timeout; the whole server stops after `--idle` without
traffic or `--duration` in total, and `stop()` unblocks it from any thread (Ctrl-C,
SIGTERM, tests). Home paths and public IPs are masked in the result JSON by the inventory
privacy filter.

## 2. How to run (🧑 one run per pair and per link)

Preconditions: `git pull` and `uv sync` on both laptops (no extras needed), both **plugged
in** and in performance mode, both on the **same link** (for the Wi-Fi matrix unplug the
Ethernet cables; for Ethernet turn Wi-Fi off, so the traffic cannot take the other path),
nothing else running — in particular **never run S1 and S3 at the same time**, and never
two S3 clients at once: they would share the link.

**1. Firewall on the *server* laptop (only for the spike, remove it afterwards).** The
server listens on **TCP 47301, 47302 and 47303** (no UDP). Replace `192.168.1.0/24` with
the lab subnet.

```powershell
# Windows, PowerShell as Administrator. Network profile must be Private (task 0.2.4).
New-NetFirewallRule -DisplayName "MeshForge S3" -Group "MeshForge lab" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 47301-47303 -RemoteAddress 192.168.1.0/24 -Profile Private
# afterwards:
Remove-NetFirewallRule -DisplayName "MeshForge S3"
```
```bash
# Linux: only needed if ufw is active (sudo ufw status)
sudo ufw allow from 192.168.1.0/24 to any port 47301:47303 proto tcp
# afterwards:
sudo ufw delete allow from 192.168.1.0/24 to any port 47301:47303 proto tcp
```
If Windows shows a "Windows Security Alert" for Python, tick **Private networks** only and
click **Allow**. Do not press Cancel: that can create a *block* rule for `python.exe` which
overrides the rule above (`Get-NetFirewallRule -Direction Inbound -Action Block -Enabled True | Where-Object DisplayName -like "*python*"`).

**2. Start the server** on the laptop that will send the bytes, bound to its lab IP on the
link being measured:

```bash
# Linux / WSL (bash)
uv run python lab/spikes/s3_transport.py serve --bind 192.168.1.20
```
```powershell
# Windows (PowerShell, native — not inside WSL)
uv run python lab/spikes/s3_transport.py serve --bind 192.168.1.20
```
It refuses `0.0.0.0`/`::` and public addresses (override: `--allow-any`), answers only
private/loopback/link-local clients, stops by itself after `--idle` seconds without traffic
(default 900) or `--duration` seconds in total (default 7200), and stops cleanly on Ctrl-C
or SIGTERM. It prints the three bound ports when it starts.

**3. Run the client** on the other laptop of the pair:

```bash
# Linux / WSL (bash) — Ethernet, full size ladder (~20 min)
uv run python lab/spikes/s3_transport.py client --server 192.168.1.20 --link ethernet
# Wi-Fi: stop at 256 MiB, otherwise 1 GiB and 2 GiB dominate the run (~1.5 h)
uv run python lab/spikes/s3_transport.py client --server 192.168.1.20 --link wifi --max-size 256MiB
```
```powershell
# Windows (PowerShell, native — not inside WSL)
uv run python lab/spikes/s3_transport.py client --server 192.168.1.20 --link ethernet
uv run python lab/spikes/s3_transport.py client --server 192.168.1.20 --link wifi --max-size 256MiB
```

`--server` can be repeated; servers are then measured one after another (each needs its own
`serve` process). Defaults: `--reps 5 --warmup 1 --pause 0.5 --chunk 1MiB
--chunk-sweep 64KiB,256KiB,1MiB,4MiB --chunk-sweep-size 64MiB --range-parts 4
--ceiling-size 64MiB --ceiling-reps 3 --connect-timeout 5 --io-timeout 30
--transfer-timeout 600`. Other useful flags: `--sizes 1MiB,64MiB,1GiB` (explicit ladder),
`--no-uploads` (halves the run time, drops `tcp-up`/`grpc-up`), `--ceiling-size 0` (skip
the ceiling check), `--name L2` (label in the report; the hostname is still stored),
`--out-dir DIR`. `--reps` below 5 makes every row **INVALID** and the client warns about it.

A run writes `lab/reports/raw/<UTC date>-S3-transport/<client>__to-<server>_<link>.json`
and prints progress plus a summary on stderr, for example:

```
loopback ceiling per transport (64MiB x 3 reps) ...
  ceiling tcp-down: 32490 Mbit/s
LAN results close to these are limited by this tool (Python, framing, CRC verification), not by the link.
...
gRPC 4 MiB message at the default 4 MB limit: passed; one byte over the limit: refused: ...
--- S3 summary [ethernet] L2 ↔ L1 ---
raw TCP download 64MiB: n=5
    934.1 ± 6.2 Mbit/s, 111.3 MiB/s, CPU 0.41 ms/MiB
...
written: lab/reports/raw/2026-09-21-S3-transport/L2__to-L1_ethernet.json
```

**Exit codes:** `0` complete · `1` cannot bind / cannot write the result · `2` usage error
(wildcard bind, non-private server address, bad size) · `3` results written but
**incomplete** (server lost, failed repetitions, gRPC missing — see `errors` in the JSON)
· `130` Ctrl-C.

**What to paste back:** the full stderr of the client run and the JSON file
(`git add lab/reports/raw/<date>-S3-transport/` and commit, or paste it). Do not edit the
JSON. Six runs cover all 6 pairs of four laptops in one direction each; the pair is
already measured in both directions (`-down` and `-up`) by a single run, so one run per
pair per link is enough.

**4. Build the report** after copying every laptop's JSON into one folder (any machine;
Wi-Fi and Ethernet files may share the folder, they are never mixed in a table):

```bash
uv run python lab/spikes/s3_transport.py report --results lab/reports/raw/2026-09-21-S3-transport --out lab/reports/2026-09-21-S3-transport.md
```

## 3. How to read the report

Sections, in order: the harness **Results** table (one row per case × metric — the raw
evidence), then

1. **Throughput by transport and payload size** — rows = transports, columns = sizes,
   cells `mean ± stdev` Mbit/s, one block per pair **and** link.
2. **gRPC chunk (message) size sweep** — throughput and CPU per chunk at the sweep size.
3. **CPU cost (ms of CPU per MiB moved, client + server)** — the same shape.
4. **Loopback ceiling** — per transport, plus this laptop's CRC-32 rate.
5. **gRPC message-limit probe** — the two one-shot outcomes.
6. **Q2 answer**, generated from the data: one block per pair + link, each with the
   baseline sentence, a judgement for gRPC (ADR-0005) and for HTTP (ADR-0003), a
   judgement for parallel ranges, and the best gRPC chunk.

**Validity and honesty rules built into the tables:**

- A cell with fewer than **5** valid repetitions is `… **INVALID (n=k)**`; a pair nobody
  measured is `TBD`. `TBD` is never replaced by a guess.
- The matrices never show a sweep row in the default-chunk cell, and on a re-run they keep
  the row with the most valid repetitions.
- Numbers from different pairs or different links are **never** mixed into one verdict:
  the Q2 section is grouped by `(pair, link)`, so a Wi-Fi gRPC row can never be compared
  with an Ethernet TCP row.
- The verdict's payload size is the largest size at which raw TCP, gRPC **and** HTTP all
  have `n ≥ 5`; if there is none, the block says so instead of choosing a transport.
- Thresholds: **≥ 85 %** of the raw-TCP baseline = "overhead acceptable, the ADR stands";
  **60–85 %** = "usable, but record the measured penalty"; **< 60 %** = "too expensive,
  the ADR needs a revision". Parallel ranges count as a gain above **×1.10** and as a
  **loss** below **×0.90** of a single HTTP GET; in between the report says "no measurable
  gain" (one connection already fills the link). A ratio below one always reads
  "×0.81 — slower", never "×0.81 as fast".
- The best gRPC chunk is chosen **inside one pair+link group only**, from valid rows only,
  and needs at least two valid chunks; a runner-up within **5 %** is reported as "not
  distinguishable at this n".
- Every number must be read against the loopback ceiling: a LAN result within a few
  percent of its transport's ceiling is **tool-limited** (Python, framing, CRC), not
  link-limited. The report prints that sentence itself.

## 4. Loopback numbers measured while building the spike

**These are loopback, not a real link.** They were produced with `serve` and `client` both
on `127.0.0.1` of one development laptop (`JARVISM3`, Linux 6.8.0-139, CPython 3.12.3,
grpcio 1.84.0, `--sizes 1MiB,8MiB,64MiB --reps 5 --warmup 1 --ceiling-size 64MiB
--ceiling-reps 3`, the `--link ethernet` label is only a label). There is no NIC in the
path and both processes share the same CPU, so these numbers **bound the software, not the
network**: they say what the tool can do, and every LAN result must be read against them.
They are *not* evidence for any transport decision.

Throughput, Mbit/s (mean ± stdev, n = 5):

| transport | 1MiB | 8MiB | 64MiB |
|---|---|---|---|
| raw TCP (server → client) | 10066 ± 1273 | 22069 ± 2096 | 34267 ± 2352 |
| raw TCP (client → server) | 19224 ± 528 | 25593 ± 1747 | 29705 ± 3500 |
| gRPC server-stream | 4312 ± 593 | 13544 ± 570 | 18286 ± 1681 |
| gRPC client-stream | 7464 ± 1287 | 13826 ± 2244 | 21032 ± 949 |
| HTTP GET | 6822 ± 1101 | 20725 ± 3606 | 29693 ± 4553 |
| HTTP 4 parallel ranges | 1949 ± 2406 | 20962 ± 1179 | 56694 ± 2697 |

gRPC chunk sweep at 64 MiB: `64KiB` 14173, **`256KiB` 21004** (best), `1MiB` 18286,
`4MiB` 11780 Mbit/s. CPU at 64 MiB (client + server): raw TCP 0.4, HTTP GET 0.4,
4 ranges 0.7, gRPC 1.0 ms/MiB — i.e. **gRPC costs roughly 2.5× the CPU per MiB of raw TCP
on this machine**, which is the part of the overhead that will still be there on a real
link. Loopback ceiling (64 MiB, n = 3): `tcp-down` 32490 ± 3043, `http-get` 31192 ± 2611,
`grpc-down` 15984 ± 2867 Mbit/s; CRC-32 verification 6430 MiB/s. The message-limit probe
behaved as designed: 4 MiB at the default limit **passed**, one byte over was **refused**
with `transport_error: StatusCode.RESOURCE_EXHAUSTED (4194304 vs. 4194303)`.

What this does *not* tell us: at 10–35 Gbit/s every transport here is orders of magnitude
above a 1 Gbit/s LAN, so on the real lab link all of them will saturate the link and the
percentages will look completely different (much closer to 100 %). The loopback run's own
generated verdict ("gRPC 53 % of raw TCP") is therefore a statement about *this CPU*, not
about the fabric. **The Q2 decision is made only from the two-laptop runs.**

## 5. Known limits

- The `http-range4` result at **1 MiB is noisy by construction** (`1949 ± 2406` Mbit/s on
  loopback): four connections for 256 KiB each means connection setup dominates. Parallel
  ranges are meant for large blobs; read that row at ≥ 64 MiB and ignore it at 1 MiB.
- Throughput is counted **at the receiver** over the window described in §1. The sender's
  own byte count is recorded per sample and compared, but the *timing* is the receiver's.
- The HTTP server is `http.server.ThreadingHTTPServer` — the standard library, not a
  production server (no sendfile, no zero-copy, one thread per connection). It measures
  what **stdlib HTTP** costs, which is what ADR-0003's V0.4 data plane would start from,
  not what an optimised HTTP server could reach.
- Single range per request only: a multi-range request is refused with `416` rather than
  answered with a multipart body. The parallel case uses `N` separate connections.
- There is no TLS anywhere in this spike. mTLS (ADR-0008) adds its own per-byte cost,
  which S3 does **not** measure; treat these numbers as the upper bound of the encrypted
  path.
- The payload is generated, never read from disk: storage is deliberately out of the
  measured path (ADR-0003's cache hits the disk; that belongs to a later benchmark).
- `--reps 5` with `--pause 0.5` is enough to see the spread but not enough to separate
  results that differ by a few percent; the tables' `stdev` and the 5 % tie rule exist so
  nobody over-reads a small difference.
- Wi-Fi results vary with distance, channel and neighbours far more than the spread within
  one run suggests. Record the conditions in the report's *Machines & conditions* table
  and, where it matters, run the pair twice.
- Without `grpcio` every gRPC row is a `grpc_unavailable` error and the run exits `3`; the
  raw TCP and HTTP rows are still valid.
- A run with `--max-size` below the default ladder is still valid and comparable for the
  sizes it did measure; missing sizes are `TBD`, never extrapolated.

## 6. What the result decides, and where the code goes next

The Q2 section of the report is the input to task **0.2.12**:

- **ADR-0005 (GPU remoting at the PyTorch level)** — whether tensors keep travelling over
  gRPC byte streams, and at which message size. If gRPC lands below ~60 % of raw TCP on
  the real link, ADR-0005 needs a revision (framed raw TCP for the bulk tensor path, gRPC
  kept for control).
- **ADR-0003 (content-addressed data plane)** — whether blobs keep travelling over HTTP,
  and whether parallel `Range` fetches are kept for speed or only for resumability and
  multi-holder fetches.
- The chunk sweep fixes the fabric's default message/chunk size, and the limit probe fixes
  what `max_receive_message_length` must be configured to on both ends (the default 4 MB
  limit is inclusive: a 4 MiB message passes, anything larger is refused with
  `RESOURCE_EXHAUSTED`).
- The measured Mbit/s per link feed the planner's transfer cost `T_transfer`
  (ARCHITECTURE §7) together with the S1 matrix, and the `cpu_ms_per_mib` column tells the
  planner how much CPU a transfer steals from the compute it is overlapping with.

`_s3/client.py` (one repetition per transport), `_s3/payload.py` (deterministic payload +
CRC verification), `_s3/meters.py` (CPU / peak RSS / server-side transfer log) and
`_s3/protocol.py` (typed failures, size rules) have **no CLI coupling**. V0.4's blob
transfer and V0.6's tensor transport can adopt the measurement helpers directly; as with
S7, reuse means **moving** them under `src/`, because the shipped packages must never
import from `lab/`. The wire formats here are spike-only (generic gRPC handlers, no
`.proto`): the real contracts stay in `proto/`.
