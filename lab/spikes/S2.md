# Spike S2 — cross-OS reachability without WSL (task 0.2.6)

**Question (ADR-0009 + ADR-0002):** for one **ordered pair** of laptops — can a **native,
non-WSL** Python process on the far machine be reached over **HTTP** and over **gRPC**;
does a long-lived **agent-initiated bidirectional gRPC stream** survive idle periods (with
gRPC keepalive on *and* off); and does the **outbound-only** connection model really work
from Windows with **no inbound firewall rule on the client**? This is the evidence that the
fabric's Windows↔Linux assumption holds *without* WSL. If it does not hold, ADR-0009 (native
Windows agent) and ADR-0002 (one long-lived stream the agent dials out) have to change.

Script: `lab/spikes/s2_crossos.py` · code: `lab/spikes/_s2/` · results:
`lab/reports/raw/<date>-S2-crossos/<client>__to-<server>_<link>.json` · report:
`lab/reports/<date>-S2-crossos.md`.

Standard library plus `grpcio` (a core dependency), so the spike runs after a plain
`uv sync` on Linux and on **native Windows** — no extras, no admin rights for the client
side, no compiler.

**A direction is one run.** The client dials the server, so a run answers
`client -> server` only. A pair of laptops needs **two runs**, one each way; a direction
nobody ran is reported `TBD`, never guessed.

## 1. What is measured

One `serve` process opens **both** listeners — HTTP on `47202` and gRPC on `47203` — so a
single temporary firewall rule for `TCP 47202-47203` covers the whole spike. The client
opens **no** listening socket at all.

| Case id | What | Transport |
|---|---|---|
| `http-ping` | `GET /ping` → the peer's identity JSON (OS, release, Python, WSL verdict) | stdlib HTTP/1.1 |
| `http-blob` | `GET /blob?bytes=N` → a streamed body, time to first byte + throughput | stdlib HTTP/1.1 |
| `grpc-unary` | `Echo` round trip, plus the time until the channel is usable | gRPC |
| `grpc-stream` | `Download`, a server-streaming RPC of `N` bytes | gRPC |
| `grpc-bidi-idle<gap>s-ka<on\|off>` | the **ADR-0002 session**: the client opens one bidirectional stream, both sides write for `--hold` seconds, the stream then goes **completely quiet** for `<gap>` seconds, and one last round trip decides whether it is still usable | gRPC |

The session case is the point of the spike. The client sends `hello` (which negotiates the
server's beat interval), then pings; the **server** pushes its own `beat` messages on the
same stream — a message from server to client on a connection the *client* dialled, which
is exactly what ADR-0002 needs and what no inbound rule on the client can provide. Then
the client asks the server to `go_quiet`, sleeps for the idle gap, and pings once more.
`survived = 1` only when that last round trip works. One case is run per
(`--idle-gaps` value × `--keepalive` mode), so keepalive on/off is a controlled comparison
on the same link: if only the keepalive-off cases die, an idle HTTP/2 connection is being
dropped by a firewall, NAT or the Wi-Fi driver, and the fabric must keep gRPC keepalive on.

**Metrics per repetition**

| Case | Metrics |
|---|---|
| `http-ping` | `connect_ms`, `ttfb_ms`, `total_ms` |
| `http-blob` | `connect_ms`, `ttfb_ms`, `mbps` |
| `grpc-unary` | `channel_ready_ms`, `rtt_ms` |
| `grpc-stream` | `channel_ready_ms`, `ttfb_ms`, `mbps` |
| `grpc-bidi-…` | `survived` (0/1), `alive_s`, `idle_survived_s`, `final_rtt_ms`, `active_rtt_mean_ms`, `msgs_up`, `msgs_down` (and `beats` in the raw sample) |

S2 is a **reachability** spike: the throughput numbers are a by-product and a sanity check.
The bandwidth question belongs to S1 and S3 — never quote an S2 `mbps` as a link
measurement.

**Typed failures** (`_s2/protocol.py`, recorded per repetition with a `fix` hint):
`connection_refused`, `connect_timeout`, `timeout`, `connection_reset`,
`host_unreachable`, `stream_dropped`, `tls_or_http2_mismatch`, `protocol_error`,
`server_error`, `measurement_invalid`. Each carries a `fix` hint — `connect_timeout`, for
example, explains that the SYN was dropped silently and names the firewall checks on
Windows and on Linux. `connection_refused`, `connect_timeout` and `host_unreachable` are
*fatal*: the case aborts at once, the client re-checks whether the peer is still there, and
if it is gone the remaining cases are **skipped and listed** in `errors` — a blocked port
costs one timeout, not one per repetition. A stream that dies **during the idle phase is not an error**: it is the
result, recorded as `survived = 0` with the diagnosis attached.

**Why no `.proto` file.** A spike must not change the shipped contracts, so the three gRPC
methods are registered through gRPC's **generic handler** API with identity (`bytes`)
serializers. What is measured is gRPC's HTTP/2 connection behaviour, not protobuf. The real
contracts stay in `proto/`.

**Safety (docs/LAB.md §6).** `--bind` must be a private/loopback address unless
`--allow-any`; both servers admit **LAN peers only** (anything else gets `403` /
`PERMISSION_DENIED`); blob sizes are range-checked before anything is allocated; every
socket has a timeout; a session is capped server-side at `MAX_HOLD_S`; the server stops by
itself after `--idle` without a request or `--duration` in total, and on Ctrl-C / SIGTERM.
Home paths and public IPs are masked in the result JSON by the inventory privacy filter.

## 2. The WSL refusal, and why it exists

`serve` and `client` **refuse to run inside WSL** and exit `4`:

```
refusing to run inside WSL: S2 must prove that a *native* process is reachable (ADR-0009).
Run this from native Windows PowerShell (or native Linux). Pass --allow-wsl only to record
a deliberately-WSL data point.
```

WSL2 sits behind its own NAT: a "reachable" result from inside WSL would be a statement
about WSL's port proxy, not about the Windows firewall and the native Python process the
agent will actually be. `--allow-wsl` records the data point anyway, prints a warning that
it does **not** validate ADR-0009, and the report marks any direction with a WSL side as
**not a native pair** and asks for a native run. Detection uses the same rules as
`lab/inventory.py` (`/proc/version`, `/proc/sys/kernel/osrelease`, `WSL_DISTRO_NAME`,
`WSL_INTEROP`).

## 3. How to run (🧑 two laptops, one direction per run)

Preconditions: `git pull` and `uv sync` on both laptops (no extras needed), both on the
**same link** (for a Wi-Fi run unplug the Ethernet cables; for an Ethernet run turn Wi-Fi
off, so the traffic cannot take the other path), Windows network profile **Private**
(task 0.2.4 — the client warns if an adapter is Public), nothing else heavy running. S2 is
cheap on bandwidth, but do not run it while S1 or S3 are measuring the same link.

**One run takes about 25–35 minutes** with the defaults (two idle gaps × two keepalive
modes × 6 repetitions each); the client prints its own estimate before it starts.

### 3.1 Firewall — only the *server* side needs a rule

The laptop running `serve` needs **inbound TCP 47202-47203**. The laptop running `client`
needs **nothing**: it only dials out, which is the whole point of the measurement. Do not
add an inbound rule on the client — it would destroy the evidence for ADR-0002.

```powershell
# On the SERVER laptop only. Windows, PowerShell as Administrator.
# Replace 192.168.1.0/24 with the lab subnet.
New-NetFirewallRule -DisplayName "MeshForge S2" -Group "MeshForge lab" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 47202-47203 -RemoteAddress 192.168.1.0/24 -Profile Private
# afterwards:
Remove-NetFirewallRule -DisplayName "MeshForge S2"
```
```bash
# On the SERVER laptop only. Linux: needed only if ufw is active (sudo ufw status)
sudo ufw allow from 192.168.1.0/24 to any port 47202:47203 proto tcp
# afterwards:
sudo ufw delete allow from 192.168.1.0/24 to any port 47202:47203 proto tcp
```

If Windows shows a "Windows Security Alert" for Python on the **server**, tick **Private
networks** only and click **Allow**. Do not press Cancel: that creates a *block* rule for
`python.exe` which overrides the rule above
(`Get-NetFirewallRule -Direction Inbound -Action Block -Enabled True | Where-Object DisplayName -like "*python*"`).
If a prompt appears on the **client**, that is itself a finding — write it into `--note`
and dismiss it without allowing anything.

### 3.2 Start the server (laptop B)

```bash
# Linux (bash), native — not inside WSL
uv run python lab/spikes/s2_crossos.py serve --bind 192.168.1.20 --name L1
```
```powershell
# Windows (PowerShell), native — not inside WSL
uv run python lab/spikes/s2_crossos.py serve --bind 192.168.1.20 --name L2
```

It refuses `0.0.0.0` / `::` and public addresses (override: `--allow-any`), answers
private/loopback/link-local peers only, prints the two bound ports, and stops by itself
after `--idle` seconds without a request (default 900) or `--duration` seconds in total
(default 7200), or on Ctrl-C / SIGTERM. **One server per port:** a second `serve` on a
port a previous one still holds is refused with "cannot listen" (exit `1`) — grpc's default
`SO_REUSEPORT` sharing is switched off, so a forgotten old `serve` can never silently take
half of the next run's connections. `--name` is how *this* machine is named in the
report (the hostname is still recorded); give a laptop the same name in every run, whether
it is serving or dialling, so the two directions of a pair line up. Other flags: `--http-port`,
`--grpc-port`, `--io-timeout`, `--quiet`, `--ready-file PATH` (writes the bound ports as
JSON once listening, for scripts).

### 3.3 Run the client (laptop A)

```bash
# Linux (bash), native — no inbound firewall rule on this machine
uv run python lab/spikes/s2_crossos.py client --server 192.168.1.20 --link ethernet --name L1 --no-inbound-rule --note "no Defender prompt appeared"
```
```powershell
# Windows (PowerShell), native — not inside WSL, no inbound firewall rule on this machine
uv run python lab/spikes/s2_crossos.py client --server 192.168.1.20 --link ethernet --name L2 --no-inbound-rule --note "no Defender prompt appeared"
```

`--no-inbound-rule` is the operator's statement that this machine has **no** inbound rule
for 47202-47203. Without it the outbound-only verdict stays `TBD` — the tool will not
claim what the operator has not confirmed. `--link` (`wifi` or `ethernet`) is required and
is what keeps Wi-Fi and Ethernet rows apart.

Defaults: `--reps 5 --warmup 1 --pause 0.5 --blob-bytes 33554432 --hold 5
--ping-interval 1 --idle-gaps 30,120 --keepalive both --connect-timeout 5 --io-timeout 20`.
Useful overrides: `--idle-gaps 30,120,300` (a longer gap if a 120 s idle already survives),
`--keepalive off` (isolate the keepalive question), `--reps 7`, `--out-dir DIR`,
`--allow-any`, `--allow-wsl`. `--reps` below 5 makes every cell **INVALID** and the client
says so before it starts.

**Then swap the roles and run it again the other way** — `serve` on A, `client` on B —
otherwise the report only knows one direction of the pair.

The run writes `lab/reports/raw/<UTC date>-S2-crossos/<client>__to-<server>_<link>.json`
and prints progress and a summary on stderr:

```
--- S2 verdict [ethernet] L1 -> L2 ---
client: Linux 6.8.0-139    server: Windows 11
  http-ping                    yes
  grpc-bidi-idle120s-kaoff     no — no reply to session ping 7 within 20 s [fix: …]
  outbound-only (ADR-0002)     yes — no listening socket and no inbound rule on the client
  metrics: HTTP first byte 1.23 ms, HTTP stream 812.4 Mbit/s, …
  what to fix:
    - grpc-bidi-idle120s-kaoff: …
```

**Exit codes:** `0` complete · `1` cannot bind / cannot write the result · `2` usage error
(wildcard bind, non-private address, bad number) · `3` results written but **incomplete**
(peer lost, failed repetitions — see `errors` in the JSON) · `4` **refused: running inside
WSL** · `130` Ctrl-C.

**What to paste back:** the full stderr of both client runs and both JSON files (commit
`lab/reports/raw/<date>-S2-crossos/`, or paste them). Do not edit the JSON. Say explicitly
which side had a firewall rule, and whether any Windows prompt appeared on the client.

### 3.4 Build the report

Copy every JSON into one folder (Wi-Fi and Ethernet files may share it — they are never
mixed into one row) and run, on any machine:

```bash
uv run python lab/spikes/s2_crossos.py report \
  --results lab/reports/raw/2026-09-21-S2-crossos \
  --out lab/reports/2026-09-21-S2-crossos.md \
  --hosts L1=L1,L2=L2
```

`--hosts LABEL=HOST` does two things: it renames `HOST` to `LABEL` in every row (matching
is case-insensitive, because Windows reports its hostname in upper case), and it declares
which directions *should* exist — every ordered pair of the listed labels that nobody
measured is added as a `TBD` row. `HOST` is whatever the runs recorded: the `--name` you
passed (so `L1=L1` above, which only declares the direction), or the machine's hostname if
you did not pass one (`--hosts L1=jarvism3,L2=DESKTOP-42`). `--results` may be repeated. `--date YYYY-MM-DD`
overrides the date otherwise taken from the folder name.

## 4. How to read the report

After the harness **Results** table (one row per case × metric — the raw evidence) come
three generated blocks:

1. **Reachability verdicts**, one row per `direction × link`: the four fixed cases, one
   column per bidi session case, and the **outbound-only** column.
2. **Latency and throughput (means)** — HTTP TTFB, HTTP stream, gRPC unary RTT, gRPC
   stream, per direction.
3. **Diagnoses and fixes** — every non-`yes` cell with its diagnosis, plus a line for any
   direction where one side was **not native** (WSL), which ADR-0009 does not accept.

Cell values, and exactly what each one means:

| Value | Meaning |
|---|---|
| `yes` | every requested repetition worked (and for a session case, survived the idle gap), with `n ≥ 5` |
| `no — <diagnosis> [fix: …]` | measured and failed; the diagnosis and the fix hint come from the typed failure |
| `flaky k/n` | `k` of `n` repetitions worked — never rounded up to `yes`, both numbers are shown |
| `INVALID (n<5)` | it worked, but with fewer than 5 measured repetitions: not a lab result |
| `INVALID (malformed)` | the result file's case entry is not a JSON object (hand-edited or corrupt): reported, never `yes` |
| `TBD` | nobody ran it |

**Validity and honesty rules built into the tables**

- The threshold is the harness-wide `MIN_VALID_REPS` (5). A cell with fewer valid
  repetitions is `INVALID (n<5)`, never `yes`.
- Only **measured** repetitions decide a cell. A failed *warmup* repetition never demotes a
  case that ran every requested repetition cleanly; it is listed under "Diagnoses and
  fixes" as a note "(not counted)" so it is not hidden either. An error record with no
  `phase` counts as measured — the conservative reading.
- A direction nobody ran is `TBD` in every column; `TBD` is never replaced by a guess, and
  `yes` for `A -> B` says nothing about `B -> A` — the two are separate rows.
- Wi-Fi and Ethernet are separate rows for the same direction and are never merged.
- When the same direction *and* link appears more than once (a re-run, or two result
  folders), the **newest** run by `timestamp_utc` wins and every file that covered the
  direction is listed in the row's `sources`. Older, worse results cannot silently win
  because of the file order.
- A session that dropped with keepalive **off** while the keepalive-**on** case survived is
  *not* counted against the outbound-only claim: it is an idle-survival result, which is a
  different column and a different conclusion (turn keepalive on).
- **outbound-only** is `yes` only when the operator passed `--no-inbound-rule` *and* the
  gRPC unary case *and* at least one long-lived session worked. It is `no` only when a
  gRPC case actually failed; if the gRPC cases never ran (the peer was lost first) or only
  produced `INVALID` results, it stays `TBD` — a model that was never tested is never
  reported as having failed.
- A direction where either side was inside WSL is listed under "Diagnoses and fixes" as
  needing a native run, and the OS column shows `(WSL)`.
- All free text (OS strings, host labels, OS error messages) is escaped before it enters a
  table cell, so a `|` or a newline in a Windows error message cannot shift the columns.

**What the table cannot tell you:** the expected-direction list is built from `--hosts`
alone, so a pair measured on Wi-Fi only shows a Wi-Fi row and **no** `TBD` row for the
missing Ethernet run. Read the `link` column before concluding that a pair is done.

## 5. Loopback numbers measured while building the spike

> **These are loopback — one machine, `serve` and `client` both on `127.0.0.1`. They are
> NOT a cross-OS result and they cannot answer this spike's question at all.** There is no
> NIC, no second operating system, no firewall and no NAT in the path, so the run proves
> only that the tool works end to end and what the *software* costs. Every claim about
> Windows↔Linux reachability, about idle streams surviving, and about the outbound-only
> model must come from a two-laptop run.

Machine: `JARVISM3`, Linux 6.8.0-139, CPython 3.12.3, grpcio 1.84.0. Command (shortened
gaps so the self-check fits in a few minutes; the `--link ethernet` label is only a label):

```
serve  --bind 127.0.0.1 --name loopback-server
client --server 127.0.0.1 --link ethernet --name loopback-client --reps 5 --warmup 1 \

       --keepalive both --pause 0.2 --no-inbound-rule
```

Result: exit `0`, every case complete, report generated and rendered correctly (verdict
table, the `TBD` row for the direction nobody ran, the per-direction metric block).

Re-run 2026-09-20 after the tester fix round (`--blob-bytes 4194304 --hold 1 --idle-gaps 3`,
otherwise as above): exit `0`, all six cases `yes`, outbound-only `yes`; a second `serve`
started on the same ports while the first was live was refused with `cannot listen on
127.0.0.1 (HTTP 47202 / gRPC 47203): [Errno 98] Address already in use`; SIGTERM stopped the
server with `stop requested` and balanced counters (`session: 12, session_ended: 12`).

What this **does** tell us: the three gRPC method shapes, the HTTP paths, the session
protocol, the failure classification, the verdict aggregation and the report generator all
work end to end, and the server really does push its own messages on a client-opened stream
(14 messages down for 9 up: `hello_ack`, `quiet_ack`, 6 pongs and 5 server `beat`s per
session). What it does **not** tell us: anything at all about Windows, about a firewall,
about NAT, or about an idle connection crossing a real network — both processes are on one
kernel with no NIC in the path, where an idle TCP connection has nothing that could drop
it. The `Ethernet` label is only a label, and 35 Gbit/s is the memory bus. **Every S2
conclusion must come from a two-laptop run.**

## 6. Known limits

- **One pair, one direction, one link per run.** Four laptops on two links is 24 runs for
  the complete matrix; the realistic plan is the pairs that matter (each Windows laptop
  with the Linux laptop, both ways) on both links.
- A `yes` is evidence for **that pair, that link, that firewall state, at that moment**. A
  different Wi-Fi network, a VPN client, a corporate policy or a third-party security suite
  can change the answer; the JSON records the Windows network profile of each adapter so a
  later "it used to work" is checkable.
- The idle gaps only bound what was tested: surviving 120 s says nothing about 10 minutes.
  If the fabric will hold idle sessions for longer, add `--idle-gaps 300,900` and pay the
  run time.
- There is **no TLS** anywhere in this spike. mTLS (ADR-0008) adds a handshake and its own
  idle behaviour; S2 measures the plaintext lower bound.
- The client declares "no inbound rule" — the tool cannot verify a firewall it does not
  have admin rights to read. It *can* and does guarantee the process opens no listening
  socket (`client_listeners_opened: 0`), and it records the network profile of every
  adapter. Treat `--no-inbound-rule` as an operator statement, which is why it is explicit.
- The throughput numbers use the stdlib HTTP server and a generic gRPC handler: they
  bound *these* implementations, not the link. Use S1/S3 for bandwidth.
- Without `grpcio` the spike cannot run at all (unlike S3, which degrades) — every case
  here is either HTTP or gRPC, and the gRPC half is the part that matters.
- IPv6 is supported by the code (`--bind` accepts a v6 address) but the lab runs on IPv4;
  an IPv6-only path is untested.

## 7. What the result decides

- **ADR-0009 (native Windows agent).** Two native `yes` rows for a Windows↔Linux pair, in
  both directions, on both links, confirm that the agent does not need WSL. A `no` on the
  Windows-as-server side would mean the fabric cannot rely on inbound connections to
  Windows at all — which ADR-0002 already assumes for the control plane, but ADR-0003
  (blob fetches) and ADR-0005 (GPU remoting) do *not*: they need inbound ports on the
  agent, and would have to be redesigned (reverse the direction, or tunnel them over the
  control stream).
- **ADR-0002 (agent-initiated bidirectional gRPC session).** The session columns decide
  whether one long-lived stream can be held idle between jobs, and whether gRPC keepalive
  must be on. If the keepalive-off sessions die and the keepalive-on sessions survive, the
  agent must ship with `keepalive_permit_without_calls` and the measured interval; if even
  keepalive-on sessions die at 120 s, the agent needs a reconnect strategy (ADR-0002's
  backoff + `Reconcile`) tuned to the measured drop time, and V0.3's heartbeat interval
  must be below it.
- The `outbound-only` column is the direct evidence for the installer story: if the client
  side truly needs no inbound rule, the Windows installer only needs a rule on machines
  that *host* data/GPU services, not on every node.
- The recorded identity (OS, build, Python, WSL verdict, network profile) of each laptop
  goes into `docs/LAB.md`; the failure diagnoses feed the setup instructions there.

`_s2/client.py` (one probe per call), `_s2/env.py` (WSL / OS / firewall-profile facts) and
`_s2/protocol.py` (typed failures) have **no CLI coupling**. V0.3's agent connection code
can adopt the session shape and the keepalive settings directly — as with S3 and S7, reuse
means **moving** the code under `src/`, because the shipped packages must never import from
`lab/`.
