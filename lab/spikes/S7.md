# Spike S7 — hardware scores per laptop (task 0.2.11)

**Question:** how fast is each laptop at the three things the planner cost model
(ARCHITECTURE §7) cares about — CPU floating point, host memory bandwidth, and GPU
floating point in fp32 / fp16 (bf16 when the card has it)? The numbers become the
`hardware scores` used to estimate `T_compute` and `rate_g` before any run history
exists, and later as ML features (V0.15). They must therefore be **comparable across
laptops** (same formula, same rule for picking the problem size) and **reproducible**
(≥ 5 repetitions, mean ± stdev, run conditions recorded).

Script: `lab/spikes/s7_hardware.py` · code: `lab/spikes/_s7/` · results:
`lab/reports/raw/<date>-S7-hardware/<host>.json` · report:
`lab/reports/<date>-S7-hardware.md`.

## 1. What is measured

| Case id | What | Score (unit) | Backend |
|---|---|---|---|
| `cpu-float32-1t`, `cpu-float32-all` | `C = A @ B`, N×N float32, 1 thread / all threads | `gflops` (GFLOP/s) | torch, else numpy |
| `cpu-float64-1t`, `cpu-float64-all` | same in float64 | `gflops` | torch, else numpy |
| `cpu-python-1t`, `cpu-python-all` | SAXPY `y = a·x + y` in pure Python, 1 process / one per core (max 16) | `python_mflops` (MFLOP/s) | stdlib, always |
| `memory-bandwidth` | STREAM copy / scale / add / triad over buffers larger than the cache, all cores | `copy_gb_s`, `scale_gb_s`, `add_gb_s`, `triad_gb_s` (GB/s) | torch (multi-threaded), numpy (single-threaded, lower bound), else stdlib (`copy` only, lower bound) |
| `gpu-float32`, `gpu-float16`, `gpu-bfloat16` | `C = A @ B` on the GPU, N×N, batches of `iters` multiplications | `tflops` (TFLOP/s), `event_tflops` cross-check | torch + CUDA |
| `gpu-copy` | device-to-device copy `b.copy_(a)` | `device_copy_gb_s` (GB/s) | torch + CUDA |

Every case also keeps `elapsed_s` per repetition and a `stability` record (first vs last
repetition) so throttling is visible.

**Formulas** (in `_s7/scores.py`; the same expression is written into every result file
as `attrs.setup.formula`):

| Score | Formula | Note |
|---|---|---|
| matmul GFLOP/s | `2 · N³ · iters / elapsed_s / 1e9` | N³ multiply-adds = 2 N³ FLOPs |
| matmul TFLOP/s | `2 · N³ · iters / elapsed_s / 1e12` | |
| SAXPY MFLOP/s | `2 · elements / elapsed_s / 1e6` | one multiply + one add per element |
| STREAM GB/s | `streams · elements · itemsize / elapsed_s / 1e9` | streams: copy 2, scale 2, add 3, triad 3 (STREAM convention) |
| device copy GB/s | `2 · bytes · iters / elapsed_s / 1e9` | read + write |

`G`/`T` are 10⁹ / 10¹², never 2³⁰ (STREAM and vendor convention).

**Sizes are derived on each machine, the rules are fixed** (`_s7/sizing.py`):

- **CPU matmul:** N starts at 128 and is grown (`N ← N · (target/elapsed)^(1/3)`, at most
  ×2 per step) until one multiplication takes ≥ `0.30 s` (`--quick`: 0.02 s), capped so
  that three matrices fit in ¼ of the available RAM and by N = 8192. The growth factor is
  an integer **rounded up** (at least 2), so the calibration never stops below the
  target but the chosen N can be up to ×2 larger than strictly needed — i.e. one
  multiplication can last up to 8× the target (`2³`); the trace in
  `attrs.setup.calibration` shows the steps. Why: a fixed N would be cache-resident
  on one laptop and swap on another; a fixed *duration* makes timer noise and turbo
  ramp-up irrelevant.
- **Memory bandwidth:** each buffer is `max(256 MiB, 8 × last-level cache)` on Linux
  (`/sys/devices/system/cpu/cpu0/cache`), 256 MiB on Windows (no cache size without
  admin), never more than ¼ of available RAM; `--quick` uses 32 MiB. Buffers are
  pre-allocated and touched once before timing, so page faults are not measured. Each
  repetition runs every kernel `iters` times, with `iters` calibrated in setup so one
  batch lasts ≈ 0.2 s (`--quick`: 0.02 s; `attrs.setup.iters`, `single_pass_s`), as
  STREAM recommends. The case runs with **all cores** (`threads_requested` = CPU count,
  `OMP_NUM_THREADS` in the child, `torch.set_num_threads`): one core rarely saturates a
  laptop's memory system, and the planner wants the *machine's* ceiling. With torch all
  four STREAM kernels run in float64 into pre-allocated outputs on every core
  (`threads_effective` records what torch actually used). numpy's element-wise kernels
  are single-threaded whatever the environment says, and its triad is two passes (not
  fused): a numpy result is a **lower bound** and `attrs.setup.notes` says so. The stdlib
  fallback only reports `copy` (a `bytearray` slice assignment is a memcpy, single
  thread, also a lower bound); the other kernels would time the interpreter, so they are
  `unsupported_ops` rather than wrong numbers.
- **GPU matmul:** N is the largest multiple of 256 (≤ 16384; `--quick`: ≤ 2048, so a
  smoke run really takes seconds) whose three N×N matrices fit in **half of the free
  VRAM** (`torch.cuda.mem_get_info`), so a desktop session on the same GPU cannot make
  the spike fail with OOM; the matrices are generated directly in the target dtype (no
  fp32 intermediate) and the peak allocation is recorded as
  `max_memory_allocated_bytes`. `iters` is chosen so one timed batch lasts ≈ 0.2 s.
  **TF32 is pinned off** (`torch.backends.cuda.matmul.allow_tf32 = False`, cudnn too;
  the state and `torch.get_float32_matmul_precision()` are recorded), so `float32` means
  real fp32 on Ampere+ cards and is comparable with older ones. Timing is wall clock
  around `torch.cuda.synchronize()`; `torch.cuda.Event` timings are recorded as
  `event_tflops` for cross-checking. bf16 runs only when
  `torch.cuda.is_bf16_supported()`; otherwise an `unsupported_dtype` error is recorded.
- **Repetitions:** `--warmup 2` + `--reps 5` per case (quick: 1 + 5), 0.2 s pause between
  repetitions. Warmup samples are stored but never enter the summary.

**How it runs.** Each case is executed in a **child process** (`_s7/child.py`), spoken to
over stdin/stdout (one JSON line per request). Reasons: a broken CUDA stack can hang or
hard-crash the interpreter (learned in 0.2.2); BLAS thread counts (`OMP_NUM_THREADS`,
`MKL_NUM_THREADS`, …) are read at import time, so the 1-thread and all-thread cases need
their own environment; and pure Python can only use all cores through processes. A child
that does not answer within its timeout (setup 300 s, repetition 120 s) is killed with
its process tree and the case is recorded as `worker_timeout`. The whole run is bounded by
`--timeout` (default 1800 s); a case that cannot start because the budget is gone is
recorded as `budget_exhausted` (never as a `worker_timeout`, which would blame the
benchmark). The child hands its real stdout to the protocol and redirects `sys.stdout`
to stderr before doing anything else, so a library that prints (a torch warning, a BLAS
banner) ends up in the parent's diagnostics instead of corrupting an answer.
Nothing here uses `fork`, `select` on pipes, or a shell, so it runs unchanged on Windows.

**Honesty fields in every result** (`extra`):

- `on_battery` — from the inventory power probe; on battery the run warns loudly and the
  report marks the laptop "BATTERY — not comparable".
- `environment.before` / `after` — power source, Linux `scaling_governor` per CPU or the
  Windows power plan, thermal zones, and `nvidia-smi` temperature / SM clock / throttle
  reasons.
- `stability.<case>.thermal_throttling_suspected` — the last repetition was > 15 % slower
  than the first (only judged when a repetition lasts ≥ 50 ms; otherwise `inconclusive`).
- `capabilities` — torch / numpy / CUDA versions actually seen by the child, and the
  typed reason (`torch_not_installed`, `cuda_unavailable`, `cuda_broken`) when the GPU
  could not be measured. A missing backend is a **run-level error**, never a silently
  missing metric, and makes the exit code 3.
- `quick: true` — a `--quick` run is a smoke test and is labelled as such in the report.
- `planner_fields` — the exact JSON paths the planner reads (e.g.
  `cpu-float32-all.summary.gflops.mean`, `gpu-float16.summary.tflops.mean`,
  `memory-bandwidth.summary.triad_gb_s.mean`).

## 2. How to run (🧑 one run per laptop)

Preconditions on every laptop: `git pull`, `uv sync` (`--extra gpu` once ADR-0011 is
accepted and torch is installed — without torch the CPU score is only the Python
fallback and the GPU section is a `torch_not_installed` error), **plugged in**, Windows
power mode *Best performance* / Linux governor `performance` if available, nothing else
running (close browsers, no other benchmarks, no S1 traffic at the same time).

```bash
# Linux / WSL (bash) — first a 5 s smoke run, then the real one (~2–5 min)
uv run python lab/spikes/s7_hardware.py run --quick
uv run python lab/spikes/s7_hardware.py run
```
```powershell
# Windows (PowerShell, native — not inside WSL)
uv run python lab/spikes/s7_hardware.py run --quick
uv run python lab/spikes/s7_hardware.py run
```

Useful flags: `--skip-gpu` (laptop without an NVIDIA GPU or with a known-broken driver:
recorded as `gpu_skipped`), `--device N` (second GPU), `--name L2` (label in the report;
the hostname is still stored), `--timeout SECONDS` (slow machine), `--out-dir DIR`.
`--reps` below 5 makes every score INVALID and says so.

The run writes `lab/reports/raw/<UTC date>-S7-hardware/<host>.json` and prints a summary
on stderr, for example:

```
--- S7 hardware scores: LAPTOP-1 ---
cpu-float32-all: n=5
    gflops 412.10 ± 6.30 GFLOP/s
...
not measured: unsupported_dtype: this GPU does not support bfloat16; skipped
!! thermal throttling suspected (...): gpu-float32
written: lab/reports/raw/2026-09-21-S7-hardware/laptop-1.json
```

**Exit codes:** `0` every case complete · `1` cannot write the result (or the folder
already holds another host's file with the same name) · `2` usage error · `3` result
written but incomplete (missing backend, failed case, budget ran out — see `errors` in
the JSON) · `130` Ctrl-C.

**What to paste back:** the full stderr output of the real run and the JSON file
(`git add lab/reports/raw/<date>-S7-hardware/` and commit, or paste it). Do not edit the
JSON. If the summary printed `!! ON BATTERY` or `thermal throttling suspected`, fix the
cause (plug in, let the laptop cool for 5 min) and run again — record both files.

**Build the comparison** after all four JSONs are in one folder (any machine):

```bash
uv run python lab/spikes/s7_hardware.py report --results lab/reports/raw/2026-09-21-S7-hardware --out lab/reports/2026-09-21-S7-hardware.md --labels L1=<host1>,L2=<host2>,L3=<host3>,L4=<host4>
```

The report has one table per metric (rows = cases, columns = laptops, cells
`mean ± stdev`), a ranking line per headline metric, and a *Run conditions* table
(backend versions, GPU, power, governor, throttling). `INVALID (n=k)` marks a laptop with
fewer than 5 repetitions, `TBD` a laptop that has no result for that row, `err: <type>` a
case whose repetitions all failed. `python_mflops` (interpreter fallback) is a separate
table and must never be compared with `gflops`. Then fill in Goal / Conclusion / Decisions
and copy the headline numbers into `docs/LAB.md` §1.

## 3. Expected output (sanity ranges, not pass/fail)

- CPU float32 all-threads with torch/numpy on a 2020+ laptop CPU: roughly 100–800 GFLOP/s;
  1 thread 20–100 GFLOP/s; float64 about half.
- `python_mflops`: 30–60 MFLOP/s per process; `-all` ≈ cores × that.
- Memory bandwidth with torch (all cores): 15–60 GB/s (`triad` usually the lowest;
  dual-channel DDR5 at the top of the range) — this is the machine ceiling the planner
  reads. numpy or the stdlib fallback (single thread): 8–25 GB/s, a lower bound that
  mostly reflects one core's load/store rate, not the memory system.
- RTX 3050 Laptop (4 GiB): fp32 ≈ 4–7 TFLOP/s, fp16 ≈ 15–35 TFLOP/s (tensor cores),
  device copy ≈ 150–200 GB/s. An fp16 number *below* fp32 means tensor cores were not used.
- `event_tflops` within a few percent of `tflops`; a large gap means CPU-side launch
  overhead dominates (N too small for that GPU).
- The ranking line under each report table is by each laptop's **best valid case** of
  that metric and names the case: for `gflops` that is `cpu-float32-all` (all cores), for
  `tflops` the fastest dtype the card supports.

## 4. Known limits

- Without torch (ADR-0011 pending) the CPU score is the **Python fallback** only and the
  GPU section is a `torch_not_installed` error: the run is still valid for memory
  bandwidth, but it is not the number the planner wants. Re-run after torch is installed.
- Matmul GFLOPS is a *peak-ish* dense-BLAS number, not the throughput of every workload;
  the planner later corrects it with measured history (ARCHITECTURE §7).
- Each memory-bandwidth repetition is a batch of `iters` passes calibrated to ≈ 0.2 s per
  kernel; if the stdev is still > 10 % of the mean, run again with the machine idle.
- Without torch the memory-bandwidth number is **single-threaded** (numpy element-wise
  kernels and the stdlib memcpy do not use the other cores), so it is a lower bound of
  the machine's bandwidth; the numpy triad is additionally not fused (two passes). Both
  are flagged in `attrs.setup.notes`. Re-run after torch is installed.
- `--quick` buffers (32 MiB) can be partly cache-resident on a 24 MiB-L3 CPU, and quick
  GPU matrices are capped at N = 2048: quick numbers are smoke tests and are labelled so.
- Windows: no cache size is read (256 MiB buffers assumed) and the power plan is reported
  by name only; iGPU-only laptops record `cuda_unavailable`.
- Only the first CUDA device is measured unless `--device` is given; multi-GPU laptops
  need one run per device with different `--name`.
- The thermal flag compares first and last repetition only; a machine that throttles
  *before* the first measured repetition (already hot from S1) looks stable but slow —
  hence `environment.before.nvidia.temperature_c` in the JSON.

## 5. Where the code goes next

`_s7/child.py` (benchmarks), `_s7/scores.py` (formulas), `_s7/sizing.py` (size rules)
and `_s7/worker.py` (bounded child protocol) have no CLI coupling; task 0.3.4 (hardware
scores at enrollment) reuses them inside the agent. Reuse means **moving** those four
modules under `src/agent/hwscore/` (the agent package must never import from `lab/`,
which is not shipped) and launching the child as `python -m agent.hwscore.child` from
the agent's own interpreter instead of by script path; the `lab/spikes/_s7/` copies then
become thin imports or are deleted. The JSON-lines protocol, the typed failure types and
the result field names stay as they are here, so S7 result files remain comparable with
enrollment scores.
