## 2. Design decisions (Lead proposals)

| # | Decision | Why |
|---|---|---|
| D259 | **Execution shape = one job, many *lanes*, many *chunks*.** A Mode 3 job is one `job` row. The planner picks a node set S; the dispatcher creates one **lane attempt** per node (`attempt.role = 'lane'`, own fencing token, slot, sandbox, fetch token, upload grant). A lane stages the project tree and builds the env **once**, then pulls chunks; **each chunk runs the entrypoint as a fresh process** inside the lane's prepared env and workdir. After all chunks are committed a **combine attempt** (`role = 'combine'`) produces the job output. **Rejected:** one child job per chunk (3,000 decisions, stagings and env checks; per-chunk overhead dominates small chunks); a long-lived user worker process speaking a chunk protocol (needs user code cooperation, breaks the "any script" promise — kept as a later `split.worker: persistent` option for model-loading workloads, see §7 Q4). | Reuses every V0.4–V0.7 guarantee (fencing, LOST, owner guard, mTLS, secrets) for lanes for free; process-per-chunk keeps failure attribution and memory isolation exact. Model-load cost per chunk is real → chunk sizing accounts for it (D265). |
| D260 | **`split:` manifest spec (0.10.1).** `over:` exactly one of `glob: <pattern>` (over the project tree or a named input mount), `list: [..]` (≤ 10 000 strings) or `list_file: <path>` (one item per line), `range: {start, stop, step}` (ints), `lines: <path>` (records of a text/CSV file; `header: true` repeats the header into every chunk). `chunk:` `auto` (default) or `{items: N}`. `combine:` `concat` · `merge-csv` · `merge-json` · `{script: [argv]}`. `max_nodes`, `min_nodes` (default 2), `speculative: true` (default), `deterministic: true` (default; D269). The entrypoint receives the chunk through **placeholders** `{items_file}` (JSON list of items), `{chunk_index}`, `{out}` and the same as env vars `MESHFORGE_CHUNK_ITEMS`, `MESHFORGE_CHUNK_INDEX`, `MESHFORGE_CHUNK_OUT`. **Resolution at submit**, on the controller, against the uploaded tree manifest: items = POSIX paths **sorted bytewise**, deduplicated; 0 items → `invalid_input`; caps: 100 000 items, 10 000 chunks. The resolved item list is stored (digest + count on the job; list as a CAS blob). | Deterministic order from submit time onwards is the base of criterion 1; glob resolved once means every lane sees the same list. Placeholders/env keep the user's script ordinary. |
| D261 | **Chunk results** = the chunk's `{out}` dir packed as a CAS tree, uploaded under the **lane's** upload grant; the controller accepts a chunk's `result_digest` only if that grant stored and verified it (V0.4 D71 rule). Lane grant quota = `split.max_chunk_output_bytes` × chunks it may complete (re-minted as it pulls). Logs: per-chunk stderr tail (64 KiB) kept with the chunk; lane log = concatenation with chunk markers. | No unverified bytes reach combine; quota bounds a misbehaving lane. |
| D262 | **Shared work-queue module (0.10.2)** `meshforge.workqueue` (new top-level controller-side package; no Mode 3 imports): **pure core** (`core.py`: item states `pending → leased → done` / `failed`, per-item `lease_seq` fencing, visibility timeout, max attempts, speculation eligibility — no DB, no clock) + **Postgres store** (`store.py`: `work_queue`, `work_item`, `work_lease` tables, migration 0025; lease = `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED ORDER BY idx LIMIT k)`; completion = conditional update `WHERE state <> 'done'` keyed by `(item, lease_seq)` → **idempotent**, first result wins, later ones return `already_done` with the winner's digest). One item may hold **≤ 2 live leases** (original + one speculative copy). Queue owner is an opaque `(kind, owner_id)` so Mode 4 batches reuse it unchanged. | ADR-0006 promise; Mode 4 (V0.12) inherits one tested component. SKIP LOCKED gives contention-free pulls under the existing single-controller model. |
| D263 | **Pull protocol on the existing session stream** (proto additions, `agent.proto`): agent → `ChunkRequest{attempt_id, fencing_token, want}` (not buffered: a lost request is simply re-sent), controller → `ChunkGrant{items:[{chunk_index, lease_id, lease_seq, items_digest, input_entries}], lease_deadline_s}` or `NoWork{reason: drained|wait, retry_after_s}`; agent → `ChunkResult{lease_id, lease_seq, outcome, result_digest, exit_code, failure_type, phase_ms}` (**buffered, replayed, acked only once stored**, like `AttemptStatus`); agent → `LeaseRenew{lease_ids}` every `lease_deadline/3`; controller → `CancelChunk{lease_id}` (speculation loser, job cancel). Prefetch window **1** (`want ≤ 2`: one running, one staging). Every message is checked against the lane's current fencing token **and** the lease; a mismatch is fenced and counted, never applied. | Pull = automatic heterogeneity balancing (ADR-0006); reuse of buffered/acked reports gives exactly-once commit across Wi-Fi drops. |
| D264 | **Chunk-level staging (0.10.4):** the grant carries the chunk's `input_entries` (path, digest, size, ≤ 4 096 per chunk; larger → a CAS blob listing them); the lane fetches **only those blobs** with its existing fetch token (scope = the input tree) via controller/peer sources, and `materialise_subset()` places them under `chunk/in/` (read-only), next to the shared project tree. The project tree minus the `over` directory is staged once per lane. Blobs stay in the agent CAS (a speculative copy or retry on the same node re-fetches nothing). | "Only needed files" is the point of 0.10.4: a 3,000-image input is not copied whole to every laptop. |
| D265 | **Planner Mode 3 (0.10.3)**, pure, in `planner/`: for a job with `split:` the candidates are **Local**, **Mode 1 per node** (= "don't split": one lane, one chunk with all items — same code path, D269) and **Mode 3 per node set**: nodes ordered by estimated rate, **prefix sets** of size `min_nodes..min(max_nodes, N)` (no 2^N search), each always including the fastest feasible node. Estimate: `T(S) = T_resolve + max_n∈S(T_stage(n) + T_env(n)) + items / Σ_n r_n + C(S)·t_overhead + T_combine + T_out`, where `r_n` = items/s from chunk history of the fingerprint on n (`history`), else single-run history ÷ item count, else scaled by hardware score (`scaled`), else assumed; per-chunk overhead `t_overhead` measured (process start + stage + upload) else assumed 1.5 s. **Chunk size auto:** target chunk ≈ `clamp(20 s × r_fastest, ≥1 item)`, then raise until overhead ≤ 5 % of predicted chunk time, and lower until K ≥ 4·|S| (tail balance). **"Don't split" wins** unless `T(S) ≤ (1 − split_margin) × T(best single)` (`split_margin` 0.10, config) — and is forced when items < 2·min_nodes. Every candidate, its rates' sources and the margin test are in the decision JSON; `compute explain` prints them. | ADR-0007 structure; prefix sets are optimal under the linear-rate model and keep the candidate count O(N); the margin stops splitting on noise (criterion 5). |
| D266 | **Stragglers (0.10.5):** only when the queue has **no pending items** and a lane is idle: pick the leased item with the largest predicted remaining time `elapsed vs p50_chunk(node)`; duplicate it when `remaining(holder) > 1.5 × p50_chunk(idle node)` and the idle node is a different node; ≤ 1 copy per item, ≤ 10 % of items speculative per job (config). First committed result wins (D262); the other lease gets `CancelChunk`, its process is killed, its partial upload is not referenced. Both copies are telemetry rows (`speculative`, `won`). If deterministic and both finish, digests are compared (D269). | Classic backup tasks (MapReduce); bounded duplicate work. |
| D267 | **Failures (0.10.6):** (a) **lane LOST** (OFFLINE / Reconcile, unchanged ADR-0015 rules) → its live leases are released to `pending` **in the same transaction** — no waiting for the visibility timeout; (b) **visibility timeout** (default `max(60 s, 4 × p50_chunk)`, renewed by `LeaseRenew`) covers partitions and hung chunk processes; on expiry the old lease is fenced; a late `ChunkResult` from it is accepted only if the item is still not done (at-least-once execution, exactly-once commit); (c) **chunk failure** (non-zero exit etc.) → retry per `retry:` / failure type on a **different** node when possible; the same item failing with a workload failure on 2 distinct nodes (or `retry.max_attempts`) → job `FAILED(chunk_failed, chunk=i)` and all lanes cancelled — **no partial output**; (d) owner-guard pre-emption of a lane → leases released, not counted as chunk failure; (e) all lanes gone with items pending → the dispatcher re-plans **new lanes for the remaining items** (planner sees the remainder); (f) a node may run **one lane per job**. | ADR-0015 consistent; criterion 4; no confidently-wrong partial results. |
| D268 | **Combine (0.10.7)** runs as a **combine attempt on an agent** (prefer the submitter node, else the node holding the most chunk results, via cache affinity), sandboxed like any attempt, inputs = chunk result trees mounted as `parts/00000/ …` in **chunk-index order**. Built-ins are trusted MeshForge code run in the sandbox: `concat` (per file name, chunks in index order, byte concatenation; a file name present in only some chunks is fine), `merge-csv` (headers must be byte-identical across chunks or `FAILED(combine_error, header_mismatch)`; first header kept), `merge-json` (top-level arrays concatenated in order; objects merged with a duplicate key = error, never last-wins). `script` = user argv with `{parts}` and `{out}`. Output = the job's normal output digest → `compute fetch` unchanged. **Rejected:** combining on the controller (parses untrusted data and burns controller CPU; user scripts must never run there). | Security model unchanged (user code only on agents); ordered input makes the combine deterministic. |
| D269 | **Determinism and criterion 1:** "don't split" for a split job is the same lane path with one chunk, so split and unsplit outputs come from identical code. `deterministic: true` (default) means: speculative/duplicate results of an item must have **equal digests**; a mismatch → job warning `nondeterministic_chunk` (shown in CLI/dashboard/records), winner kept. Criterion 1 is defined as **byte-identical combined output**, measured with deterministic workloads (fixed seeds, `torch.use_deterministic_algorithms`, fixed thread count, CPU inference for the identity run — §7 Q3). | Precise, testable meaning; float differences across GPU vs CPU are physics, not a bug, and must not be hidden by a loose comparison. |
| D270 | **Progress (0.10.8):** controller aggregates in memory per job (rebuilt from `work_item` on restart): counts by state, per lane (node, done, failed, items/s EWMA, current chunk, staging/running), speculative count, ETA = remaining items / Σ live rates. Event `split.progress` (≤ 2/s per job, coalesced) + `GET /v1/jobs/{id}/chunks?state=&node=&cursor=` (paged) + `GET /v1/jobs/{id}/split` (summary). CLI: `compute run` / `compute job watch` show a bar + one line per node (`--no-progress` for scripts, JSON with `--json`). Dashboard Job detail gets a **Chunks** tab: chunk grid coloured by state (virtualised, 10 000 cells), per-node table, makespan predicted vs elapsed. Shown numbers equal stored rows (standing rule). | Visible balancing is also the evaluation demo. |
| D271 | **Telemetry (feeds V0.9 dataset):** new `chunk_record` (job, lane attempt, node, chunk index, items, bytes in/out, stage/run/upload ms measured on the agent with a monotonic clock, lease seq, speculative, won, outcome, failure class) written in the same transaction as the commit; job-level `run_record` for Mode 3 gets `strategy = mode3`, `node_set`, `chunk_items`, `chunks`, predicted vs actual makespan, `ideal_bound_s` (D274). Telemetry **schema v3** (bump + export of a second Parquet table `chunks.parquet`, D222 determinism test extended). Forced strategy (D215) gains `mode3:<node,node,…>` and `mode1:<node>` for split jobs. | V0.15 learns per-node item rates from chunks; regret for split decisions needs both. |
| D272 | **Mode 3 benchmark families (0.10.9):** `image_classify` (3,000 synthetic images generated from a seed at stage time in the bench input tree, small fixed-weight CNN built in code; CPU/GPU), `hash_files` (sha256 + zlib over files; I/O heavy, a "don't split" lesson on slow Wi-Fi), `montecarlo_range` (range items, per-item seed; pure CPU, ideal scaling), `csv_aggregate` (`lines` + `merge-csv`). Each: deterministic output, self-check, size → runtime hint, campaign-ready. | Covers CPU-, GPU-, I/O-bound and both combine types; criterion 1 workload is `image_classify`. |
| D273 | **Security:** lanes and combine are attempts → mTLS session, node identity, owner policies (`allowed_users`, `exec`, `gpu`) and the owner guard apply **per node of S** (feasibility); secrets delivered per lane exactly as Mode 1; every chunk message fenced by lane token + lease seq; a lane can complete only leases it holds; result digests only from its own grant; item paths are validated relative paths inside the tree (no `..`, no absolute, no symlink escape) and `list` strings are passed only via the items file, never into argv or a shell. Threat model gets a Mode 3 section (a malicious lane can return wrong bytes for its chunk — mitigated only by `deterministic` speculative cross-check and owner trust; documented honestly). | System is RCE by design; splitting must not widen it. |
| D274 | **Criteria calibration (Lead proposal):** **C1** byte-identical combined output for `image_classify` 3,000 on 3 laptops vs a single-laptop run, CPU-deterministic mode (D269). **C2** makespan = job `RUNNING` (first lane started) → `SUCCEEDED`; ideal bound = `N / Σ r_n` with `r_n` each node's **steady-state** items/s measured *in the same session* by single-node runs, **plus** the largest single-node env/stage time and the combine time (otherwise the bound ignores unavoidable work); pass at ≤ 1.25 × only for runs whose best single-node time ≥ 5 min (shorter runs are reported, not judged). **C3** speedup vs best single ≥ 2.0 × is only physically possible when `Σr/r_best ≥ ~2.3`; criterion becomes **speedup ≥ 0.8 × Σr/r_best and ≥ 2.0 × on the lab trio if their Σr/r_best ≥ 2.5**; both numbers reported. **C4** kill -9 of one lane's agent at ~50 % progress → C1-identical output, every item committed exactly once (ledger check like D132). **C5** pure-planner + real-dispatch tests: tiny/fast items or slow links → `mode1`/`local` chosen with the margin printed. | The roadmap marked C2/C3 "(calibrate)"; these make them falsifiable and fair to heterogeneous hardware. |
| D275 | **Limits & config** (`[controller.split]`): `max_items` 100 000, `max_chunks` 10 000, `split_margin` 0.10, `target_chunk_s` 20, `max_overhead_frac` 0.05, `min_chunks_per_node` 4, `visibility_timeout_min_s` 60, `speculative_max_frac` 0.10, `progress_event_hz` 2. Agent `[agent.split] prefetch` 1. Validation in settings; documented in OPERATIONS. | Configuration over constants. |
| D276 | **New dependencies:** none for runtime. `hypothesis` (dev only) for work-queue property tests — **ask-first rule: §7 Q5**; fallback = seeded randomised tests in-house. | Small footprint. |

## 4. Standing checklist

V0.4–V0.9 items 1–31, plus:

```
32. No confidently-wrong output: a split job either produces the combined output of ALL items, each committed once,
    or fails with the chunk and reason named. Never a partial result labelled success.
33. Item order is decided once (bytewise-sorted at submit) and every later step (chunks, combine, records) uses it.
34. Every chunk message is fenced by lane token AND lease seq; a fenced message is counted, logged, never applied.
35. Commit of a chunk result, its chunk_record and its lease release happen in one transaction.
36. Lane LOST releases its leases in the same transaction as the LOST transition.
37. Shown progress numbers equal the work_item rows (test compares them).
```
