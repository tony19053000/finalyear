## 2. Design decisions (settled by the Lead before spawning)

| # | Decision | Why |
|---|---|---|
| D102 | **Planner = new package `controller/planner/`, pure and synchronous** (no DB, no asyncio): `plan(request, snapshot, policy, now) -> Decision`. Inputs are a frozen `ClusterSnapshot` (nodes + state + hardware + scores + live load + free slots + cache holdings + network links + history stats) built by the dispatcher once per dispatch tick. Stages exactly as ADR-0007: `candidates()` → `feasible()` (each rejection = `(node_id, reason_code, text)`) → `estimate()` → `rank(policy)`. `placement.py` rules move into `planner/feasibility.py`; `check_placement` stays as a thin wrapper for the manual path. | Testable without a database; the same function later serves Mode 3 (V0.10) and the ML policy (V0.15). |
| D103 | **Placement request**: `placement: {node_id?, local?, policy?}` (REST + `compute run --node/--local/--policy`). `node_id` given = **pinned** (candidate set of one; manual path keeps its exact V0.4 behaviour, incl. D65 `QUEUED → FAILED`). Omitted = **auto**. `submitter_node_id` (CLI sends its own node id when the laptop has an enrolled agent) marks which candidate is **Local** (ARCHITECTURE §5: Local is always a baseline candidate, never a separate code path — 0.6.11). | One path for Local, Mode 1, pinned and auto. |
| D104 | **When planning runs.** At submit: a *static* feasibility pass over all enrolled, non-revoked nodes (hardware/capabilities only, ignoring liveness/load). None could ever run it → `409 no_feasible_plan` with every rejection, no job row. Otherwise the job is `QUEUED`. At every dispatch tick: the full planner over the live snapshot; a job with no *currently* feasible node stays `QUEUED` (decision recorded once per distinct reason set, not per tick). `PLANNING` stays a recorded pass-through state. A queued auto job whose only feasible nodes are all revoked/removed → `FAILED(no_feasible_plan)`. | Jobs wait for a busy fabric, but never wait for hardware that does not exist. |
| D105 | **Slots (0.6.1).** Per node: `cpu_slots` and `gpu_slots`. Agent advertises its owner's limits in `Hello` (`[agent.execution] max_cpu_jobs` default 1, `max_gpu_jobs` default 1 per visible GPU; new Hello fields — implementer takes the next free numbers and records them in ARCHITECTURE §20); controller caps with `[controller.jobs] max_attempts_per_node` (kept as the upper bound). A GPU-required job takes a GPU slot; `gpu: preferred` takes a GPU slot if free, else a CPU slot; others a CPU slot. Slot use is derived from live attempts in the DB inside the dispatch transaction (no in-memory counter to drift). An old agent without the fields = 1 CPU slot, 0 GPU slots unless `exec-gpu` (then 1). | Concurrency without double-booking across a controller restart. |
| D106 | **Queue order & priority.** `job.priority` int −10…10 (default 0; manifest `priority:` or `--priority`). Dispatch order: effective priority desc, then `queued_at` asc; effective = priority + ⌊wait / `priority_aging_s` (600)⌋ capped at +10 → no starvation. Head-of-line blocking avoided: a job that cannot be placed now does not block lower jobs that can (bounded scan `dispatch_batch`). Retry `not_before` (D110) respected. | Fair, explainable, testable with an injected clock. |
| D107 | **Policies (0.6.3)**: `random` (RNG seeded from `job_id` + attempt number → reproducible), `round_robin` (cursor in memory; reset on restart is fine), `least_loaded` (fewest used slots, then lowest live CPU%), `strongest_suitable` (highest hardware score for the job's kind: GPU score if GPU job else CPU score; missing score ranks last), `resource_score` (weighted free RAM + free slots + score; weights in settings), `cache_affinity` (most cached bytes of the job's tree + inputs + env, from `cache_location`; ties → least_loaded), **`cost_model`** (lowest estimated completion time, D108). **Default = `cost_model`** (setting `[controller.planner] default_policy`). Every policy breaks final ties by `node_id` so results are deterministic. Selectable globally, per job, and per submit flag. | `cost_model` is ARCHITECTURE §7's analytical policy; criterion 4 (pick Local for a transfer-dominated job) needs it. The roadmap list did not name it — recorded as a roadmap note. |
| D108 | **Estimator v0 (0.6.4)**, analytical, per candidate: `T = T_queue + missing_bytes / bw(src→n) + T_env + T_compute + out_bytes / bw(n→ctl)`. `missing_bytes` = tree + inputs bytes not held by `n` (cache index; Local with seeding D109 = 0). `bw` from the network matrix (D111) else from `transfer_event` history for that node else `[controller.planner] default_bw_bytes_s` (flagged `assumed`). `T_env` = 0 if env hash cached on `n`, else history median build time for that base/runtime, else default. `T_compute` = median runtime of the same **workload fingerprint** (`sha256(tree_id + entrypoint + env_hash)`) on that node; else on any node scaled by CPU/GPU score ratio; else `[controller.planner] default_compute_s` (flagged `assumed`). `out_bytes` = median of the fingerprint's past outputs else 0. Every term carries `source ∈ {measured, history, scaled, assumed}`. | Physics where known, history where not (ADR-0007); the `source` flag keeps `compute explain` honest. |
| D109 | **Local seeding (0.6.11).** When `compute run` runs on a laptop with an enrolled agent (it already reads `node.json`), it also puts the project tree's blobs into **that agent's CAS** using `common/cas.py` + the GC lease index (same process rules as the agent; hash-verified; skipped silently with a logged reason if the CAS dir is not writable by this user or over quota) and submits `submitter_node_id` + `seeded=true`. The planner then counts 0 missing bytes for Local. The agent picks the blobs up via its normal CAS lookup (no proto change). | Without it Local pays a controller round trip for files already on the laptop, and criterion 4 is false in practice. |
| D110 | **Retry policy (0.6.7)** — see ADR-0015. Manifest `retry: {max_attempts: 1-10 (default 3), backoff_s: (default 5, doubling, cap 300)}`. An attempt ending with a **retryable** failure (§13 table; per-instance `Failure.retryable` wins) or `LOST` moves the job `RUNNING/PREPARING → RETRYING → PLANNING → QUEUED` with `not_before`, in **one transaction** with the attempt's end; past `max_attempts` → `FAILED(<last failure_type>)` with `retries_exhausted`. Placement on retry: auto jobs **exclude** nodes per failure type (`node_lost`/`transfer_error`/`integrity_error`/`timeout`: that node for `retry_exclude_s` 600; `vram_oom`: nodes with ≤ that GPU's VRAM; `resource_busy`: none). Pinned jobs retry on the same node only (and `QUEUED → FAILED` D65 still applies). Every retry is a new attempt with a new fencing token; the job's history keeps all attempts. | Retries are the point of V0.6; exclusion keeps a sick node from eating every attempt. |
| D111 | **Network matrix (0.6.6).** New peer-server route `GET /v1/probe?bytes=N` (N ≤ 8 MiB, zero-filled, token kind `probe` signed like D98 with `req`/`hold`, ≤ 60 s). Controller command `ProbeLink{target endpoint, token, sizes}`; the agent measures RTT (3 × 0-byte GETs, median) and throughput (one 4 MiB GET; 8 MiB if it took < 0.5 s) and replies `ProbeResult` (reliable report path). Scheduler in the controller: each ordered pair at most once per `probe_interval_s` (900), ≤ 1 probe per node at a time, ≤ `probe_budget_bytes_per_min` fabric-wide, never on a node running a GPU job or > 80 % CPU, staggered with jitter. Controller↔node links come from `transfer_event` (no extra traffic). Table `network_link(src, dst, rtt_ms, bw_bytes_s, samples, measured_at)` EWMA (α 0.3); rows older than 1 h are `stale` (estimator falls back). | Measured `bw` without flooding personal laptops' Wi-Fi. |
| D112 | **Decision records (0.6.5).** Table `plan_decision(id, job_id, attempt_no, policy, chosen_node_id or NULL, created_at, snapshot_digest, candidates JSONB)`; `candidates` = list of `{node_id, mode: local|offload, feasible, reject_code, reject_text, estimate: {terms with source}, score, rank}` bounded (≤ 64 nodes). Written in the same transaction that creates the attempt (or once per changed reason set while waiting, D104). Later the actual phase timings are joined via `attempt` (no copy) — training data for V0.15. `GET /v1/jobs/{id}/decisions` + `compute explain <job> [--attempt N]` prints a table: candidates, rejections with reasons, predicted breakdown with `source`, and actual vs predicted once finished. | Criterion 3; explainability and ML labels (ADR-0007). |
| D113 | **At-least-once commands (0.6.9).** Every controller→agent command carries `command_id`; the agent keeps a bounded LRU (4096) of applied command ids **per process** and, more importantly, every command's effect is idempotent by its own key (`StartAttempt`: `(attempt_id, fencing_token)`; `CancelAttempt`: attempt; `RefreshFetchToken`/`RefreshUploadGrant`: `(attempt_id, fencing_token)` + newest wins; `PrepareEnv`/`GcRequest`/`ProbeLink`: request id). Re-delivery path per command: reconcile-driven (attempt commands) or controller re-send on missing Ack after `command_resend_s` (10 s, ≤ 5 tries, then logged) for the rest. G1 writes the audit table into ARCHITECTURE §13 — one row per command: key, re-delivery trigger, test. | "Exactly-once effect" must be shown per command, not asserted. |
| D114 | **Upload grants across a restart (0.6.14).** Mirror D95: on Reconcile a held attempt stored `RUNNING`/`UPLOADING` with no live upload grant in this process gets `RefreshUploadGrant{attempt_id, fencing_token, grant, blob_url, blob_port}` (next free ControllerMessage payload). The agent's uploader retries a refused grant (waits for refresh) / unreachable controller (backoff 0.25→5 s) resuming completed parts, until `[agent.execution] upload_retry_s` (120) → `output_error` (retryable). The upload deadline (D94) still bounds the whole thing. | A controller restart must not fail every uploading job (criterion 2). |
| D115 | **Crash recovery (0.6.8).** After a restart: jobs in `PLANNING`/`RETRYING` → re-planned (they are just queue entries); `PREPARING`/`RUNNING`/`COLLECTING` keep their attempts and wait for Reconcile (exists); the orphan sweep's `LOST` now retries (D110) instead of failing; a `plan_decision` without its attempt (crash between) is impossible by D112's single transaction — test it with a kill between statements. Criterion 2 test: real controller process, 20 running jobs, `SIGKILL`, restart, every job reaches the right terminal state, each workload's side-effect file written exactly once. | Most machinery exists; V0.6 proves it end to end and wires LOST → retry. |
| D116 | **Failure classification (0.6.10).** Agent maps: exit by SIGKILL with cgroup/Docker `OOMKilled` or kernel OOM evidence → `oom`; stderr tail (last 64 KiB, already captured) matching `CUDA out of memory` / `torch.OutOfMemoryError` → `vram_oom`; `ENOSPC` anywhere in staging/env/output → `disk_full`; workload over its own limit → `deadline_exceeded`; infrastructure step over its budget → `timeout`; env build failure → `env_error` + controller remembers `(node, env_hash)` as known-bad for `env_bad_ttl_s` (3600, feasibility rejects it). Windows: job-object memory limit / `STATUS_NO_MEMORY` → `oom`. Each mapping has a test that *causes* it (allocate until killed in a memory-limited container/cgroup; fill a tiny tmpfs/quota dir; Python that raises the CUDA-OOM message on CPU-only machines is acceptable for the marker test only). | Retry decisions and ML labels are only as good as the classification. |
| D117 | **Duplicate execution (ADR-0015).** Guarantee = **at-least-once execution, exactly-once commit**: an agent *killed* never runs twice; a *partitioned* agent whose lease expired may keep running while the retry runs elsewhere — its later reports are fenced, its result is never committed, and it is told `CancelAttempt{release}` on reconnect. Criterion 1 ("0 duplicated") is measured as duplicate **commits** and duplicate executions **under kills**; overlapping executions under partition are counted and reported separately in the lab output. Manifest `retry: {on_lost: false}` lets a non-idempotent job opt out of LOST retries. | Honest: no system can promise exactly-once execution across a partition without the workload's help. |
| D118 | **Chaos suite (0.6.12)** in `tests/cluster/chaos/`, marker `chaos` (not in the default cluster run; nightly/CI-optional): seeded scenarios — random agent SIGKILL, agent SIGSTOP (partition-like), proxy cuts (D23) between agent and controller, controller SIGKILL+restart, disk-full on one agent — over N jobs whose workload appends `(job_id, attempt_id)` to a per-job file on the agent's disk and to a shared ledger the test reads. Invariants checked after quiescence: every job terminal; SUCCEEDED jobs have exactly one committed attempt; no job FAILED with a retryable type while retries remained; no attempt row left live; ledger duplicates only where a partition was injected. Seed printed on failure for replay. | Criteria 1–2 rehearsed before the 🧑 lab run. |
| D119 | **Carry-overs into G1** (refactors first, as pure commits with tests unchanged): split `controller/jobs/dispatcher.py` (1074) into `dispatcher.py` (loop + queue) / `dispatch.py` (placement → attempt) / `recovery.py` (reconcile, offline, orphans, backstop, upload deadline); split `common/gc_index.py` (831; V0.5 G5 reviewer); confirm controller `gc.py:133 _on_change` SQLite write is off the event loop (fix if not); D59 subprocess grandchildren surviving an agent SIGKILL on Linux (`PR_SET_CHILD_SUBREAPER` + kill the process group / cgroup v2 when available) — needed by the chaos suite. | Make room before adding the planner and retries; chaos would hit D59. |

## 4. Standing checklist

V0.4 brief §4 items 1–13 verbatim + V0.5 §4 items 14–15, plus:

```
16. Determinism: the planner is a pure function of (request, snapshot, policy, now); same inputs -> same
    Decision, including random (seeded). Unit tests build snapshots by hand; no DB in planner tests.
17. A retry never runs while an earlier attempt of the same job can still commit: every end-and-retry is one
    transaction, every report checks the fencing token, and a test kills the controller between steps.
18. Every rejection/estimate a user can see carries a reason code AND its data source; nothing in
    `compute explain` is a guess presented as a measurement.
```
