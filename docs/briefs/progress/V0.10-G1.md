## Decisions / deviations (for the Lead)
1. **Pure resolver lives in `common/split_items.py`, not `controller/jobs/split_items.py`.** `compute run
   --dry-run` must print the same items and the CLI may not import the controller (import-linter). The
   controller module `controller/jobs/split_items.py` is the glue (resolve in a thread, store the list blob,
   build the `SplitRecord`). No logic is duplicated.
2. **`list` / `list_file` keep the written order; repeats are refused** (`item [i] repeats` / `line N repeats`)
   instead of being sorted + deduplicated. D260's "sorted bytewise, deduplicated" is applied to paths (`glob`);
   sorting a user's explicit list would reorder their combine output, silent dedup would change the count.
   The order is still fixed once at submit (checklist 33). `range` = numeric order; `lines` = file order.
3. **`lines` items are record indices** (0..N-1); the list blob carries `records: [[offset, length]...]`
   (each record with its `\n`), `header: [offset, length] | null` and `source` (path/sha256/size). Blank
   records (whitespace only) are skipped; bytes are never decoded. G4 decides what the entrypoint sees
   (likely a chunk file = header + its records).
4. **Item-list blob format v1** (canonical JSON): `{"v":1,"over","count","items",...}`; `glob` adds
   `files: [[sha256, size]...]` parallel to `items` (G4's `input_entries`, G3's bytes per item).
5. **Job columns:** `split` (JSONB canonical spec, `none_as_null`), `split_items_digest`, `split_item_count`,
   **`split_item_bytes`** (extra vs the brief: total bytes of glob files / lines records, NULL otherwise - G3
   needs bytes per item). DB CHECK: all four NULL, or spec + digest + 1..100 000 items.
6. **Placeholders**: a non-split entrypoint containing `{items_file}`, `{chunk_index}`, `{out}` or `{parts}` is
   refused (`entrypoint: the placeholder {out} is only substituted in a split: job`); `{parts}` is refused in a
   split entrypoint; `{items_file}` / `{chunk_index}` are refused in `combine.script`. Unknown `{...}` text is
   left alone (no escape syntax invented). A queued pre-V0.10 job whose entrypoint literally contains one of
   these tokens would now fail `internal_error` at dispatch (re-validation) - judged negligible.
7. **Spec details I chose** (not in D260): bare string `over: "x/*"` = glob; `combine` default `concat`;
   `min_nodes` 2..64, `max_nodes` 2..64 or absent (= all suitable), `max_nodes >= min_nodes`; `range` bounds
   within +-(2^53-1), step != 0 (negative allowed); list items 1..1024 chars, no NUL, not blank; a glob ending
   in `/` is refused ("a whole folder is folder/**") - globs match files only, never folders; a matching
   symlink is followed inside its own tree (40 hops max) and must end at a file.
8. **Dispatch refusal** is in `DispatchPlanner._decide` (first check): `FAILED(no_feasible_plan,
   "not_supported_yet: split execution arrives in G4")`, pinned or auto. G4 removes it.
9. **GC** pins `split_items_digest` of every non-terminal job.
10. **Migration 0026 chains from 0024** on this branch (0025 = G2 not here). At merge: set
    `down_revision = "0025"`, add "0025" to the chain in `tests/component/store/test_store_migrations.py`
    and set `head.down_revision == "0025"` there.
11. `split.max_chunk_output_bytes` (D261) is **not** added - it is G4's knob with a default G4 must choose;
    adding it later changes the canonical form of split jobs only (none run before G4).
12. Settings: `[controller.split] max_items` / `max_chunks` only (the other D275 knobs belong to G3-G7).
    File caps (`list_file` 64 MiB, `lines` 2 GiB, line 16 MiB) are `SplitLimits` defaults, not config.
