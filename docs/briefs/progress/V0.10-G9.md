## Design (implementer decisions - for the Lead)
- **I1 Real workload, harness size.** (a)-(c) run the benchmark library's own `split.image_classify` job folder
  (`build_job`: integer CNN kernel, pinned numpy env, glob over `data/img/*.ppm`, built-in `concat`) with
  `images: 300`. 300 images is below the campaign's 5 s runtime window, so `build_split_job` lowers
  `MIN_RUNTIME_S` **in the test process only** around `build_job` (the window is a campaign measurement rule, not
  a job property; params model, input caps and seed range are still checked). The job itself is unchanged - the
  chunk kernel never reads the window. Needs the package index for numpy (skip otherwise, as V0.9 G2's test).
- **I2 Forcing the split in (a)/(b) by configuration, not a private API.** `Placement.node_set` is not accepted
  by `POST /v1/jobs` (bench-only, D287), so a fresh fabric is given `[controller.planner] default_compute_s =
  600` (no history: the planner assumes a slow job and splits over all three; auto chunking gives ~20 chunks).
  The decision itself is criterion 5's subject in (c); (a)/(b) test the split's correctness.
- **I3 "Same digest" = the job output digest** of the split job vs the same manifest pinned to one agent (one
  lane, one chunk - D269's path), compared in (a) and again after the kill in (b); plus `verify_output` on the
  fetched output (every image once, in order, each label recomputed in-process).
- **I4 Ledger (`check_exactly_once`)**: every work item `done` with exactly one `completed` lease (=
  `done_lease_seq`); exactly one `committed`+`won` chunk record per chunk with that lease seq and result
  digest; committed chunks cover items 0..N-1 contiguously; the set of `(chunk, lease_seq)` over **all** leases
  == the set over chunk records (every lease has a row, no orphan rows). (b) also asserts the killed lane is
  `lost/node_lost`, a `released` lease of it exists and has a `released` chunk record.
- **I5 (c) slow link = configuration, real CLI.** `[controller.planner] default_bw_bytes_s = 1000` (the floor),
  `default_compute_s = 10`, `[controller.network] enabled = false` (no probe overrides the assumption); the job
  is submitted with the **real `compute run`** from node 0's data dir, so node 0 is the Local candidate and its
  cache is really seeded (`seeded: true`, D109). Checked: decision rank 1 = `local` on node 0, every split row's
  margin test `passed: false` with `set_s > threshold_s`, the remote rows' `items_fetch` term `assumed` and
  larger than the whole Local estimate, and `compute explain` prints `not split: the best set ... (best single
  node <node0>)`, `fail:` and the `ITEMS_FETCH` column. The job then runs on node 0 and passes `verify_output`.
  A *measured* slow link (FaultLink throttle + transfer history) was not used: controller<->node bandwidth in
  the planner comes from transfer history, which a fresh fabric does not have, and REST blob traffic is not
  proxied unless `record_links` - the lab checklist covers the real Wi-Fi case.
- **I6 (d) owner guard acts on benchmark jobs only** (V0.9 D246: user jobs are never pre-empted), so (d) is a
  campaign's forced `mode3` run (`strategies: [mode3]`, all three nodes, D287) of `split.image_classify` at
  `images: 6000` (inside the window). The owner's `pause_benchmarks` overlay is written once one chunk is
  committed and the owner's lane holds a lease (`[agent.policy] reload_interval_s = 0.2`). If a job ends before
  the pause reached its lane, the next run of the campaign (3 repetitions, the campaign minimum) is tried - a
  bounded retry, never a timing assert. Checked: that lane `failed/owner_preempted`, exactly one lane on that
  node (never re-placed), no lease of it granted after its `ended_at`, its lease `released` (not `failed`), no
  `failed` chunk record, ledger exactly once, `verify_output` with the run's own seed, run `done` with this job
  (not requeued). The remaining runs are cancelled.
- **I7 One support module** `tests/_support/mf_split_cluster.py` instead of a fourth copy of the
  upload/submit/wait/sql/output helpers the G4/G5/G8 cluster files each define; those files are not migrated
  (out of scope - follow-up).
- **I8 A small lab tool, not only prose** (`lab/mode3_check.py`, like V0.6's `sched_check.py`): the checklist
  needs (1) job folders outside the campaign window (C2 is judged only for >= 5 min single runs, D274, but a
  campaign run is capped at 3 min) -> `build`; (2) the whole-output check on a laptop -> `verify` (prints a
  content digest too); (3) the D274 C2/C3 arithmetic from the two exports -> `report` (pure maths in
  `lab/_mode3/analysis.py`: rates from single-node runs' committed chunks, bound = N/sum r + slowest lane
  stage+env + combine, C2 judged only when the best single >= 300 s else `REPORTED`, C3 = speedup >= 0.8 x
  sum r / r_best and >= 2.0 on a trio with ratio >= 2.5; a missing input is `INCONCLUSIVE`, never a pass).
- **I9 Lab design.** C1 and C4 use **campaign-forced** `mode3` runs (D287) so they do not depend on the planner
  choosing to split a ~10 s job (it rightly may not: C5); C1's campaign also has `local`/`mode1` runs on every
  laptop -> one digest across all 12 jobs is a stronger C1 than one pair. C4 uses 20 000 images (the param max,
  ~1 min) so a human can kill at 30-70 %, with 3 repetitions as a bounded retry; its "same digest" partner is
  the same folder built by `mode3_check.py build` and pinned. C2/C3 use a user `montecarlo_range` job of several
  minutes split by the planner itself. C5 on the real link uses `hash_files` (60 x 1 MiB, one round).
