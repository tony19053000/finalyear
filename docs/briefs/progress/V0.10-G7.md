## Design (implementer decisions - for the Lead)
- **I1 Progress is read from the rows, never counted in memory.** D270 says "aggregates in memory per job
  (rebuilt from work_item on restart)". Checklist 37 ("numbers equal rows") is guaranteed by construction
  instead: every summary (REST and event) is one `REPEATABLE READ` snapshot of `work_item` / `work_lease` /
  `attempt` / `job_transition` / `plan_decision` (`split/progress.py::read_progress`). The tracker's memory
  holds only *when* to read (dirty set, last read time) and the last published `comparable()` (dedupe). A
  restart therefore rebuilds nothing: its first resync lists the running split jobs and publishes each one's
  current rows. Cost: <= `progress_event_hz` reads per running split job per second (7 small indexed
  statements each).
- **I2 Touches.** Minimal hooks outside my files: `Dispatcher(on_split_change=...)` is called after every
  chunk message the dispatcher handled (job id) and after a visibility-timeout pass that expired leases
  (None = every tracked job); the server's committed-change sink touches the job of every job/attempt change
  (lane start/LOST, combine, job end). Mode 1 jobs are recognised (one batched lookup, LRU-cached) and
  ignored. A periodic resync (`progress_resync_s`, 5 s) re-reads running split jobs anyway.
- **I3 Rate bound + coalescing.** A job is read (and so published) at most `progress_event_hz` (2) times a
  second; touches in between coalesce into the next read, which always happens - the last state (e.g. the
  terminal one) is never lost. An unchanged read publishes nothing (`comparable()` leaves out time-only fields).
- **I4 Lane rate** = items of the lane's last `progress_rate_window` (8) committed chunks, excluding the
  earliest, over the time from the earliest to the latest of those commits (steady-state throughput,
  staging excluded); one commit -> its items over the time since the lane's first lease. Not an EWMA (D270
  wording): an EWMA lives in memory and cannot be rebuilt exactly; this window is a pure function of rows.
  ETA = remaining items / sum of **live** lanes' rates; `null` until a live lane has committed (nothing is
  claimed that was not measured). Each lane also reports `last_commit_at` so a stalled lane is visible.
- **I5 "Staging/running" per lane** is not knowable from the controller's rows (prefetch: a lane holds one
  running + one staging lease). The lane shows its attempt state and the chunks it holds (`current`, with
  `speculative`). The attempt state already says STAGING / ENV_READY / RUNNING for the lane itself.
- **I6 Predicted makespan** = the rank-1 candidate's `estimate.total_s` of the job's **first** dispatched
  decision (C2 semantics: the plan before any re-plan); elapsed = first `running` arrow -> now / job end.
- **I7 `list_items` lives in `workqueue/reads.py`** (not `store.py`): read-only, no locks; keeps G6's
  `store.py` edits conflict-free. Keyset by `idx`; filters `states` and `site` (live lease there, or the
  winning lease's site); returns live leases + the winning lease.
- **I8 Chunk map** (`GET .../split?map=true`): one char per chunk (`p l s d f`, s = leased with a speculative
  copy), <= 10 000 chars, for the dashboard grid in one request; not in the bus event (bounded event size).
- **I9 Chunk stderr tail (D281) is NOT in G7**: it needs a proto field on `ChunkResult`, agent capture and a
  stored column - it belongs with `chunk_record` in G8 (D271). The Chunks tab shows each chunk's
  `failed_kind`, failed nodes and tries, which the rows have today.
- **I10 Warnings (D283 item 10)**: the summary and event carry the job's warnings (code + count); the CLI
  watch and the Chunks tab show them.
- **I11 CLI shape.** The CLI has no `job` group, so D270's `compute job watch` is **`compute watch JOB`**.
  It polls `GET .../split` every `[cli] progress_interval_s` (1 s; numbers = rows) instead of following the
  event WebSocket (the CLI has no event client; one small GET a second is bounded). `--json` prints the
  summary **once** (the repo's `--json` contract: one request, one sorted line - `test_v08_g6_json`); a
  stream would break that contract. Transient network errors are retried (5 in a row), then exit 6.
  `compute run -f` on a split job shows the progress on stderr instead of the logs (the lanes' logs are
  per-chunk processes; `--no-progress` keeps the log stream for scripts).
- **I12 `/chunks?start=N`** (besides the opaque cursor): the dashboard's "this chunk" panel asks
  `?start=N&limit=1` instead of forging a cursor; `start` + `cursor` together is 400.
- **I13 Dashboard grid** is one SVG (CSP `style-src 'self'`: sizes are attributes, colours `fill-*`
  classes), rows virtualised with the existing `useWindowedRows` (288 px viewport: ~33 rows of cells drawn of
  up to 834). Selection: click, arrow keys on the focusable grid region, or the "Chunk #" field. The tab
  refetches the summary (with map) on a `split.progress` that changed the counts (<= 2/s) and polls every
  10 s while the job runs (stream down); elapsed ticks every second on the controller's clock.
- **I14 Small hooks outside G7's files** (deviation from "api/, cli/, frontend/ only"): `jobs/dispatcher.py`
  (`on_split_change` param, 2 call sites), `server.py` (tracker wiring, `_publish_changes` touch, stop),
  `events/bus.py` (event type), `settings.py` (4 knobs), `cli/client.py` + `cli/settings.py` + `cli/app.py`,
  `tests/_support/mf_fake_lanes.py` (`gate` event to freeze results), `tests/e2e/parity.py` (`watch` row).
  Nothing in `split/service.py`, `split/store.py`, `workqueue/store.py` or `workqueue/core.py` (G6's).
