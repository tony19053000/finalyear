## Decisions / deviations for the Lead
- **API change (minimal, one model):** `EvalReportOut.ml: EvalMlOut | None` (+ its sub-models) in
  `api/planner_eval_models.py`, needed because the stored v2 report must validate. OpenAPI + `schema.d.ts`
  regenerated by `npm run gen:api` (node_modules symlinked from main for the run, removed). **G5b also
  regenerates these two files - merge conflict expected there: re-run `npm run gen:api` after merging.**
  No decision/explain API model touched. `ml_model_routes` doc string still says "pending_g4 until G5"
  (left for G5b, it changes OpenAPI text).
- **CLI eval timeout** 300 s -> 3600 s (`_EVAL_TIMEOUT_S`): the POST now trains one fold per family before
  replaying. The dashboard's POST (if any) is G5b's; the request is synchronous - a long-running job model
  for evaluations is a follow-up if lab datasets make folds slow.
- **No predict budget offline** (folds, loader, regret check): a wall-clock budget would make reports
  depend on machine load; latency is criterion 3's job.
- **Fold exclusion includes F's workload groups** (D316 rule), not only `family == F` - stricter than the
  brief's wording, same intent (no leak).
- **Fold per-term metrics are the pure model's** (y_hat on all held-out rows) plus `usable_rate`; the
  report has no "effective" (ML-or-calibration) MALE per term - the regret rows already measure the
  effective planner.
- **G3 tests edited** (they pinned `regret == "pending_g4"` as the new value, which D371 retires):
  `test_v015_g3_fit_gate.py`, `test_v015_g3_tester_r1_gate.py`, `test_v015_g3_registry_pg.py` now assert
  `not_run`; `test_v014_g4_report.py` / `test_v014_g4_planner_eval_cli.py` assert `eval_version` 2; the
  ml purity module list gained `child.py`, `folds.py`, `regret.py`, `registry_loader.py`, `holdout.py`
  (pure).
- `ModelSource.serving_version()` added (configured pin, else registry pinned/active) - no load.
- Mode 3: `ml_fallback` counts the chosen candidate's `estimate.terms()` (lane rate nested blocks are not
  double counted); per-lane blocks inside `split` are not counted separately.
