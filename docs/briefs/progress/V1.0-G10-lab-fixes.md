## BUG-1 - Docker env build fails ENOSPC after the torch download (D442)

**Root cause (verified).** The `envbuild` container (`agent/execution/docker_runtime.py`,
`_envbuild_kwargs`) is created with the same `/tmp` tmpfs as every job container, sized by
`[agent.execution] tmp_size_mb` (default 512 MB), and `HOME=/tmp`. pip resolves its temp dir from
`TMPDIR` -> `/tmp`; with `--no-cache-dir` and `--target /env` it downloads each wheel into a temp dir,
unpacks it into a second temp dir (the `--target` staging) and only then moves it into `/env`. A 554 MB torch
wheel (several GB unpacked) cannot fit a 512 MB tmpfs -> `OSError [Errno 28] No space left on device`
although the Docker disk had 21 GB free. (tmpfs pages also count against the build container's memory
limit, so a bigger tmpfs would have traded ENOSPC for OOM.) Reproduced exactly by
`tests/component/envs/test_v1_0_g10_env_build_tmp_docker.py` (16 MB tmpfs, 40 MB wheel: same pip error).

**Fix (D442).**
* The build gets its own temp folder `ENV_BUILD_TMP = /meshforge-build-tmp` **on the build container's
  layer** (the Docker disk): created empty, `0o700`, owned by the build user, in the same `put_archive` as
  `/env`; `TMPDIR` points there. pip removes its temp dirs; anything left would count in the layer size that
  is checked against `[agent.envs] max_env_bytes` before commit (`env_too_large`, no image saved). Before the
  build, the envs disk floor (`free_disk_floor_mb`) is checked as before. Docker cannot cap a container
  layer's size portably (`storage_opt size` needs overlay2 on xfs+pquota), so the transient download +
  unpack is bounded by the disk floor and the commit-time cap, not by a hard quota - same as `/env` itself.
* The job's `/tmp` stays the 512 MB tmpfs; the sandbox check (`Tmpfs` holds only `/tmp` with exactly the
  planned options) is unchanged.
* At commit, `env_image_changes` adds `ENV TMPDIR=<base's TMPDIR or /tmp>`: the build's `TMPDIR` must not
  reach the job (that folder is on the run container's read-only root filesystem - `tempfile` would fail).
  Docker cannot delete an `ENV` at commit, only set it. Existing env images (no `TMPDIR`) are unaffected
  and not rebuilt (the env hash does not change).
* **venv / subprocess runtimes and Windows:** checked, no change needed. They run uv on the host with
  `UV_CACHE_DIR = <envs root>/uv-cache`; uv downloads and unpacks into its cache dir (verified: a `uv pip
  install --target` succeeds with `TMPDIR=/nonexistent`), never the container tmpfs. On Windows the
  Docker runtime uses the same `envbuild` container (Docker Desktop, Linux containers) -> same fix.

## BUG-2 - a failed env build is retried for every chunk of a lane (D443)

**Root cause (verified).** A lane runs each chunk as one `runtime.run` (`lane_chunk.py::_chunk_run`); the
runtime builds the env when it is not cached. A failed build was reported as a **chunk** failure
(`ChunkResult(failed, env_error, retryable=True)` by D267c's rule "another node may succeed"), and the lane
pulled the next chunk - which built the env again. On a single-lane job the controller only ends the job
after every chunk has failed and the first one has also used its retries (probe: 32 results for 30 chunks);
with a ~4 min torch build per try that is hours of downloads - in the lab 8 builds (~4.4 GB) before the
human cancelled. No `env_error` ever reached the job, and `(node, env)` was never marked known-bad (D116
only reacts to an *attempt* ending `env_error`). Reproduced by
`tests/unit/agent/test_v1_0_g10_lane_env_failure.py` (4 chunks -> 4 builds before the fix).

**Fix (D443).** A chunk's run that failed **in its env phase** - the runtime entered the env phase
(image, env build, setup) and the workload never started (`observer.env_started` set, `run_started` not;
not cancelled) - is not a chunk result:
* `_chunk_run` raises `LaneEnvFailedError(failure_type, text, retryable)` (log `agent.lane.env_failed`,
  with `env_hash`); the chunk's folder is cleaned as always; **no** `ChunkResult`, **no** further
  `ChunkRequest`.
* `_run_lane` ends the lane `FAILED` with that typed failure and the lane's final logs (the install
  output). `retryable` = the type's default (`env_error` false, as in Mode 1; an `env_timeout` true).
* Controller (no code change needed): the lane's end releases its lease **uncounted** (D267a - the chunk
  did nothing wrong, no failed chunk try); the dispatcher's D116 hook marks `(node, env key)` known-bad with
  the node's env-policy fingerprint (D433), so no new lane for this env goes to that node; other live lanes
  pull the chunk; if it was the last lane the job ends `FAILED(env_error)` with the build's text (no re-plan
  for a non-retryable failure). Proven by `tests/component/controller/test_v1_0_g10_lane_env_failure_pg.py`.
* A chunk whose **workload** ran and failed keeps D267c exactly (chunk result, lane goes on).

## G10-C - L3 lane ended `failed unauthorized` while staging after the stream drop (D447)

**Evidence.** L3 agent log: lane attempt of job_01M72YDCB1R6V8E3ST71SMVDDW `staging` 14:39:56Z, no
`agent.lane.items` line, stream `INTERNAL` 14:40:03.96Z (the masked controller end, D444), attempt
`failed unauthorized` 14:40:04.43Z; L1's `b-split.log`: "the attempt ended (node_lost: node_offline)". So the
controller ended the lane when it lost the session and revoked its fetch tokens (`FetchTokens.revoke` on the
attempt's end); the lane was still downloading its **item list**, which then got 401.

**Root cause (real bug).** The item list is fetched by `Executor._lane_prepare` straight after STAGING,
**outside** the staging retry loop (D95/D429) that every other staging fetch uses. A 401 became
`FetchError(unauthorized)` -> final `FAILED(unauthorized)`, not retryable - and a cut link failed the lane at
once too. Beyond this lab case (where the controller had already ended the lane, so the outcome was moot),
the same path fails a live lane for good after a controller restart (old token refused until the re-mint
after Reconcile) and would defeat a reconnect grace (D445).

**Fix (D447).** `executor.py`: the item-list download runs under `_retry_staging` (a refused controller
token waits for `RefreshFetchToken` and retries with it; a transfer error is retried with backoff; with no
progress for `staging_retry_s` it ends `transfer_error`, retryable); the work root is created first (the
list's temp file lives there). No lane*.py or controller change.

**Tests.** `tests/unit/agent/test_v1_0_g10c_lane_items_retry.py` (real Executor, httpx MockTransport blob
surface): refused list -> waits, retried with the refreshed token, lane runs; cut download -> retried;
refusal never refreshed -> `transfer_error` retryable, never `unauthorized`. All 3 failed before the fix
(final `unauthorized` / immediate `transfer_error`).

## G10-B - lanes end on drained, reconnect grace, env-failure backstops (D445, D446, D448, D449, D450)

Lead tasks after D442/D443 (approved: tester a534ec5d). Commits e625c7da, d9309609, f8dcc7f7 and the
D445 commit.

**D446 - BUG-3: a lane ends on `NoWork(drained)` when it arrives.** Root cause (triage above): the
controller queues `NoWork(drained)` for the other lanes at the last commit (`split/service.py`
`_drained`); the agent put it into the lane's inbox, read only by the next `ChunkRequest`. Fix (agent,
`lane.py` `_lane_no_work`): an unasked `NoWork(drained | stop)` acts at once. In the pull loop
(`LaneState.pulling`) the running chunk - a lost speculative copy, or the env build inside it - is killed
with no result, and `_ask` reads the waiting `NoWork` from the inbox without sending a new request
(`drained` -> `DONE`, `stop` -> `cancelled`). Before the pull loop (still staging) the attempt is stopped
(`Executor._stop`): `drained` -> stop reason `lane_drained` -> `DONE exit 0` (`Executor._stopped`),
`stop` -> `cancelled`. `NoWork(wait)` is never sent unasked and changes nothing. Tests:
`tests/unit/agent/test_v1_0_g10_lane_drained_now.py`.
**D446 r1** (tester e8f23d5c: a grant and the `NoWork` queued in one controller batch let the granted copy
run): `_lane_no_work` sets `LaneState.drain_pending` in the pull loop; `_chunk` (top) and `_chunk_run`
skip every chunk not started yet with no result, and a drain while the current chunk's item files are
fetched cancels that fetch (`attempt.step`). Tests: `test_v1_0_g10_lane_drained_adversarial.py` (5x green),
`test_a_drain_cancels_a_long_input_fetch_of_the_current_chunk`.

**D445 - reconnect grace for running attempts (Lead decision).** Lab L3 (G9-D): the agent lost its lease
under memory pressure and reconnected 8-17 s later still running the attempt; the controller had ended it
`node_lost` at the lease expiry and answered the Reconcile `CancelAttempt(not_live_on_controller)` - 15
min of work lost, twice.
* `[controller.liveness] attempt_grace_s` (default **60 s**, 0 = off, max 3600). On an OFFLINE caused by a
  **lease expiry**, the node's `RUNNING` attempts (Mode 1 jobs and split lanes) are *held* by the
  dispatcher (`recovery.py` `_hold`, in memory): the row stays `RUNNING`, nothing is re-placed, tokens and
  grants stay, a lane's live chunk leases are extended to `grace + visibility_timeout_s`
  (`ChunkStore.hold_lane`, `wq.renew` - never shortened). Other live states (`ASSIGNED`/`STAGING`/
  `UPLOADING`) are lost at once as before.
* The node's next Reconcile that lists a held attempt **with its own fencing token** resumes it
  (`controller.jobs.attempt_resumed`, `stats.attempts_resumed`); one listed with another token, or not
  listed although its start was acked, is lost `agent_lost_attempt` (D66 unchanged).
* No reconnect within the grace: the periodic step (`_grace_expiry`) runs today's path - `LOST(node_lost,
  node_offline)`, retried per §12.1; a later reconnect is told `CancelAttempt{release}`.
* Never held: a revocation (`node_revoked` at once), a Goodbye, a replaced/expired certificate (OFFLINE by
  `STREAM_CLOSED`); held attempts are lost too when such an OFFLINE follows. The orphan sweep skips held
  attempts. A controller restart forgets the holds (`reconnect_grace_s` then applies, as before).
* **Trade-off:** a node that really died delays the retry of its running attempts (and the chunks its lane
  held) by `attempt_grace_s`; a node that comes back keeps its work instead of losing it and running it
  again from zero. 60 s covers the measured 8-17 s reconnects with margin while a dead laptop costs one
  minute. Fencing is unchanged: only the attempt's own token on its own node (mTLS identity) resumes it.
* **r1** (review of tester 357f9f48): D1 - a revocation of an already-offline node (no session for
  `REVOKE`) or of the certificate its last session used (`cert_superseded`, a re-enrolment) ends its held
  attempts at once: `Revocations.sync` calls `Dispatcher.on_revoked(nodes, serials)`, which queues a
  `_Revoked` item when a held attempt matches (the hold keeps the session's `cert_serial`). M1 - the API's
  `AttemptSummary.reconnect_grace_until` (wall clock, null = not waiting; OpenAPI, `schema.d.ts`,
  `docs/api` regenerated); `compute jobs <id>` shows a `waiting` row and the web UI's attempts table a
  "waiting for node to reconnect (Ns)" line. M2 - every end of a held attempt drops the hold (`_after` for
  reports and controller ends, the backstop). M3 - **flapping:** each loss after a resume gets a fresh
  grace (a node that keeps flapping keeps its attempt, bounded by the job's time limit and the backstop);
  a second loss before the resume keeps the first deadline.
* Tests: `tests/component/controller/test_v1_0_g10_reconnect_grace.py` (real PG + mTLS sessions): drop +
  reconnect within the grace keeps the attempt and the job succeeds on it; a lane is held with its leases
  kept; no reconnect -> `node_lost` + retry, a late reconnect is released; another token does not resume;
  a revocation never waits.

**D448 - backstop: a chunk `env_error` from an older agent ends that lane.** An agent before D443 reports
a failed env build as a chunk failure and pulls the next chunk. `SplitService._result` now releases such a
chunk uncounted and calls the dispatcher's `_end_lane_env`: `end_attempt(FAIL, env_error, "env build
failed on this node (reported per chunk): ...", retryable=False)`, the D116/D433 known-bad record, and

another lane: one chunk, job succeeds elsewhere, no failed chunk try, known-bad; alone: job
`FAILED(env_error)` after one chunk).

**D449 - a Docker daemon blip is `resource_busy`, never `env_error`.** `docker_unavailable` (the daemon
cannot be reached - raised inside the env phase because `enter_env()` runs before the client opens) was
`env_error`: it ended a lane (D443) and marked `(node, env)` known-bad. It is now retryable
`resource_busy` (`DOCKER_BLIP`) at every site, and `_env_phase_failure` never ends a lane for
`resource_busy` - the chunk fails retryable and the next one tries again. Tests: unit
`test_a_docker_daemon_blip_does_not_end_the_lane`; component `test_docker_sandbox_g3_tester.py` (an
unreachable daemon is `resource_busy`).

**D450 - Docker ENOSPC during the env build or setup step is `disk_full`.** The output pump keeps a tail
(`OutputPump.keep_tail`, thread-safe, every stream) while the `envbuild` / `setup` container runs; a failed
step whose output has the installer's ENOSPC text (`DISK_FULL_MARKER`) is `disk_full` (reason
`disk_full`), as the venv runtime has done since D116 - not `env_error` (no known-bad env for a full disk;
the planner avoids the node, D126). This includes an ENOSPC on the container's sized `/tmp` tmpfs in a
setup step (the job's own `tmp_size_mb`): typed `disk_full` too, although the host disk has room - the
message names the step's own output. Tests: `tests/unit/agent/test_v1_0_g10_docker_disk_full.py`, and a real
Docker setup step filling its 16 MB `/tmp` in `test_v1_0_g10_env_build_tmp_docker.py`.

## BUG-4 - a hung chunk holds its lease ~17 min on L4 (D451)

Source: `origin/lab/chat` 20261111-002946-L1-to-LEAD; `origin/lab/L4` REPORT "Stuck chunk 68" and its
follow-up. Job job_01M73B13999W9AWDT89F7KDX2H chunk 68 on L4 (Windows, venv runtime, RTX 3050): the venv's
`Scripts\python.exe` (launcher, pid 13032, 0.02 s CPU) started 00:04:03, the real interpreter (pid 19640,
`C:\Program Files\MeshForge\0.17.1-1\python\python.exe`) **17 s later**; then 12 threads all
`Wait/UserRequest`, 1.6 s CPU, 431 MB (torch imported), no output, never reached CUDA. The agent was healthy
and renewed the lease ~17 min; speculation copied the chunk only when the queue ran empty. Not reproducible
outside MeshForge (30/30 CUDA starts in the same venv); Event Viewer clean.

**Investigation.** The Windows spawn path (`agent/process.py`) already gives the child stdin `DEVNULL`,
drains stdout and stderr on separate reader tasks, uses `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP |
CREATE_SUSPENDED`, assigns a kill-on-close job object (memory, process count, CPU-rate hard cap) and then
resumes. So a full pipe or an inherited console/stdin is ruled out. Two real weaknesses:
1. **The double process.** A Windows venv's `python.exe` is a launcher: it reads `pyvenv.cfg` `home` and starts
   the base interpreter as a second process with `__PYVENV_LAUNCHER__`, then waits. Every chunk paid an extra
   process start, and the 17 s gap was inside that hop. The pid the agent supervised was the launcher, not the
   worker.
2. **Invisible error dialogs.** A process that hits a critical error (a DLL / drive that cannot be opened, a GP
   fault) can raise a modal system dialog and wait for a click. The agent is a service (session 0, no desktop),
   so a worker blocked like that waits for ever with every thread in a user-request wait. This matches the
   evidence (all threads waiting, ~0 CPU, no crash, process gone only when the job cleaned up), but it is not
   proven: L4 did not capture a dump.

The exact cause of chunk 68's hang is therefore **not proven**. Both weaknesses are removed, and the hang can no
longer hold a chunk unnoticed.

**Fix (D451).**
* **(a) One worker process on Windows.** `venv_runtime.direct_python`: the base interpreter
  (`pyvenv.cfg` `home` + `python.exe`) is started directly with `__PYVENV_LAUNCHER__` = the venv's python. That
  is exactly what the launcher does; CPython `getpath` then makes `sys.executable` the venv's python and finds
  the venv next to it, so `sys.prefix` and site-packages are the venv's. Anything unusual (no `pyvenv.cfg`, no
  `home`, a missing file) keeps the launcher. POSIX is unchanged (its venv python is a symlink).
* **(b) No invisible dialogs.** `agent/win_error_mode.quiet_error_mode()` at agent start adds
  `SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX | SEM_NOOPENFILEERRORBOX` to the agent's error mode. It is
  inherited by every child (workload, launcher, env build): a failing call fails, a crash ends the process. It
  is a no-op off Windows and never fatal.
* **(c) Progress watchdog (agent side).** `agent/execution/stall_watch.py`. While a chunk's process runs, the
  lane samples the CPU time of its whole process tree (psutil) every `stall_check_s` and notes every output
  byte.
  - A chunk is **stalled** when it has had no output and less than `stall_cpu_share` CPU-seconds per second for
    `max(stall_floor_s, stall_factor x expected)`. `expected` = the median per-item run time of the lane's last
    20 finished chunks x the chunk's items; before the first finished chunk, the floor alone applies.
  - **Report, never kill:** log `agent.lane.chunk_stalled` (once per stall; `agent.lane.chunk_resumed` if it
    recovers), and send the new `ChunkLeaseRef.stalled_s` (proto field 3, LeaseRenew only) with the lease in
    every renewal.
  - CPU that cannot be read is no evidence (never a stall). A stalled chunk does not update the lane's pace.
  - Docker chunks are not judged yet: the observer holds a container id, not a pid.
  - Settings `[agent.split]`: `stall_watch` (default true), `stall_floor_s` (300, 10..86400), `stall_factor`
    (4, 1..1000), `stall_cpu_share` (0.02, 0..1), `stall_check_s` (10, 0.5..300).
* **(d) Controller side.**
  - `split/messages.py` keeps a lease's `stalled_s` only when it is finite and > 0, clamped to 30 days.
    An old agent reports none.
  - `split/service.py`: a lease renewed with `stalled_s` is **marked** (`controller.split.chunk_stalled`, once
    per stall). The mark lasts until a renewal without it (`chunk_resumed`), a result for that lease, the
    chunk's commit, or the lane's end. Renewals go on as usual.
    - **Another node's lane exists** (`action=copy_first`): the next lane on another node that asks gets a
      copy of the stalled chunk first, before any pending chunk. An idle lane gets it on its next poll, a busy
      lane when its chunk ends. `split/store.request` -> `speculation._speculate_stalled`. No time estimate is
      needed. The `workqueue` lets a stalled item's copy through with items still pending (`only=` /
      `stalled=True`). Every other rule holds: another node, one live ordinary lease, the job's speculation
      budget, `split.speculative`. The first result wins and the loser gets `CancelChunk` (D266).
    - **No lane on another node** (`action=alone`, `stats.stalls_alone`): the lease keeps being renewed. A
      reclaim would only run the chunk again on the same node. The warning tells the operator to check the
      node.
  - Telemetry: the longest `stalled_s` per lease is written to the new operational column
    `chunk_record.stalled_s` (migration 0038). It is not a dataset column; the schema version is unchanged.
    It is null when nothing was reported.
  - Marks and peaks live in memory (bounded at 10 000 each). A controller restart forgets them, and the next
    renewal (every third of the lease timeout) marks the lease again.
  - Not done (not cheap, API/frontend files in use): a `chunk_stalled` job warning or a field in `compute jobs
    show/explain`. The API's warning code is a `Literal` with a generated frontend schema.
