## D452 - `--exclude-node <name>` refused when a REVOKED node has the same name

**Finding.** `compute run --exclude-node Mohit` exited `USAGE_ERROR` "matches 2 nodes": L3 re-joined
after its revoke (G9-B f) as a new node with the same hostname, and the old REVOKED row still matched.

**Cause.** `cli/job_commands.py _resolve_excluded` matched the name against every row of `GET /v1/nodes`,
revoked ones included. `--node` accepted only a canonical node id (no names at all).

**Fix.**
* The resolver moved to `cli/shared.py _resolve_node_refs(client, values, option)` - the CLI's **one**
  NODE-by-name resolver. Names and hostnames (case-insensitive) match only **non-revoked** nodes; an exact
  `node_<ULID>` is taken as is without a request (a revoked node's id too); none or several matches is still
  a usage error naming the option.
* `--exclude-node` uses it (`_resolve_excluded` is now a thin wrapper), and so does `compute run --node`,
  which now also accepts a laptop's name or hostname (resolved once the client is open, before upload);
  `--node NAME --exclude-node <same node>` is still refused.
* Not changed: `compute nodes NODE_ID`, `compute node revoke/gc/prepare` stay id-only - `compute nodes`
  has a pinned rule (tests `test_cli_g5_fix_round`, `test_cli_node_id_validation_tester`) that a non-id
  argument is refused before any request is built.

**Tests.** `tests/unit/cli/test_v1_0_g11_lab_fixes.py` (revoked twin ignored, revoked-only name unknown,
revoked id still works with no request, `run --node NAME` pins the live node, unknown name refused before
submit); existing `test_v1_0_g9b_exclude_node.py` unchanged and green.

**Lab re-run (L1, after v0.17.3).** With L3's old revoked row still listed in `compute nodes`:
`compute run <proj> --exclude-node Mohit -f` -> accepted, the job never lands on L3;
`compute run <proj> --node Mohit -f` -> runs on the re-joined L3 (`compute jobs <id>` shows its new node id).
Paste both job ids and the `NODE` column of `compute jobs`.

## D453 - `node_revoked` visible only in `--json`

**Finding.** After `compute node revoke` of L3 with a running job, the job failed `node_lost /
placed_node_offline`; the cause `node_revoked` was "visible only in --json attempts[].detail".

**Cause.** The job's own `failure_detail` is the placement reason (`placed_node_offline`, the pinned node is
gone); the revoke is recorded on the **attempt** (`failure_type node_lost`, `detail node_revoked`). Since
v0.17.1 (G9-B, `render.attempt_failure_text`) `compute jobs JOB_ID` does print the attempt's `failed` row,
and with the v0.17.2 payload it renders `node_lost: node_revoked` (re-checked) - but only in the attempt
block, under a label that renders unindented (`_cell` strips the leading spaces) so it reads like another
job field; the job-level rows at the top and the `compute run -f` end line (`job_... failed (node_lost)`)
never carried it. That is where an operator looks, so the cause was effectively hidden.

**Fix.** `render.job_failure_cause(payload)`: for a failed job, the last ended attempt's failure (highest
fencing token with a `failure_type`) as `attempt_failure_text`, when it says more than the job's own
`failure_type: failure_detail`. Shown as a `failure_cause` row right under `failure_detail` in
`compute jobs JOB_ID`, and appended to the `run -f` end line (`; last attempt: node_lost: node_revoked`).
Server text is scrubbed like every cell. `--json` is unchanged.

**Tests.** `tests/unit/cli/test_v1_0_g11_lab_fixes.py` (cause text, no row when it adds nothing or the job
did not fail, newest attempt wins, control characters scrubbed, `compute jobs JOB` shows one
`failure_cause` row, `run -f` end line names the last attempt).

**Lab re-run (L1 + one spare laptop).** Start a long job pinned to the spare laptop
(`compute run <proj> --node <laptop>`), then `compute node revoke <its node id>`. Expect
`compute jobs <job id>` to show `failure_cause | node_lost: node_revoked` under `failure_detail`.
Paste that table. (Re-join the laptop afterwards as in G9-B f.)

## D454 - `compute data rm` does not free the controller's disk

**Finding.** L1's disk was 96-99 % full; `compute data rm ds5g@3` removed the version but freed nothing.

**Cause.** The controller GC (`controller/gc.py`, V0.5 G5) is LRU **under quota**: it evicts only while the
store is over `[controller.gc] cas_bytes` (100 GiB) and never anything used within `min_age_s` (1 day). L1's
store was under quota, so removed datasets stayed until the quota was hit and a day had passed.

**Fix.**
* `ControllerGc.referenced()` - what any row still names, a superset of the existing `protected()` (both
  now share one query, `_references(every=...)`): the tree, bundle, split lists, chunk results, outputs and
  final logs of **every** job (finished ones too: `compute get` / `compute logs` read them), **every** named
  input (pinned or not) and every stored ML artefact. A finished job's `job_input` rows are history, not a
  reference: the input's own row owns its tree, so removing it can free it (rm stays refused while an
  unfinished job uses it).
* `ControllerGc.sweep(reason, dry_run=, among=)`: under `BlobStore.gc_guard` **exclusive** for the whole
  sweep (the same guard as a GC pass; a job submit and a named-input push hold it shared from their tree
  check to their row), it reads the references, then unlinks every stored blob not referenced and not used
  within the new `[controller.gc] sweep_min_age_s` (600 s - an upload, `have` answer or download in flight;
  same 10-minute floor OPERATIONS already advises for `min_age_s`). Each batch re-checks index pins/leases in
  its index transaction. Files are deleted only after the references were read; a push racing the sweep
  either lands first (its tree keeps the blob) or after (typed 409, never a broken tree).
* `DELETE /v1/data/{name}/{version}`: after the row is deleted (committed), sweeps **only** the removed
  tree's manifest and members (`among`) and answers `swept`, `freed_blobs`, `freed_bytes`,
  `kept_recent_blobs`. A failed sweep is logged (`controller.data.sweep_failed`) and leaves the blobs to GC;
  the removal itself stands. GC off -> `swept: false`.
* New admin endpoint `POST /v1/data/gc?dry_run=` (`DataGcOut`: `dry_run`, `removed_blobs`,
  `removed_bytes`, `kept_recent_blobs`, `kept_recent_bytes`, `failed_blobs`, `duration_s`) and
  `compute data gc [--dry-run] [--json]` printing `freed N blobs / X` (or `would free`). GC off ->
  `config_error`.
* `compute data rm` prints `freed N blobs / X on the controller` (+ a hint when recent blobs were kept).
* The hourly LRU pass and its 1-day `min_age_s` are unchanged (safety net). New `GcIndex.items()` /
  `members_of()` reads in `common/gc_index.py`. Logs: `controller.gc.sweep` (counts, bytes, duration).
* Docs: CLI.md (command + `--json` rows), OPERATIONS.md ("Freeing controller disk now"), ARCHITECTURE
  controller GC paragraph + config table, regenerated `docs/api/*` and the frontend OpenAPI contract.

**Tests.** `tests/component/controller/test_v1_0_g11_data_sweep.py` (real PostgreSQL + HTTPS controller):
rm frees only the unshared blobs and reports exact bytes; a blob shared with another (unpinned) input or a
finished job's project stays; a finished job's input history does not keep the input, an unfinished one
refuses rm; recently used blobs survive rm and `data gc` and are freed later; `data gc` dry-run counts and
unlinks nothing, the real sweep frees only an abandoned upload; token required; GC off; 8 rounds of a push
racing the rm sweep never register a broken tree. Unit: `test_v1_0_g11_gc_index_sweep_reads.py`, CLI rows in
`test_v1_0_g11_lab_fixes.py`.

## D456 - planner learns a per-node fixed chunk cost and a first-chunk cost

**Finding.** Lab round 10 (`origin/lab/L1:lab/coord/L1/REPORT.md` 2026-11-12 "G11 perf evidence", controller
journal granted -> committed per chunk): a Windows venv lane pays a fixed cost on **every** chunk (L4 ~20 s,
L2 ~10 s, L3 CPU ~11 s; L1 Linux Docker ~0) and 12-16 s more on its first chunk.
job_01M74WKXPN8V7XM1N9HEBYNZ6N (24 items, 2 a chunk, L1 + L2 + L4) took 51 s; the planner said 28 s.

**Cause.** `split.py` used **one** `chunk_overhead` per job (the median stage + upload of every chunk of the
fingerprint - dominated by L1's many cheap chunks, and blind to the env check, the process start outside
`run_ms` and the cold first chunk). Every lane was costed with it.

**Fix.**
* New pure module `controller/planner/chunk_cost.py`. Samples = the fingerprint's committed chunks per node,
  the **same** rows the D438 per-node item rate uses (latest `[controller.planner] history_runs` per
  (fingerprint, node)), plus up to that many latest **first** chunks of a lane (a lane has one, so they are
  rare in the latest window). Wall = `ended_at - leased_at` (both controller clock = grant -> commit); first =
  the lane's earliest lease (any outcome). Residual `r = wall - stage - items x s` (`s` = the node's
  seconds per item; stage is the item fetch, already the `items_fetch` term).
  `fixed_s = max(0, median r of non-first chunks)` (>= 3 samples); `first_s = max(0, median r of first
  chunks - that median)` (>= 1 sample; a first chunk whose env phase looks like a build -
  `env > 4 x steady env + 1 s` - is skipped: the planner's `env` term prices builds). Medians: a stalled
  or clock-stepped chunk does not move them.
* `queue_reads._chunk_history` reads the samples (one bounded query, window functions; no schema change)
  and `History` carries `chunk_fixed_s_by_node` / `chunk_first_s_by_node` (+ sample counts).
* Cost model (`split.py`): each `Lane` has `fixed` (its own `t_n`, else the shared `chunk_overhead`:
  history, then `[controller.split] chunk_overhead_s`) and `first` (else none). A chunk on `n` takes
  `c x per_item + t_n`; water filling uses `ready = start + first`; so lane time = `start + first + k x t_n +
  items x per_item`. Tail, risk, dominance pruning (now also compares `t`) and the one-lane chunk use the
  lane's own `t_n`; auto chunk size uses the **fastest lane's** `t_n` for the overhead rule. Prefix sets
  gain a third O(N) order (`per_item + t_n / c_ref`), identical to the rate order when every lane has the
  same `t_n`. Combine still uses the shared overhead.
* Explain: the `chunk_overhead` term keeps its name (CLI/UI unchanged); it now includes the rate-weighted
  first-chunk extras, its source is the weakest of the lanes' terms, and - only when some node's cost was
  learned - `detail.first_s` and `detail.per_node: {node: {fixed_s, fixed_source, fixed_from
  (node|shared), fixed_samples, first_s, first_samples}}`. `common/explain_text.term_note` renders it as
  `per chunk <node> 20.0s (n=12) +15.0s first (n=2), <node> 0.5s (shared)` (CLI + Plan tab, same function).
* Replay: the four history maps are optional keys (written only when not empty); the snapshot digest
  drops them when empty, so every older decision replays byte-identical (golden + ML-off golden green).

**Limitation.** `s` comes from the chunk process's run time, which on a venv lane includes the interpreter
start + imports; that part stays inside `s`, not `t_n`. At the history's chunk size the prediction is
exact; at a very different size the split is approximate. ADR-0024's per-chunk `spawn_s` (deferred) would
separate it.

**Lab case (unit test, `test_lab_case_*`).** History built from the round-10 per-chunk table (4-item chunks:
L1 6.3 s / first 6.5 s, L4 26.6 / 42.3 s, L2 31.5 / 43.2 s; run time = training + ~6 s import assumed on
the venv lanes) -> learned L1 0.0 s, L4 14.2 s + 15.8 s first, L2 3.9 s + 11.8 s first. The 24-item,
2-a-chunk job on L1 + L2 + L4: **predicted 42.2 s vs real 51 s (-17 %)**; the shared overhead on the same
history predicts 31.6 s (-38 %). The planner now picks L1 alone for that job (38.0 s), matching what the
lab saw (L1 ran 11 of 12 chunks, L2 none).

**Tests.** `tests/unit/planner/test_v1_0_g11_chunk_cost.py` (22: estimator clean / noise / outliers /
unusable / too few / first-chunk / env build / clamp; lane terms + fallback; lane-time formula; slow-start
node idle in a short job and less share in a long one; chunk size from the fastest lane's cost; unchanged
decision without learned costs; decision JSON + explain note; replay round trip + older replay digest; lab
case within 20 %). `tests/component/controller/test_v1_0_g11_chunk_cost_pg.py` (4, real PostgreSQL:
fixed + first per node, first chunk beyond the `runs` window, failed first lease, too few rows).
