## The G3 -> G4 interface (what the dispatcher glue needs)

**Input** - build `PlanRequest.split` with `meshforge.controller.planner.inputs.split_info(manifest,
item_count=job.split.item_count (or the remainder on a re-plan), item_bytes=job.split.item_bytes,
project_tree=job.tree_id, input_trees={mount: tree_id})` and pass it as `plan_request(..., split=...)`.
`None` for a whole job (nothing changes for those: rows, digests, decisions are byte-identical).

**Output** - `plan()` returns the usual `Decision`; for a split job `decision.split: SplitPlan | None`
(None only when nothing was chosen):

```python
SplitPlan(
    split: bool,                 # True = Mode 3; False = "don't split": ONE lane (same lane path, D269)
    lanes: tuple[LanePlan, ...], # fastest first, one per node; lanes predicted to get no chunk dropped
    chunk_items: int,            # items per chunk (last may be smaller)
    chunks: int,
    predicted_makespan_s: float, # == decision.chosen.estimate.total_s
    margin: MarginTest,          # set_s, best_single_s, best_single_node_id, margin, threshold_s, passed, forced
)
LanePlan(node_id, slot: "cpu"|"gpu", local: bool, rate_items_s, rate_source, start_s, active)
```

* `decision.chosen` is a normal `CandidateEval`: `mode` `local` / `offload` (one lane) or `split`;
  `chosen.node_id` = the first (fastest) lane, `chosen.slot` = that lane's slot; `chosen.node_set` = all.
  Each lane carries its **own** slot (GPU choice per lane is the glue's, like `choose_gpus` today).
* `decision_record(decision)` works unchanged (`chosen_node_id` = first lane). `split_json(plan)` in
  `planner/decision_json.py` gives the plan as JSON if G4/G8 want to store it (e.g. on the job).
* `decision.all_static_rejections` reads node rows only (set rows never fail a job).
* `split_too_small` (items < 2 x min_nodes) and pinned jobs never split; `chunk: {items: N}` is kept
  even on one lane (the entrypoint may rely on N).
* G4 still owns: the `no_split_support` feasibility (old agents; add it in `feasibility.static_rejection`
  guarded by `request.split is not None` - G3 did not, the capability name is G4's), removing the
  `SPLIT_NOT_SUPPORTED_YET` refusal in `jobs/planning.py`, and the config wiring below.

**Config wiring (not done - `jobs/planning.py` / settings are the glue's):** D275's knobs are
`SplitConfig(split_margin=0.10, target_chunk_s=20, max_overhead_frac=0.05, min_chunks_per_node=4,
max_chunks=10_000, chunk_overhead_s=1.5, tail_frac=0.5)` on `PlannerConfig.split`; defaults equal D275.
When `[controller.split]` gains them, `DispatchPlanner.__init__` builds
`PlannerConfig(..., split=SplitConfig(...))`. Until then the defaults apply. (I did not add settings
fields that nothing reads.)

**History (G8):** `History.item_rate_by_node` / `item_rate_samples_by_node` (chunk history: median of a
fingerprint's committed chunks' items / run s per node) and `chunk_overhead_s` / `chunk_overhead_samples`
are empty until `chunk_record` exists; the bounded one-statement query + its statement-count component
test belong with that table. Until then rates fall back to run history / scaled / assumed.

## Decisions / deviations (for the Lead)
1. **Water-filling start model instead of `max_n(T_stage + T_env)`.** Each lane starts pulling when its
   own stage + env is done; makespan `M` solves `sum max(0, M - start_n) x r'_n = items`. Equal starts give
   exactly D265's formula; unequal starts no longer charge one slow env build to the whole set. A lane
   predicted to start after `M` is `active: false` and is left out of `SplitPlan.lanes`.
2. **Per-chunk overhead inside the lane's rate** (`r'_n = c / (c (1/r_n + f_n) + t_o)`) instead of the
   serial `C(S) x t_overhead`: the serial form charges every chunk's overhead to the makespan although lanes
   pay it in parallel (it over-penalises splitting by |S|). Shown as its own term `chunk_overhead`.
3. **Per-item fetch `f_n`** (D264: a lane fetches only its chunks' items): `item_bytes / items` over the
   best source of the items' tree (fresh probe from a holder / controller history / default). The stage
   term is the trees **minus** the items. This is what makes the "slow link -> don't split" C5 case real.
4. **Tail term**: `max(tail_frac x longest chunk, end of the slowest active lane's first chunk - M)`.
   The second part is what stops "one fast node + slow ones" from splitting (a slow node's single chunk
   outlasts the fast node's whole run) - pull without speculation really behaves like that.
5. **Combine term**: `t_o` + the other lanes' share of the output (history) moved to the combine node
   (the submitter if a lane, else the fastest). Paid by single lanes too (same lane path), so it cancels in
   the margin test except for the parts transfer. `T_resolve` is 0 (resolved at submit, D260).
6. **Two orders of prefix sets**: by rate (D265) **and** by standalone time `start + items x per item`;
   deduped, still O(N). Rate-only prefixes were up to 180x off brute force when the fastest node had a long
   env build; with both: exact for equal starts (400 seeded cases N <= 5), <= 10 % with unequal starts
   (the residue is chunk sizing around an inactive lane). Each set's nodes are listed fastest first.
7. **Margin test vs the best single by prediction**, whatever the policy; when not splitting, the
   **policy's** single node runs (same as a whole job). For `cost_model` (default) they coincide.
8. **Rates**: chunk history (`history`, `from: chunk_history`) > the node's whole-run history / items
   (`history`, `from: run_history` - only valid if the glue feeds whole-job run times for the fingerprint)
   > another node scaled by hardware score with D131's least-work rule (`scaled`) > the fastest other
   node's rate as is (`history`, `scaled: false`) > `default_compute_s` for the whole job (`assumed`).
   Every term keeps the weakest source of what it was built from.
9. **Set rows** use `mode: "split"`, `node_id` = first (fastest) node; rows of a split job add
   `node_set`, `chunk_items`, `chunks`, and (single rows) `rate_items_s`, `rate_source`, `start_s` or (set
   rows) `inactive`, `margin_test`. Rows of a whole job are byte-identical to before (test). `reason_key`
   keys set rows by mode, not node.
10. **API/UI**: `CandidateOut.mode` gains `"split"` and the optional fields above (+ `MarginTestOut`);
   `frontend/openapi.json` + `schema.d.ts` regenerated; `PlanTable.tsx` row key includes `node_set`
   (set rows share their head's node id). The dashboard does not yet *show* sets - G7 (Chunks tab).
11. **D278**: `SplitLimits.max_list_bytes` (64 MiB, capped at `[controller.blobs] max_blob_bytes` by the
   controller glue) counted item by item while resolving - never below the real blob size (test: a cap one
   byte under the blob refuses for every `over` kind); `max_lines_file_bytes` 2 GiB -> **256 MiB** (still
   100 000 records of 2.6 KiB) instead of moving the scan out of the GC guard (smaller change, same bound
   on how long GC/submits wait); `MAX_SPLIT_ITEMS` docstring says the migration froze it.
12. Two new `RejectCode`s (`split_too_small`, `split_too_few_nodes`) are set-row codes, not in
   `STATIC_CODES`; `test_every_reject_code_has_a_case` (V0.6) lists them as covered by the G3 tests.
