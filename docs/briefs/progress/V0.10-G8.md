## Design (implementer decisions - for the Lead)
- **I1 One job, several run records; the job row.** `run_record` stays per attempt (ADR-0018: one write path,
  the reconciler). A split job's lanes and combine all get records (`attempt_role`), every one carrying the
  job's **first plan** and strategy; the **combine that ended the job DONE** is the *job row* and alone carries
  `split_makespan_ms` / `split_job_ms` / `split_combine_ms` / `split_ideal_bound_s`. No separate job-record
  table (a second write path for one row per job).
- **I2 Strategy of a split job = its first plan**: `mode3` if the rank-1 row of its first dispatched decision is
  a set, else `local` / `mode1` by that single lane - the same on every record of the job (the combine may run
  on the submitter while the lane ran elsewhere). A re-plan after all lanes were lost is visible in the chunk
  records, not in the strategy.
- **I3 Labels compare split jobs by `split_job_ms`** (first lane dispatched -> job end, controller clock):
  the label filter keeps `attempt_role` null / `run` / `combine` (lanes never count; the combine's
  `workload_status` is `ok` only on the job row), and `metric_value("total_ms")` returns `split_job_ms` for a
  combine row - `total_ms` keeps its meaning (the attempt's own phases). `LABELS_VERSION` unchanged (shape
  unchanged). Both job times are differences of two controller timestamps - one clock, not the agents'.
- **I4 Ideal bound from the job's own measurements** (D274 says "rates measured in the same session by
  single-node runs" - that is the lab's C2 procedure): items / sum over nodes of (committed items / committed
  `run_ms`) + the slowest lane's stage + env + the combine's run. Recorded per job so the dataset carries it;
  the lab may still compute the D274 bound from separate single-node runs.
- **I5 Workload identity of split benchmark jobs from the campaign run**: chunks write no
  `results/workload.json`; family / params / seed come from `bench_run` (the controller made the job), status
  `ok` on the job row. Its correctness rests on the per-chunk self-checks (a failed check exits 4 -> chunk
  fails -> retried elsewhere -> job FAILED: never "ok"). `compute_ns` is null for split families (honest:
  no single kernel time; the quality report counts it as a missing field for those configs).
- **I6 Built-in combines, not a check script.** D272 names `merge-csv` for csv_aggregate; the families use the
  built-ins (concat ×2, merge-csv, merge-json - all three exercised). Whole-output verification is library
  side (`SplitFamily.verify_output`, tests + lab), not inside the fabric.
- **I7 `csv_aggregate` aggregates per row** (sum/min/max + a SHA-256 chain per record): a per-chunk
  aggregate would make the combined output depend on the chunking and break criterion 1's identity.
- **I8 `image_classify` is CPU, integer arithmetic** (fixed int weights in [-8,7], int64 im2col matmul, shifts
  instead of floats): identical output on every laptop, so criterion 1 can be byte-identical across CPUs.
  D272's GPU variant is a follow-up (float GPU outputs differ across devices, §7 Q3).
- **I9 Chunk records** (`split/records.py`): a row per applied result (`committed` / `lost` / `failed`, the
  agent's measurements, verified output bytes, stderr tail) plus, at a commit, a row for every other lease of
  that chunk without one (`superseded` speculative copy, `expired`, `released`) - both copies of a speculated
  chunk are rows. A loser's late report **completes** its `superseded` row (only while `run_ms` is null - the
  one update a chunk record gets). Released results and fenced messages write nothing; chunks that never
  commit keep only their failed tries. PK `(job_id, chunk_index, lease_seq)`, no FK.
- **I10 stderr tail**: the agent sends the end of the redacted per-chunk tail (`[agent.split]
  chunk_stderr_tail_bytes` 16 KiB, proto bound 64 KiB - more is a refused message); the controller decodes
  (UTF-8, replaced, NUL dropped) and keeps 16 KiB of a failed try / 2 KiB of a done one (config) - bounded
  storage (10 000 chunks x 2 KiB). Bytes the live redactor still holds back (a possible secret prefix) are not
  in the tail: at worst the last few bytes are missing, never a secret. Never exported.
- **I11 Forced mode3 = `placement {"mode": "auto", "node_set": [...]}`** (API `Placement.node_set`, set only
  by the bench submitter). The planner restricts candidates to the set, splits over **all** of it whatever the
  margin says (`margin_test.forced = "node_set"`, the test still recorded), keeps idle-predicted lanes, and
  waits when a set node cannot take a lane (static refusal -> `no_feasible_plan`). `mode1:<node>` for a split
  family = the existing pinned "don't split". Campaign spec: `strategies: [mode3]` + optional `mode3_sets`
  (default: every selected node); mode3 only for split families; split families condition `none` only
  (conditions on lanes undefined in V0.10). `spec_digest`, run JSON and config ids are unchanged for specs
  without mode3.
- **I12 Runner**: a mode3 run counts against every node of its set (node load reads `placement.node_set` of
  live bench jobs; `submit_next` needs the whole set in the budget; `planned_nodes` includes set members).
  Cool-down after a mode3 job still keys on the run's head node only (residual, see follow-ups).
- **I13 Carry-over (d)**: the dashboard refetches `?map=true` at most once per 2 s per job with one trailing
  refetch and at once on job end (`applySplitEvent`). **Live-lanes-only `split.progress` not done**: the
  applier writes the event's lanes into the cached summary, so dropping dead lanes would hide them until the
  next refetch (which now happens only on count changes) - not cheap to do correctly; left for the >10-node
  fleet work.
- **I14 Carry-over (b)**: `SiteTimesCache` keyed by the queue's committed count read in the same request
  (a commit always invalidates - never a stale p50 after a commit), TTL `speculation_cache_s` 5 s (planner
  rates change on re-plan without a commit), LRU `speculation_cache_jobs` 256.
- **I15 Fixed a stale CLI JSON field**: `compute telemetry export --json` now adds `telemetry_schema` (from the
  new `X-MeshForge-Telemetry-Schema` header) and `table`; the existing `schema_version` is the `--json`
  contract's own, unchanged.
- **I16 Touched older tests** (version bump is the expected change): v2 pins -> v3 in 5 V0.9 tests, migration
  head 0029 (`test_store_migrations.py`, which also had a stale `down_revision == "0026"` assert), base
  metadata table list (+`chunk_record`), export spy signature.
