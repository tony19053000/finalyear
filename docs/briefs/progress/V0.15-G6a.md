## Deviations from the brief
- D375 places `classify.py` "pure: groups -> examples -> folds -> fit -> regret". Split in two because the
  groups/replays/calibrations live in the controller's database and the controller may not import an ML
  library (import contract `ml-libraries-only-in-ml-train`): the groups -> examples step (re-planning, the
  regret per class) is `planner_eval/classifier_examples.py` (pure, controller side), served by a new admin
  route; examples -> folds -> fit -> regret is `ml/train/classify.py` (the child). Same pattern as
  `ml dataset` -> `ml compare`.
- Two new admin routes (classifier examples, decision replay) -> `frontend/openapi.json` +
  `frontend/src/api/schema.d.ts` regenerated (generated files only; no frontend code touched). G6b also
  regenerates them: re-run `npm run gen:api` after merging both.
- D377 (4) "planner falls back per term (`predictor_error`/`ml_model_unavailable`)": with the artefact blob
  gone the model source cannot load the set at all (after the controller restart that empties its cache),
  so the **whole decision** plans with calibration (no `ml_model_version` on the row) and
  `in_use.unavailable` says why; `ml_model_unavailable` is what a **replay** of an earlier ML decision
  answers. A loaded set keeps serving from memory until the controller restarts (by design: the source only
  reloads on a version change or after a failed load) - the test restarts the controller.
- D377 (2)/(3): harness data is too small for the activation gate (`too_few_held_out`, 6 < 20 held-out
  rows), so the test asserts a recorded rejection reason and then promotes the set to `active` by SQL to
  exercise serving. The gate verdict on harness noise is not under test.
- D377 (6) is run right after training (before any new run ends) so the downloaded dataset has the stored
  set's digest: the real `fit` child twice -> the stored set version, `set.json` byte-identical; a second
  `ml train` is `no_new_runs` (the scheduled path never retrains unchanged data).
