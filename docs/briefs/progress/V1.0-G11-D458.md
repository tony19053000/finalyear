# V1.0 G11 - D458: cached venvs follow the agent's base interpreter across upgrades

Source: lab chat `origin/lab/chat:lab/chat/20261112-045140-*` (L4, Windows). Release target v0.17.3.

## Finding

After upgrading the Windows agent from 0.17.1-1 to 0.17.2-1 on L4, Mode 3 chunks ran
`C:\Program Files\MeshForge\0.17.1-1\python\python.exe`, the previous version's interpreter.

## Cause

* The Windows installer copies each version side by side (`{app}\<ver>-<rev>\`) and **never deletes the old
  folder** on an upgrade. It keeps the old folder so a failed upgrade can roll back to the old `python.exe`
  (G5), and only uninstall removes `{app}` as a whole. Windows has no `current` pointer (D385; the Linux
  package has `/opt/meshforge/current`).
* A venv's `pyvenv.cfg` `home` therefore named `...\0.17.1-1\python`. The venv env hash covered only
  `cpython-3.12.x` + platform, which is the same in both versions, so 0.17.2 reused the 0.17.1 venvs.
  The D451 `direct_python` then started `home\python.exe` directly, which was the old interpreter.
* The existing "home missing -> damaged" rule (V0.17 G4) never fired, because the old folder was still there.
  If someone deleted that folder by hand, every cached venv broke at once and had to be rebuilt.

## Fix

1. **The env hash names the base interpreter** (`agent/envs/hash.py`, `agent/envs/builder.py`,
   new `agent/envs/base_python.py`). `EnvInputs.interpreter` = sha256 of `[implementation, resolved
   real path of the base executable, full sys.version, platform tag]`. Only the digest goes into the
   hashed JSON, never the path. The field is included only when set, so Docker and `--target` hashes are
   unchanged and the golden hash tests still hold. The interpreter probe (one process per agent process,
   cached) now also returns `sys.version` and `realpath(sys._base_executable or sys.executable)`.
   A cache hit costs no extra process. Upgrades and rebuilt system Pythons give a new venv key, so the
   upgraded agent builds a new venv on its own interpreter. POSIX follows the same rule: the resolved
   path behind `/opt/meshforge/current/...` changes with each version, so each upgrade builds fresh
   venvs. The `current` path is still what `uv venv` is given (SP3 F2).
2. **A venv is never run on a missing or moved base.** At seal time the marker records `base_home` (the
   resolved `pyvenv.cfg` `home`). `env_state` returns `damaged` (evict + rebuild, log `agent.envs.base_moved`)
   when that `home` now resolves elsewhere, for example when `current` was re-pointed. The old rule is kept
   alongside it: a missing `home` folder also means `damaged`. The check compares against the recorded
   value, not the current interpreter's folder. uv rewrites `home` (verified: a managed Python's `home` is
   the `cpython-3.12-<plat>` alias, and a venv interpreter given to `--python` becomes its base), so a
   direct comparison with the current folder could rebuild in a loop. The hash already ties each key to
   one interpreter. `direct_python` shares the `pyvenv.cfg` parser (`base_python.pyvenv_home`).
3. **The agent GC evicts stale venvs, with or without a quota** (`agent/gc/collector.py`). Each full pass
   (one that reconciles) checks every `venv/<hash>`. Its base is stale when its `home` (or recorded
   `base_home`) is gone (`base_missing`), or when it lies in a MeshForge bundle other than this agent's own
   (`base_old`, judged by `BUILDINFO.json`). Stale venvs are removed under the same protections as quota
   eviction: not leased, not pinned, older than `min_age_s`, and taken under their build lock. Log:
   `agent.gc.stale_env_evicted` / `agent.gc.stale_env_kept`. A dev agent (no bundle) applies only the
   `base_missing` rule. A uv-found Python outside any bundle (e.g. `env.python: "3.11"`) is never `base_old`.
   Venvs from before D458 have no `base_home`. For them the resolved `pyvenv.cfg` `home` is used, so the
   0.17.1 venvs on L4 are recognised as `base_old`.

## What the installer does now (unchanged by D458)

* **Upgrade:** installs the new version next to the old one, re-points the service, and keeps the old folder
  for rollback. It still never deletes old version folders.
* **Uninstall:** removes the whole `{app}` folder. Data, including `envs/`, is kept unless the owner chooses
  "remove data". The kept venvs then have a missing `home`, so they are `damaged` on reuse and the GC
  evicts them as `base_missing`.
* **Linux package:** replaces `/opt/meshforge/<old>` and re-points `current`. Old venvs (keyed on the old
  real path) are no longer selected, and GC removes them (`base_missing` once the folder is gone, else
  `base_old`).

Old version folders are now safe to delete: after the first GC pass of the new agent, no cached venv points
into them. Automatic pruning of old version folders (for example, keep only the previous one for rollback)
is a possible installer follow-up. It is not done here.

## Tests

`tests/unit/agent/test_v1_0_g11_venv_base_interpreter.py` (18):
* key: different base path / full version / platform / implementation give a different key; the same base
  gives the same key; the identity uses the resolved path (POSIX `current` link); no interpreter gives the
  pre-D458 hashed form; a non-digest value is refused; `ensure_venv` keys follow the probed base; a 3-field
  probe still gets an identity; one probe per process (the cache hit spawns nothing).
* stale home: a missing `home` is rebuilt, never run; the marker records the resolved `home`; a `current`
  re-point makes the venv `damaged`; `direct_python` never returns a missing base.
* GC: `stale_base` rules (old bundle, own bundle, system Python, vanished, pre-D458 marker, dev agent, no
  `pyvenv.cfg`); old-base and vanished-base venvs are evicted with no quota and the current one is kept;
  a cheap (non-reconciling) pass does not judge; leased and young stale venvs are kept until free.

`tests/unit/agent/test_v07_g6_only_binary.py`: its fake interpreter gained `identity=""`.

## Lab check (L4, Windows)

Upgrade 0.17.2-1 -> 0.17.3-1, then run a Mode 3 job. Expected:
* the chunk processes run `C:\Program Files\MeshForge\0.17.3-1\python\python.exe` (Task Manager command line);
* the agent log shows `agent.envs.build_started` for a new venv hash;
* after the next full GC pass, `agent.gc.stale_env_evicted reason=base_old` for the old venvs;
* `findstr /s home "C:\ProgramData\MeshForge\envs\venv\*\pyvenv.cfg"` names only `0.17.3-1`.
