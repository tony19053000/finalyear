## D459 - a new workload's lanes fall back to the shared overhead

**Finding.** Big 480-item split predicted 557.4 s, real 558 s (D456 PASS). Small 24-item split run3
`job_01M77DM46NTQ3777EN6EDY18SP` (L1 + L2) predicted 38.3 s, real 52 s (+36 %): L2's chunk cost for that workload
was still `shared` 0.015 s although the big job had just measured L2 at 2.79 s fixed + 12.1 s first chunk.

**Cause.** D456 learns `fixed_s` / `first_s` per (fingerprint, node) only (`queue_reads._chunk_history`). A new
workload - or one with fewer than 3 steady chunks on a node, as the small split had on L2 - has no per-node
sample, so every such lane used the job's shared overhead (median stage + upload, ~0). Yet most of that cost is
the node's and its runtime's (interpreter start, venv activation, Docker exec), not the workload's.

**Fix.**
* `planner/chunk_cost.py`: `pooled_chunk_cost(samples)` - the same estimator and minimums over chunks of several
  workloads; each chunk's residual uses its **own** workload's seconds per item on that node (median `items / run
  s` of that workload's chunks), so a slow workload's items are never read as fixed cost.
  `expected_runtime(capabilities, base)` - the runtime kind the agent would pick (its docker > venv > subprocess
  order over the runtimes its capability tags offer that fit `env.base`). `with_node_history(...)` fills the new
  `History.node_chunk_*_by_node` maps for nodes without a fingerprint cost.
* `controller/jobs/planner_memory.py` (new): `node_chunk_history(db, nodes, runs)` - per (node, runtime kind) over
  the node's latest `history_runs` committed chunks of any workload plus up to `history_runs` latest lane-first
  chunks; runtime kind = the lane attempt's `attempt.runtime`. Bounded: a window of the latest
  `16 x runs x nodes` chunk records (cap 50 000, `recorded_at` index), a final row cap. Read only when the tick's
  batch has a split job (`read_fabric`).
* `jobs/planning.py`: a split job's request gets the node history for the runtime kind each node would use.
* `planner/split.py _chunk_terms`: order per node **fingerprint -> node_history -> shared (history) -> assumed**;
  `fixed` and `first` always come from one source (`first_s` is relative to that source's `fixed_s`).
* Explain: `per_node[].fixed_from` is `node` (= history) / `node_history` (+ `runtime`) / `shared`; the
  `compute explain` note labels each lane `history n=..`, `node_history venv n=..`, `shared` or `assumed`.
* Replay: the five `node_chunk_*` keys are written only when non-empty; absent = no node history; the digest
  leaves them out while empty, so every older decision replays byte-identical.

**Tests.** `tests/unit/planner/test_v1_0_g12_node_history.py` (pooled estimator with mixed rates, minimums, bad
rates; runtime prediction table; runtime-kind isolation; a node with its own cost untouched; fallback order;
decision JSON + explain labels; unchanged decisions without node history; replay round trip and older digest;
lab case: shared 38.1 s vs real 52 s, node history 48.3 s = -7 %).
`tests/component/controller/test_v1_0_g12_planner_memory_pg.py` (real PostgreSQL: pooling across fingerprints,
runtime isolation, the latest-runs window, too few rows, no runtime recorded, `read_fabric` wiring).

## D460 - the planner alternates local / split on identical runs

**Finding.** Runs 1-4 of the same 24-item workload chose local, split, split, local.

**Cause.** Two things. (a) In the recorded runs the alternation was mostly **feasibility**: L2 was `slots_full`
while its previous lane or speculated chunk still ran, so the split set lost (L1's report). That is correct and is
not overridden. (b) In general, two candidates of different modes within a few percent flip on every new
measurement's noise, and each flip pays cold starts the estimate does not see.

**Fix.** Mode hysteresis (`planner/hysteresis.py`, new): `PlanRequest.previous_mode` = the rank-1 mode of the
workload's latest **dispatched** decision of an unconstrained job (`planner_memory.previous_modes`: no
`node_id`, `node_set` or `exclude_nodes` in its placement; latest 8 per fingerprint read). If the new pick has
another mode and the previous mode still has a feasible candidate, the previous mode's best candidate is kept
unless the new best is at least `[controller.planner] mode_switch_margin` (default 0.10, 0 = off, max 0.5)
faster. Whole jobs (`plan.py`: the kept row moves to rank 1) and split jobs (`split_plan._hysteresis`: keeps
Mode 3 even below the split margin, or keeps a single over a set that passed it). Never applied to pinned /
`--local` / `--exclude-node` / forced-set jobs, rule policies, objectives other than `min_time`, ML-planned
decisions, refusals, or a set blocked by `require_measured_rates`. The chosen row carries `kept_mode {...}`;
`compute explain` / the Plan tab's sentence: `kept previous mode mode3 (new best local 40.10s within 10% of
42.00s)`. Replay: `request.previous_mode` written only when set, config `mode_switch_margin` only when > 0;
`PlannerConfig.mode_switch_margin` defaults to 0 so older replays decode to the planner without hysteresis.

**Tests.** `tests/unit/planner/test_v1_0_g12_hysteresis.py` (keep / switch at exactly 10 %, margin 0, first
decision unaffected, pins / exclude / objectives / rule policies untouched, refused previous mode not kept, split
keep-set and keep-single, blocked set never kept, determinism, replay byte-identical, corrupt replay refused,
explain sentence, setting bounds); component test above (`previous_modes`: pinned / excluded / waiting skipped).
