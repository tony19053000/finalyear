## G4 fix round 1 (tester r1 FAIL, tests `41effbdc`) - Lead decisions D367-G4 (numbered at merge)
- **D367-G4-1 (G4-R1-1): every term's `detail.ml` is in that term's own unit.** The one-lane split
  candidate's `compute` term used to carry the chunk rate's block (raw_s in seconds *per item*, so explain
  printed `ML 0.00s -> 4.64s` and `raw_prediction` returned per-item seconds). Now `split_plan._ml_lanes`
  keeps the rate blocks aside (no `ml` key in the Rate's detail any more) and `_ml_compute` gives each
  one-lane candidate's compute term its own `detail.ml`: the rate's used / reason / y_hat / interval, with
  `raw_s` = the analytical compute seconds (`items x` raw seconds per item - the raw planner's own formula),
  so `raw_s x e^y_hat == seconds`; the rate's block (seconds per item) is nested as `detail.ml.rate`, and
  `ml/targets._raw_seconds_per_item` reads the chunk_rate raw from there. (The Lead's suggested name
  `detail.ml_rate` was not used as a sibling key: the tester's oracle test strips only `detail.ml` when it
  compares ML-off and ML-on rows, so a sibling key would have broken it; nested under `ml` it is stripped
  with the rest.)
- **D367-G4-2 (G4-R1-2): warm-up at build.** `ml_input()` runs one representative batch (4 rows per modelled
  term: all-NaN, all-zero, two mixed) through the *unwrapped* predictor, outside the budget, before returning
  the `MlInput`. Any failure (raise, wrong row count, unreadable version) -> one
  `controller.ml.model_warm_up_failed` log line and `ml_input` returns **None** (the model is unavailable,

## Notes / design decisions taken here (for Lead review)
- **Two predict calls per Mode 3 decision, not one (deviation from "one call per decision").** Lane terms
  (`lane_stage`, `lane_env`, `chunk_rate`) must be corrected *before* sets are generated (chunk sizing, water
  filling, pruning and the margin test use them); a candidate's `combine` depends on its combine node and active
  lane count, which exist only after the corrected lanes are costed. So: one call for every lane term of every
  lane, then one call for every candidate's combine. Mode 1 is one call. The D363 budget is per call (so a split
  decision may spend up to 2 x 20 ms in the model); measured predict p99 ~5 ms per call.
- **Lane features describe the lane as its one-lane candidate** (`job_lanes` 1, `job_chunk_items` = the one-lane
  row's chunk): the set's shape depends on the corrected lane rates, so serving cannot know it first.
  **Resolved by D366 (Lead, Q-A accepted):** G1's dataset now gives a *set* decision's lane rows the same
  one-lane shape (`ml/targets._set`: `_plan_shape(lane_row)`; the combine keeps the set's lanes/chunk, live and in
  training), `FEATURE_VERSION` 2 (fingerprint `(1, 2)` published), `KNOWN_VERSIONS` = {(1, 2)}: a version-1 file is
  refused (exit 2) with "feature_version 1 datasets are not read since D366 ... rebuild it with `compute planner ml
  dataset --out FILE`" (no lab data exists, so nothing is lost). Parity is now bit-identical for every term with no
  exception (`test_v015_g4_parity` set-lane rows asserted exactly, `job_lanes` 1 asserted; the set's combine row
  asserted with the set's active lane count). Mutation **M11** (set-lane rows keep the set's shape) is killed by
  `test_dataset_rows_of_a_split_job_equal_the_live_queries[forced_set]`.
- **Extra reason `below_min_predicted`** (not in the brief's list): a raw term under the dataset floor
  (`MIN_PREDICTED_S` 0.05 s; `chunk_rate` <= 0) is never corrected - no training row was ever that small. Order:
  exact -> predictor_error -> no_model -> below_min_predicted -> ood -> interval_too_wide -> used.
- **The corrected term keeps its analytical raw as `detail.ml.raw_s`** (stored form, 6 decimals; `chunk_rate`
  = 1 / the row's rounded `rate_items_s`). `calibration.raw_prediction` reads it first, `ml/targets` reads a corrected
  lane rate's raw from the one-lane row's `compute.detail.ml.raw_s` (a one-lane row's compute detail is its rate's).
  Without this, the next training set would learn residuals of the *ML-corrected* prediction (and the
  calibration would fit factors on them) - a feedback loop.
- **D363 fallback = re-plan the whole decision** on the calibration path when anything of the model fails
  (raise, wrong row count, non-finite, lo > hi, |y_hat| > 50, budget exceeded, feature builder raising). The
  fallback session never touches the model (not even `has_model`), so it cannot fail again. `Decision.ml.error`
  holds the error's type name (`budget_exceeded`, `malformed_prediction`, ...); the dispatcher counts every one
  (`ml_predictor_errors`) and logs `controller.jobs.ml_predictor_error` at most once per 60 s.
- **The budget cannot pre-empt a synchronous call**: `BudgetedPredictor` measures the call and discards an
  over-budget answer (the plan uses calibration). It bounds what a slow model can *change*, not the time spent.
- **Replay of a fallback decision** stores `ml.fallback` and replays in the same fallback without needing the
  model (it would never be asked); a decision whose model was used needs the same version (`load(v)` must return
  an `MlInput` whose `version == v`), else `ml_model_unavailable` (Q23).
- **Q21:** `ml_model_version` is a key on every candidate row (like `pruned`), not a column; the API's typed
  models are unchanged (`detail` is free-form, so the stored `detail.ml` reaches the answer and the CLI). G5 adds
  typed fields + the Plan-tab rendering (and `ml_model_version` on `DecisionOut`) when it builds the UI.
- **`ModelSource`** (`controller/ml/predictor.py`): `async current() -> MlInput | None`, read once per tick by the
  dispatcher like `CalibrationSource`; a raising source keeps the previous model and logs. G4 ships
  `StaticModelSource`; server.py only gained `self.ml_source = None` and `ml=self.ml_source` (G3 sets it).
- **In-memory predictor** lives in `ml/train/memory.py` (it calls sklearn/LightGBM models, so the
  `ml-libraries-only-in-ml-train` contract puts it there; nothing outside `ml/train` imports it - tests do).
- **Pre-existing, not G4:** `uv run mypy src` reports one error in `bench/workloads/kernels/_support.py:161`
  (`no-any-return` from `import torch`) in this worktree env, which lacks the `gpu` extra (torch); the file is
  untouched by G4.
