# V1.0 G9 - lab fix group (L1's V0.4-V0.8 bug list) - plan + progress

Source: lab chat `lab/chat/20261105-005913-L1-to-LEAD.md` (bug list), triage `20261105-170000-LEAD-to-L1.md`,
evidence `origin/lab/L1:lab/coord/L1/REPORT.md` + `lab/reports/raw/2026-11-04-V0.5-data/*`.
Ships in **v0.17.1** (with F4-F6). Decisions D429-D435 (roadmap design change log).

## Root causes found by the Lead (from the raw evidence)

* **#1/#3 "first 5 GB Wi-Fi fetch always fails".** Two separate things:
  * (a) **No retry after the first minute.** `Executor._stage` computes its retry deadline as
    `staging start + staging_retry_s` (60 s). A 5 GB fetch takes 300-480 s, so the first transient error
    (`RemoteProtocolError` at 84 s / 95 s / 158 s on L2/L3/L4) finds the deadline already passed and the
    attempt fails `transfer_error` at once. The retry (next attempt) then resumes the verified chunks and
    succeeds - exactly the "first attempt fails, retry always succeeds" pattern.
  * (b) **Attempt 1 "all agents node_lost" was the controller's Wi-Fi link going down**, not heartbeat
    starvation inside MeshForge: lease misses are staggered (19:55:57.2 / 58.5 / 58.8), L1's *own* agent lost
    its lease too (19:56:14), and zeroconf logged `[Errno 101] Network is unreachable` on 192.168.31.13 at
    19:56:19. During attempt 2 there were short `lease_missed` (suspect, recovered) events while 5 GB flowed.
    MeshForge can only make the link less saturated and recover well (F4 already fixed the 4-min discovery gap).
* **#1 "failure_detail null".** The controller stores the agent's text on the *attempt* (`attempts[].detail`),
  but the CLI never prints an attempt's failure type or detail, and the job's `failure_detail` is (correctly)
  null for a job that succeeded on retry.
* **#6 revoke detail empty.** The code sets `detail = node_revoked` (`jobs/recovery.py::_offline`); most likely
  the same display gap. Must be proven by a test through the REST API.
* **#2 resume not shown.** `agent.cas.input_staged` (dataset line) has no `chunks_resumed` field.
* **#5 cuda-pytorch on no-Docker Windows.** The planner allows `cuda-pytorch` on a node with the subprocess
  runtime; on Windows that is the bundled interpreter, which has no torch -> `ModuleNotFoundError` -> `user_error`.
* **#7 env_known_bad.** `KnownBadEnvs` is keyed `(node, env key)` only; the owner's `[agent.envs]` policy is not
  part of it, so a policy change cannot clear it.
* **clock_uncertain every ~20 min.** Alerted on `consistent=false` alone while `bound_ms` was 60-81 ms (offset
  -11..+10 ms): an NTP slew/step between pings makes the intervals disjoint; the estimator already widens the
  bound to cover all of them, so the bound is the honest measure.
* **#8 Windows Live CPU.** Not root-caused (no Windows here). Hypotheses: the burn job was capped by a job CPU
  limit (owner `max_cpu_percent` / Job Object rate cap) so the machine total stayed near idle+cap; the 0 %
  sample = a failed/abandoned read reported as 0.

## Groups

### G9-A - agent data plane on Wi-Fi (#1, #2, #3)  [implementer -> tester -> reviewer]
1. **D429 staging retry window = time without progress.** `staging_retry_s` counts from the last try that made
   progress (>= 1 verified chunk/blob installed or bytes advanced), not from staging start. Same in
   `execution/lane_staging.py` and the input-staging path. A try with progress resets the window and the backoff.
   Log `agent.execution.stage_retry` gains `progressed`. Settings description + docs updated.
2. **`chunks_resumed`** on `agent.cas.input_staged` (and any transfer row the CLI shows, if it already carries it).
3. **D430 bulk data is background traffic (DSCP CS1)**, best effort: the controller's HTTP listener (blobs are
   served there) and the agent's peer blob server set `IP_TOS = 0x20` on Linux (accepted sockets inherit it);
   the agent's blob-fetch client sockets set it too (httpx `socket_options`). Windows: skip silently (needs a
   QoS policy). Setting `dscp_bulk = "cs1" | "off"` (default `cs1`) where each listener is configured. Never
   on the gRPC session port. A failed setsockopt logs once and continues.
4. **D431 optional fetch rate cap** `[agent.fetch] max_rate_mbit` (default 0 = off): one process-wide token
   bucket over all received blob bytes (TCP flow control slows the sender). For shared Wi-Fi labs.
Acceptance: unit tests with an injected clock for (1) incl. "error at 90 s of a 300 s fetch is retried and
resumes"; a real-socket test that a mid-body connection drop (server closes the stream) is retried and the
second try asks only for missing chunks; (3) `getsockopt(IP_TOS) == 0x20` on a real accepted socket (Linux);
(4) bucket math with a fake clock + one real loopback transfer slower than the cap allows unthrottled.

### G9-B - planner/controller/CLI (#1 display, #5, #6, #7, #10, clock)  [implementer -> tester -> reviewer]
1. **CLI shows attempt failures**: `compute jobs <id>` attempt rows add `failed <type>: <detail>`; `compute run -f`
   retry line `the attempt ended (transfer_error: <detail>)`. Component test: revoke a node with a running
   attempt -> REST `attempts[].detail == "node_revoked"` (fix the code if it is not).
2. **D432 torch is a probed capability.** Agent advertises `exec-torch` when the subprocess runtime's interpreter
   has torch (`importlib.util.find_spec`, no import). Planner: `cuda-pytorch` needs `exec-docker`, or
   `exec-subprocess` + `exec-torch` (reject `NO_RUNTIME_FOR_BASE`, message names "install Docker or PyTorch for
   the agent"). Agent defence in depth: such a job reaching the subprocess runtime without torch fails
   `env_error` (typed reason), never `user_error`. Check golden/replay decisions.
3. **D433 known-bad envs follow the owner's env policy.** Agent advertises an env-policy fingerprint (short hash
   of the `[agent.envs]` settings that change what builds: only_binary, indexes, ...); entries are recorded with
   the fingerprint seen then, and `is_bad` is false (entry dropped) when the node's current fingerprint differs.
4. **`compute run --exclude-node <id|name>`** (repeatable) -> API `exclude_nodes` (max 16): planner rejects
   those nodes with a typed reason shown by `compute explain`; persisted with the job so retries and controller
   restarts keep it; 422 when it excludes the pinned node.
5. **D434 clock alert on the bound only.** `clock_uncertain` alert + audit row only when `bound_ms > 250`;
   `consistent=false` alone is logged (info) and still shown in the API. Update docs that state the old rule.
6. UI Cancel button: done by the Lead (see below).

### G9-C - Windows live CPU (#8)  [implementer -> combined tester+reviewer]
**D435** the sampler computes system CPU from its own `psutil.cpu_times()` delta (no psutil module-global
state); a failed or abandoned read is reported as unknown/last-good, never as 0 %; Windows-specific test with a
real burn (CI windows runner) that system CPU rises above idle. Add `meshforge-agent doctor cpu` (or similar)
that prints 1 s samples + the owner's CPU cap for N s, for the lab re-run.
