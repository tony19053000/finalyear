Source: lab chat `lab/chat/20261105-005913-L1-to-LEAD.md` (bug list), triage `20261105-170000-LEAD-to-L1.md`,
evidence `origin/lab/L1:lab/coord/L1/REPORT.md` + `lab/reports/raw/2026-11-04-V0.5-data/*`.

## Root causes found by the Lead (from the raw evidence)

* **#1/#3 "first 5 GB Wi-Fi fetch always fails".** Two separate things:
  * (a) **No retry after the first minute.** `Executor._stage` computes its retry deadline as
    `staging start + staging_retry_s` (60 s). A 5 GB fetch takes 300-480 s, so the first transient error
    (`RemoteProtocolError` at 84 s / 95 s / 158 s on L2/L3/L4) finds the deadline already passed and the
    attempt fails `transfer_error` at once. The retry (next attempt) then resumes the verified chunks and
    succeeds - exactly the "first attempt fails, retry always succeeds" pattern.
  * (b) **Attempt 1 "all agents node_lost" was the controller's Wi-Fi link going down**, not heartbeat
    starvation inside MeshForge: lease misses are staggered (19:55:57.2 / 58.5 / 58.8), L1's *own* agent lost
    its lease too (19:56:14), and zeroconf logged `[Errno 101] Network is unreachable` on 192.168.31.13 at
    19:56:19. During attempt 2 there were short `lease_missed` (suspect, recovered) events while 5 GB flowed.
    MeshForge can only make the link less saturated and recover well (F4 already fixed the 4-min discovery gap).
* **#1 "failure_detail null".** The controller stores the agent's text on the *attempt* (`attempts[].detail`),
  but the CLI never prints an attempt's failure type or detail, and the job's `failure_detail` is (correctly)
  null for a job that succeeded on retry.
* **#6 revoke detail empty.** The code sets `detail = node_revoked` (`jobs/recovery.py::_offline`); most likely
  the same display gap. Must be proven by a test through the REST API.
* **#2 resume not shown.** `agent.cas.input_staged` (dataset line) has no `chunks_resumed` field.
* **#5 cuda-pytorch on no-Docker Windows.** The planner allows `cuda-pytorch` on a node with the subprocess
  runtime; on Windows that is the bundled interpreter, which has no torch -> `ModuleNotFoundError` -> `user_error`.
* **#7 env_known_bad.** `KnownBadEnvs` is keyed `(node, env key)` only; the owner's `[agent.envs]` policy is not
  part of it, so a policy change cannot clear it.
* **clock_uncertain every ~20 min.** Alerted on `consistent=false` alone while `bound_ms` was 60-81 ms (offset
  -11..+10 ms): an NTP slew/step between pings makes the intervals disjoint; the estimator already widens the
  bound to cover all of them, so the bound is the honest measure.
* **#8 Windows Live CPU.** Not root-caused (no Windows here). Hypotheses: the burn job was capped by a job CPU
  limit (owner `max_cpu_percent` / Job Object rate cap) so the machine total stayed near idle+cap; the 0 %
  sample = a failed/abandoned read reported as 0.

### G9-A - agent data plane on Wi-Fi (#1, #2, #3)  [implementer -> tester -> reviewer]
1. **D429 staging retry window = time without progress.** `staging_retry_s` counts from the last try that made
   progress (>= 1 verified chunk/blob installed or bytes advanced), not from staging start. Same in
   `execution/lane_staging.py` and the input-staging path. A try with progress resets the window and the backoff.
   Log `agent.execution.stage_retry` gains `progressed`. Settings description + docs updated.
2. **`chunks_resumed`** on `agent.cas.input_staged` (and any transfer row the CLI shows, if it already carries it).
3. **D430 bulk data is background traffic (DSCP CS1)**, best effort: the controller's HTTP listener (blobs are
   served there) and the agent's peer blob server set `IP_TOS = 0x20` on Linux (accepted sockets inherit it);
   the agent's blob-fetch client sockets set it too (httpx `socket_options`). Windows: skip silently (needs a
   QoS policy). Setting `dscp_bulk = "cs1" | "off"` (default `cs1`) where each listener is configured. Never
   on the gRPC session port. A failed setsockopt logs once and continues.
4. **D431 optional fetch rate cap** `[agent.fetch] max_rate_mbit` (default 0 = off): one process-wide token
   bucket over all received blob bytes (TCP flow control slows the sender). For shared Wi-Fi labs.
Acceptance: unit tests with an injected clock for (1) incl. "error at 90 s of a 300 s fetch is retried and
resumes"; a real-socket test that a mid-body connection drop (server closes the stream) is retried and the
second try asks only for missing chunks; (3) `getsockopt(IP_TOS) == 0x20` on a real accepted socket (Linux);
(4) bucket math with a fake clock + one real loopback transfer slower than the cap allows unthrottled.

### G9-D - "a long single chunk loses its lease forever" (L1 C10.10-c)  [implementer -> combined tester+reviewer]
**Root cause (not the lease).** The lab's `mc` folder (`lab/mode3_check.py build`) kept the benchmark
library's job time limit, `limits.timeout: 15m` (`bench/workloads/materialise.py` `JOB_TIMEOUT`). A split
job's time limit bounds **each chunk** on the agent (V0.10 G4; no whole-lane deadline), and a pinned
"don't split" run is one lane with **one chunk of every item** (D265). On L2 (~3.1 items/s) the 5000-item
chunk needs ~27 min, so the runtime killed it at 900 s (+ staging = the observed 07:29:56 -> 07:45:00) as
`deadline_exceeded`, and `agent/execution/lane_base.py` `CHUNK_FAILURE_NOT_RETRYABLE` did not list that type:
the chunk was reported **retryable**, its lease went `failed` (that is `failed_tries`, not an expiry) and the
queue gave the same, only chunk to the same, only lane again - from zero, every 15 min, until
`retry.max_attempts` (3, ~45 min). Leases, renewals (every 20 s) and the visibility timeout were fine: a
2-hour renewed lease on real PostgreSQL is never expired (new component test).

**D437 change.** (1) A chunk over the job's own time limit never runs again on the node where it timed out
(re-running starts from zero and meets the same limit). The agent reports it `deadline_exceeded`
(non-retryable); the controller decides (**D437 r1**, `controller/split/store.py` `_deadline_retryable` /
`_deadline_elsewhere`): retried while a live copy of it runs on another node (the copy is kept, never
released), else retried **once** if a live lane of the job sits on a node it has not failed on - that node's
lane gets it, the timed-out node's lane is excluded (`workqueue.store.lease_next(exclude=)`, also no
speculative copy there) - else final: the job fails `chunk_failed ... deadline_exceeded`. So a single-lane
(pinned / "don't split") run fails once; a second time-limit failure is final. If the other lane is lost
before it takes the chunk, the exclusion lifts (no hang): the chunk runs on the first node once more and
then fails for good. The per-node record is the chunk's `chunk_record` row (written in the same
transaction). The chunk's text says "the job's limits.timeout bounds each chunk; never re-run on this node -
raise limits.timeout in compute.yaml". (2) `mode3_check build` gives a lab job `limits.timeout` =
10 x the whole-job hint on the reference laptop (hint capped before rounding; whole minutes, >= 15 min,
<= 1 week) and prints it (`mc`: ~5340 s). (3) Hardening: the lane's renew loop survives a failed write (logged `agent.lane.renew_failed`; it
used to end silently for the rest of the lane). (4) `compute run -f` of a split job: a lane that ended `done`
followed by the combine prints "the lane finished; following the combine step (attempt N)", no longer "the
job was retried" (the log WebSocket retry frame carries `role` / `previous_role`); the web log view says
"the lane ... finished; following the combine step ..." too.
**By design, documented:** the per-chunk limit equals the job's limit, so a single-node run is bounded exactly
like the same job run whole (Mode 1) - never by anything shorter; a job slower than its limit on a node now
fails once and clearly instead of looping. Not done (follow-up): the planner does not compare a predicted
chunk time with the job's limit (the predictions are uncalibrated, x6.7 off in this run).

**G9-D2 (D440).** The 40P01 behind the soak flake is real PostgreSQL behaviour on the queue row's update chain,
not test timing: `ChunkStore.request` / `result` / `renew` / `expire` now re-run the whole transaction on `40P01` /
`40001` (bounded, jittered, logged `controller.store.conflict_retry`; `controller/store/conflicts.py`); the
`workqueue/store.py` "deadlock freedom" claim is corrected. Tests: `tests/unit/controller/test_v1_0_g9d2_conflict_retry.py`
(first try 40P01/40001 then OK; exhausted -> `JobStoreError`; other errors never retried; the real `ChunkStore.expire`
re-run; every writing op wrapped; the dispatcher loop survives store errors and runs the next tick); the soak test
passed 18/18 under 6 parallel runs.

### G9-E - tiny jobs must not be split on assumed rates (L1 C10.10-e, V0.10 part D)  [implementer -> tester -> reviewer]
**Root cause.** Job `hf` (60 items, ~0.8 s of real work) was split over 3 nodes. No run of the workload
was recorded, so `planner/split.py::item_rate` (the `if not others:` branch) gave every lane an `assumed`
rate (`default_compute_s` = 60 s for the whole job, scaled by hardware score: 1/s on L1, 0.57-0.78/s on the
others) -> ~66 s whole vs ~43 s split, and `planner/split_plan.py::_margin` passed the set on those numbers
alone. Second cause: the evidence that would have stopped it was never read - `History.item_rate_by_node`
/ `chunk_overhead_s` (the D265 chunk history) were never filled in production, and run history counts
`role = run` attempts only, so **a split job never had any history** (every "don't split" run is a lane).

**D438 change.** (1) `[controller.split] require_measured_rates` (default true; `SplitConfig`): a Mode 3
set whose every active lane's rate is `assumed` never passes the margin test - `MarginTest.blocked =
"rates_assumed"` (decision JSON / API `margin_test.blocked`, written only when set); the job runs whole
(Local / Mode 1, one lane). An ML-corrected assumed rate stays assumed. A campaign's forced `mode3` set
still splits (the block is recorded). (2) The dispatch read (`jobs/queue_reads.py::_chunk_history`) fills
the chunk history from `chunk_record`: per node the median `items / run s` of the latest `history_runs`
committed chunks of the fingerprint, and the median `stage + upload` per chunk - so the first ("don't
split") run is the evidence; the second decision uses measured rates (a tiny job stays whole on its own
per-chunk overhead, a long one splits). (3) `compute explain`, the web plan view and the margin sentence
show `fail: ... <= ..., blocked: rates_assumed` / "would pass only on assumed per-item rates - ... runs
whole and the next run decides on the measured time". Replay: the key is written only when true; absent
decodes to false (the planner that made every older decision) and the snapshot digest drops it when false,
so goldens and stored replays reproduce byte for byte; `REPLAY_VERSION` stays 2.
**Consequence (lab procedure):** the first run of a new split workload now runs on one node; a speed-up
measurement runs the workload once first (or uses a benchmark campaign's forced set).
Tests: `tests/unit/controller/test_v1_0_g9e_assumed_rates.py` (the hf fabric: whole with the default, split
with the switch off; measured tiny -> whole, measured long -> split; forced set; objectives; replay key;
explain texts), `tests/component/controller/test_v1_0_g9e_assumed_rates_pg.py` (real controller: first run
whole + blocked, second decision reads the chunk record as `history`, a long recorded rate splits over 3
nodes). Lane component tests that need a split on a first run set `require_measured_rates = false`.

### G9-F - PowerShell completion through the `.cmd` launcher (L2 C8.10-g)  [implementer -> tester -> reviewer]
**Root cause.** The installed `compute` is `C:\Program Files\MeshForge\bin\compute.cmd`
(`scripts/bundle_lib.py` `launcher_windows`). Windows runs a batch file through `cmd.exe /c`, so from PowerShell
the tree is `powershell -> cmd.exe /c ""...\compute.cmd" --install-completion" -> python`. Typer asks shellingham,
which returns the first ancestor that is a shell: `cmd` -> "Shell cmd is not supported." The explicit
`compute --install-completion powershell` did not help: with detection on, Typer's two options are flags, the
eager callback runs first and `powershell` was never read. Only `compute` offers completion
(`meshforge-agent` / `meshforge-controller` have `add_completion=False`), so only it is affected.

**D439 change.** (1) `meshforge/cli/shell_detect.py`: on Windows, walk python's ancestors (one Toolhelp
snapshot; cmd.exe command lines via `NtQueryInformationProcess` class 60) and skip any `cmd.exe` started with
`/c` (or `/r`) - it runs one command, so it is a launcher, never the user's shell; an interactive cmd (no switch,
`/k`) is the user's shell (a `.cmd` typed in cmd runs inside that same process). Unreadable command line: the
first such cmd is skipped only when the next shell above is PowerShell. Other OSes keep shellingham.
(2) `compute --install-completion <shell>` / `--show-completion <shell>` name the shell (taken out of argv in
`main`). (3) cmd.exe, an unknown or an undetected shell: one line ("tab completion is not available in cmd.exe
(Command Prompt) - open PowerShell and run `compute --install-completion` there") and exit 4, like every
completion install failure (D191 d). No launcher change, no installer change. The D187 PowerShell installer
(no `Set-ExecutionPolicy`, idempotent profile block) is unchanged.
Tests: `tests/unit/cli/test_v1_0_g9f_completion_shell.py` (fake process trees, `/c` parsing, Typer wiring,
end-to-end; on `unit (windows-latest)` a real `.cmd` launcher run from powershell/pwsh prints the PowerShell
script and from `cmd /k` gives the cmd line); `lab/windows/package_check.py installed` checks the installed
`compute.cmd --show-completion` from PowerShell (`package-windows` CI job); CI mypy `--platform win32` step.

**Lab re-run (L2, on the build with G9-F).** In Windows PowerShell (normal user):
1. `compute --show-completion | Select-Object -Last 1` -> `Register-ArgumentCompleter -Native -CommandName compute -ScriptBlock $scriptblock`.
2. `compute --install-completion` -> `powershell completion installed in C:\Users\<you>\Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1` (+ the "if PowerShell says running scripts is disabled" note); run it again; then `(Select-String -Path $PROFILE -SimpleMatch '# compute shell completion (MeshForge)').Count` -> `1`; `Get-ExecutionPolicy -List` unchanged.
3. Open a new PowerShell: `compute jo<Tab>` -> `compute jobs`; `compute jobs --<Tab>` lists options.
4. In `cmd.exe`: `compute --install-completion` -> one line "tab completion is not available in cmd.exe ...", `echo %ERRORLEVEL%` -> `4`.
5. If `pwsh` (PowerShell 7) is installed: steps 1-3 in pwsh (its own `$PROFILE`, `pwsh completion installed in ...`).

**Root cause of #8 (found in code, Windows confirmation pending - lab step below).** Neither hypothesis as
written: `psutil.cpu_percent(interval=None)` keys its baseline by `threading.get_ident()`, and the sampler runs
every sample on a **fresh** `DeadlineThread` daemon thread. glibc reuses the finished thread's ident (checked
here: 20 sequential threads, 1 ident), so Linux worked by accident; on Windows a new thread normally gets a new
id, so each sample compared two `GetSystemTimes` reads microseconds apart -> 0.0 (zero delta) or tick noise
(32/0/27/32 %), whatever the machine did, and psutil's dict grew one entry per sample (small leak).
* **Hypothesis A (job capped):** checked in `execution/plan.py` + `process.py`. A job with no `resources.cpus`,
  no `[agent.execution] default_cpus` (default empty) and no owner `max_cpu_percent` gets **no** CPU limit: no
  Job Object CPU-rate control is set. With `max_cpu_percent = P` the job gets `threads x P/100` cores and the
  Job Object **hard** cap holds the whole job (all its processes) at P % of the machine (L2's 50 % -> at most
  ~50 % + the owner's own load). `resources.cpus = C` -> `min(C, cap)` / threads. So A explains a lower-than-
  100 % reading on a capped laptop, not a near-idle one. No policy change made.
* **Hypothesis B (failed read as 0):** partly. A timed-out sample was already dropped (not sent); but a raising
  CPU read was sent as 0.0 with a degraded note, and the per-thread baseline above produced 0.0 readings.

**What changed (D435).** `agent/resources/cpu.py` `CpuMeter`: its own baseline (thread-independent, locked),
busy = (total - idle - iowait)/total, `guest`/`guest_nice` excluded (as psutil), small negative per-field
deltas clamped; typed unknowns `read_failed` / `backwards` (sum went down: rebase) / `no_time` (keep baseline) /
`short_window` (< 0.25 s since the baseline: keep it, do not read). Sampler: last good value reused <= 30 s
(`degraded` gets `cpu: stale (<reason>)`), else `cpu_percent = None` + `cpu: unknown (<reason>)`. Monitor: a
sample with unknown CPU is not sent (`MonitorStats.cpu_unknown`, warning on the 1st and every 100th);
`to_resource_update` raises `ValueError` for one. No proto change (the controller already shows "no sample" as
unknown). Effect: the first report after start waits one interval (the prime->first-tick window is < 0.25 s).
