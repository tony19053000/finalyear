## Fixes made in this run (found by the new tests / review of the first run's code)
1. `WINDOWS_IMPORT_CHECK` missed `win32con`, `win32gui` (used by `winservice_ops`): a bundle without them would
   have passed the build and failed at `setup`.
2. `windows_installed()` looked at `%ProgramData%\MeshForge\config`, which a normal user cannot even stat (the
   data root grants only SYSTEM/Administrators/service): the installing user's Start-menu launcher would have
   looked for a token in its own profile ("MeshForge is not running"). Now `current.txt` + the data root itself.
3. The upgrade health check matched only the JSON form `"agent.started"`; a migrated developer config with
   `[log] format = "console"` would have rolled every upgrade back. `log_has_agent_started` matches both.
4. `migrate-identity` typed by an elevated admin ran in user mode: any private file it wrote would have been
   the admin's only (service locked out). It now sets system mode, like the installer.
5. The installer's migration used `%USERNAME%` (the *administrator* under over-the-shoulder UAC); it now uses
   the session's user first, and `windows_home_of` finds `C:\Users\<name>` for that user (pure, tested).
6. `common.system_cli.apply` routed every program through the Windows branch: a developer's
   `meshforge-controller` on a Windows laptop with the agent installed would have warned about the agent's
   state. Now only programs with `windows=True` (the agent).
7. Planning's "sudo" prefix in the two-identities message used `sys.platform` while the rest used the model's
   flag (untestable mix): `admin_prefix()`.
8. Gate tests: the constant-time scan allow-list gained the installer's exit-code compares (and the launcher's
   changed `!=` line); the test-extras map knows pywin32 - only on Windows (`win32service`), because listing
   it everywhere made every `extras("agent")` test skip on Linux (16 tests, caught by comparing skip lists).

## Deviations from the brief (for the Lead)
- **No `.exe` launchers** (`meshforge-agent.exe`, `compute.exe`, `meshforge-console-open.exe`): `.cmd` launchers
  in the bundle + `.cmd` PATH shims in `C:\Program Files\MeshForge\bin`; the Start-menu entries run
  `pythonw.exe` directly. An `.exe` would have to be a uv/distlib trampoline, which embeds its interpreter path
  in a binary trailer and cannot pass `-I`. Effect: `meshforge-agent` / `compute` work from any prompt;
  "meshforge-console-open" is the Start-menu entry, not a command.
- **No pywin32 post-install step**: none is needed with `-I` (its `.pth` + `pywin32_system32` work as shipped);
  the build proves it by importing every module with `-I`. No registry writes.
- **Logs are files** (`logs\service.log`, `logs\agent.log`), not the Event Log (ARCHITECTURE table updated).
- **Job envs** live in `C:\ProgramData\MeshForge\envs` (the agent's `data_dir/envs` default), not under
  `cache\`; the root is service-modify, so it works; uninstall "remove all data" removes both.
- **Identity file owner**: the identity *folder* is owned by the service SID; files copied by the installer's
  migration are owned by the administrator who ran it (their ACL is exact: service + SYSTEM + Administrators).
  Administrators can take ownership of any file anyway; no extra rights result.
- **Health check** = SCM RUNNING + the console answers `/console/v1/health` + (joined laptops only)
  `agent.started` since the start. A laptop that has not joined never logs `agent.started` (the supervisor waits
  for the join), so requiring it would fail every fresh install.
- **Rollback** is the minimal one the brief asks for (previous `python.exe`, started, checked); G5 owns the
  rollback matrix.
- **Admin CLI on Windows runs in process** (elevated) instead of re-executing as the service (impossible for a
  virtual account) - as Q32 says; files it writes are made the service's.
- **CI fabric test** needs a controller with PostgreSQL on `windows-latest` (no Linux containers): the shared
  `postgres_server` fixture gained `MESHFORGE_TEST_PG=external` (the runner's preinstalled PostgreSQL,
  `postgres`/`root`). Test: `tests/cluster/test_v017_g4_windows_service_fabric.py`, runs only with
  `MESHFORGE_TEST_WINDOWS_SERVICE=1` on Windows.
- **CPU cap on Windows**: V0.7 G6 already enforces it with a job object hard CPU-rate cap (so `not_enforced`
  has no `max_cpu_percent`); the CI job proves it from inside a job run by the service
  (`QueryInformationJobObject` on its own job: enable + hard-cap flags, rate > 0).
- The `.iss` is additionally **compiled on Linux under Wine** (`tests/component/packaging/test_v017_g4_iss_compiles.py`,
  digest-pinned `amake/innosetup` image, Inno Setup 6.7.1; the builder pins 6.7.3).

## 🧑 Lab steps (Q34 laptop: Windows 11, NVIDIA, Docker Desktop, already joined via the dev task)
From the CI artefact `package-windows` (or a local build), copy `MeshForge-Agent-Setup-<ver>-1.exe` to the
laptop. Keep the controller laptop running the fabric this laptop joined.
1. Before (normal PowerShell in the dev checkout): `uv run meshforge-agent identity show` -> paste the node_id;
   `schtasks /query /tn MeshForgeAgent /fo LIST` -> paste.
2. Note the time, double-click the installer (SmartScreen: More info -> Run anyway; UAC: Yes). Paste the finish
   page text (or `C:\ProgramData\MeshForge\logs\setup-result.json`) and the time it took.
3. Elevated PowerShell: `meshforge-agent identity show` (expect the SAME node_id, and "acting on the MeshForge
   service's state"); `sc.exe qc MeshForgeAgent`; `sc.exe queryex MeshForgeAgent`;
   `schtasks /query /tn MeshForgeAgent /fo LIST` (expect Disabled). Paste all.
4. Controller laptop: `uv run compute nodes` -> this laptop CONNECTED, same node_id. Paste.
5. Reboot; sign in; wait 2 min: `sc.exe queryex MeshForgeAgent` (RUNNING, note PID);
   `Get-Content C:\ProgramData\MeshForge\logs\agent.log -Tail 5`. Sign out and back in: `sc.exe queryex
   MeshForgeAgent` (same PID). Paste.
6. Start menu -> MeshForge: the console opens; Checks page: paste the Docker, GPU, CUDA, firewall lines.
   Start menu -> "MeshForge - give Docker access" (UAC: Yes); open MeshForge again: Docker check ok. Paste.
7. Owner settings: accept jobs on, share GPU on. On the controller: submit a GPU job pinned to this node whose
   requirements install torch (CUDA build) and print `torch.cuda.is_available()` and a tensor on `cuda:0`
   (the V0.15 lab GPU job works). Paste the job output and `compute job show <id>`.
8. (Optional, a second Windows user) sign in as a non-admin user: Start menu -> MeshForge -> "request access"
   -> an admin approves in UAC -> the console opens. Paste what you saw.
9. Settings -> Apps -> MeshForge Agent -> Uninstall -> "remove all data?" No. Then elevated, in the checkout:
   `uv run python lab\verify_uninstall.py --os windows` -> paste (expect "clean", data kept).
