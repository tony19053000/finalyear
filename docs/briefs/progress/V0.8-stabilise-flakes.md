# V0.8 stabilisation lane - D200 + D156 flakes

Backend only. Lane owner: implementer (stabilisation). Status/roadmap untouched (Lead owns).

## 1. D200 - `test_peer_with_rotted_blob_on_disk_is_detected_per_chunk` (DONE)

**Root cause: the test's assumption, not production.** The fetcher's sources share
one work-stealing queue (D89); which source takes a given chunk is a scheduling
race. Instrumented 180 runs (spy on `TransferScheduler._fetch_chunk`):

* chunk 2 went to the **controller on every run** (the peer's two workers take the
  queue head 0, 1; the controller's two take 2, 3) - the rot on chunk 2 never
  mattered;
* chunk 9 went to the controller on ~1 run in 6 (orderings drift once the first
  responses land). Then the peer never sent a single rotted byte, so
  `corrupt_chunks == 0` and an un-dropped peer were the **correct** answers.

In every run where the peer served a rotted chunk it was counted and the peer
was dropped with `integrity_error` - no production miscount.

**Fix (test only):** every chunk of the holder's file has one flipped bit, so
the first chunk the peer serves, whichever it is, must be caught. The test is
now stronger, not weaker: it asserts the peer really served chunk bytes
(`served >= 2`: manifest + >= 1 range), `1 <= corrupt_chunks <= per_source`
(detected per chunk and dropped at once - at most its in-flight requests came
back bad), `dropped == integrity_error` (was only `is not None`), the peer won
0 units, served at most `1 + per_source` requests, the controller won all 16
units, and the bytes/CAS are right and clean.

**Evidence:** 25/25 consecutive standalone passes; whole file 20 passed, exit 0.

## 2. D156 - `test_fabric_outputs_logs::test_criterion_1` wss follow open TimeoutError (DONE)

**Root cause: a lost WebSocket handshake, not a tight timeout and not a slow
server.** It was already found and fixed in V0.7 G4 item 0 (`011e920`, D156 e);
the Known Bugs entry in STATUS was never cleared. The flake ran
`websockets.sync`, which reads the TLS socket from a background thread while
the caller writes the upgrade request: two threads in one OpenSSL connection.
With TLS 1.3 the server's post-handshake session tickets arrive exactly then
and the request or the 101 response is lost - the open then times out
whatever the budget. G4's fix: the CLI follows with the asyncio client (one
thread drives TLS) and the controller/peer TLS contexts send no tickets.

Re-verified today:

* **Mechanism still real** - with `num_tickets = 0` removed from
  `controller/server_tls.py` (temporary, restored by `git checkout`), the
  threaded client in `tests/cluster/test_v07_g4_ws_follow_tls.py` hangs with
  `TimeoutError: timed out while waiting for handshake response` despite a
  **10 s** open budget: 2/2 runs unloaded. (Under load 50+ it did not trip in
  1 run - the race is about interleaving, which is why the original flake hit
  only full-suite runs.)
* **Budget is not tight** - at HEAD under a CPU burner (48 busy processes on
  16 cores, load 52-62), the slowest of 40 wss opens per run was 0.063 / 0.050
  / 0.054 s against the default 5 s `[cli] timeout_s` (~80x headroom). So no
  timeout was inflated.
* **Repeated runs at HEAD** - under that load: `test_v07_g4_ws_follow_tls`
  3/3 (40 opens + 10 `compute logs -f` each), `test_fabric_outputs_logs.py`
  whole file 6/6 (3 passed, 1 skipped torch, exit 0 each, 145-223 s per run),
  plus `-k test_criterion_1_outputs` 12/12 (5 under load, 7 after). Not one
  open timed out.

**Change (keeps the failure honest):** when an open does time out (a really
overloaded controller or a slow network), `compute` used to print
`cannot follow the job's logs (TimeoutError)` typed `network_error`, and
`compute run -f` did not say the job was already submitted.

* `cli/follow.py`: only the open is bounded; an open timeout is now a typed
  `timeout` - "the log stream did not open within 5s - the controller may be
  overloaded or the network slow; retry, or raise [cli] timeout_s" (same hint
  as the REST client). A timeout after the open stays `network_error`.
  Exit code unchanged (6 UNAVAILABLE).
* `cli/job_commands.py` (`compute run -f`): any follow failure now adds
  "`<job>` was submitted and keeps running - follow it with
  `compute logs -f <job>`, or cancel it with `compute cancel <job>`".

**Regression tests:** `tests/unit/cli/test_v08_stabilise_follow_open.py` (5:
typed open timeout naming the budget; a post-open timeout is not called an
open timeout; `run -f` keeps-running note for timeout / network / auth
failures with the right exit codes), `tests/component/test_v08_stabilise_follow_open_real_socket.py`
(real asyncio client vs a real socket that accepts and never answers the
upgrade: typed timeout after ~0.5 s, no hang). `test_v06_g3_follow_retry.py`'s
fake `connect` is now awaitable like the real one. The existing cluster guard
`test_v07_g4_ws_follow_tls.py` catches the server half being reverted (shown
above).

**Commands:** ruff check / format --check clean, mypy src clean (321 files),
`-m unit` 11690 passed / 7 skipped / 3 xfailed, exit 0;
touched tests (`tests/unit/cli`, both component files) 1836 passed / 2 skipped,
exit 0. Whole component suite not run (per lane rules).
