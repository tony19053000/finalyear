## Decisions taken in the implementation (for the Lead)
- Install mode: `MESHFORGE_INSTALL_MODE` is not a settings field (prefix shared, ignored by the model). macOS
  system mode -> `ConfigError` (out of scope). Windows system dirs: data `%PROGRAMDATA%\MeshForge`, config
  `...\MeshForge\config` (G4 reuses).
- Bundle facts live in `common/buildinfo.py` (`common/bundle.py` is the existing project tarball module).
- F1: only the agent's own version (`3.12` / `3.12.14` / default) uses the bundled interpreter; other requests
  still go through `uv python find`. Dev venvs unchanged.
- F2: both fixes - the venv is built from `/opt/meshforge/current/...` (verified: uv keeps that path in
  `pyvenv.cfg` and the `bin/python` link), and a venv whose `bin/python` symlink dangles is `damaged`
  (rebuilt). Windows venvs (copied launchers, no pointer) are G4's problem.
- F3 interpreted as: the tool-env allow-list is pinned by an exact-set test (SSL_CERT_* stay: the *node's*
  own trust settings, kept on purpose since V0.7); a build host's environment cannot reach the bundle
  because the launchers run `python -I` and the unit sets the service environment.
- Migration: plan read-only, refuse all-or-nothing. A bad config blocks only when an identity is migrated
  (otherwise it is just not migrated, noted). `--from` + hidden `--root-dir`/`--service-user ''` for tests.
  `migration.pending` in the target makes `load_or_create` refuse (copying or blocked). Owner policy file
  (`policy.toml`) is NOT migrated (safe default; G3 wizard asks) - follow-up for the Lead.
- Q15: detection = `/etc/meshforge` AND `/opt/meshforge/current` (after `apt remove` the conffile dir stays,
  so `/etc` alone would redirect a dev). `MESHFORGE_INSTALL_MODE=user` is the explicit opt-out.

- **Path unit (deviation, brief item 5 says "enable --now"):** an agent that never joined exits 4
  `not_enrolled`, so on a fresh laptop "enable --now" would leave a *failed* unit. The service has
  `ConditionPathExists=/var/lib/meshforge/identity/node.crt` (fresh install = inactive) and
  `meshforge-agent.path` (`PathChanged=` on that file) starts it when `join` writes the certificate.
  `PathChanged`, not `PathExists`: a service that stopped itself (exit 4/5) or was stopped by an admin is not
  restarted behind anyone's back (tested: garbage cert -> exit 4, NRestarts 0, no loop). G3 (console must run
  before the join) will likely replace this with an in-process wait -> Lead decision then.
- **Re-install after `apt remove`:** dpkg passes the last configured version to `postinst` (looks like an
  upgrade) and prerm had disabled the units, so the re-install would have stayed stopped. `prerm remove` now
  writes `/var/lib/meshforge/.package-removed`; `postinst` treats its presence as a fresh install.
- **Debian version** of PEP 440 `0.1.0.dev0` is `0.1.0~~dev0-1` (`~~` so dev < a/b/rc < final, as in PEP 440;
  dpkg-checked in a unit test). The build revision `-N` (`--revision`) repackages one bundle (used for the
  upgrade test).
- **Depends** found by `ldd`, not guessed: `libc6 (>= 2.28), libcrypt1, libgcc-s1, libstdc++6, zlib1g, passwd`
  (+ Recommends `sudo`). `build_deb.py` fails if the bundle needs a system library not mapped/declared.
- **lintian:** 0 errors, warnings only (`maintainer-script-calls-systemctl` - we call systemctl directly rather
  than via debhelper snippets; `no-manual-page`; `initial-upload-closes-no-bugs`;
  `copyright-without-copyright-notice` - no license chosen yet). Overrides only for the bundled runtime under
  `/opt/meshforge/*/python/*`, each with its reason.
- `postrm` runs `systemctl reset-failed` (a failed unit would otherwise stay listed after removal; the verifier
  checks `systemctl list-units --all`).
- Migration message on a fresh laptop now says the identity is created "when this laptop joins a fabric".
- `lab/verify_uninstall.py` is stdlib-only and Python-3.10-compatible (runs with the laptop's own python3 after
  the package - and its bundled Python - is gone); one POSIX `sh` probe, `--docker NAME` for containers.
