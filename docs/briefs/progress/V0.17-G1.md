## Decisions taken in the implementation (for the Lead)
- Install mode: `MESHFORGE_INSTALL_MODE` is not a settings field (prefix shared, ignored by the model). macOS
  system mode -> `ConfigError` (out of scope). Windows system dirs: data `%PROGRAMDATA%\MeshForge`, config
  `...\MeshForge\config` (G4 reuses).
- Bundle facts live in `common/buildinfo.py` (`common/bundle.py` is the existing project tarball module).
- F1: only the agent's own version (`3.12` / `3.12.14` / default) uses the bundled interpreter; other requests
  still go through `uv python find`. Dev venvs unchanged.
- F2: both fixes - the venv is built from `/opt/meshforge/current/...` (verified: uv keeps that path in
  `pyvenv.cfg` and the `bin/python` link), and a venv whose `bin/python` symlink dangles is `damaged`
  (rebuilt). Windows venvs (copied launchers, no pointer) are G4's problem.
- F3 interpreted as: the tool-env allow-list is pinned by an exact-set test (SSL_CERT_* stay: the *node's*
  own trust settings, kept on purpose since V0.7); a build host's environment cannot reach the bundle
  because the launchers run `python -I` and the unit sets the service environment.
- Migration: plan read-only, refuse all-or-nothing. A bad config blocks only when an identity is migrated
  (otherwise it is just not migrated, noted). `--from` + hidden `--root-dir`/`--service-user ''` for tests.
  `migration.pending` in the target makes `load_or_create` refuse (copying or blocked). Owner policy file
  (`policy.toml`) is NOT migrated (safe default; G3 wizard asks) - follow-up for the Lead.
- Q15: detection = `/etc/meshforge` AND `/opt/meshforge/current` (after `apt remove` the conffile dir stays,
  so `/etc` alone would redirect a dev). `MESHFORGE_INSTALL_MODE=user` is the explicit opt-out.
