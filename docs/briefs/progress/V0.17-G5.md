## Deviations / decisions for the Lead
1. **Forced-failure trigger location (Q38 said "under the admin-only data dir").** It is
   `fail-upgrade-to` in the **program** folder: `/opt/meshforge/.upgrade/`, `/opt/meshforge/controller/.upgrade/`,
   `C:\Program Files\MeshForge\upgrade\`. On Linux `/var/lib/meshforge` is owned by the service account, which runs
   job code; a root maintainer script that reads or writes there can be redirected by a swapped folder or symlink.
   The program folders are root/Administrators-only by construction (the ProgramData root is service-modify on
   Windows too). One-shot: removed after the rollback it caused. The upgrade records (`state`,
   `rolled-back.json`, `interrupted.json`) live there for the same reason.
2. **`.previous` is a hard-link copy** (`cp -al`), not a byte copy: dpkg replaces files by rename, so the copy
   costs no disk (the brief's ~100 MB / ~520 MB for the controller) and survives the unpack; falls back to a
   real copy after a free-disk check, else an explicit "cannot switch back by itself" warning. `.previous` is
   deleted after a good upgrade (kept only while needed, or while it is what runs after a rollback).
3. **Version refusal reuses `REJECT_CODE_PROTOCOL_VERSION`** with the reason word `version_unsupported:` instead
   of a new enum value (proto comment updated, generated `.pyi` refreshed): the agents that are too old are exactly
   the ones that would not know a new code (they would retry forever), and every agent since V0.3 stops on
   PROTOCOL_VERSION. An unreadable `agent_version` (a hand-set string) is refused too. Controller `X.0` accepts
   any `(X-1).*`.
4. **Windows "will not stop during rollback" now writes `current.txt` = the new version** (the one the binPath
   names and that still runs) - the brief's invariant; G4 left `current.txt` on the old version while the SCM named
   the new one. The tester's G4 test `test_n1_...` was updated with a comment.
5. **Windows "migration raises during an upgrade"** now restores and starts the previous version (brief row 2); the
   G4 tests that pinned "neither version runs" (`test_a_migration_error_during_an_upgrade_...`,
   `test_n3_migration_failure_during_upgrade_...`) were updated to the G5 behaviour. A *blocked* migration (an
   identity question for the owner) still leaves the service stopped (Q13), unchanged.
6. **Linux "migration fails during an upgrade"**: `current` is re-pointed to `.previous` without a restart (the
   running process is the previous version; restarting it would hit the same identity refusal). The record says
   rolled back.
7. **Half-upgrade rule (Q39)**: another boot id + phase `unpacking` -> revert to `.previous` (dpkg may have deleted
   part of the old tree; the hard-link copy is complete); phase `configuring` -> let the new version start;
   same boot -> nothing (an upgrade is running). `dpkg --configure -a` (the repair run) finishes either way. On
   Windows the service cannot rewrite Program Files, so detection is the setup journal: the next installer run
   finishes, or reverts to the journalled interpreter.
8. **`meshforge-agent doctor` is new** (the brief names it; it did not exist): version/bundle, joined, last upgrade,
   the console's checks; exit 1 on a rolled-back or interrupted upgrade. It is an admin sub-command (re-executes as
   the service user via sudo on Linux; elevated on Windows).
9. **SDK quick start**: `meshforge.sdk` is still empty (Remote GPU SDK = roadmap 0.11.6). The page documents what
   works today - driving the fabric from Python through `compute` (`--json`, exit codes) - and says the SDK comes
   later. The page's program is executed by the cluster test.
10. **Screenshots**: console + dashboard taken by the agent from the real UI. The packaged controller's setup page
    is a lab TODO too (the e2e harness shows test paths and a loopback warning - not a user's view). Placeholders
    are listed in `LAB_SCREENSHOTS` (6 entries).
11. **Release version**: `pyproject.toml` stays `0.1.0.dev0`; the release workflow refuses a tag that is not
    `v<project version>`. Bumping the version is a release step for the team (see risks).
12. **ci.yml** edits are additive (two new jobs, one new types step, the header comment, `ci-ok` needs the new
    jobs). The verifier JSON of `package-linux` lands in `reports/verify-uninstall/` because the helper writes there

## Risks / follow-ups
- **Version bump hazard:** many tests hard-code `agent_version="0.1.0.dev0"` (Hello fixtures). With G5's rule
  they keep passing only while `[project].version` is a `0.1` version; bumping to `0.17.0` for the first release
  will make the controller refuse those Hellos (TOO_NEW). Before tagging: replace the literals with
  `meshforge.__version__` (≈ 20 places in `tests/`), or the release commit's CI goes red.
- The controller rollback starts the previous version with **this** package's unit file; a future unit change that
  the previous version cannot run under would need the old unit kept too (not needed today: the units only
  reference `current`).
- `dpkg --verify` reports `/opt/meshforge/current` as changed while a rollback is in effect (we re-point a
  dpkg-owned symlink); the next install resets it.
- Windows: a forced-failure trigger planted in Program Files by an Administrator only; no owner check (the folder
  ACL is the lock).
- `merge` note: the other CI-fix branch edits `build_bundle.py`/a G2 tester file; G5 touched neither.
