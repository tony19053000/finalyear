## Decisions taken in the implementation (for the Lead)
1. **Controller program dir `/opt/meshforge/controller/<ver>` + `/opt/meshforge/controller/current`**
   (not `/opt/meshforge/<ver>` like the agent): both packages can be installed on one machine (brief
   item 3) and dpkg forbids two packages owning `/opt/meshforge/current`. `stable_root()` works
   unchanged (`<parent>/current`).
2. **Controller config file `/etc/meshforge/controller.toml`** (unit sets `MESHFORGE_CONFIG`; the CLI
   re-exec passes the same): the agent keeps `config.toml` (G1 migrates it, G3's console edits it), so the
   two packages never edit one file.
3. **Controller CLI re-exec only for admin sub-commands** (`token fabric node user ca db doctor`): the
   bare command is the server; a human's `meshforge-controller` stays a developer server in their own
   state (a second server over the service's cluster would be refused by the managed lock anyway).
4. **Managed DB tests are `slow`** (like SP2's): they need the 39 MB bundle once (cached in
   `.cache/meshforge-pg`). `--run-slow` runs them; offline they skip with the reason.
5. **Q19 mirror URL is pinned but not uploaded yet** (needs a GitHub release on our repo - a human step,
   agents do not push): `https://github.com/tony19053000/finalyear/releases/download/pg-16.15.1/...`.
   The fetcher tries it first and falls back to upstream; the sha256 decides.
