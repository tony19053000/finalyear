## Design (implementer decisions - for the Lead)
- **I1 Chunks are the work items.** One work-queue item per chunk (payload `{"first","count"}`), queue
  `kind="mode3"`, `owner_id=job_id`, created in the dispatch tx; chunk size fixed at queue creation; a re-plan
  (D267e) reuses the queue (done chunks kept).
- **I2 Lane tokens.** Lanes of one round get tokens `attempt_epoch+1..+N`; the Mode 1 "current attempt" rule is
  bypassed for `role='lane'` (every lane of the round is current). Lanes never end the job by their own report.
- **I3 Job lifecycle.** QUEUED->PREPARING at dispatch; first lane RUNNING -> job RUNNING; **last chunk commit**
  -> parts index blob + `job.split_parts_digest` + RUNNING->COLLECTING->SUCCEEDED in the commit tx (the G4 stub
  of combine; G5 replaces the end with a combine attempt; the parts index = its ordered input). Chunk failing
  for good (`retry.max_attempts` tries or `[controller.split] max_failed_nodes`=2 distinct nodes, or
  non-retryable) -> job FAILED with the chunk's own failure type and detail `chunk_failed: chunk k failed on N
  node(s) (...)`, queue closed failed, every live lane gets CancelAttempt. No new FailureType value (avoids a
  proto enum + CHECK change).
- **I4 Lane end (D267a/d/e)** in the transaction that ends it: `release_holder` (uncounted). Last live lane gone
  with the queue open: cancel requested -> CANCELLED; else `retry_verdict` with attempts = lane rounds (1 +
  RETRYING arrows) -> RETRYING->PLANNING->QUEUED (new lanes for the remainder) or FAILED (queue cancelled).
- **I5 Grants / item list instead of input_entries.** ChunkGrant carries `first_item/item_count` + the slice
  digest (sha256 of the canonical JSON array of the chunk's items); the lane downloads the job's item-list
  blob once (its fetch token's scope includes it) and verifies it. The list (G1 format v1) already holds
  path+sha256+size per glob item, so `input_entries` would only repeat it (deviation from D264 wording, same
  effect).
- **I6 Unverified results.** A `done` digest the lane's grant did not store -> the lease is **released**
  (uncounted, chunk runs again) - never committed, never counted as a chunk failure (e.g. after a controller
  restart forgot the grant's history). Size over `max_chunk_output_bytes` -> chunk `output_error`, not retried.
- **I7 Late results** from a LOST lane are still offered to the queue (D267b: commits only if the chunk is not
  done) - from the lane's own node, own token, digest verified under its grant.
- **I8 Lane quota** (D261): base = `max_output_bytes/blobs`; `UploadGrants.raise_quota` adds
  `max_chunk_output_bytes` + 1 blob per newly granted chunk; a refresh after restart adds the live leases.
- **I9 Lane credentials live MAX_FETCH_TOKEN_TTL_S** (a lane runs many chunks); backstop skips lanes (each
  chunk's `limits.timeout` is enforced on the agent; a hung lane loses leases by visibility timeout).
- **I10 `ChunkRequest`/`LeaseRenew` are never acked/buffered** (controller UNACKED set); `ChunkResult` is a
  report with deferred ack (acked once stored, also when fenced).
- **I11 Lock order** everywhere: attempt row, job row, then work-queue rows (ADR-0019 addendum).

## THE G3 SEAM (read this when merging G3)
- `src/meshforge/controller/split/placement.py::plan_lanes(decision, snapshot, *, spec, item_count, max_chunks)
  -> LanePlan | None` is the ONLY placeholder. It takes the planner's ordinary Mode 1 `Decision` and returns
  `LanePlan(lanes: tuple[CandidateEval,...], chunk_items, split, reason)`: feasible-now, `exec-split` nodes in
  rank order, <= max_nodes, < min_nodes -> one lane ("don't split"); chunk = spec items or ceil(items/(4*lanes))
  (one chunk of all items when not split); capped by max_chunks.
- Caller: `jobs/planning.py::DispatchPlanner._decide_split` (builds the request with the shared `_request`
  helper - extracted from `_decide`, so G3's new request fields go in ONE place), then `_start` per lane
  (slot, GPUs, start snapshot) -> `DispatchLanes`. G3: replace `plan_lanes`' body (or the call) with the Mode 3
  plan object; put its decision JSON into `DecisionRecord` (today: the Mode 1 record with `chosen_node_id` =
  first lane). The chunk size only matters at queue creation (first round).
