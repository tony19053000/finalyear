## 3. CI flakes - root causes

**a. `test_benchmarks_heartbeat[nice10]` - product bug, fixed (D424, Lead to confirm).**
The controller and agent share one event loop in that test. CI log (run 40733787742, shard 1): heartbeats on
time for 7.3 s, then one 1.27 s gap, `lease_missed` + `lease_expired` in the same tick at `silence_s 1.274`,
agent BACKOFF. The benchmark child was really niced (sampled: all 16 BLAS threads at nice 10), so the gap is a
stall of the whole process (GC / runner steal), not CPU starvation by the benchmark. The lease timer judged the
lease the instant it woke from the stall, before the loop had read the heartbeats already waiting - the same
would happen to a real controller whose loop stalls (GC, VM pause, starved laptop): every node expired at once.
Reproduced deterministically: `time.sleep(1.3)` on the shared loop -> `controller:None` / `agent:BACKOFF`
(`tests/component/agent/test_v10_g7_loop_stall_keeps_online.py` failed before the fix, passes after).
Fix in `controller/session/leases.py`: if the timer wakes > 10 % of a heartbeat interval after its planned
wake-up **and** a lease event is due, it listens one interval, then judges; max 2 deferrals in a row (a dead
node is still expired, worst case + 2 intervals and only after a controller stall); `lease_timer.stall_deferred`
warning, `LeaseTimer.stall_deferrals` counter. The heartbeat test keeps the wip's event-loop-stall measurement
in its failure message.

**b. fresh-clone `test_identity_lock` "unraisable exception warnings" - test bug, fixed (wip b560af23).**
CI (run 40733787742) shows 5 `ReentrantCallError` from `multiprocessing.resource_tracker` at the setup of
`test_lock_blocks_next_epoch_and_reset_too`. 5 = the named semaphores of one `multiprocessing.Event`. The
previous test's `pytest.raises(...) as info` keeps a frame -> exception -> traceback -> frame cycle in which the
`lock_holder` Event lives; a later cyclic GC fired inside the next fixture's `ctx.Event()` while the tracker
held its lock, and each finalizer re-entered the tracker. The fixture now uses a `Pipe` (two fds, nothing
registered with the tracker). Product code uses file locks only.

**c. `test_grandchildren_are_swept_even_after_the_child_exits_by_itself` - test bug, fixed.**
CI timestamps show the test ended < 1.3 s after the supervisor returned, i.e. its 10 s wait loop exited at once
(`_gone` True) and the assertion right after read `_gone` False. Measured: after `killpg(SIGKILL)` an orphan
goes `running -> zombie -> dead ('X', being reaped) -> gone`, and psutil reports `STATUS_DEAD` in that window;
the helper counted only zombie/missing as gone, so it flipped gone -> alive -> gone (21 flips in 300 kills).
The supervisor did kill the tree. New shared `tests/_support/mf_procs.py pid_gone()` (zombie, dead or missing);
used by this test and the single-shot check in `test_v09_g4b_fix1_conditions.py` (which also had a
`pid_exists` -> `Process()` race). `test_v10_g7_pid_gone.py` fails with the old rule, passes with the new.
Other tests with the old rule only poll in a loop (a transient "alive" just polls again) - left as they are.
