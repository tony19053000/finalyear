## 1. `meshforge.cli` circular import (DONE)

**Cause.** The shared command helpers (`_settings`, `_client`, `_die`, `_fetch`, `JsonOption`,
`_checked_node_id`, the `--token-file`/`--ca` ContextVars, ...) lived in `cli/app.py`, and `app.py`
imports every `*_commands` module at its end to register them. `import meshforge.cli.job_commands`
(or any of the 8 command modules) first therefore re-entered a half-initialised command module.

**Fix.** The helpers move verbatim to a new leaf module `src/meshforge/cli/shared.py` (imports
`render`, `exits`, `settings`, `common` only; never `app` or a command module). Every command module
now does `from meshforge.cli import shared as cli` (same `cli.` call sites, looked up at call time);
`app.py` keeps the Typer app, the root callback, `nodes`, `status`, `_watch`, `main` and the
registration, and calls `cli._client(...)` etc. too, so one patch point (`shared._client`) covers every
command. Dependency direction: `app -> *_commands -> shared`. CLI behaviour unchanged; lint-imports
7 kept / 0 broken (the contracts are package-level).

Patch surface moved: tests that patched `meshforge.cli.app._client` / `_checked_node_id` /
`_echo_json` or called `app._settings` / `_stored_login` now use `meshforge.cli.shared` (7 files in
`tests/unit/cli/`). App no longer re-exports the helpers, so a stale `setattr(app, "_client", ...)`
fails loudly (AttributeError) instead of silently not patching. `lab/_fabric/api.py` (lab token/CA
helpers) switched to `shared` as well - found by the unit tier (`tests/unit/lab`, 32 failures before).

**Test.** `tests/unit/cli/test_v08_d202_import_order.py`: discovers every module under
`meshforge.cli` at test time (pkgutil) and imports each one FIRST in a fresh subprocess, then checks
the full command tree is reachable (21 modules + a non-vacuity check, 22 tests). Mutation: reverting
`job_commands` to `import app as cli` -> 21 failed. The "import app first" workaround in
`tests/component/test_v08_stabilise_tester_r1_follow.py` is removed (4 passed).

## 2. D200 rotted-peer test fails fast (DONE)

`test_peer_with_rotted_blob_on_disk_is_detected_per_chunk` wraps the fetch in
`asyncio.wait_for(..., 30)`; a timeout becomes `AssertionError("peer not dropped after a corrupt
chunk")` instead of the 120 s pytest-timeout. Mutation: `self.drop(source, error)` in
`agent/cas/scheduler.py` replaced by `pass` -> fails in 30.15 s with exactly that message; restored
with `git checkout src/meshforge/agent/cas/scheduler.py` (tree clean). Real code: whole file passes.

## 3. `compute run -f` on UNAUTHORIZED (DONE)

`job_commands._follow_failed_hint(job_id, failure_type)`: on `UNAUTHORIZED` the advice line says the
job was submitted and keeps running, that the controller refused this login for its log stream
(expired, revoked, or not allowed), and to log in again with `compute login`, then check on it with
`compute jobs` - no `compute logs -f` suggestion (it would be refused the same way). Every other
failure keeps the old hint. Exit code unchanged (3 AUTH). Tests in
`tests/unit/cli/test_v08_stabilise_follow_open.py`: a typed UNAUTHORIZED from `follow_logs`, and the
real `follow_logs` classifier on a 403 WebSocket handshake; both assert exactly 2 stderr lines, no
`logs -f`. Mutation: branch disabled -> both fail.
