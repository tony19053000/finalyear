# V1.0 G8 - two CI flakes from run 40799402426 (main, b775e7cf) - progress

Both are **test bugs**. The product behaviour is correct in each case and is unchanged. No `src/` change,
no migration. I root-caused and fixed each one (no retry, no skip). I reproduced each before the fix and

## 1. `tests/unit/controller/test_v07_g6_unbound_scores_expiry.py::test_the_loop_repeats_every_interval`

CI: job 123223695167 (fresh-clone, windows-latest): `assert 1 >= 2` on `FakeRegistry.cutoffs`.

**Root cause.** The test started `expire_unbound_scores_forever(interval_s=0.01)`, slept a fixed **50 ms**,
cancelled, then asserted at least 2 rounds. So it counted work done inside a wall-clock window. Any
event-loop stall of about 40 ms or more inside that window (a busy 2-vCPU runner in the middle of a 20k-test
run, GC, preemption) leaves 1 round. The product loop (`scores.py`: `while True: sleep(interval);
expire_once()`) is correct: it keeps going after failures and sleeps one interval before each round.

**Fix (test).** `FakeRegistry(rounds_wanted=3)` sets an `asyncio.Event` on its 3rd round. The test waits on
that event (`asyncio.timeout(30)` only bounds a hung loop), then cancels and checks that all cutoffs are
`now - max_age`. New companion test `test_the_loop_waits_one_interval_before_the_first_round` (interval
3600 s: no round runs at start-up) pins down the other half of the loop contract.

**Evidence.** Script `repro1.py` runs the old and new scenarios 100 to 300 times each:

| condition | old (50 ms window) | new (wait for rounds) |
|---|---|---|
| idle, loop clock quantised to 15.625 ms (Windows tick) | 0/300 fail | 0/300 fail |
| 8 busy loops pinned on the same CPU, test at normal priority | 0/200 fail | 0/200 fail |
| same CPU, test at `nice 19` (starved loop) | **99/100 fail** (rounds: `{1: 99, 2: 1}`, the CI signature) | 0/100 fail |

The real pytest files under the starved condition: HEAD's version FAILED, the fixed file `5 passed`.
Timer resolution alone does not reproduce it. A loop stall does.

## 2. `tests/component/controller/test_v10_g3_listener_auth.py::test_http_port_is_tls_and_every_api_call_needs_a_token`

CI: job 123223695296 (component shard 2): `BrokenPipeError: [Errno 32]` from `tls.recv(64)` in `_https`, on
the **foreign-fabric client certificate** probe.

**Root cause.** The HTTP port is `CERT_OPTIONAL` with the fabric CA (`server_tls.ssl_context`). A foreign
certificate is correctly refused. But under TLS 1.3 the client's handshake finishes *before* the server has
verified the client certificate, so the refusal shows up on the client's first read. `strace` of a failing
probe shows the sequence:

```
write(3, "\27\3\3\0P...", 85) = 85      # our GET (handshake already "done" client-side)
read(3, "", 5)                = 0       # server closed: no TLS alert
write(3, "\27\3\3\0\23...", 24) = -1 EPIPE  # OpenSSL sends its own alert on the unexpected EOF
```

* The server sends **no alert** because CPython 3.12 `asyncio/sslproto.py::_do_handshake` routes
  `ssl.SSLError` to `_on_handshake_complete` -> `_fatal_error` (abort) without `_process_outgoing()`, so the
  queued `unknown_ca` alert is dropped.
* Our request bytes reach the closed socket, and the server kernel answers with a RST.
* If that RST arrives before OpenSSL's alert write, the write fails with EPIPE and Python raises
  `BrokenPipeError`. Otherwise Python's `suppress_ragged_eofs` turns the EOF into `b""` (status 0).

The test accepted `ssl.SSLError` / `ConnectionResetError` / `b""` as refusal, but not `BrokenPipeError`. Its
sibling `_tls_outcome` already accepted it.

**Fix (test).** In the foreign-cert branch, catch `(ssl.SSLError, ConnectionError)` (`ConnectionError` covers
BrokenPipe, Reset and Aborted) and record the result as refused (0). A comment explains the three ways the
refusal shows up. The positive paths (`/healthz` 200, token-less 401s) still use `_https` unguarded. The
security assertion is unchanged: a foreign certificate gets no HTTP answer other than 401.

**Evidence.** Raw outcome tally of 2000 foreign-cert probes against one real `mtls` controller (LAN bind):

| condition | `status=0` (EOF) | `BrokenPipeError` | anything else |
|---|---|---|---|
| idle | 1868 / 1869 | 132 / 131 (6.6%) | 0 |
| 16 busy loops on 16 CPUs | 186 | **1814 (91%)** | 0 |

Then I called the fixed test function itself 300 times in a row: idle 300/300 OK, under the 16 busy loops
300/300 OK. Under the same load, HEAD's file FAILED and the fixed file passed.

## Follow-ups (not in scope)
- F1 (diagnostics, low): because of the asyncio behaviour above, a client with a wrong or expired certificate
  on the HTTP port gets EOF/EPIPE instead of a TLS `unknown_ca` / `certificate_expired` alert. Security is
  fine (no data, the connection is closed). But the CLI/agent error for "wrong fabric certificate" on the
  HTTP port may read as a network error. It is worth checking that `compute`/agent blob clients map EOF/EPIPE
  after the handshake to a typed "certificate refused" hint. The gRPC ports (BoringSSL) do send the alert.

### F1 implementation (in review, uncommitted)
- **What:** the agent's HTTPS clients (bundle/manifest/chunk/blob fetch, uploads) now show
  "<the controller | peer node X> ... refused this laptop's certificate - wrong fabric or expired certificate?"
  instead of a bare `RemoteProtocolError`/`ReadError`. Code: `src/meshforge/common/tls_refusal.py` (shared
  check + wording), `src/meshforge/agent/http_refusal.py` (`RefusalWatchStream`, wrapped round every TLS stream
  in `agent/http_connect.py`). TLS server behaviour unchanged. The CLI never presents a client certificate, so it
  cannot hit this case and is unchanged.
- **Rule:** only a *read* is evidence. Before the server's first byte, a zero-byte EOF/reset (or a refusal alert)
  is marked, provided everything we wrote on the connection is <= 64 KiB (`SMALL_REQUEST_BYTES`). A write error
  is never marked by itself (tester D1: an early `413` + close during a big upload). Large requests are never
  marked: measured, an early `413` + abort during a 64 MiB PUT reaches the asyncio client as a bare reset with
  zero bytes (10/10) because our own transport fails on its queued write and drops the answer unread.
- **Known heuristic limit (D2, accepted by the Lead):** a server that *accepted* the certificate but closes before
  sending any byte (crash, kill) looks the same on the wire and is reported as a refusal, with hedged wording
  ("... without answering: it most likely refused this laptop's certificate"). Pinned by
  `tests/component/agent/test_v10_g8_f1_edge_net.py::test_server_closing_before_any_byte_with_accepted_cert`.
- **Intended behaviour change:** a non-refusal raw `ssl.SSLError` on read/write (anyio lets it through httpcore
  unmapped) now surfaces as httpx `ReadError`/`WriteError`, a retryable network error, instead of escaping as an
  `OSError` (which `fetch_bundle` used to report as a local "cannot store the bundle" `internal_error`).

## F2. `tests/component/controller/test_stream_end_liveness.py::test_graceful_close_is_offline_at_once_and_agent_closed`

## F3. `tests/component/controller/test_v07_g3_tester_r2_cert_ends.py::test_a_certificate_with_milliseconds_left_never_leaves_a_zombie[1.0]`

CI: run 40871951455, component shard 3: `AssertionError: <StatusCode.INTERNAL: (13, 'internal')>` (the
test accepts UNAUTHENTICATED / UNAVAILABLE / CANCELLED). The controller log has `session.cert_expired`, then
`session.ends end_reason='cert_expired' state=offline`. The product ended the session correctly.

**Root cause (test bug: a grpc.aio client-side artefact, already known as D399 / V0.6 G4 / V0.7 G4).** The
controller never sends INTERNAL here. `SessionManager._cert_expired` (the `not_after` timer) closes the
session `cert_expired`, and the servicer ends the stream with `UNAUTHENTICATED` + `meshforge-reason:
cert_expired` (`session/servicer.py` `_CERT_ENDS`). The FakeAgent writes a heartbeat every 0.1 s. If a
heartbeat is in flight when the server ends the call, the send fails in grpc core (`Failed "execute_batch":
(<SendMessageOperation>,)`). grpc 1.84 `grpc/aio/_call.py::_write` then calls `set_internal_error`. That
sets the call's status, *on the client*, to INTERNAL `"Internal error from Core"` with **no trailing
metadata**, and the reader raises that status instead of the server's. A torn TLS/HTTP2 stream (RST_STREAM)
is not the cause: every reproduced INTERNAL had exactly these details plus a failed write of ours. The same
overwrite can also happen *after* the reader got the real status: the code is right, but
`trailing_metadata()` is empty afterwards (seen once in the provoked run below). That is a latent flake in
`test_the_cut_old_laptop_is_refused_again_at_every_hello` (it reads `meshforge-reason` with heartbeats
running), and in its `_hello_once` probe (the interceptor refuses the call while the Hello write is in
flight).

**Fix (tests only, no `src/` change).**
- `tests/_support/mf_session_client.py`: `FakeAgent.write` records the first `AioRpcError` a write raised
  (`write_error`). New `ended_by_client_write_relabel(agent)` is true only when the end is exactly INTERNAL
  `"Internal error from Core"` **and** a write of this agent raised that same error
  (`GRPC_CLIENT_RELABEL_DETAILS`).
- The zombie test accepts INTERNAL only through that helper. It now also asserts the controller's record
  (`wait_session_end_reason` == `cert_expired`) for every connected run, so the server's truth is checked
  directly. Before, only "no zombie" was checked.
- `test_the_cut_old_laptop_is_refused_again_at_every_hello`: `finish_heartbeats()` before the supersede
  (the pattern used by `test_supersede_racing_a_graceful_close_leaves_nothing_live`; liveness is tolerant,
  10 s lease). `_hello_once` probes again (max 5) only when the Hello *write* was relabelled. A refused write

## F4. Lab L4: a joined Windows agent loops DISCOVERING -> BACKOFF (`controller_not_found`) - product fix (in review, uncommitted)

Source: `origin/lab/L4` `lab/coord/L4/REPORT.md` "C17-e (recheck)". Windows 11 laptop L4, installed v0.17.0 agent.
The console join with an invite code worked (enrolment listener 192.168.31.13:47101 reachable,
`Test-NetConnection` True). Afterwards the service logged `agent.discovery.none` (service type
`_meshforge-ctl._tcp.local.`, timeout 5 s) and `controller_not_found` 198 times. L3 (another Windows laptop)
connected fine.

**Root cause (product).** `agent.controller_address` was empty, so `resolver_for` returned `MdnsResolver` only
(`agent/discovery.py`). The join learned a working unicast address (the code's host), but nothing kept it:
`enrollment.join` stored only `ca.crt` + `node.crt`, and the session port was not known to the agent at all.
The join code names the **enrolment** port (47101), not the session port (47100), and `EnrollResponse` had no
session port. So one machine whose mDNS answers do not arrive had no way to connect, although unicast worked.

**Decision (ADR-style).**
- *Context:* mDNS is best-effort. Multicast is filtered by some Wi-Fi adapters, APs and firewall profiles.
  Unicast TCP to the controller is the path that actually matters.
- *Decision:*
  1. Contract first: `EnrollResponse.session_port` (`uint32`, field 5, additive). The controller fills it with its
     bound session port (`ControllerRuntime.grpc_port`, read per call; 0 before the session listener is bound).
  2. `agent/known_controller.py`: `controller.json` in the **identity directory** (not `config.toml`):
     `{"format": 1, "address", "source": "join"|"session", "updated_at"}`. It is written at join as
     `<host the code named (or the console's pick)>:<session_port>`. It is rewritten after every **accepted**
     session whose address differs, which means only after mTLS against the pinned CA succeeded. It is deleted by
     `identity.reset` (leave / reset). A re-join to a controller that sends no port deletes the old hint, so a hint
     never outlives its fabric. Writes run under the identity lock and are atomic. Every failure is logged and
     swallowed (the hint is an optimisation, never a reason to stop).
  3. Resolution order: **`controller_address` > mDNS > last-known** (`LastKnownFallbackResolver`, used whenever
     the client has an identity dir). The hint is re-read on every cycle, so a console join in the same process
     is seen by the next cycle.
- *Why mDNS before the hint (and not hint first with an mDNS refresh):* when the controller's DHCP lease moves
  it, mDNS (where it works) has the new address on the first cycle. A hint-first agent would dial the dead
  address first: a connect timeout plus a backoff on every reconnect until something refreshed it. The price of
  mDNS-first is one browse timeout (`agent.discovery.timeout_s`, 5 s) per reconnect on machines where mDNS is
  broken. That costs only at (re)connect time and never while ONLINE. When both fail (mDNS silent and the
  controller moved), it is the old BACKOFF loop. The troubleshooting entry gives the workaround
  (`controller_address`, plus a DHCP reservation).
- *Alternatives rejected:* (a) write `controller_address` into `config.toml` at join. That file is the owner's,
  and a pinned address would disable mDNS, so a DHCP move would break the node for good. (b) remember only after
  a successful session. That does not fix L4, which never had one. (c) assume `<enrol host>:47100`. That is wrong
  for any non-default `grpc_bind` port. (d) fold `Enroll` into the session port (the old G3 plan). That is a
  bigger change in the listener/mTLS design and out of scope.
- *Trust (unchanged):* the hint is only a dial target. The session channel still verifies the controller against
  the fabric CA (`load_session_tls`) and presents the node certificate, exactly as for an mDNS answer. A tampered
  `controller.json` (in the owner-only identity directory) can at worst cause a failed dial, never a trusted
  connection to a wrong controller.
- *Consequences:* an agent of this version joined to an **older** controller (no `session_port`) gets no join-time
  hint. It still gets one after its first accepted session. A controller of this version and an older agent:
  the field is ignored (proto3). **Existing enrolments** (joined with v0.17.x, like L4 now) have no
`controller.json`. They get one at their first accepted session, so on a laptop where mDNS is silent this takes
one re-join, or one connection with `controller_address` set (which can be removed again afterwards). User-facing
upgrade note in `docs/user/troubleshooting.md`: "enrolled before V1.0 (v0.17.x): set controller_address once (or
re-join); after one connection you can remove it". `join --force` deletes the old hint *before* it stores the new
pair, so a crash in between can never leave the old fabric's address next to the new enrolment (review point 2).
Decision log: D427 in `docs/DEVELOPMENT_ROADMAP.md`.

**Wrong-port hint (coordinator request).** The join code names the enrolment port (47101). An owner who copies that
into `controller_address` used to get a silent reconnect loop: the enrolment listener presents the fabric server
certificate, asks for no client certificate and answers `Session` with `UNIMPLEMENTED`, which is classified as
transient. Now `resolver_for` logs `agent.discovery.enroll_port_configured` when the configured port is 47101, and
the session client logs `agent.session.not_a_session_port` once per address on an `UNIMPLEMENTED` stream end
(the same text, `discovery.ENROLL_PORT_HINT`, naming `<ip>:47100`). It still retries, because a controller in the
middle of an upgrade can answer the same way. The default ports now live once in `common/netaddr.py`
(`CONTROLLER_SESSION_PORT`, `CONTROLLER_ENROLL_PORT`), and the controller's `DEFAULT_GRPC_PORT` /
`DEFAULT_ENROLL_PORT` alias them.

**Windows firewall / service account (finding, no rule added).** python-zeroconf's browser sends its **first**
query as QU (unicast-response requested; `zeroconf/_services/browser.py`, 0.151.3) and the later ones as QM
(multicast responses to 224.0.0.251:5353). Windows Defender Firewall lets a unicast reply to our own multicast
query through for about 3 s ("allow unicast response to multicast", on by default), with no rule needed. Multicast
replies (QM) need an inbound UDP 5353 allow rule that covers our program. As far as I know (not checked on a
Windows machine), the built-in "mDNS (UDP-In)" rule is scoped to the DNS Client service (`svchost.exe` /
`dnscache`). A service (`NT SERVICE\MeshForgeAgent`) never triggers the "allow this app" prompt. A per-user copy
run earlier in a terminal can have created a per-program allow rule from that prompt, which could explain L3 vs
L4. The Public network profile and Wi-Fi client isolation are other candidates. The installer adds no firewall
rule (only the peer-port rule, and only when peer serving is on, D389). With the last-known fallback a joined
agent no longer depends on mDNS, so **no rule is added**: an inbound UDP 5353 allow would widen the attack surface
for a convenience that is now optional. If the lab shows that even the first-time console discovery list is empty
on such laptops, revisit with a rule scoped to the agent program and the Private profile (needs a Lead decision).

**Code:** `proto/meshforge/v1/enroll.proto` (+ regenerated `enroll_pb2.py[i]`, `docs/api/grpc.md`),
`controller/enrollment/listener.py` + `controller/server.py` (fill `session_port`), `agent/known_controller.py`
(new), `agent/discovery.py` (`LastKnownFallbackResolver`, `resolver_for(identity_dir=)`), `agent/session/client.py`
(pass the identity dir; `_remember_controller` after the Reconcile of an accepted stream, lock wait <= 1 s),
`agent/enrollment.py` (store/clear at join; `JoinResult.session_address`), `agent/identity.py`

never connects").

**Tests.** `tests/unit/agent/test_v10_g8_f4_known_controller.py` (29: the 47101 configured-port hint, file round trip, no rewrite when unchanged,
damaged file ignored and repaired, bad address never stored, reset deletes, join store/IPv6/port-0-clears, resolver

## F5. Lab: "Run jobs" turned on after the agent connected is never honoured - product fix (in review, uncommitted)

Source: lab (installed v0.17.0), `lab/coord/ANNOUNCE.md` 2026-11-03 (5). Owners turned on "Run jobs" (and, on
L2/L3/L4, "Allow jobs without a container") in the agent console **after** the agent had connected. The
controller logged `session.policy_updated accept_jobs=true`, yet every `compute run --node <id>` got 409 "the node
does not accept jobs (its owner has not enabled [agent.policy] accept_jobs)". A node restarted after the switch
worked (L4 ran a hello job).

**Root cause (both sides).**
- *Agent:* `execution/offer.py build_execution` returned `disabled_setup()` when the start-up policy had
  `accept_jobs = false` - no runtime probed, none built, no `exec*` tag in `Hello.hardware.capabilities` - and built
  the subprocess/venv runtimes only with `allow_unsandboxed = true` at start. A live `PolicyUpdate` changes the
  policy and slots, never the capabilities or the runtime set, so even an allowing controller would have had
  nothing to run the job with (documented as "needs one restart"; the console offered it as `restart_needed`, the
  wizard path did not).
- *Controller:* `planner/feasibility.static_rejection` refuses `NOT_EXEC` when `exec` is missing, with a text that
  blamed the owner even though the live policy said jobs were on. Separately, the submit-time checks
  (`jobs/placement.check_placement` / `check_auto`) used the Hello's slots, not the session's `PolicyUpdate` slots
  the planner uses, so a GPU switch flipped live was judged differently at submit and at dispatch.

**Decision (D428, proposed - Lead to record in the decision log).** *What a node CAN run* (capabilities) is
separate from *what its owner ALLOWS* (the live policy).
1. The agent probes every runtime at start whatever the policy says (Docker, subprocess, venv, CPU cgroups) and
   advertises `exec*` (+ `exec-split`, `exec-gpu`) for what it found. Probing is not executing: nothing of a job is
   fetched, built or run while `accept_jobs` is off.
2. ALLOWS is checked live everywhere: the executor's `plan_attempt` (unchanged: `policy_denied:policy_not_accepting`,
   unsandboxed runtimes skipped when not allowed), `compute node prepare` (new: `PrepareService(policy=...)` fails
   every item `unauthorized`/`policy_not_accepting`, never builds with an unsandboxed runtime when it is not
   allowed: `policy_unsandboxed`), and the controller (unchanged planner `policy_rejection`; the submit-time checks
   now take `LiveSession.policy_slots`).
3. `RESTART_KEYS` is empty; `policy set` and the console's `restart_needed` no longer ask for a restart.
4. Fail-closed unchanged: a broken/unsafe live file or a bad `PolicyUpdate` is `DENY_ALL` with `(0, 0)` slots.
5. Turning Run jobs **off** is live: the next plan/submit is refused `policy_not_accepting` (a pinned queued job
   fails `node_rejected_policy_not_accepting`, a static rejection as before); an attempt already sent is refused by
   the agent.
- *Old-agent compatibility:* an agent older than this fix that started with jobs off really has no runtime, so the
  controller cannot admit it on a live `accept_jobs = true` (no version sniffing). It keeps `NOT_EXEC`; when its live
  policy says jobs are on the text now says so ("the node's agent has no runtime ... an agent older than V1.0 that
  started with Run jobs off needs one restart"). The old text is kept in every other case so the golden planner
  corpus (V0.14/V0.15 byte-for-byte replay) is unchanged. An old controller with a new agent already behaves
  correctly (it sees `exec` and applies the live policy).
- *GPU:* `exec-gpu` comes from the runtime probe (CAN); "Let jobs use this laptop's GPU" is `max_gpu_jobs` (live
  slots, ALLOWS) -> `no_gpu_slots` at submit and at dispatch alike.
- *Alternatives rejected:* (a) re-probe on a live switch and re-Hello: rebuilds executor/cache/GC/prepare wiring
  mid-session for no gain over probing once; (b) console auto-restart of the fabric part: misses `policy set`, kills
  running attempts on an unrelated toggle; (c) controller trusting live `accept_jobs` without `exec`: an old agent
  has no runtime, so the attempt would only fail on the agent.
- *Trade-off:* an opted-out laptop now gets the Docker probe (API calls; with a local probe image, one GPU-probe
  container) and the cgroup probe at start, and advertises `exec-subprocess`/`exec-venv` even when the owner
  disallows them (the planner already rules them out through `allow_unsandboxed`). This reverses the V0.7 G5
  "nothing is touched on a laptop that runs no jobs" wording for probes only.
