# V1.0 G8 - two CI flakes from run 40799402426 (main, b775e7cf) - progress

Both are **test bugs**. The product behaviour is correct in each case and is unchanged. No `src/` change,
no migration. I root-caused and fixed each one (no retry, no skip). I reproduced each before the fix and
stress-ran it after.

## 1. `tests/unit/controller/test_v07_g6_unbound_scores_expiry.py::test_the_loop_repeats_every_interval`

CI: job 123223695167 (fresh-clone, windows-latest): `assert 1 >= 2` on `FakeRegistry.cutoffs`.

**Root cause.** The test started `expire_unbound_scores_forever(interval_s=0.01)`, slept a fixed **50 ms**,
cancelled, then asserted at least 2 rounds. So it counted work done inside a wall-clock window. Any
event-loop stall of about 40 ms or more inside that window (a busy 2-vCPU runner in the middle of a 20k-test
run, GC, preemption) leaves 1 round. The product loop (`scores.py`: `while True: sleep(interval);
expire_once()`) is correct: it keeps going after failures and sleeps one interval before each round.

**Fix (test).** `FakeRegistry(rounds_wanted=3)` sets an `asyncio.Event` on its 3rd round. The test waits on
that event (`asyncio.timeout(30)` only bounds a hung loop), then cancels and checks that all cutoffs are
`now - max_age`. New companion test `test_the_loop_waits_one_interval_before_the_first_round` (interval
3600 s: no round runs at start-up) pins down the other half of the loop contract.

**Evidence.** Script `repro1.py` runs the old and new scenarios 100 to 300 times each:

| condition | old (50 ms window) | new (wait for rounds) |
|---|---|---|
| idle, loop clock quantised to 15.625 ms (Windows tick) | 0/300 fail | 0/300 fail |
| 8 busy loops pinned on the same CPU, test at normal priority | 0/200 fail | 0/200 fail |
| same CPU, test at `nice 19` (starved loop) | **99/100 fail** (rounds: `{1: 99, 2: 1}`, the CI signature) | 0/100 fail |

The real pytest files under the starved condition: HEAD's version FAILED, the fixed file `5 passed`.
Timer resolution alone does not reproduce it. A loop stall does.

## 2. `tests/component/controller/test_v10_g3_listener_auth.py::test_http_port_is_tls_and_every_api_call_needs_a_token`

CI: job 123223695296 (component shard 2): `BrokenPipeError: [Errno 32]` from `tls.recv(64)` in `_https`, on
the **foreign-fabric client certificate** probe.

**Root cause.** The HTTP port is `CERT_OPTIONAL` with the fabric CA (`server_tls.ssl_context`). A foreign
certificate is correctly refused. But under TLS 1.3 the client's handshake finishes *before* the server has
verified the client certificate, so the refusal shows up on the client's first read. `strace` of a failing
probe shows the sequence:

```
write(3, "\27\3\3\0P...", 85) = 85      # our GET (handshake already "done" client-side)
read(3, "", 5)                = 0       # server closed: no TLS alert
write(3, "\27\3\3\0\23...", 24) = -1 EPIPE  # OpenSSL sends its own alert on the unexpected EOF
```

* The server sends **no alert** because CPython 3.12 `asyncio/sslproto.py::_do_handshake` routes
  `ssl.SSLError` to `_on_handshake_complete` -> `_fatal_error` (abort) without `_process_outgoing()`, so the
  queued `unknown_ca` alert is dropped.
* Our request bytes reach the closed socket, and the server kernel answers with a RST.
* If that RST arrives before OpenSSL's alert write, the write fails with EPIPE and Python raises
  `BrokenPipeError`. Otherwise Python's `suppress_ragged_eofs` turns the EOF into `b""` (status 0).

The test accepted `ssl.SSLError` / `ConnectionResetError` / `b""` as refusal, but not `BrokenPipeError`. Its
sibling `_tls_outcome` already accepted it.

**Fix (test).** In the foreign-cert branch, catch `(ssl.SSLError, ConnectionError)` (`ConnectionError` covers
BrokenPipe, Reset and Aborted) and record the result as refused (0). A comment explains the three ways the
refusal shows up. The positive paths (`/healthz` 200, token-less 401s) still use `_https` unguarded. The
security assertion is unchanged: a foreign certificate gets no HTTP answer other than 401.

**Evidence.** Raw outcome tally of 2000 foreign-cert probes against one real `mtls` controller (LAN bind):

| condition | `status=0` (EOF) | `BrokenPipeError` | anything else |
|---|---|---|---|
| idle | 1868 / 1869 | 132 / 131 (6.6%) | 0 |
| 16 busy loops on 16 CPUs | 186 | **1814 (91%)** | 0 |

Then I called the fixed test function itself 300 times in a row: idle 300/300 OK, under the 16 busy loops
300/300 OK. Under the same load, HEAD's file FAILED and the fixed file passed.

## Follow-ups (not in scope)
- F1 (diagnostics, low): because of the asyncio behaviour above, a client with a wrong or expired certificate
  on the HTTP port gets EOF/EPIPE instead of a TLS `unknown_ca` / `certificate_expired` alert. Security is
  fine (no data, the connection is closed). But the CLI/agent error for "wrong fabric certificate" on the
  HTTP port may read as a network error. It is worth checking that `compute`/agent blob clients map EOF/EPIPE
  after the handshake to a typed "certificate refused" hint. The gRPC ports (BoringSSL) do send the alert.

### F1 implementation (in review, uncommitted)
- **What:** the agent's HTTPS clients (bundle/manifest/chunk/blob fetch, uploads) now show
  "<the controller | peer node X> ... refused this laptop's certificate - wrong fabric or expired certificate?"
  instead of a bare `RemoteProtocolError`/`ReadError`. Code: `src/meshforge/common/tls_refusal.py` (shared
  check + wording), `src/meshforge/agent/http_refusal.py` (`RefusalWatchStream`, wrapped round every TLS stream
  in `agent/http_connect.py`). TLS server behaviour unchanged. The CLI never presents a client certificate, so it
  cannot hit this case and is unchanged.
- **Rule:** only a *read* is evidence. Before the server's first byte, a zero-byte EOF/reset (or a refusal alert)
  is marked, provided everything we wrote on the connection is <= 64 KiB (`SMALL_REQUEST_BYTES`). A write error
  is never marked by itself (tester D1: an early `413` + close during a big upload). Large requests are never
  marked: measured, an early `413` + abort during a 64 MiB PUT reaches the asyncio client as a bare reset with
  zero bytes (10/10) because our own transport fails on its queued write and drops the answer unread.
- **Known heuristic limit (D2, accepted by the Lead):** a server that *accepted* the certificate but closes before
  sending any byte (crash, kill) looks the same on the wire and is reported as a refusal, with hedged wording
  ("... without answering: it most likely refused this laptop's certificate"). Pinned by
  `tests/component/agent/test_v10_g8_f1_edge_net.py::test_server_closing_before_any_byte_with_accepted_cert`.
- **Intended behaviour change:** a non-refusal raw `ssl.SSLError` on read/write (anyio lets it through httpcore
  unmapped) now surfaces as httpx `ReadError`/`WriteError`, a retryable network error, instead of escaping as an
  `OSError` (which `fetch_bundle` used to report as a local "cannot store the bundle" `internal_error`).

## F2. `tests/component/controller/test_stream_end_liveness.py::test_graceful_close_is_offline_at_once_and_agent_closed`

CI: run 40837018014, component shard 5: `assert await end_reason(...) is SessionEndReason.AGENT_CLOSED` got
`None` right after `wait_state(..., OFFLINE)` passed. The controller log has `session.closed
end_reason='agent_closed'`.

**Root cause (test bug, same as `f956ffa`).** A clean end puts two writes on the session's write chain:
`set_node_state(OFFLINE)` and then `close_session` (`session/ends.py::finish_end`). They are two
transactions, in that order on purpose (D19 chain order; the V0.6 G4 exit list confirmed it after the same
race in `test_rest_cli_g5_adversarial`). So for a moment the node reads OFFLINE while `node_session.end_reason`
is still null. The test polled the node state, then read `end_reason` once. If the reader ran between the two
commits, it saw `None`. The sibling `test_goodbye_then_cancel_is_still_agent_closed` had the same pattern. The
abrupt-end tests were already safe (they poll `end_reason`; the SUSPECT write is committed before it). The
controller-stop test drains the chains first. No `src/` change: the order is the design, and no product reader
needs OFFLINE and `end_reason` to change together.

**Fix (test).** A shared helper `wait_session_end_reason` (`tests/_support/mf_session_client.py`) polls until the session row is closed and returns the reason. Both
tests now assert `AGENT_CLOSED` on that value (the assertion itself is unchanged).

**Evidence.**
- Gap widened on purpose (a scratch plugin delays `Registry.close_session` by 100 ms): HEAD's file fails exactly
  these 2 tests (11 passed). The fixed file passes 13/13.
- The 2 tests repeated 200x each with `stress -c 16` on 16 CPUs: HEAD failed 1 of the 288 runs that finished
  before the timeout (the CI signature). Fixed file: 400/400 passed (exit 0).

**F2 sweep (every other `tests/component` file that reads `end_reason`, 20 files).** The same scratch plugin
(`close_session` delayed 100 ms) on HEAD's test files: 6 failed / 126 passed. Each failure is the same family:
something the test can observe is committed or sent before `close_session`, and the test read `end_reason` once.
- OFFLINE before close (D19 chain order): `agent/test_agent_goodbye.py::test_a_real_agents_requested_stop_is_offline_now_and_agent_closed`,
  `controller/test_admission_deadline.py::test_a_hung_registry_refuses_the_hello_unavailable_and_the_goodbye_is_offline`,
  `controller/test_session_server.py::test_reconnect_after_offline_is_online_again` (lease expiry: OFFLINE, then
  `close_session(lease_expired)`).
- The gRPC status reaches the agent before `close_session` commits (the handler is unblocked in memory first,
  `SessionEnds.close`): `agent/test_agent_session.py::test_second_agent_with_same_identity_supersedes_first_which_exits_conflict`
  (`superseded`), `controller/test_session_server_tester.py::test_second_hello_on_open_stream_with_extreme_epoch_is_protocol_error`
  and `::test_agent_message_with_empty_message_id_closes_protocol_error` (`protocol_error`).

All 6 now wait with `wait_session_end_reason`. The
assertions on the reason itself are unchanged. After the fix, the 20 files plus `test_stream_end_liveness.py`:
145 passed with the 100 ms delay (exit 0), and 145 passed without it (exit 0).

**F2 review follow-ups.**
- `tests/cluster/test_fabric_liveness.py`: all 5 `end_reason` reads were one-shot reads over REST after waiting for
  OFFLINE or a reconnect. Two are the real race (`test_g`, `test_l`: `agent_closed` right after OFFLINE). Three are
  only safe by luck (`lease_expired` is closed after OFFLINE; a new session is admitted without waiting for the
  old chain's close). All 5 now use the new `Fabric.wait_session_end(node, session_id)` (`tests/_support/mf_cluster.py`).
  `test_fabric_controller_stop.py` and `test_fabric_restarts.py` are safe as written: the stopping controller drains
  its chains before it exits, and the start-up sweep runs before it serves.
- The two local `wait_closed` helpers (`test_session_server.py`, `test_session_server_fixes.py`) are gone. Their
  call sites use the shared helper. `ended_at` and `end_reason` are always set in the same UPDATE
  (`close_session`, `sweep_open_sessions`), so "closed" and "has a reason" are the same check.
- Product check: `end_reason` is shown only by REST `GET /v1/sessions` (`api/shape.py::session_summary`), which
  returns the row as stored. The CLI's `Client.sessions` has no caller. The dashboard never calls `/v1/sessions`.
  No code treats "OFFLINE with an open session row" as an error. So there is no product bug. ARCHITECTURE §12.3
  (after D20) now states that node state leads the session row.

## F3. `tests/component/controller/test_v07_g3_tester_r2_cert_ends.py::test_a_certificate_with_milliseconds_left_never_leaves_a_zombie[1.0]`

CI: run 40871951455, component shard 3: `AssertionError: <StatusCode.INTERNAL: (13, 'internal')>` (the
test accepts UNAUTHENTICATED / UNAVAILABLE / CANCELLED). The controller log has `session.cert_expired`, then
`session.ends end_reason='cert_expired' state=offline`. The product ended the session correctly.

**Root cause (test bug: a grpc.aio client-side artefact, already known as D399 / V0.6 G4 / V0.7 G4).** The
controller never sends INTERNAL here. `SessionManager._cert_expired` (the `not_after` timer) closes the
session `cert_expired`, and the servicer ends the stream with `UNAUTHENTICATED` + `meshforge-reason:
cert_expired` (`session/servicer.py` `_CERT_ENDS`). The FakeAgent writes a heartbeat every 0.1 s. If a
heartbeat is in flight when the server ends the call, the send fails in grpc core (`Failed "execute_batch":
(<SendMessageOperation>,)`). grpc 1.84 `grpc/aio/_call.py::_write` then calls `set_internal_error`. That
sets the call's status, *on the client*, to INTERNAL `"Internal error from Core"` with **no trailing
metadata**, and the reader raises that status instead of the server's. A torn TLS/HTTP2 stream (RST_STREAM)
is not the cause: every reproduced INTERNAL had exactly these details plus a failed write of ours. The same
overwrite can also happen *after* the reader got the real status: the code is right, but
`trailing_metadata()` is empty afterwards (seen once in the provoked run below). That is a latent flake in
`test_the_cut_old_laptop_is_refused_again_at_every_hello` (it reads `meshforge-reason` with heartbeats
running), and in its `_hello_once` probe (the interceptor refuses the call while the Hello write is in
flight).

**Fix (tests only, no `src/` change).**
- `tests/_support/mf_session_client.py`: `FakeAgent.write` records the first `AioRpcError` a write raised
  (`write_error`). New `ended_by_client_write_relabel(agent)` is true only when the end is exactly INTERNAL
  `"Internal error from Core"` **and** a write of this agent raised that same error
  (`GRPC_CLIENT_RELABEL_DETAILS`).
- The zombie test accepts INTERNAL only through that helper. It now also asserts the controller's record
  (`wait_session_end_reason` == `cert_expired`) for every connected run, so the server's truth is checked
  directly. Before, only "no zombie" was checked.
- `test_the_cut_old_laptop_is_refused_again_at_every_hello`: `finish_heartbeats()` before the supersede
  (the pattern used by `test_supersede_racing_a_graceful_close_leaves_nothing_live`; liveness is tolerant,
  10 s lease). `_hello_once` probes again (max 5) only when the Hello *write* was relabelled. A refused write
  means the call had already ended, so it was never an admission.
