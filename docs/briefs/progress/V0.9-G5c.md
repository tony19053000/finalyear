## 0.0 — the cool-down race (D255)

**Cause (confirmed by a deterministic reproduction before the fix).** `BenchRunner.tick` runs
`BenchStore.sync()` first and only then reads, per node, the load (`node_bench_load`: non-terminal benchmark
jobs, read live from `job`) and the last end (`seconds_since_last_end`: `max(bench_run.ended_at)`). A job that
reached terminal **after** `sync` but before the load read made the node look free (load 0) while its run was
still `submitted` with `ended_at = NULL` - so the cool-down saw the previous run's end (or none) and the node got a
slot. The next `sync` stamped `ended_at` = the job's final transition, i.e. a few ms before the new
`submitted_at`: the gate's 0.034 s gap. Under load the window (sync -> load read) is wide enough to hit.

**Fix (`controller/bench/control.py`, `runner.py`).**
1. The last end also counts a still-`submitted` run whose linked job is terminal, at the job's final transition
   time (`coalesce(last job_transition.at, job.updated_at)` - exactly what `sync` will stamp).
2. New `CampaignControl.node_slots(campaign_id, nodes)` reads load and last end in **one** `REPEATABLE READ`
   snapshot; the runner uses it. A job ending while the runner reads is seen either running (fills the slot)
   or ended (cool-down), never neither, whatever the statement order.
   `node_bench_load` / `seconds_since_last_end` stay (same helpers) for other callers/tests.

Remaining limit (documented in the runner docstring): with `max_concurrent_per_node > 1` a *sibling* job that
ends between the tick's read and its submit is not covered (no lock against job state); with the default 1 the
running job fills the slot, so the invariant holds.

**Tests.** `tests/component/controller/test_v09_g5c_runner_cooldown.py` (real Postgres): the store's `sync` is
wrapped so the job ends right after the real `sync` - before the fix node_a got `{"node_a": 1}` (failed), after
it `excluded == cooldown`; plus an old unsynced end frees the node, a running job = `full`, `node_slots` before /
after the end. The three unit-test fakes gained `node_slots` (delegating to their two methods).

**Original test 20x under load:** `test_v09_g5b_runner.py::test_runner_runs_a_started_campaign_throttled_and_refuses_manual_submit`
run 20 times as 4 parallel streams x 5 sequential runs (each stream its own Postgres container; no xdist in the
venv, so the parallel streams are the load) - **20/20 passed, every exit code 0** (53-64 s each). Plus
`test_v09_g5b_runner.py` + `test_v09_g5b_tester_r1_runner.py` + the new file: 31 passed, exit 0.
