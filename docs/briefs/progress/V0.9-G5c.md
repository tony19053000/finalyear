## 0.0 — the cool-down race (D255)

**Cause (confirmed by a deterministic reproduction before the fix).** `BenchRunner.tick` runs
`BenchStore.sync()` first and only then reads, per node, the load (`node_bench_load`: non-terminal benchmark
jobs, read live from `job`) and the last end (`seconds_since_last_end`: `max(bench_run.ended_at)`). A job that
reached terminal **after** `sync` but before the load read made the node look free (load 0) while its run was
still `submitted` with `ended_at = NULL` - so the cool-down saw the previous run's end (or none) and the node got a
slot. The next `sync` stamped `ended_at` = the job's final transition, i.e. a few ms before the new
`submitted_at`: the gate's 0.034 s gap. Under load the window (sync -> load read) is wide enough to hit.

**Fix (`controller/bench/control.py`, `runner.py`).**
1. The last end also counts a still-`submitted` run whose linked job is terminal, at the job's final transition
   time (`coalesce(last job_transition.at, job.updated_at)` - exactly what `sync` will stamp).
2. New `CampaignControl.node_slots(campaign_id, nodes)` reads load and last end in **one** `REPEATABLE READ`
   snapshot; the runner uses it. A job ending while the runner reads is seen either running (fills the slot)
   or ended (cool-down), never neither, whatever the statement order.
   `node_bench_load` / `seconds_since_last_end` stay (same helpers) for other callers/tests.

Remaining limit (documented in the runner docstring): with `max_concurrent_per_node > 1` a *sibling* job that
ends between the tick's read and its submit is not covered (no lock against job state); with the default 1 the
running job fills the slot, so the invariant holds.

**Tests.** `tests/component/controller/test_v09_g5c_runner_cooldown.py` (real Postgres): the store's `sync` is
wrapped so the job ends right after the real `sync` - before the fix node_a got `{"node_a": 1}` (failed), after
it `excluded == cooldown`; plus an old unsynced end frees the node, a running job = `full`, `node_slots` before /
after the end. The three unit-test fakes gained `node_slots` (delegating to their two methods).

**Original test 20x under load:** `test_v09_g5b_runner.py::test_runner_runs_a_started_campaign_throttled_and_refuses_manual_submit`
run 20 times as 4 parallel streams x 5 sequential runs (each stream its own Postgres container; no xdist in the
venv, so the parallel streams are the load) - **20/20 passed, every exit code 0** (53-64 s each). Plus
`test_v09_g5b_runner.py` + `test_v09_g5b_tester_r1_runner.py` + the new file: 31 passed, exit 0.

## 0.2 — OwnerGuard lock (D253 T3-1)

One `asyncio.Lock` around every evaluate + pre-empt (`refresh` -> `_refresh`, `on_poll`'s retry). `on_poll` with
nothing pending returns without the lock (the common case, every 2 s); under the lock it re-checks `_pending`
(the other path may have finished it). The strict xfail
`test_a_slow_preemption_racing_the_event_path_counts_once` is now a plain test (passes); added two event paths
racing a slow first pre-emption (one call) and "a poll with nothing pending takes no lock".

## 0.3 + 0.4 — bounded pre-emption revert, per-attempt stop (D253 T3-2, D252.6)

One commit: both change `Executor.preempt_benchmarks`.
- New `[agent.bench] preempt_revert_timeout_s` (default 10, (0, 600]); `Executor.preempt_revert_timeout_s`
  (public attribute, tests shorten it). `_bounded_revert`: `wait_for(conditions.stop_all(...), bound)`; on
  timeout logs `agent.bench.revert_timeout` (node_id, timeout_s, attempts, conditions) and the `finally` still
  stops every selected attempt. `ActiveCondition.finish` is shielded, so the revert carries on in the
  background and the marker stays until it succeeds (start-up sweep otherwise).
- **Extension (needed for "still stop the attempts" to mean anything with a real condition):** the attempt's
  terminal report awaits `condition.finish()`; for a **pre-empted** attempt that wait is bounded by the same
  setting (`_condition_report`) - past it the report says `reverted = false`, reason `revert_timeout`, so the
  run is requeued instead of the attempt hanging. Non-pre-empted attempts keep the unbounded G4 behaviour
  (follow-up: bound it generally?).
- 0.4: `_preempt_one` - per attempt try/except around `_stop` + `preempt_stopped`, logs
  `agent.execution.preempt_stop_failed`; a failed one stays "marked, not stopped" so the guard's retry picks it
  up (D251 B2 path). `shutdown`'s `_stop` loop got the same per-attempt try/log (`agent.execution.stop_failed`).
- Tester strict xfail `test_a_hanging_stop_all_does_not_leave_the_attempt_running` flipped. **Test change:**
  it now sets the bound to 1 s (default 10 > its 5 s `wait_for`) and waits (bounded, <= 2 s) for the step's
  cancel to be delivered before `_leaks` - a cancel is asynchronous - and asserts the final report is
  `owner_preempted` **before** the runtime is released, so an attempt that was never stopped cannot pass.
- New `tests/component/agent/test_v09_g5c_preempt_bounded.py`: real `cpu_load:1` burner, controller `revert`
  hung -> pre-emption returns < 5 s, `revert_timeout` logged, attempt `failed/owner_preempted`, report
  `reverted=false`/`revert_timeout`, marker + burner still there; release -> background revert removes marker
  and burner. Second test: one attempt's `_stop` raising -> the other two stop, the guard retry gets the third.
