## 0. The honest starting point

Agent-side, V0.3–V0.17 are almost all done. Physically, **almost nothing has been proven on the four laptops**:
13 🧑 lab tasks are still open (0.2.3/0.2.4, 0.3.15, 0.4.15, 0.5.11, 0.6.13, 0.7.12, 0.8.10, 0.9.10, 0.10.10,
0.14.8, 0.15.11, 0.17.8) plus Windows checks (0.3.2, 0.3.13, 0.4.8, SP1/SP3 labs). V1.0 criterion 1 ("all
acceptance criteria pass on the release build") therefore cannot be met by agents alone.

Four hard truths:

1. **One lab campaign, not thirteen.** Each lab needs all four laptops set up, on the same network, for hours. Doing
   them one by one costs the team weeks. V1.0 folds **every open 🧑 step** into one ordered campaign run on the
   **release-candidate packages** (install once → soak → evaluate → rehearse demos). Old checklists are reused as
   sections, not rewritten.
2. **The research claim may come out "not separable".** The ML planner only ships "better" with a paired bootstrap
   win against calibration (D357). With four laptops and a few weeks of runs, a `not_separable` verdict is a real
   possibility. The report must print whatever the data says; the planner then keeps calibration as default
   (that is already the live fallback). We do not tune until it wins.
3. **Mode 2 and Mode 4 are not in v1.0.** ADR-0012 deferred them; nothing for V0.11/V0.12/V0.13/V0.16 is built.
   The release, demos, docs and report say this plainly: v1.0 = Local + Mode 1 + Mode 3 + planner (rule, v2,
   ML). The "Combined GPU" and "Remote GPU" cells of the brief's 2×2 are future work with the design in ARCHITECTURE.
   No slide, demo or README may imply otherwise (CLAUDE.md §8: never simulated).
4. **72 h is three real days of four laptops left on.** Any reboot, sleep or Wi-Fi drop that is not ours restarts
   the clock or must be attributed. Ethernet switch is still not bought (Blockers); soak on Wi-Fi is allowed but
   attribution must separate network loss from our failures.

## 2. Design decisions (Lead proposals)

| # | Decision | Why |
|---|---|---|
| D406 | **Release build = the `v1.0.0-rc.N` packages from release CI** (agent `.deb`, controller `.deb`, Windows installer). Every 🧑 step and every evidence run records the package version + git SHA; evidence from a dev checkout does not count for criterion 1. A code fix during the campaign makes `rc.N+1`; which earlier evidence must be redone is decided by the manifest's `affected_by` paths (D407). | "On the release build" must be checkable, and a late fix must not silently invalidate old evidence. |
| D407 | **Acceptance manifest** `release/acceptance.yaml`: one row per success criterion of V0.3–V0.17 (incl. V0.1/V0.2 where they still apply) with `id` (e.g. `V0.6-c2`), text, `kind` ∈ {`auto`, `lab`, `waiver`}, `evidence` (pytest node ids / lab checklist section + analyzer command), `affected_by` (source globs), and for waivers a `reason` + ADR/decision ref. Deferred versions (V0.11–V0.13, V0.16) appear as one `waiver` row each citing ADR-0012. A unit test parses the roadmap and **fails if any criterion has no row** or any row points at a missing test. | No silent gaps; the manifest is the single list the release report is built from. |
| D408 | **`scripts/release_check.py`** runs every `auto` row (pytest by node id, tiers unit/component/cluster/e2e/chaos) against the installed packages where possible (`MESHFORGE_USE_INSTALLED=1` runs the cluster tier using `/opt/meshforge/current` Python), ingests `lab` evidence JSON from `lab/reports/raw/`, and writes `docs/reports/release-v1.0-acceptance.md` + `.json`: per row PASS/FAIL/MISSING/WAIVED, SHA, package version. Exit 0 only if no FAIL/MISSING. | Criterion 1 becomes one command plus pasted lab files. |
| D409 | **Soak = 72 h continuous, 4 laptops (≥ 1 Windows), installed services, mixed load.** Load generator submits a seeded mix (Mode 1 short/long, Mode 3 split jobs, benchmark jobs, ~1 job / 30 s average, Poisson, cancellations 5 %) plus chaos (D411) from hour 6 to hour 66; first and last 6 h are quiet baselines for leak slopes. | Leaks show as slope between two quiet windows; chaos in the middle proves recovery under load. |
| D410 | **Soak pass rules (all must hold):** (1) **lost jobs = 0**: every submitted job ends in a terminal state with a ledger record matching the controller DB (reuse `mf_ledger` idea: submit log vs DB vs outputs); jobs failed by chaos must be retried to SUCCEEDED or end FAILED with a recorded cause — never stuck > 10 min after their deadline; (2) **crashes = 0**: no unplanned exit of controller/agent/Postgres (service restart counters, journal/Event Log, exit codes) — restarts we caused by chaos do not count; (3) **memory**: per process (controller, each agent, Postgres total) RSS growth from quiet-window-1 median to quiet-window-2 median **< 10 %** and linear-fit slope over the whole run < 5 MB/h; (4) **FDs (Linux) / handles (Windows) / threads**: quiet-window-2 median ≤ quiet-window-1 median + 5 %; (5) **DB growth** proportional to jobs: bytes/job stable (2nd-half ratio within ±20 % of 1st half), no table growing without jobs (sessions, leases), WAL/disk bounded; (6) **disk**: agent cache stays under its cap, logs rotate; (7) heartbeat: no node OFFLINE that the attribution does not explain (sleep, chaos, network). | Concrete and measurable from samplers; matches roadmap criterion 2 "no crashes, leaks, or lost jobs". |
| D411 | **Chaos actions on real laptops** (seeded schedule, ≥ 1 action / 45 min, each logged with time + target): kill -9 agent; kill -9 controller (and service restart); stop/start Postgres under controller; reboot a laptop; disconnect Wi-Fi/Ethernet 30 s and 5 min (`lab/netem` on Linux, `netsh interface set` on Windows); netem 200 ms / 5 % loss for 10 min; fill agent disk to 95 %; kill a job's child process tree; cancel in-flight Mode 3 job; revoke + re-join a node (once); controller upgrade `rc.N → rc.N` reinstall (once). Linux actions are scripted over SSH from the controller; Windows actions run by a small `lab/chaos_win.ps1` on that laptop with the same seed. | Reuses D118's catalogue; covers every failure path the earlier criteria claimed. |
| D412 | **Profiling & tuning is measure-first and bounded.** Profile (py-spy for controller/agent, `EXPLAIN ANALYZE` on top-10 queries from `pg_stat_statements`, `scripts/ui_perf` for the dashboard) during the soak's quiet window and an evaluation run. Fix only items with measured cost ≥ 10 % of a path or a soak-rule risk; each fix needs a before/after number. Targets: planner decision p95 < 200 ms at 4 nodes / 100 queued jobs; job submit→start overhead p50 recorded and not regressed; controller idle CPU < 5 %. | Avoids open-ended tuning; numbers go into the report. |
| D413 | **Security review = checklist-driven + independent reviewer agent**, not a new pentest: re-check every THREAT_MODEL threat against the release code; `scripts/threat_model_check.py`; dependency audit (`pip-audit` on `uv.lock`, `npm audit` on frontend); secrets scan of the release packages; open ports per installed role vs D389; mTLS/token on every endpoint (route inventory test); bandit/semgrep with triaged findings. Outcome: `docs/reports/release-v1.0-security.md` with each finding fixed or accepted (decision ref). Known gaps (unsigned installer Q2, no sandbox beyond Docker for subprocess runtime) are stated as accepted risks. | Honest, repeatable, within budget. |
| D414 | **Docs complete = a checklist, not a rewrite:** user guide (`docs/user`, Windows screenshots from the lab), ARCHITECTURE.md matches the code (each section marked current/deferred), **API reference** generated (OpenAPI via `scripts/export_openapi.py` → `docs/api/`, gRPC from `.proto` via a doc generator, SDK from docstrings), ADR index complete with every Proposed ADR moved to Accepted/Superseded, CLI.md generated from `--help`, PROJECT_SUMMARY updated with measured numbers. A CI check fails if OpenAPI/CLI docs drift from the code. | Docs the team can defend at evaluation; drift caught automatically. |
| D415 | **Research question (RQ):** *"On a LAN of heterogeneous personal laptops, does a planner that chooses between LOCAL, Mode 1 and Mode 3 using calibrated and learned time predictions reduce job completion time compared with a fixed local baseline and conventional schedulers, and by how much?"* Sub-questions: RQ1 makespan/latency vs baselines; RQ2 prediction error (ML vs calibration vs raw); RQ3 which components matter (ablations); RQ4 overhead of the fabric itself (Local vs Mode 1 on the same node). | One measurable question that matches the brief's core question for the shipped modes. |
| D416 | **Baselines (forced per job via the manifest policy override):** B0 **Local only** (the submitting laptop); B1 **round_robin**; B2 **random** (seeded); B3 **least_loaded**; B4 **rule-based planner v2 uncalibrated**; B5 **planner v2 calibrated** (V0.14); B6 **ML planner** (V0.15, `server.ml_source`); plus **oracle** (best measured configuration per group, from the evaluator) for regret. Mode 3 split count follows each policy's rule (baselines use the fixed default split). | Covers "no distribution", naïve distribution, rules, and learning. |
| D417 | **Metrics, repetitions, CI:** per job: end-to-end time, queue wait, transfer bytes/time, overhead; per run: makespan, throughput, regret vs oracle, prediction MALE/MAPE. **Design:** workload families from `docs/BENCHMARKS.md` (Mode 1 + Mode 3, ≥ 6 families, ≥ 2 held out from ML training), each (family, size, policy) cell **≥ 10 repetitions**, policy order randomised in blocks to cancel drift, link recorded (Wi-Fi / Ethernet). **CIs:** 95 % paired bootstrap (2 000 resamples, fixed seed) over matched groups for differences vs B5 and vs B0, reusing planner_eval helpers; report effect size as median speedup with CI; verdicts better / not_separable / worse exactly like D341/D357. | Paired design is the strongest test four laptops can afford; same rules as V0.15 keep the claim consistent. |
| D418 | **Ablations:** (A1) ML without hardware-score features; (A2) without live-load features; (A3) without cache/locality features; (A4) calibration off; (A5) Mode 3 disabled (planner may only pick LOCAL/Mode 1); (A6) Mode 1 disabled (LOCAL/Mode 3); (A7) planner on Wi-Fi vs Ethernet. A1–A4 offline via the evaluator (D372) on the campaign data; A5–A7 live, ≥ 5 reps per cell on 3 families. | Shows which parts earn their place without tripling lab time. |
| D419 | **Reproducibility:** `eval/` (or `scripts/eval/`) holds `run_campaign.py` (seeded, resumable, writes raw JSON with SHA + package version + inventory), `analyze.py` (raw → tables/figures, byte-identical for same input), and `make_report.py` → `docs/reports/v1.0-evaluation.md` + figures. Raw data is archived (Q49). A CI job re-runs analysis on a committed small sample and checks the hashes. | Criterion 3 "reproducible experiment scripts" is then checkable. |
| D420 | **Demos only for shipped modes:** scripted, deterministic scenarios `demo/01-local.sh`, `02-mode1-offload`, `03-mode3-split` (with a node killed mid-way and recovery), `04-planner-explains` (planner choosing Local vs M1 vs M3 for three jobs, with the dashboard "why" panel), `05-install-join` (Windows install → join, recorded). Each has a reset step, expected output, a fallback recording, and runs in < 5 min. Mode 2/4: a one-slide "deferred, designed, not built" note — no mock. | Evaluators get a reliable show; nothing simulated. |
| D421 | **Release:** `CHANGELOG.md` (Keep a Changelog, generated from roadmap tasks + decision log per version, edited by hand), tag `v1.0.0` only after `release_check.py` exits 0, soak passed and report merged; release notes list shipped modes, deferred modes, known issues, accepted risks. | Criterion order enforced by the tag rule. |

## 7. Risks (honest)

- **Lab calendar time** is the critical path (~7–8 days of all four laptops). Exams/holidays can block it.
- **ML may not beat calibration** → report `not_separable`, keep calibration default; this is still a valid result.
- **Distribution may lose to Local** for short jobs on Wi-Fi → expected; the planner choosing Local is the right answer and the report shows the crossover point.
- **Windows soak stability** (sleep, updates, Defender) — disable sleep/updates for the window; attribute outside events.
- **Fixes during the campaign** reset evidence; the `affected_by` rule limits the redo.
- **No Ethernet switch** → all results Wi-Fi only; A7 ablation dropped. Buying one (Q46) removes most noise.
