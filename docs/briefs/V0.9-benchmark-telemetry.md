## 2. Design decisions (Lead proposals — team approves before G1)

| # | Decision | Why |
|---|---|---|
| D211 | **Two layers: the record and the dataset.** PostgreSQL stays the source of truth (a *run record* = one attempt + everything known at its start and end). The *dataset* is a **Parquet export** (pyarrow) built from records by a pure function; nothing writes Parquet during execution. | One write path; export is re-runnable and testable; Postgres already has the data. |
| D212 | **Telemetry schema v1 (0.9.1)** = a versioned `run_record` view/table: ids (campaign, group, config, repetition, job, attempt), workload family + params (JSON + flattened known columns), forced strategy + node, planner choice it *would* have made, start snapshot (node load, RAM free, GPU util, queue depth, cache warm/cold, network row to the chosen node), phase timings (queue, prepare, fetch, env, **compute**, upload), bytes in/out, exit status, failure class (*workload* vs *infrastructure*), node clock offset. `schema_version` column; a test fails if a field changes without a version bump. Migration **0021**. | Every later version (V0.10–V0.16) adds families, not new schemas; ML (V0.15) needs a stable contract. |
| D213 | **Compute time is measured on the agent** with a monotonic clock and reported as a duration; wall-clock timestamps are only for ordering. Controller records **per-node clock offset** (NTP-style from heartbeat round trips, ±RTT/2 bound) and stores it with each record. **Only a recent window** of exchanges (last N or last T seconds) feeds the estimate, so an old minimum-RTT exchange cannot hide drift (D226). | Cross-machine timestamps are unreliable on Wi-Fi laptops; durations are not. Same mechanism fixes D210 item 1. |
| D214 | **Workload library (0.9.2)** = Python package `meshforge.bench.workloads`, each family a small, deterministic job with a param schema (pydantic), a seed, a size→expected-runtime hint, and a self-check of its output. v1 families: CPU (matmul-numpy, primes, sort, zlib, sha256, numerical integration), memory (array copy, pandas groupby), GPU (torch matmul, conv2d, elementwise, image resize — skipped cleanly with reason on no-GPU nodes), ML (small CNN infer/train on synthetic data, small transformer inference; batch/model/seq sweeps). Target **5 s – 3 min per run** (ADR-0012 risk). No downloads at run time: synthetic data only, models built in code. | Reproducible, offline, cheap enough for thousands of runs. |
| D215 | **Forced strategy (0.9.4)** = the job is submitted with `pinned_node_id` + tag `benchmark` + `campaign_id`; the planner still runs and its *would-have-chosen* answer is recorded (explain). "Strategy" in V0.9 = **LOCAL (the submitter's node) or Mode 1 on node X**; Mode 3 strategies are added by V0.10 (criterion 4). Benchmark jobs get the lowest priority class and never pre-empt user jobs. | Labels must cover choices the planner did not make; recording its pick gives V0.14 a regret metric for free. |
| D216 | **Campaign spec (0.9.3)** = YAML: families × param ranges × conditions × strategies × nodes, repetitions (≥ 3), sampler (`grid`, `random`, `lhs` via scipy-free own LHS), seed, budget (max runs / max hours). `compute bench plan <spec>` prints the expanded run list *before* anything runs; the **expansion is deterministic** from (spec, seed). Order is randomized (seeded) and interleaved across configs so drift does not bias one config. | Reproducible (criterion 2); a human sees the cost first. |
| D217 | **Conditions (0.9.5)** v1: CPU load generator (n cores busy), GPU load generator, cache warm/cold (evict named input / env before run), queue pressure (k filler jobs), network shaping via `tc netem` **Linux only, needs root → opt-in agent capability**, Wi-Fi vs Ethernet = a *session label* set by the human, node-unavailable = agent paused by the runner. Every condition is applied *and verified* (measured load / measured RTT recorded); unverified → run marked `condition_failed`, not silently labelled. | Labels are only as true as the condition; Windows nodes get the conditions they can do, the rest are reported missing. |
| D218 | **Labels (0.9.6)** per *group* (same workload+params+conditions): vector of measured costs per strategy (median + CV of compute, total, bytes), `best_strategy` = lowest median total **only if** it beats the next by more than the noise (CI of medians not overlapping), else `tie`. | A noisy "best" teaches the ML planner noise. |
| D219 | **Campaign runner (0.9.7)** = controller-side module (not a new service), state in Postgres → **resumable** after controller restart; throttle (max concurrent per node, cool-down between runs); **owner guard**: agent reports user activity (input idle time / foreground CPU from non-fabric processes); above threshold the node is skipped and the run requeued; owner `pause benchmarks` switch on the agent. Infra failure (agent lost, transfer error) → retried up to N, counted for criterion 1. | Unattended overnight runs on the team's own laptops must not annoy owners. |
| D220 | **Quality report (0.9.8)** = `compute bench report <campaign>` + JSON: per config n, median, CV, outliers (MAD rule), missing fields, condition failures, infra failure rate, groups with too-high CV (> 10 % flagged). Same numbers on the Benchmarks page. | Criterion 3 is checked by code, not by eye. |
| D221 | **Benchmarks page (0.9.9)**: campaigns list (progress, ETA, failure rate, pause/resume/cancel), campaign detail (quality report, per-family charts: runtime vs param by node, strategy comparison), dataset download (Parquet). Reuses V0.8 components + event bus (`campaign.progress`). | Operator surface; evaluation evidence. |
| D222 | **Reproducibility rule (criterion 2)**: same campaign ID → same export **row set and values** (stable sort, stable column order, no export-time timestamps inside the file); a test exports twice and compares bytes. Re-*running* a spec gives the same run list, not the same timings (that is what CV is for). | Precise, testable meaning of "reproducible". |
| D223 | **New dependencies (ask-first rule):** `pyarrow` (runtime, controller extra), `pandas` (dev/report only, or controller extra — Q3), `torch` already used on GPU nodes. No scipy, no MLflow/W&B. | Small footprint; offline LAN. |
| D224 | **Agent live-log redaction off the event loop** (V0.8 G1 carry-over, RE-D2 residual): moved to a worker thread with a bounded queue, keeping the T-14 drain/cancel ordering; a regression test reproduces T-14. Lives in G1 because G1 touches the agent's reporting path. | Benchmarks load the agent hard; a blocked loop would skew timings. |

## 5b. Brief for **G1 — Telemetry schema v1 + clocks** (0.9.1 + D211–D213, D224, worktree; after G0 merges)

0. **Item 0 = D226 non-blocking list** (snapshot allowlist + test, clock_offset round-up + window doc, THREAT_MODEL `/v1/clock` row, injected time source).
1. **Clock offset per node (D213).** Reuse `meshforge.common.clock_offset` (G0) for agent↔controller: the
   heartbeat carries the agent's wall time at send and echoes the controller's last time (proto field add,
   backward compatible); controller keeps a per-node offset + bound (rolling window, consistency rule from G0)
   in the registry; exposed on node detail (`clock_offset_ms`, `bound_ms`, `consistent`) and alerted when the

1. **Spec form.** A condition is a string `name` or `name:arg` (e.g. `cpu_load:2`, `gpu_load:50`,

   `netem` only on Linux with the sudoers rule present and verified by a dry-run `tc -n`; `gpu_load` only with

   lists node × condition), or with `on_unsupported: skip` marks those runs `skipped` with reason. Condition apply
   / verify / revert is a new agent RPC carried with the job dispatch (the agent applies before `prepare`, reverts
   after the attempt ends in **every** terminal path including cancel and agent restart — persisted "applied"
   marker swept at agent start).
3. **Controllers (agent side, `agent/conditions/`).**

     (`lab/` documents the exact rule); verify measured RTT/bandwidth with the existing probe; revert always,
     including on crash (marker). Windows → unsupported.
