## 0. The honest starting point

Today MeshForge installs like a developer project: `git clone`, `uv sync --extra …`, a Docker Compose PostgreSQL,
a hand-edited systemd *user* unit or a `schtasks` line, and `meshforge-agent join` typed in a terminal. All of
that works. None of it meets criterion 1 ("download to joined fabric in < 10 minutes, **no terminal**").

Four hard truths shape this brief:

1. **The agents cannot touch Windows.** Every Windows build, install and service check is a 🧑 step until a CI
   runner exists. The GitHub repository and first push are **still not done** (STATUS Blockers). V0.17 cannot reach
   quality on 🧑 copy-paste loops alone, so **G0 makes the private GitHub repo + Windows CI runner a hard
   prerequisite** (Q1). Without it, Windows work moves at the speed of humans pasting logs.
2. **"Service" changes who the agent is.** The agent currently runs as the logged-in user and keeps its identity
   in that user's data folder (ADR-0013). A real OS service runs as a service account and has no per-user folder.
   Moving to services means **moving the identity, cache and config to machine-wide locations**, and migrating
   the laptops that already joined. This is the largest design change in V0.17, and it is easy to get wrong
   (a laptop that silently enrols as a *new* node).
3. **"No terminal" needs a UI on the agent laptop.** The dashboard lives on the controller. A laptop that has not
   joined yet has no controller to open. So the agent needs its **own small local UI**: the first-run wizard
   (0.17.4) and the owner settings (0.17.5). The owner policy belongs to the laptop owner, not the controller
   (D142), so this UI is also the right home for 0.17.5.
4. **An unsigned installer gets a SmartScreen warning.** "Windows protected your PC → More info → Run anyway"
   is a real step for a fresh user. Code signing costs money (Q2). We can meet the time criterion with the warning;
   we must not pretend it is not there.

## 2. Design decisions (Lead proposals)

| # | Decision | Why |
|---|---|---|
| D384 | **Bundled runtime = relocatable CPython + locked wheels, not a frozen exe.** The build takes `python-build-standalone` CPython 3.12 (the one `uv python install` uses), installs `meshforge` + the `agent` (or `controller`) extra from `uv.lock` into it with `--no-deps --require-hashes`, and adds a pinned `uv` binary for job environments. Output: one folder per OS/arch (`meshforge-<ver>-<os>-<arch>/`). The installers only wrap this folder. Script: `scripts/build_bundle.py`, reproducible (same lock → same file list and hashes). | PyInstaller/Nuitka break the child processes we rely on (ML child, benchmark children, `uv` env builds), confuse antivirus and need per-library hooks (grpc, cryptography, numpy). A real interpreter behaves exactly like our tested one. Torch is **not** bundled: jobs get it through their own environments. |
| D385 | **Install layout.** Program files are read-only: `C:\Program Files\MeshForge\<ver>\` / `/opt/meshforge/<ver>/` with a `current` pointer (Windows: the service points at the versioned path, rewritten by the installer). Machine state: `C:\ProgramData\MeshForge\{config,identity,cache,logs,db}` / `/etc/meshforge` (config) + `/var/lib/meshforge/{identity,cache,db}` + journal. ACLs: SYSTEM + the service account + Administrators only; identity keeps ADR-0013's owner-only rule, with the service account as owner. | Side-by-side versions make upgrade and rollback a pointer swap. Separating code from state is what lets uninstall keep or remove data on request. |
| D386 | **Agent as a real OS service.** Linux: system unit `meshforge-agent.service`, user `meshforge` (system user, created by the package), `Restart=always`, `RestartPreventExitStatus=4 5`, hardening (`ProtectSystem=strict`, `ReadWritePaths=/var/lib/meshforge`, `NoNewPrivileges`). Windows: a native service `MeshForgeAgent` hosted by **pywin32's service framework** inside the bundled Python (no third-party wrapper, keeps ADR-0009), account `NT SERVICE\MeshForgeAgent` (virtual account), start Automatic (Delayed), recovery restart ×3 then stop; exit 4/5 map to "do not restart". Starts at boot, survives logoff. Validated first by spike **SP1** (§4). | Answers the open "does it survive logoff?" check by construction. A virtual account needs no password and has no rights beyond what we grant. Fallback if SP1 fails: WinSW (MIT, one exe) — recorded, not default. |
| D387 | **Identity and config migration.** On install (or first service start) the agent looks for a per-user identity (`%LOCALAPPDATA%\MeshForge\identity`, `~/.local/share/meshforge/identity`) and, if the machine location is empty, **moves** it (copy → verify fingerprint → re-ACL → rename old to `identity.migrated-<date>`). It never mints a new identity while an old one exists unmigrated; two identities → stop with a clear message. Same for `config.toml`. Old systemd user unit / `MeshForgeAgent` scheduled task are disabled and removed. | A laptop that silently re-enrols as a new node splits its telemetry history and breaks the ML training data. ADR-0013's "never silently mint" rule applies to migration too. |
| D388 | **Docker / GPU checks are reports, not gates.** Installer and wizard show: Docker present + daemon reachable from the service account (Windows: the account must be in `docker-users`; the installer offers to add it), NVIDIA driver + `nvidia-smi` + CUDA visible **from the service** (checked by the service itself, not the installer's admin process), free disk. Missing items lower what the laptop offers (the existing runtime/GPU detection) and say why. | The agent already works without Docker or GPU (subprocess runtime, CPU jobs). Blocking install would fail criterion 1 on every laptop without Docker. GPU from a Windows service is a known risk (session 0), so SP1 tests it. |
| D389 | **Firewall rules are named and owned.** Windows: `netsh advfirewall` rules `MeshForge-Agent-Peer` (TCP 47120, only if peer serving is on) and, on a controller, `MeshForge-Controller-{gRPC 47100, Enroll 47101, HTTP 47110}`, profile Private + Domain only (never Public). Linux: if `ufw` is active, a `ufw` app profile; otherwise nothing (we never enable a firewall). Uninstall deletes rules **by name**; the uninstall check lists every rule containing "MeshForge" and must find none. | Criterion 2 needs a precise list to remove. Public-profile exposure of an RCE system would be wrong by default. |
| D390 | **Controller install = Linux package with managed PostgreSQL.** `meshforge-controller` package (D384 bundle, controller extra) + **bundled PostgreSQL 16 binaries** managed by the controller: `[controller.db] mode = "managed"` (default for installs) runs `initdb` once (data in `/var/lib/meshforge/db`, `scram-sha-256`, generated password in a root/service-only file), starts the server as a child bound to a Unix socket + `127.0.0.1` only, stops it on shutdown, and refuses to start if the cluster belongs to another major version. `mode = "external"` (a DSN) stays for the dev Compose setup and power users. Windows controller: **out of scope for V0.17** unless Q4 says otherwise (the same managed code would work; packaging and testing it doubles 0.17.3). | No Docker requirement on the controller, no shared system PostgreSQL to clash with, one code path the agents can test on Linux. The dev default password problem (STATUS tech debt) ends here: managed mode generates the secret. |
| D391 | **Agent local console (0.17.4 + 0.17.5).** The agent serves a small HTTP UI on **`127.0.0.1:47130` only** (never the LAN), built from the same React app as a second entry (`frontend/src/agentConsole/`), same design system. Access: the service writes a random console token to `ProgramData\MeshForge\console\token` readable only by Administrators and the user who installed (Linux: group `meshforge-admin`, the installing user is added); the Start-menu shortcut / `.desktop` launcher reads it and opens the browser with the token in the URL **fragment**, which the page swaps for an HttpOnly cookie. Endpoints: status, join (code + optional chosen controller), owner policy read/write (same validator as `policy_cli`), node name, Docker/GPU checks, logs tail, leave fabric. | The laptop owner, not the controller, controls what runs there (D142). A loopback-only UI plus a file-permission token keeps other local users and the LAN out without passwords. Reusing the React app keeps one UI codebase. |
| D392 | **First-run wizard.** Opens at the end of install (and from the shortcut until joined). Steps: 1) welcome + what this laptop will share; 2) **join**: controllers found by mDNS listed, user pastes the `mf1-…` code (or scans the QR shown on the controller dashboard's Invites page with the laptop's webcam via the browser, `jsQR`, opt-in); 3) owner policy with safe defaults (accept jobs **off** until the owner turns it on, GPU sharing off, caps 50 % CPU) — explained in plain words; 4) checks (D388); 5) done → link to the controller dashboard. "Create fabric" exists only in the controller console (controller package): create admin user, generate CA, show first invite. | Matches the existing trust model exactly: the code still carries the CA pin, the wizard is just a front end to `join`. Defaults stay safe: installing must never make a laptop run strangers' code without the owner saying yes. |
| D393 | **Upgrade and uninstall (0.17.6).** Upgrade = install new version side by side → stop service → controller: `pg_dump` backup to `db/backups/pre-<ver>.dump` (keep last 3) → switch pointer → start (migrations run) → health check within 60 s, else switch back and restore the backup. Agent ↔ controller compatibility: controller accepts agents of the same minor and the previous minor; others get a clear `version_unsupported` (uses the existing protocol version field + a new min-agent-version setting). Uninstall: stop + remove services, firewall rules, shortcuts, PATH entries, legacy task/unit; **keep data by default**, with a "remove all data (identity, cache, database)" option. `lab/verify_uninstall.py` (both OSes) checks: no service, no process, no rule, no task, no file under program dirs (and none under data dirs when the option was chosen). | Criterion 2 needs a verifier, not a promise. Keeping data by default prevents losing a fabric's database on an accidental uninstall. |
| D394 | **Linux packaging = `.deb` only** (Ubuntu 22.04/24.04, the team's distro and WSL), built with `nfpm` from the D384 bundle. AppImage rejected: it cannot install a system service cleanly, which is the point. Other distros: a `.tar.gz` of the bundle + `install.sh` (documented, not lab-tested). | One well-tested format beats two half-tested ones. |
| D395 | **Windows installer = Inno Setup** (free, scriptable, per-machine, supports custom pages and silent install `/VERYSILENT` for tests), built on the Windows CI runner. Signed if Q2 approves a certificate; otherwise unsigned and the docs show the SmartScreen step. MSI/WiX rejected for V0.17 (much more work, only matters for enterprise deployment). | Fastest path to a polished installer with an uninstall entry in "Apps & features". |
| D396 | **User documentation (0.17.7)** lives in `docs/user/`: install (Windows, Linux), create a fabric, join a laptop, what the owner settings mean, run a workload (dashboard + `compute`), SDK quick start, upgrade/uninstall, troubleshooting. Written for a non-specialist, with screenshots from the real installers (🧑 provides Windows ones). OPERATIONS.md stays the operator/developer runbook. | The college evaluation and any real user read these, not OPERATIONS. |
| D397 | **Fresh-machine tests (0.17.8, 🧑).** Windows: a fresh Windows 11 VM (Hyper-V/VirtualBox, no GPU) **and** one real team laptop after uninstalling the dev setup. Linux: a fresh Ubuntu 24.04 VM for the controller and one for an agent. Timed run for criterion 1 with a stopwatch from "download finished" to "node shows CONN yes" in the dashboard, recorded in `lab/checklists/V0.17-install.md`. Install → upgrade (from a V0.17.0 build to V0.17.1) → uninstall → verifier on each. | "Fresh" means fresh; a dev laptop with uv and Docker already present would hide missing steps. |
| D398 | **(SP2 result, team 2026-10-24) Controller requires Ubuntu 24.04+ (glibc ≥ 2.36); agents keep 22.04/24.04.** Managed PostgreSQL binaries = theseus-rs/postgresql-binaries 16.15.1 (sha256-pinned, mirrored by us; zonky rejected: no pg_dump/pg_restore, OpenSSL 1.1). Controller `.deb` declares `Depends: libc6 (>= 2.36)`; `PgBinaries.check()` fails with `binaries_unusable` on older glibc. Orphan safety: PDEATHSIG=SIGINT exec shim + restart reconciliation (`/proc` exe+cwd match) + systemd `KillMode=mixed`. Locale C. | The team's controller runs 24.04; building PostgreSQL ourselves is not worth it. |
| D399 | **(Lead, 2026-10-24) CI installs all extras for the main jobs; a separate fresh-clone job runs plain `uv sync` → every CLI starts (`--help`) and the non-extra unit subset passes, with extras-needing test modules skipped at collection by a conftest hook.** Windows portability bugs found by CI are fixed in `src/`, not skipped. | Full coverage on CI and a proof that a plain install still works. |

## 4. Spikes (G0) — each answers one question with a pasted result

- **SP1 (Windows, needs runner or 🧑):** bundled Python + pywin32 service under `NT SERVICE\MeshForgeAgent`:
  starts at boot, survives logoff, restarts on crash, does not restart on exit 4/5, spawns a `uv` env build and a
  child process tree that is fully killed on stop, sees the GPU (`nvidia-smi` + a CUDA tensor in a job env), reaches
  Docker when in `docker-users`. **Fail → D386 fallback (WinSW) or user-account service; Lead decides with data.**
- **SP2 (Linux, agent-runnable):** bundled PostgreSQL 16 binaries: initdb/start/stop as a child from the bundle
  path, crash of the controller leaves no orphan postmaster (or it is adopted on restart), `pg_dump`/restore round
  trip, size of the binaries.
- **SP3 (Linux + Windows):** D384 bundle: build twice → identical hashes; size (target < 150 MB agent, < 250 MB
  controller incl. PostgreSQL); `meshforge-agent --version`, `hardware show`, a real job with an env build run from
  the bundle with no system Python and no `uv` on PATH.

## 7. Questions for the team (Lead recommendation in **bold**)

1. **Q1 GitHub repo + CI:** create the private repo and push now, and allow a Windows CI runner (GitHub-hosted
   `windows-latest` is free for private repos within minutes limits)? **Yes — a hard prerequisite for V0.17.**
2. **Q2 code signing:** buy a code-signing certificate (roughly $100–400/year; an EV cert removes SmartScreen
   faster)? **No for now: ship unsigned, document the SmartScreen step, revisit before V1.0.**
3. **Q3 agent runs as a service account** (D386/D387: machine-wide identity, migrate existing laptops)?
   **Yes.** Alternative: keep per-user (simpler, but stops at logoff — fails "self-running").
4. **Q4 Windows controller:** package the controller for Windows too? **No in V0.17 (Linux controller only);
   the managed-DB code stays cross-platform so it can be added later.**
5. **Q5 Linux formats:** `.deb` only + tarball? **Yes.**
6. **Q6 QR join via webcam:** include it? **Yes, opt-in, small (QR on the Invites page + browser scanner); paste
   stays the main path.**
7. **Q7 default owner policy after install:** accept jobs **off** until the owner turns it on in the wizard?
   **Yes — the wizard asks explicitly; the safe default stays.**
8. **Q8 fresh machines:** can the team provide a fresh Windows 11 VM (any laptop with virtualization) and one real
   laptop willing to remove its dev setup? **Needed for 0.17.8.**
9. **Q9 data on uninstall:** keep by default, "remove all data" opt-in? **Yes.**
10. **Q10 auto-update:** out of scope (manual upgrade by installing the new version)? **Yes, out of scope for V0.17;
    a "new version available" notice in the console is fine.**

**Out of scope:** auto-update, macOS, MSI/enterprise deployment, Windows controller (unless Q4), Mode 2/4 service
pieces (`accept_gpu_sessions` stays a setting only).
